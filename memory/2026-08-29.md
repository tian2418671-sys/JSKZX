## 二、AI 打标崩溃 + 进度条修复（下午）

### 问题现象
1. 打标过程中渲染进程 native 崩溃: `{"reason":"crashed","exitCode":-36861}`（= `0xFFFF7003`，Chromium 层崩溃，无 JS 堆栈）
2. 本地向量匹配（第二层）进度条卡住不动

### 崩溃根因（三层定位后找到的真凶）
**打标流程每改一张卡 → `persistCardUpdate` → `flushLibraryReactivity`(100ms 防抖) → `triggerRef(library)` → 触发 `watch(library)` → 全量重建搜索索引 + Token 预热**。打标 LLM 层每卡间隔 1500ms > 100ms 防抖，即**每打标一张卡就全库重建一次索引**（几千张卡逐字符正则分词 + Token 估算），渲染进程 CPU/内存持续峰值 → native 崩溃。日志「⚡ Token 缓存预热完成」后立即崩溃完全吻合。

### 修复清单

**js/composables/useAITools.js**（打标三层漏斗）
- 三层全部 `library.value.find()` O(n²) → 建 `Map` O(1) 索引（`cardIndex`）
- 规则匹配层（第一层）：实时进度（每张 `current+1`，状态「① 规则匹配中 (x/y)」）；每 64 张 `await` 让出主线程
- 向量匹配层（第二层）：进度条联动（`vectorMatchBase` + `vectorMatchActive`，把 `vector:batchProgress` 事件合并进 `aiTaggingProgress`）
- **修复 LLM 层索引 bug**：`currentId = targetIds[i]` → `llmTargetIds[i]`（旧代码给错误卡重复打标、漏掉真正要兜底的卡）

**js/components/App.vue**（关键崩溃修复）
- `watch(library)` 检测到 `isAITagging` 时跳过全量索引重建，置 `pendingRebuild` 标记 + 取消在途任务；打标结束（`isAITagging` → false）延迟 250ms 补建一次

**js/utils/tokenEstimate.js**
- 超长文本防护：>200KB 先截断再估算，避免 `match`/`replace` 产生巨型临时数组

**main.js**
- 加 `crashReporter`（本地 `.dmp` 转储，`uploadToServer:false` 不联网）
- `render-process-gone` 崩溃详情落盘 crash.log + `crashed/oom/killed` 时 1.5s 后自动 `win.reload()` 恢复

## 八、2026-08-29 夜：🔴 修复 v2.1.0 启动崩溃 TDZ（Cannot access 'Ms'）

### 现象（构建开发版冒烟测试发现）
- `npx electron . --disable-gpu --enable-logging` 启动即报：
  - `[Vue 错误] ReferenceError: Cannot access 'Ms' before initialization`（setup 内）
  - 连锁 `Cannot read properties of undefined (reading 'fontSize')`
- vite build **不报错**，纯运行时崩溃（交接文档坑 6 的经典场景）

### 根因
- `App.vue` 中 `watch(library)` 回调引用 `isAITagging.value` + `watch(isAITagging)` 直接以 `isAITagging` 为源
- 但 `isAITagging` 是 `useAITools()` **L4051 才解构**，而这两个 watch 定义在 **L3906（useAITools 之前）**
- `const` TDZ：watch 定义时立即把 `isAITagging` 当 getter 访问 → 未初始化 → 崩溃
- 来源：08-29 崩溃修复（打标跳过索引重建）新增的 watch 放在了 useAITools 解构之前

### 修复
- 把 `watch(library)` + `watch(isAITagging)` 两个块**移到 useAITools 解构之后**（语义不变，顺序修正）
- 原位置留注释说明原因（防回归）
- 冒烟验证：启动全流程正常（加载 73 卡、索引构建、Token 预热、自动打标落盘、蒙版淡出），TDZ 消失

### 附带验证
- 启动早期 snapshot_config 写入触发 `EPERM: rename`（目标文件被占/360 锁）——被 atomicWriteJson 修复的 catch 正确捕获，**tmp 被清理无残留**（修复前会留 .tmp 垃圾）

### ⚠️ 通用教训
- **任何 watch 引用后续 composable 解构的 ref → 必须把 watch 放到解构之后**，否则 TDZ 运行时崩溃（build 不报错）

## 九、2026-08-29 夜：向量依赖 @xenova/transformers 缺失修复

### 现象
- 应用内触发向量引擎/模型下载报：`Cannot find module '@xenova/transformers'`（vectorWorker.js require 失败）
- 根因：`node_modules/@xenova` 整个缺失——`package.json` 声明了依赖但从未成功安装

### 安装失败根因（重要）
- `npm install @xenova/transformers@^2.17.2` 失败：其**必需依赖 sharp ^0.32.0** 安装时要从 `github.com/lovell/sharp-libvips` 下载 libvips 二进制 → 国内网络下载失败 → 整个安装回滚
- `sharp` 是 transformers 的 `dependencies`（非 optional），不能跳过

### 修复（npmmirror 镜像）
```powershell
$env:npm_config_sharp_binary_host="https://npmmirror.com/mirrors/sharp"
$env:npm_config_sharp_libvips_binary_host="https://npmmirror.com/mirrors/sharp-libvips"
npm install @xenova/transformers@^2.17.2 --registry=https://registry.npmmirror.com
```
- 安装成功：@xenova/transformers v2.17.2 + 嵌套 sharp v0.32.6 + onnxruntime-node v1.14.0
- `require('@xenova/transformers')` 验证通过（pipeline 可用）
- ⚠️ 注意：npm 会警告 `Unknown env config "sharp-binary-host"`（下划线转连字符），但 sharp 的安装脚本仍能读到，不影响
