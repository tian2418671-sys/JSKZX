## 二、Bug 明细与验证

### 🔴 BUG-1（严重）搜索后刷新，同一张卡重复出现

- **现象**：中文单字搜索 → 刷新 → 列表里同一张卡出现两次。
- **根因**：`searchIndex` 的 `build/buildAsync` **多轮全量重建重叠**：只在自己开头 `clear()`，既无代次保护，也无「同对象只索引一次」保证。刷新期间 `watch(library)` 被反复触发（数组引用替换 + 每张新解析卡 `triggerRef`）→ 旧对象在新构建 `clear()` 之后又被写回；同一对象被两个循环各 push 一次。**只有「精确 token」分支**会原样返回倒排桶 → 所以中文单字搜索最容易看到（英文多词走兜底分支自带身份去重）。
- **修复**：`generation` 代次号（在途构建自检退出）+ 索引幂等（`cards.has(card)` 直接 return）+ `search()` 结果 `[...new Set(results)]`；App 侧 `indexBuilding/indexDirty` 合并重建（在途只记一次补建）。
- **验证**：
  - 单测 `test/searchIndex.test.mjs` **7 项**（含「构建期间搜索返回上一代完整索引」双缓冲用例）✅
  - 大库脚本 `library-dup-search-refresh.mjs`：A~F 全阶段 `dup(lib)=0 / dup(list)=0`，库稳定 11,186 张 ✅
  - **生产模式**真实界面复测（搜索「龙」/「的」→ 点刷新 → 再搜）：可见列表 `dup=0` ✅

### 🔴 BUG-2（严重）刷新后整个大库从界面消失

- **根因**：主进程扫描 catch 分支返回 `{files:[], error}`，渲染层 `if (result && result.files)` 把空数组当真值 → `library.value = []`（磁盘未动）。这也解释了历史上「刷新中途只剩 478 张」的不完整计数。
- **修复**：先判 `result.error` 提前返回；库非空时**拒绝接受 0 文件结果**并提示。
- **验证**：连点刷新 ×6 库始终 11,186 张 ✅（脚本 F 阶段）

### ⚠️ BUG-3（严重，已缓解）刷新/搜索渲染进程 OOM

- **根因**：索引为每张卡常驻一份小写全文（11,186 卡 ≈531MB 字符，中文 UTF-16 更高）→ 加载完堆即 3.0GB / 上限 4.19GB，刷新重建再分配一份 + 并发重入 → `render-process-gone {reason:"oom", exitCode:-536870904}`。
- **修复**：索引不再保留文本（`_extractText` 按需复算）+ 单卡上限 `MAX_INDEX_TEXT=200000` + 重建合并。
- **验证**：堆基线 3039MB → **2013MB**；连点刷新 ×6 后 1893MB。**但压力场景（搜索+连续刷新叠加）峰值仍到 3.3GB** → 判定「已缓解，未根除」。

### 🔴 BUG-4（严重）库加载 79.9s —— 每次启动重写数千张 PNG

- **根因**：写盘判据看「**清洗后**的内存状态」；开启「🧹导入时忽略卡片自带标签」时每次加载都清空原生 tags → 永远判定需要物理清洗 → 写回 PNG → 下次启动又被当原生标签清掉 → **无限重写**（mtime 全变 → 刷新又全量重解析）。
- **修复**：改为按「**磁盘原有标签**」（`diskTagsBefore`）判定；仅当盘上确有该清掉的标签、或确有新标签要补时才写。
- **验证**：`3,415 张` → `971 张`（一次性残留清洗）→ **第 2 次启动 0 张**；本轮多次启动日志中已无写盘/自动打标行 ✅

### 🔴 BUG-5（严重）给「原本没有正则脚本」的卡新增第一条时列表不刷新

- **现象**：用户反馈的「添加正则/状态栏后反馈缓慢，必须切换选项卡才看到效果」在无脚本的卡上仍复现。
- **根因**：`regexScripts = computed(safeData → cardData)`。**Vue 3.4+ 的 computed 在「新值 === 旧值」时不再向下传播** —— `triggerRef(cardData)` 后 `safeData` 重算但**返回同一个对象**，依赖它的 `regexScripts` 不会被标脏：
  - 卡上**已有** `extensions.regex_scripts`：原地 `push`，computed 缓存的就是同一个数组对象 → `.length` 天然变化 → 侥幸正常（这就是上一轮 21→22 能通过的原因）；
  - 卡上**没有**该字段：新增会**整体替换数组** → 缓存里的旧空数组永不失效 → 面板恒显示「0 条脚本」。
- **修复**：新增 `cardContentVersion`，`refreshCardData()` 时自增，`regexScripts` 取值前先读它。
- **验证**（dev + CDP，卡「双瞳洗澡」，原本 0 条）：

| 步骤 | 结果 |
|---|---|
| 点「+ 立即新增一条正则脚本」（**不切任何 Tab**） | 徽标 **0 → 1 条**、DOM 行数 **0 → 1** ✅（修复前 0/0） |
| 点「🗑️ 删除」 | 枚举到原生窗口 `Pid \| #32770 \| 确认操作` ✅，此时行数仍为 1（未误删） |
| 发送 `WM_COMMAND/IDOK` | 行数 **1 → 0**、徽标 0 ✅（无需切 Tab） |
| 脚本 `_probe-regex-ui.mjs`（已适配 0 条 + 原生弹窗） | **PASS** ✅ |

### 🟡 BUG-7（中）索引/预热在窗口隐藏时永久停摆

- **根因**：分片让步只挂 `requestIdleCallback`；Chromium 在**窗口隐藏/最小化**时完全不回调，`setTimeout` 被节流至 ≥1s（后台 5 分钟后更狠）→ 224 个分片要跑几十分钟；`tokenCache.warmupAsync` 是**纯 idle**（永不回调）。启动闸门单独 `await requestIdleCallback(cb, {timeout})` 连 timeout 都不兑现（实测 **3 分钟仍未开始建索引**、搜索恒空）。
- **修复**：统一 `yieldToMain()`（前台 idle / 后台 `MessageChannel`，含定时器兜底）；闸门改 `waitForIdle()`。
- **验证**：隐藏窗口下 11,186 卡索引（349,552 词）+ Token 预热均正常完成 ✅

### 🟡 BUG-8/9/10（轻）

- BUG-8：载入期「非角色卡 JSON」日志刷屏 → 同因同类 1 条 + 封顶 40 条 + 收尾汇总（`跳过 385 个…已折叠 345 条`）✅
- BUG-9：`npm test` 挂起 → `MessageChannel` 仅在真实 DOM 创建 + Node 下 `unref()` ✅（178/178，5.2s 退出）
- BUG-10：磁盘 111 个 0 字节 `.tmp` + 1.17GB 缓存无人清理 → 缓存整体移除 + `cleanupLegacyEmbedCache()` 一次性回收（实测回收 **44 文件 / 758MB**）✅

### 3.2 P2：内嵌提取缓存 A/B（同机交替、每次重启、同一大库）

| 方案 | fetch | worker | assemble | 首屏合计 | 缓存占盘 |
|---|---|---|---|---|---|
| **无缓存（现版本）** | 2.5~3.4s | 1.4~8.9s | 9.6~22.3s | **16.0~31.2s** | 0 |
| v1 `.json` 分片 | 9.3s | 2.0s | 11.0s | 36.9~43.3s | 1.17GB |
| v2 `.json.gz` 分片 | 29.1s | 1.6s | 52.8s | **85.3s** | 385MB |
| v8 二进制分片（过渡试验） | 62.5s | — | — | 137s | 385MB |

- 机理：PNG 头部提取内嵌 JSON 本身只要 ~3s（自适应窗口 + 128 路并发 + 按需流式，GC 可回收）；缓存把 1.2GB **对象**一次性常驻主进程 → 堆压力/GC 抖动 + 额外 IPC 克隆 → 慢 2~5 倍。`v8.deserialize` 产出 dictionary-mode 对象，跨 IPC 更慢。
- ⚠️ **重要观察：绝对值随机器状态大幅波动**。同一份代码、同一大库，首屏实测从 **16.0s 波动到 31.2s**：
  - 全程 `fetch` 恒稳 **2.5~3.4s**（I/O + 并发读 PNG 头，受环境影响小）；
  - 波动集中在 CPU/内存密集的 `worker` / `assemble`（同一版本 1.4s ↔ 8.9s）；
  - 采样确认**不是降频**：`%Processor Performance ≈ 190%`（有睿频）、整体 CPU 占用 20~33%，但 VS Code ×3 进程与 Defender（MsMpEng 累计 1300s+ CPU）在抢内存带宽；该类「组装 1.3GB 对象」的负载对内存带宽/竞争极敏感。
  - ⇒ **结论口径**：性能对比必须**同一次会话内交替 A/B**（本次缓存结论即如此得出，2~5 倍差距远超噪声）；跨会话的绝对值只能当参考区间。
- ✅ 移除缓存后**未再生成任何 `embed_cache_*`**，`.embed_cache_removed` 标记已写入（只扫一次目录）。

## 五、遗留与建议

1. **OOM 未根除**：压力场景峰值堆 3.3GB / 上限 4.19GB，需继续压（连续刷新 10+ 次、大库↔小库来回切、边打标边刷新）。
2. **冷启动（刚开机）已量化，但未真机实测**：

   `node scripts/png-head-io-probe.mjs` 实测（`I:\03\角色色卡`，库合计 10,072MB / 11,663 个 PNG+JSON）：

   | 指标 | 数值 |
   |---|---|
   | 每次启动读取量（复刻主进程窗口逻辑） | **约 9,565MB（9.3GB）** |
   | 文件打开次数 | **11,663 次** |
   | 热缓存实读耗时 | 2.3s（等效 4,206MB/s，即 `fetch≈3s` 的真相） |
   | 冷启动额外 I/O 估算 | 按 600MB/s 冷盘：≈**16~19s**；按 2~3GB/s 的 NVMe：≈**3~6s** |

   **为什么读这么多**：`chara` 内嵌块位于**文件末尾附近**（块结束偏移 P50≈616KB / P90≈897KB /
   P99≈1010KB），所以 ≤1MB 的卡（9,487 个，占大头）必然要整文件读；>1MB 的卡里还有 1,902 个的块
   不在前 1MB，只能走“读 8MB / 读整文件”兜底。
   ⇒ 原以为「把首读窗口缩到 64KB」能省 I/O 的设想**不成立**（64KB 只能命中 24%）。

   **推荐动作**：
   - 先实测确认痛不痛：**重启电脑后第一时间**执行
     ```
     node scripts/measure-startup.mjs --label 冷启动 --timeout 240000
     ```
     与热启动基线（首屏 16~31s、fetch 2.5~3.4s）对比。
   - 若冷启动 `fetch` 明显恶化（>10s），按性价比选：
     ① **尾读 + 标记搜索**：`chara` 块在文件末尾 → 只读文件**最后 ~256KB**，在缓冲里搜 `tEXt`/`chara\0`
        标记再解码（预估读量 9.3GB → ~3GB）。需重验 11k 卡全部提取正确（风险：块跨越尾窗、图像数据里撞标记）。
     ② **懒加载分片缓存**（不是旧方案）：只缓存「路径+mtime+size → 内嵌 JSON **文本**」，按需读单片、
        不把 1.2GB 对象常驻内存（当初 85.3s 的锅就在“对象常驻”，而不是“缓存”本身）。
     ③ 什么都不做：冷启动多花几秒，换掉 1.17GB 磁盘 + 一堆缓存维护代码（当前默认选择）。
3. **阈值未自适应**：`MAX_INDEX_TEXT=200000`、日志封顶 40 条目前写死。
4. **移动版（JSKZX）未同步**本轮修复（本文只覆盖桌面版）。
