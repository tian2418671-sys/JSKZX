### P5-1 清单文件 `manifest.json`

```jsonc
{
  "id": "global-assets",                 // 唯一 id，须与目录名一致
  "name": "全局资产库",
  "version": "1.0.0",                    // 扩展自身语义化版本
  "apiVersion": "1",                     // 宿主扩展 API 主版本，不匹配则拒载
  "minAppVersion": "2.3.0",              // 低于当前宿主才载入
  "author": "…",                         // 必填（同 ST 惯例）
  "description": "…",
  "main": "index.js",                    // 入口（必需）
  "styles": ["style.css"],

  "activation": ["onStartup", "onCommand:global-assets.open"],   // 懒激活，避免拖慢启动
  "contributes": {
    "commands": [{ "id": "global-assets.open", "title": "打开全局资产库", "category": "工具" }],

```

加载前做 schema 校验（缺 `id`/`main`/`version`/`apiVersion` → 拒载 + 列表标红原因）。v1 用**手写校验 + 单测**，不为两三个字段引入 `ajv`。

**命名口径（🔧 评审后精确化）**：**事件总线命名对齐 ST**（`event_types` / `eventSource` 风格，E47 已有口径整理）；**manifest 结构则是「VS Code（`contributes` / `activation`）+ Obsidian（独立目录与独立数据文件）+ Chrome MV3（声明式 `permissions`）」的混合**，**不是** ST manifest 的复刻 —— ST 的 `display_name` / `loading_order` / `js` / `requires` / `optional` / `dependencies` / `generate_interceptor` 等字段**有意不采纳**（它们服务于"无隔离、Node 侧执行"的运行时，与本方案 P5-2 的沙箱模型不兼容）。仅保留 `hooks` 一处沿用 ST 命名。

### P5-2 隔离方案：iframe 沙箱为主 + 内置可信快速通道（🔧 评审后修订）

> **修订说明（v1.0 → v1.1）**：v1.0 原写 `sandbox="allow-scripts allow-same-origin"` —— **该组合存在逃逸向量，已废止**（同时设置二者会使嵌入页事实上摆脱沙箱限制）。
> 且本仓库既有 **5 处沙箱一律只用 `allow-scripts`**（E49~E51），v1.0 的写法反而偏离了项目自身的事实标准。**这是本次评审最重要的技术发现。**

| 方案 | 隔离 | 集成 | 复用现有资产 | 结论 |
|---|---|---|---|---|
| 宿主进程内 `import()`（同 ST） | 弱 | 最低 | 高 | ✅ 仅**内置可信**扩展 |
| **iframe 沙箱 + postMessage RPC** | 强 | 中 | **高**（E46：`app://` + 内存路由 + CSP 已有先例） | ✅ **v1 默认** |
| 独立 `utilityProcess` / BrowserWindow | 最强 | 最高 | 低 | ❌ v1 不做 |

**修正后的沙箱规格（双保险：源隔离 + 最小 sandbox）**

| 项 | v1.1 规定 | 依据 |
|---|---|---|
| `sandbox` 属性 | **`allow-scripts`（仅此一项）**；不给 `allow-same-origin`，也不给 `allow-popups` / `allow-top-navigation` | E49~E51（项目既有标准） |
| **源隔离** | 扩展页 URL = **`app://ext--<id>/index.html`**（host ≠ `index.html`）→ 与宿主**不同源**，即便将来误开 same-origin 也触达不到宿主（双保险） | E52：`standard: true` 下 origin 由 host 决定 |
| **主进程映射** | `protocol.handle('app')` 的 host 分支新增 `ext--` 前缀 → 映射到 `userData/extensions/<id>/`，并**照 `main.js:845-851` 的越界校验模式**校验（解析结果必须落在扩展根内），另加 `isPathAllowed` 式白名单 | E53：现有分支会把 `app://ext--x/…` 解析到 `appRoot/ext--x/…` → 直接 403，**必须新增分支** |
| parent/top 访问 | 沙箱内 `window.parent` 会抛 `SecurityError` → 复用 `hostStub.js:191-196` 的 getter 兜底（回落本地 window）；宿主通信**只走 RPC** | E51（项目既有解法） |
| 通信 | **仅 postMessage RPC**（postMessage 本就是为跨源设计，无需 same-origin） | — |
| 存储 | iframe 内**不使用** localStorage（无 same-origin 时不可用）→ 一律走宿主 `storage` API | 与 P5-5 设计一致 |
| 视图集成 | `modal` = 宿主弹窗外壳 + iframe 内容区；`fullscreen` = 全屏容器 + iframe（图谱类） | — |
| 共享库 | `libs.echarts / showdown / handlebars / DOMPurify` 由宿主注入，避免每个扩展重复打包 | E42 |

**逃逸测试用例（🔧 评审新增 —— P5 骨架期独立验收项，与 hello-world 同期打通）**

| # | 用例（在扩展沙箱内执行） | 预期 |
|---|---|---|
| 1 | 读 `window.parent.document` / 访问宿主 DOM | 抛 `SecurityError`（经 getter 兜底回落本地 window），**不可**触达宿主 |
| 2 | 改 `top.location` / `top.location.href` | 被阻止；宿主页面不跳转 |
| 3 | 借 `parent.document` 拿到自身 iframe 元素并移除 `sandbox` | 失败（无同源访问权 ⇒ 拿不到宿主 document） |
| 4 | 访问 `window.electronAPI` / `require` / `process` | 全部 `undefined`（宿主 preload 不在 iframe 内执行） |
| 5 | 在 iframe 内 `localStorage.setItem` 后刷新宿主 | 不落宿主 origin / 抛错，宿主存储无污染 |

> 这 5 条必须**在 P3/P4 搬运真实功能之前**跑通：AR-27/AR-28 的历史教训是"沙箱链路坑很深"，而这两个缺陷**并未覆盖"同源 iframe 逃逸 sandbox"这一向量**（本次评审发现），需由新用例补位。

| 将来如需翻译 / 摘要 | **按用途逐个开结构化接口**（如 `ai.translate(ids, opts)`），不做通配 prompt | 攻击面可控 |
| 若最终仍要开放任意 prompt | 必须：显式用户确认（"扩展 X 请求调用 AI，预计 N 次"）+ 单会话调用次数上限 + 扩展日志留痕；**默认关闭** | — |

**硬性禁止**：`require` / 直接 `fs`（铁律：文件操作走路径白名单 IPC）；读 API Key（`secret:decrypt` 不出宿主）；未声明 `network` 的网络请求；向 IPC 直传 Vue 响应式 Proxy（历史坑 AR-14 同类：`An object could not be cloned`）；单次调用超 2s 记警告、超 10s 中止。

### P5-4 事件总线（命名对齐 ST，复用原生实现）

`APP_READY` / `LIBRARY_LOADED` / `CARD_SELECTED` / `CARD_UPDATED` / `CARDS_IMPORTED` / `TAG_CHANGED` / `TAGGING_PROGRESS` / `TAGGING_DONE` / `WORLDINFO_UPDATED` / `MODE_CHANGED` / `SETTINGS_CHANGED`。
实现用原生 `EventTarget` 或 `mitt`（~200B），**不自研事件框架**。

### P5-5 持久化分工（避免主配置膨胀）

### 8.4 处置（新 BUG 出现后的固定动作，顺序不可颠倒）

| 2 | 「实验与工具」**不是随便存东西的地方，里面全是实验性/不稳定功能** —— 稳定工具不能与它混放；要么新建「工具」菜单 | 新建 **工具**菜单（命令面板 / 清理无效全局标签 / 同名查重 / 版本查重 / 清洗历史外来标签）；「实验与工具」收窄为 **实验**（只留全盘打捞卡片、本地 AI 对话测卡） |
| 3 | 把「维护组」独立成 **维护**菜单；该菜单内子项命名**去掉中英混合，只保留中文** | 新建 **维护**菜单（历史快照 / 回收站 / 全局回收站 / 清理全部快照 / 清理孤儿快照）；标题去掉 `.bak` / `.trash` / `jsTavern_Trash` 等英文（技术名移到悬停说明） |
| 4 | 把「全局资产库」与「关系图谱」**扩展化**，并问难度 | 已在 §12.4 给出实测难度评估；**用户同日决定：扩展化暂缓、转后续** —— 设计、难度基线、重启前置已存档到 [`docs/规格与计划/后续升级计划.md`](../规格与计划/后续升级计划.md) 第四节 |

**术语定名**：本项目对外统一用「**扩展**」（extension）指代可安装的功能模块，**不再用「插件」**指代它 —— 因为「插件」在本项目里已经指“**卡内酒馆助手脚本**”（`PluginWorkspace.vue` / 卡内脚本页签），两者混用必然造成沟通事故（P5-0 已提出改名，此处正式确认）。

### 12.4 扩展化难度评估：全局资产库 vs 关系图谱（基于实测代码规模）

| 对象 | 代码规模（实测） | 宿主耦合 | 扩展化难度 | 主要障碍 |
|---|---|---|---|---|
| **全局资产库** | `GlobalAssetModal.vue` **89 行**（纯展示） | `App.vue` 内 17 处引用 | **低**（P5 就绪后约 1~2 天） | 全库遍历必须由宿主提供「分页 + 游标」，不能把整库丢进沙箱 |
| **关系图谱** | `useGraph.js` **405 行** + `GraphModal.vue` 76 行 + `WbGraphModal.vue` 70 行 | `App.vue` 内 **106 处**引用 | **高**（P5 就绪后仍有 3~5 天 + 性能调优，且 11k 卡很可能达不到现状流畅度） | ①沙箱拿不到宿主 DOM（需 `ui.mount()` 容器）②ECharts ~1MB（需宿主 `libs.echarts`）③**11k 卡的头像限流 / 连线预算 / 构建缓存 / 300ms 防抖，在 RPC 桥下每次取数都要跨进程，会慢一个数量级** ④106 处宿主耦合要拆成 API |

**结论与建议**：
1. **先做 P5 骨架，再拿「全局资产库」当第一个真实扩展**（验证框架、摸清 API 缺口）；
2. **关系图谱先走「只注册」**（命令入口 / 菜单项由扩展贡献点提供，重计算与 ECharts 暂留宿主），
   待 `cards.query()` / `ui.currentGroup` / `assets.avatarUrl` / `libs.echarts` / `ui.mount()` 五项齐备后再评估真外置；
3. 若坚持图谱也真外置：需接受 **11k 卡图谱性能下降**，或采用「重计算留宿主 + 只外置面板 UI」的折中。

> **2026-09-20 决定：扩展化整体暂缓**（先专注当前功能与稳定性）。本节评估与 §六 P5 设计**原样保留**，不作废；
> 重启时直接读 [`docs/规格与计划/后续升级计划.md`](../规格与计划/后续升级计划.md) 第四节（含前置清单与实测基线），无需重新调研。
