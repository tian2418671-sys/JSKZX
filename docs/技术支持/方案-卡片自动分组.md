# 方案：卡片自动分组（按标签 / 规则自动建文件夹并归位）

> **状态**：待评审（草稿 v1.0）｜**日期**：2026-09-20｜**影响面**：**【高】会物理移动卡片文件**
> **位置**：本文是**设计方案**（评审用），定稿后另出实现规格放 `docs/规格与计划/`。
> **阅读顺序**：先看 §〇 一句话与 §二 现状（都已取证，可跳转复核），再看 §三 设计与 §七 待裁决。

---

## 〇、一句话

**在文件级**把卡片按「标签 / 规则」自动移进同名分组文件夹（文件夹不存在时自动创建）——
底层能力（建文件夹、物理移动、路径派生键迁移）**已经全部具备**，本方案要做的是
**规则层 + 预览确认 + 可回滚**这三件工程化的事，而不是重写移动逻辑。

---

## 一、目标与不做什么

### 1.1 目标（用户原话拆解）

| # | 目标 | 说明 |
|---|---|---|
| G1 | **卡片自动分组** | 由程序判定每张卡该进哪个分组，不需要人手一张张拖 |
| G2 | **文件级实现** | 分组就是**磁盘上的文件夹**（与现有分组机制一致，不是纯内存标签） |
| G3 | **自动创建文件（夹）** | 目标分组文件夹不存在时自动建立 |

### 1.2 明确不做（本期）

| 不做 | 原因 |
|---|---|
| 不做「后台常驻自动整理」 | 物理移动是**不可逆**操作，必须是用户显式触发的动作 |
| 不用 AI 判定分组 | 成本与不确定性高；先做**确定性规则**，AI 可作为后期「建议分组」而非直接移动 |
| 不改动现有分组/分类语义 | 现有「全部 / 未分类 / 预设分组 / 自定义分组」体系保持原样 |
| 不做多级嵌套分组 | 现有结构是**库根 + 一层子文件夹**（见 §2.4），本期不引入层级 |

### 2.1 已经具备的底层能力（本方案直接复用，不重写）

| 能力 | 位置 | 事实 |
|---|---|---|
| **建分组文件夹** | `main.js:1169` `fs:createGroupFolder` | `mkdir{recursive:true}`；名称净化非法字符 `[\\/:*?"<>|]` → `_`；`isPathAllowed` 白名单校验 |
| **物理移动卡片** | `main.js:1206` `fs:moveCardToGroup` | **目标目录不存在时自动 `mkdir`**（= 用户要的「自动创建文件夹」已具备）；只处理**库目录内**的卡片；同名冲突**追加时间戳后缀、绝不覆盖**；返回 `{ newFilePath, newSubFolder }` |

| **批量移动** | `js/composables/useCardGroups.js:324` `batchChangeCategory()` | 对选中卡逐个 `moveCardToGroup`，统计成功数 |
| **单个快速移动** | 同上 `quickMoveGroup(item)` | 选项弹窗（可新建）→ 移动 |
| **分组选项列表** | 同上 `buildGroupOptions()` | 预设分组以**中文名**为移动目标；自定义分组直接用名称；排除「全部」视图 |
| **分组重命名 / 删除** | `main.js:1189` `fs:renameGroupFolder`、`main.js:1239` `fs:deleteEmptyGroupFolder` | 重命名会同步迁移子文件夹内卡片路径；删除**只允许空目录** |
| **空分组自动清理** | `useCardGroups.js`（删除卡片后调用） | 已有先例，可复用 |

### 2.2 卡片上可用于判定的字段（做规则的输入）

| 字段 | 位置 / 形态 | 备注 |
|---|---|---|
| `item.customTags` | 数组 | 用户/自动打的标签（P1 起三层漏斗产出） |
| `item.data.data.tags`（或 `item.data.tags`） | 数组或逗号分隔字符串 | 卡内原生标签 |
| `item.name` | 字符串 | 卡名（可做关键词/正则匹配） |
| `item.category` | 字符串 | 当前分组（**可能是"全部"以外的中文名**） |
| 有世界书 / 有正则 | 已有过滤视图 `has_lorebook` / `has_regex`（见 `useCardGroups.js:56` 的不可删视图名单） | 可作为内置规则条件 |

### 2.3 现有的"自动"先例（可类比，但不直接复用）

| 先例 | 位置 | 与本方案的关系 |
|---|---|---|
| 自动打标规则 | `js/utils/cardLoader.js` 的 `defaultAutoTagRules` / `compileAutoTagRules(customRules, disabledNames)` | 结构是 `{ name, regex, tag }` → **本方案的分组规则可设计为同构** `{ name, regex, group }`，可复用"逐条开关 / 分组启停 / 落盘"的交互经验 |
| 规则表 UI | `js/components/AutoTagRulesModal.vue` | 新功能的规则表界面可参照它的形态（系统预设 + 自定义 + 逐条开关） |
| 智能查重（会移动文件） | `useCardGroups.js` 的批量移动 / 回收站 | 说明"批量物理移动 + 二次确认"在本项目已有成熟范式 |

### 2.4 分组在磁盘上的真实结构（决定了能做什么）

- 库根目录 = 「全部」；**一层子文件夹 = 一个分组**；「未分类」= 卡片放在**库根**（`fs:moveCardToGroup` 里 `isRootTarget` 分支回到 `libraryPath`）
- 分组名 = **文件夹名**（预设分组用中文名）→ 所以**分组名必须能作为合法目录名**（净化逻辑已有）
- **结论**：不支持多级嵌套（本期不做），也不建议做（会上探路径派生键的迁移复杂度）

### 2.5 缺口（= 本方案要新建的东西）

| 缺口 | 说明 |
|---|---|
| **判定层** | 目前没有任何"这张卡该属于哪个分组"的规则引擎 |
| **预览层** | 没有任何"先看看会发生什么"的界面；直接批量移动对用户太危险 |
| **回滚层** | `moveCardToGroup` 只保证失败时内存不变；**一旦成功就无法一键撤回**（移动历史未记录） |
| **入口 / 设置** | 没有自动分组的菜单入口与规则配置界面 |

## 三、设计

### 3.1 分组依据：两种模式（建议**先做 A，B 作为进阶**）

#### 模式 A：按标签自动分组（推荐首发）

- **规则**：卡片含标签 `X` → 移入分组 `X`（**标签名即分组名**，文件夹不存在则自动创建）
- **为什么首选**：
  1. 与本项目既有的**标签体系天然咬合**（标签已经在卡片上，P1 的三层漏斗负责产出标签）；
  2. 判定**确定性 100%**，没有"猜"的成分；
  3. 用户心智简单：「我打什么标签，就进什么文件夹」。
- **多标签冲突策略（必须定）**：按**标签优先级**（可拖拽排序）取第一个命中的；无命中 → **保持原位不动**（默认）或不进任何分组。

#### 模式 B：按自定义规则自动分组（进阶）

- **规则结构**（与打标规则同构，便于复用交互与落盘经验）：
  ```
  { name: '原神角色', match: { type: 'name' | 'tag' | 'author' | 'hasLorebook' | 'hasRegex', pattern: '...' },
    group: '原神', enabled: true, order: 10 }
  ```
- **匹配类型**：卡名关键词 / 卡名正则 / 标签包含 / 有世界书 / 有正则
- **优先级**：规则按 `order` 自上而下，**首个命中者胜出**（与打标规则的"逐条 try"不同，分组必须有唯一结果）

### 3.2 触发时机（建议只做前两个）

| 时机 | 建议 | 理由 |
|---|---|---|
| **手动一键（含预览）** | **做** | 安全、可控；用户明确知道自己要整理时才动文件 |
| **导入新卡后提示** | **做（可选开关）** | 新卡通常"未分类"，此时归位风险最低 |
| 每次启动自动整理 | **不做** | 不可预期地移动文件会摧毁信任 |
| 定时后台整理 | **不做** | 同上，且与"库目录被其它程序占用"叠加会出问题 |

### 3.3 执行流程（**核心是"先预览、后执行、可回滚"**）

```
① 用户点「自动分组」
      ↓
② 扫描 + 计算计划（只读，不动文件）
   对每张卡判定目标分组 → 生成计划表：
     [卡名]  [当前分组]  →  [目标分组]   原因(命中哪条规则/标签)
     跳过项也列出并说明原因（已在目标分组 / 未命中任何规则 / 库外卡片）
     同时列出「将要新建的分组文件夹」
      ↓
③ 预览确认（弹窗，可勾选/取消单条）
   统计：将移动 N 张 / 跳过 M 张 / 新建 K 个文件夹
   默认**不勾选**"包含已手动分组的卡片"（见 §3.5 安全默认）
      ↓
④ 执行（逐张 moveCardToGroup，复用现有原语，天然带着三类键迁移）
   进度条 + 逐条结果；失败项保留在计划里并显示原因
      ↓
⑤ 写移动日志（可回滚）+ 空分组清理提示
```

### 3.4 UI 入口与界面（建议）

| 界面 | 内容 |
|---|---|
| **入口** | 「标签」菜单（与打标同域，符合现有菜单语义）或侧边栏分组区按钮；**建议两处都有，同一个命令 id** |
| **规则设置弹窗** | 参照 `AutoTagRulesModal.vue`：系统预设规则 + 自定义规则 + 逐条开关 + 拖拽调优先级 |
| **预览/执行弹窗** | 计划表（可勾选）+ 统计数字 + 「新建的文件夹」列表 + 执行/取消 |
| **移动日志** | 设置里可查看"最近一次自动分组"的明细，并提供**一键回滚** |

### 3.5 安全设计（物理移动必须有的护栏）

| 护栏 | 说明 |
|---|---|
| **默认只处理「未分类」** | 已是某个分组的卡**默认不动**（用户手动归过类，不该被程序覆盖）；要覆盖需显式勾选 |
| **预览先行** | 没有预览就没有执行（避免"点一下全库重排"） |
| **绝不覆盖同名文件** | 已有能力（`fs:moveCardToGroup` 追加时间戳），**不要绕过它另写移动逻辑** |
| **失败不改内存** | 已有能力（`moveCardToGroup` 返回 false 时内存不变），沿用 |
| **必须复用 `moveCardToGroup`** | 它负责三类 path 派生键迁移（覆盖层 / 测卡会话 / 记忆）—— **绕过它 = 静默丢失用户数据**（项目缺陷 AR 族多次踩过） |
| **可回滚** | 记录本次 `[{ oldPath, newPath, group }]`，提供"回滚本次自动分组"（按记录反向移动） |
| **库外卡片跳过** | 主进程已拒绝库外卡片；预览阶段就标为"跳过：不在库目录内，请先收编" |
| **大批量限速 + 可中断** | 张数多时逐张执行并显示进度；提供"中止"（已完成的不回退，日志里记录到哪一步） |

## 四、风险与回退（本节按项目铁律 6 与风控要求写）

| 风险 | 触发条件 | 影响 | 处置 |
|---|---|---|---|
| **路径派生键漏迁移** | 有人"顺手"另写移动逻辑、不走 `moveCardToGroup` | 卡片覆盖层 / 测卡会话与变量 / 长期记忆**静默丢失** | 强制复用原语 + 静态检查（见 §6 验收）+ 评审时把这条写进代码注释 |
| 误移动（判定错误） | 规则写错（如正则过宽） | 大量卡被搬走 | **预览先行**；默认不碰已分组的卡；可回滚 |
| 目标文件夹名非法 | 标签名含 `:` `/` 等 | 建目录失败 | 已有净化（`main.js:1174`）；预览阶段先做一次**名称合法化试算**并把结果展示给用户（如 `C++:基础` → `C++_基础`） |
| 同名文件冲突 | 两张同名卡被移进同组 | 覆盖丢卡 | 已有保护（追加时间戳）；预览表要对"同组同名"给**显式警告** |
| 大库卡顿 | 11k 卡逐张移动 | 界面卡住 / 磁盘压力 | 逐张 + 进度 + 可中止；**先在 75 张小库验收**，再到 11k 卡实测（同会话 A/B 口径） |
| 库目录被占用 | 其它程序锁文件 | 部分移动失败 | 失败项单独列出并提供"重试失败项"，不回滚已成功的 |
| 与"空分组自动清理"冲突 | 移动后原分组空了 | 分组消失让用户困惑 | 遵循既有行为（只删空目录），但**自动分组后给出提示**："原分组 X 已空，是否删除？" |

**回退方式**：
1. **功能级**：不做任何"自动触发"，只有用户点了才动；出问题 = 不点；
2. **操作级**：一键回滚（按移动日志反向移动）；
3. **数据级**：移动是 `rename`（同盘），不复制不删除；历史快照（`.bak_history`）机制不受影响。

## 六、验收（每期都要过三关 + 本功能的专项）

**通用水准**：`get_errors` → `npm test` + `python scripts/check.py` → **真实启动冒烟**（`npm start` 或 dev 模式）。

**专项验收（必须在隔离库上做）**：

1. **纯函数层单测**：判定函数对典型卡（有标签 / 无标签 / 多标签 / 名称命中 / 无命中）给出预期目标分组；
2. **预览与执行一致性**：预览说移动 N 张，执行后实际移动数 = N（跳过项不执行）；
3. **路径派生键迁移**：**造一张带测卡会话 + 覆盖层 + 记忆的卡**，自动分组后三者**全部跟随**（抽查即可，这是本功能最容易静默丢数据的地方）；
4. **失败隔离**：故意让一张卡移动失败（如目标同名冲突），验证其它卡照常完成、失败项有明细、内存状态与磁盘一致；
5. **回滚**：执行后一键回滚，卡片回到原分组且派生键也跟着回（同第 3 条的验证方式）；
6. **默认安全**：已是某分组的卡在**不勾选**覆盖时**一张都不动**；
7. **大库**：11k 卡库跑一次预览（只读）不卡死；执行选 1~2 个标签验证吞吐与中断。

**新增静态检查（建议，机器可执行）**：
- 一条 `pychecks` 检查：**除 `useCardGroups.moveCardToGroup` 外，不得存在其它直接调用 `electronAPI.moveCardToGroup` 的地方**（防止后人绕过键迁移另写移动）—— 这条是把 §四 第一条风险变成机器约束。
