## 〇、一句话

**在文件级**，按「**分组自己声明的收纳条件**」把卡片自动移进同名分组文件夹（文件夹不存在时自动创建）——
底层能力（建文件夹、物理移动、路径派生键迁移）**已经全部具备**，本方案要做的是
**分组档案 + 预览确认 + 可回滚**这三件工程化的事，而不是重写移动逻辑。

## 一、目标与不做什么

### 1.1 目标（用户原话拆解）

| # | 目标 | 说明 |
|---|---|---|
| G1 | **卡片自动分组** | 由程序判定每张卡该进哪个分组，不需要人手一张张拖 |
| G2 | **文件级实现** | 分组就是**磁盘上的文件夹**（与现有分组机制一致，不是纯内存标签） |
| G3 | **自动创建文件（夹）** | 目标分组文件夹不存在时自动建立 |

### 1.2 明确不做（本期）

| 不做 | 原因 |
|---|---|
| **不做「标签即分组」** | 文件夹数量在原理上不可控（LLM 层标签自由产出），且标签/分组语义错配 —— 见 §3.1 |
| 不做「后台常驻自动整理」 | 物理移动是**不可逆**操作，必须是用户显式触发的动作 |
| 不用 AI 判定分组 | 成本与不确定性高；先做**确定性规则**，AI 可作为后期「建议分组」而非直接移动 |
| 不改动现有分组/分类语义 | 现有「全部 / 未分类 / 预设分组 / 自定义分组」体系保持原样 |
| 不做多级嵌套分组 | 现有结构是**库根 + 一层子文件夹**（见 §2.4），本期不引入层级 |

### 2.4 分组在磁盘上的真实结构（决定了能做什么）

- 库根目录 = 「全部」；**一层子文件夹 = 一个分组**；「未分类」= 卡片放在**库根**（`fs:moveCardToGroup` 里 `isRootTarget` 分支回到 `libraryPath`）
- 分组名 = **文件夹名**（预设分组用中文名）→ 所以**分组名必须能作为合法目录名**（净化逻辑已有）
- **结论**：不支持多级嵌套（本期不做），也不建议做（会上探路径派生键的迁移复杂度）

### 2.5 缺口（= 本方案要新建的东西）

| 缺口 | 说明 |
|---|---|
| **判定层** | 目前没有任何「这张卡该属于哪个分组」的规则引擎 |
| **预览层** | 没有任何「先看看会发生什么」的界面；直接批量移动对用户太危险 |
| **回滚层** | `moveCardToGroup` 只保证失败时内存不变；**一旦成功就无法一键撤回**（移动历史未记录） |
| **入口 / 设置** | 没有自动分组的菜单入口与收纳规则配置界面 |

## 三、设计

### 3.1 为什么否决「标签即分组」（模式 A）

v1 给出的否决理由是「文件夹太多很麻烦」——这个说法太软，容易被反驳「用户自己控制标签不就行了」。
以下是**四条系统论证**：

#### (1) 文件夹数量在原理上不可控

| 标签来源 | 数量特性 | 对分组的影响 |
|---|---|---|
| 规则层预设 | **38 条**（§2.3 实测，分 4 组） | 上限已知但已不小 |
| **LLM 兜底层** | **自由生成，不可枚举**（P1 三层漏斗的第三层，Prompt 引导下的语义打标） | **每次打标批次都可能产出新标签 → 新文件夹** |
| 向量层 | 匹配已有标签体系，随体系膨胀 | 间接放大 |
| 用户自定义 + `customKeywords` | 无上限 | 持续增长 |

规则层 38 个还能说「可控」，**LLM 层是致命的**——「白发红瞳」「赛博朋克风」这类语义标签会**直接物化成磁盘文件夹**。
分组数破百后，**侧边栏本身先于分组功能失效**。

#### (2) 标签与分组的语义根本错配

- **标签**：多对多的**描述性**标记，一张卡命中越多越好（三层漏斗的设计目标就是叠加——规则命中后**仍进向量层补语义**），服务于搜索 / 过滤 / 统计；
- **分组**：一对一的**互斥容器**，一张卡只有一个物理位置，服务于存储组织。

用内置 4 组规则检验：世界观/题材勉强可做分组维度；**种族/物种**（兽耳、精灵）是**特征**不是收藏分类；
**人物类型**（如「女性角色」）是**半库卡片都会命中**的维度——按它分组会把半库卡片搬进同一个文件夹；
**性格/关系**（如「傲娇」）完全不该是文件夹名。38 条预设里**适合做分组维度的只有约 1/4**。

#### (3) 「多标签冲突策略」把模式 A 自己逼进死角

v1 已意识到一卡多标是常态，解法是「按**标签优先级**（可拖拽排序）取第一个命中」。这个解法的代价：

- 标签上百个时，**拖拽排序上百个标签来决定分组归属是不可用的交互**；
- 「标签优先级」这一概念**只为分组服务**，却寄生在标签体系上——标签列表排序本来可能有别的语义（频率、时间），被分组需求污染；
- 更根本的：既然要用户手动维护一份「标签 → 归属优先级」的**有序清单**，**这份清单本质上就是一张「标签 → 分组」映射规则表**——那为什么不直接做规则表，而要借道标签？

> **结论**：模式 A 做到能用的程度，就**自动变成了模式 B**。A 只是 B 的伪装得更简单的特例。

#### (4) 标签的动态性与物理移动的不可逆性冲突（数据漂移）

推演：用户跑一次三层漏斗 → LLM 给一批卡打标 → 自动分组把它们移进对应文件夹 → 用户**换模型 / 改 Prompt 重跑打标** →
标签集合变化，新卡不再命中旧标签 → 但已移动的卡按安全默认**不再动** →
库的最终状态 = **多个打标批次快照的混合物**，与当前标签体系永久不一致。

标签是**可重算的**（重跑即覆盖），物理移动是**不可逆的**（默认不动已分组卡）——把前者当作后者的判定源，
两者**生命周期根本不匹配**。而声明式配置是用户**显式写的稳定配置**，不受打标批次影响，不存在漂移。

#### (5) 对 v1 三条辩护理由的逐条回应

| v1 理由 | 回应 |
|---|---|
| 「与既有标签体系天然咬合」 | 咬合 ≠ 适合做分组；标签作为**可选判定条件输入**（而非映射源）才是正确咬合方式（§3.6） |
| 「判定确定性 100%」 | 确定性地产出 100 个文件夹，**确定性的垃圾也是垃圾** |
| 「用户心智简单：打什么标签进什么文件夹」 | 心智并不简单——用户必须额外理解「标签优先级排序」，见 (3) |

### 3.2 「要新规则体系，而不是复用」——精确化后的边界

原表述需拆成两层，否则实现时会摇摆：

| 层面 | 裁决 | 理由 |
|---|---|---|
| **判定语义 / 数据模型** | **必须全新** | 打标规则 `{name, regex, tag}` 是「匹配 → 叠加标记」（一卡可多命中）；分组规则是「匹配 → **唯一**归位」（必须唯一结果、有顺序语义、match 类型多样、目标受约束）。两者**表面同构、语义相反**，照抄必然出问题 |
| **交互工程经验** | **可以借鉴，不是照搬** | 规则表 UI 形态（列表 + 开关 + 排序）、`disabled` 清单式落盘（**零迁移**）、弹窗交互范式——这些是**已验证的工程资产**，为「新」而放弃它们是负收益。**借鉴骨架，不借鉴语义** |

### 3.3 替代设计：声明式分组档案（Group Profile）

#### (1) 核心转变：反转视角

```
模式 A / B 的视角：这张卡命中了什么规则 → 移到哪个组      （规则产出分组）
声明式的视角：    这个分组收纳什么样的卡 → 卡进来          （分组声明成员资格）
```

#### (2) 数据模型（v1 版实现）

```js
// 落盘位置：appConfig 下（与 autoTagRules 同级），键名 autoGroupProfiles
// 归一化函数：normalizeGroupProfiles(list)（与 P1 的 normalizeTagFunnel / normalizeDisabledRules 同构，落盘前收敛脏值）
autoGroupProfiles: [
  {
    id: 'profile-genshin',        // 稳定唯一 id（分组名可被用户改，id 不改）
    group: '原神',                 // 目标分组名 = 文件夹名（净化逻辑已有，见 §2.1）
    enabled: true,
    match: {
      // v1 只放开「已取证」的五种；author 待取证后再加（§3.11）
      type: 'tag'           // 统一取标签入口 extractCardTags（§2.2）
          | 'name-keyword'  // item.name 包含关键词
          | 'name-regex'    // item.name 正则
          | 'hasLorebook'   // 布尔条件，无 pattern
          | 'hasRegex',     // 布尔条件，无 pattern
      pattern: '原神',       // 布尔型条件（hasLorebook / hasRegex）**无此字段**
    },
    note: '按作品归档'        // 预览时展示给用户的判定依据说明
  }
]
```

**v1 约束：每个分组最多挂一条收纳规则**（v1 简化）；S5 放开「同分组多规则 + 条件组合（all/any）」。

#### (3) 为什么它从数据模型层面根治文件夹爆炸

| 约束 | 效果 |
|---|---|
| 规则**寄生在分组上**，不能凭空造分组 | **文件夹数量 ≡ 用户显式创建的分组数**，与标签体系完全解耦——这是**模型保证**，不是 UI 劝说 |
| 用户心智 | 「我建了 5 个分组，给其中 3 个配了自动收纳」——分组是用户**本来就要管理**的对象，配置只是顺手的增强 |
| LLM 产出再自由 | 也变不成文件夹——LLM 标签只是卡片上的数据，只有当用户在某分组的收纳条件里**显式引用** `type:'tag'` 时才参与判定 |

### 3.4 冲突处理：从「标签优先级」改为「分组顺序」

一张未分类卡同时满足两个分组的收纳条件时：**按分组在侧边栏的顺序取第一个命中**。

相比模式 A 的方案：

- 排序对象从「上百个标签」变为「**个位数分组**」；
- 分组顺序是用户**本来就有**的概念（侧边栏显示顺序，§2.6 已取证），**不引入新概念**；
- 预览时对冲突卡显示「该卡同时命中 [原神(序 1)、东方(序 2)]，将进入**原神**」——可理解、可当场调整顺序。

### 3.5 与原始需求 G1~G3 的对齐检查（否决 A ≠ 否决需求）

| 需求 | 对齐情况 |
|---|---|
| G1 自动分组 | 对齐。判定层 + 执行层不变，只是规则源从「标签映射」变为「分组档案」 |
| G2 文件级 | 对齐。仍走 `fs:moveCardToGroup` |
| G3 自动创建文件夹 | **保留但触发时机受控**：收纳规则声明的 `group` 不存在时，预览中列出「将创建分组文件夹 X」，执行时由既有 `mkdir` 逻辑创建——**仍是自动创建**，但创建的名称和数量来自**用户显式配置**，而非标签自动衍生 |

### 3.6 与打标体系的正确咬合方式

标签从「映射源」**降级为「可选条件输入」**：用户可以在某分组的 `match` 里写 `{ type:'tag', pattern:'原神' }` ——
此时打标质量影响**该分组**的召回，但**爆炸半径被限制在单个分组内**，且预览界面显示命中原因（「标签：原神」），用户能看到判定依据。

**建议**：预览表对 `tag` 型条件额外提示「此判定依赖当前标签，**重跑打标后建议复查**」。

### 3.7 触发时机（建议只做前两个）

| 时机 | 建议 | 理由 |
|---|---|---|
| **手动一键（含预览）** | **做** | 安全、可控；用户明确知道自己要整理时才动文件 |
| **导入新卡后提示** | **做（可选开关，S6）** | 新卡通常「未分类」，此时归位风险最低 |
| 每次启动自动整理 | **不做** | 不可预期地移动文件会摧毁信任 |
| 定时后台整理 | **不做** | 同上，且与「库目录被其它程序占用」叠加会出问题 |

### 3.8 执行流程（**核心是「先预览、后执行、可回滚」**）

```
① 用户点「自动分组」
      ↓
② 扫描 + 计算计划（只读，不动文件）
   对每张卡判定目标分组 → 生成计划表：
     [卡名]  [当前分组]  →  [目标分组]   原因(命中哪个分组的哪条条件)
     跳过项也列出并说明原因（已在目标分组 / 未命中任何分组条件 / 库外卡片）
     冲突项标出「同时命中 [X(序1)、Y(序2)]，将进入 X」
     同时列出「将要新建的分组文件夹」
      ↓
③ 预览确认（弹窗，可勾选/取消单条）
   统计：将移动 N 张 / 跳过 M 张 / 新建 K 个文件夹
   默认**不勾选**「包含已手动分组的卡片」（见 §3.10 安全默认）
      ↓
④ 执行（逐张 moveCardToGroup，复用现有原语，天然带着三类键迁移）
   进度条 + 逐条结果；失败项保留在计划里并显示原因；可中止（已完成的不回退）
      ↓
⑤ 写移动日志（可回滚，格式见 §4.1）+ 空分组清理提示
```

### 3.9 UI 入口与界面（建议）

| 界面 | 内容 |
|---|---|
| **入口** | 「标签」菜单（与打标同域，符合现有菜单语义）+ 侧边栏分组区按钮；**同一命令 id**（注册表镜像项，P2 已具备能力） |
| **分组档案设置弹窗** | 分组列表（取 `buildGroupOptions()`）+ 每分组一条收纳条件（类型下拉 + pattern 输入 + 启用开关）+ 顺序提示「按侧边栏顺序取第一个命中」；交互形态参照 `AutoTagRulesModal.vue`（**只借鉴骨架**，§3.2） |
| **预览/执行弹窗** | 计划表（可勾选）+ 统计数字 + 「新建的文件夹」列表 + 冲突明细 + 执行/取消 |
| **移动日志** | 设置里可查看「最近一次自动分组」的明细，并提供**一键回滚**（§四） |

### 3.10 安全设计（物理移动必须有的护栏）

| 护栏 | 说明 |
|---|---|
| **默认只处理「未分类」** | 已是某个分组的卡**默认不动**（用户手动归过类，不该被程序覆盖）；要覆盖需显式勾选 |
| **预览先行** | 没有预览就没有执行（避免「点一下全库重排」） |
| **绝不覆盖同名文件** | 已有能力（`fs:moveCardToGroup` 追加时间戳），**不要绕过它另写移动逻辑** |
| **失败不改内存** | 已有能力（`moveCardToGroup` 返回 false 时内存不变），沿用 |
| **必须复用 `moveCardToGroup`** | 它负责三类 path 派生键迁移（覆盖层 / 测卡会话 / 记忆）—— **绕过它 = 静默丢失用户数据**（项目缺陷 AR 族多次踩过）。**这条写进代码注释** |
| **回滚也必须复用 `moveCardToGroup`** | 回滚 = 反向批量移动，同样涉及三类键迁移；**禁止**为回滚另写反向 `fs.rename` 快捷路径（见 §4.2） |
| **可回滚** | 记录本次移动明细（格式见 §4.1），提供「回滚本次自动分组」 |
| **库外卡片跳过** | 主进程已拒绝库外卡片；预览阶段就标为「跳过：不在库目录内，请先收编」 |
| **大批量限速 + 可中断** | 张数多时逐张执行并显示进度；提供「中止」（已完成的不回退，日志里记录到哪一步） |

## 四、回滚设计（v2.0 加强）

### 4.1 移动日志的正确形态：**按卡名 + fromGroup 记，不回守路径**

v1 记录 `[{ oldPath, newPath, group }]` 并「按记录反向移动」。**失效场景**：

- 自动分组后，用户用 `fs:renameGroupFolder` **重命名了原分组**（该操作会迁移卡路径）→ 日志里的 `oldPath` **全部失效**；
- 用户手动移动 / 删除了某张卡 → 回滚该卡时**找不到文件**。

**修正**：

| 项 | 做法 |
|---|---|
| 日志字段 | `[{ cardName, fromGroup, toGroup, folderName, movedAt }]`（**不记绝对路径**，或仅作为辅助信息记录） |
| 回滚定位 | 回滚时**按卡名在当前库里查实际路径**，而非死守日志路径 |
| 变动检测 | 卡片已变动（不在预期位置 / 已被删除 / 分组已被重命名）→ 标记「**无法自动回滚：卡片已变动**」并**单独列出**，**不静默跳过、也不报错中断整批** |
| 记录 `fromSubFolder` | 回滚要重建可能已被删除的空分组 → 需记录 `fromGroup`（= 文件夹名），见 4.3 |

### 4.2 回滚本身也是移动，**必须走 `moveCardToGroup`**

回滚 = 反向批量移动，**同样涉及三类派生键迁移**。如果实现时「顺手」写了反向 `fs.rename` 快捷路径，
就精准踩中 §3.10 第一条风险（静默丢失覆盖层 / 测卡会话 / 记忆）。

**约束**：§六 静态检查的适用范围**必须写明包含回滚代码路径**；验收第 5 条按第 3 条同等标准验证派生键跟随。

### 4.3 与「空分组清理」的交互

执行后原分组变空 → 用户确认删除（§3.10 已提示）→ 之后点回滚 → 原分组文件夹**已不存在**。

技术上可行（`fs:moveCardToGroup` 目标目录不存在时自动 `mkdir`），但：

- 日志需记录 `fromGroup`（文件夹名）；
- 回滚 UI 需说明「将**重建**已删除的空分组 X」。

### 4.4 风险与回退（本节按项目铁律 6 与风控要求写）

| 风险 | 触发条件 | 影响 | 处置 |
|---|---|---|---|
| **路径派生键漏迁移** | 有人「顺手」另写移动逻辑、不走 `moveCardToGroup` | 卡片覆盖层 / 测卡会话与变量 / 长期记忆**静默丢失** | 强制复用原语 + 静态检查（范围含回滚路径）+ 评审时把这条写进代码注释 |
| **回滚路径失效** | 回滚前用户改名分组 / 手动移动 / 删除卡片 | 回滚失败或搬错 | §4.1 按卡名定位 + 变动检测单独标记 |
| **回滚绕过原语** | 为回滚另写反向 rename | 同第一条（静默丢数据） | §4.2 明确禁止 + 静态检查覆盖 |
| 误移动（判定错误） | 条件写错（如正则过宽） | 大量卡被搬走 | **预览先行**；默认不碰已分组的卡；可回滚 |
| 目标文件夹名非法 | 分组名含 `:` `/` 等 | 建目录失败 | 已有净化（`main.js:1174`）；预览阶段先做一次**名称合法化试算**并把结果展示给用户（如 `C++:基础` → `C++_基础`） |
| 同名文件冲突 | 两张同名卡被移进同组 | 覆盖丢卡 | 已有保护（追加时间戳）；预览表要对「同组同名」给**显式警告** |
| 大库卡顿 | 11k 卡逐张移动 | 界面卡住 / 磁盘压力 | 逐张 + 进度 + 可中止；**先在 75 张小库验收**，再到 11k 卡实测（同会话 A/B 口径） |
| 库目录被占用 | 其它程序锁文件 | 部分移动失败 | 失败项单独列出并提供「重试失败项」，不回滚已成功的 |
| 与「空分组自动清理」冲突 | 移动后原分组空了 | 分组消失让用户困惑 | 遵循既有行为（只删空目录），但**自动分组后给出提示**：「原分组 X 已空，是否删除？」；回滚时按 §4.3 重建并说明 |
| **归位落空被误报为 bug** | `autoTagOnImport` 关闭 / 新卡无标签，而收纳条件用 `type:'tag'` | 新卡永远不归位 | §3.11 第 5 条：预览与提示文案显式说明该依赖 |

**回退方式**：

1. **功能级**：不做任何「自动触发」，只有用户点了才动；出问题 = 不点；
2. **操作级**：一键回滚（按 §4.1 日志反向移动，走同一原语）；
3. **数据级**：移动是 `rename`（同盘），不复制不删除；历史快照（`.bak_history`）机制不受影响。

## 六、验收（每期都要过三关 + 本功能的专项）

**通用水准**：`get_errors` → `npm test` + `python scripts/check.py` → **真实启动冒烟**（`npm start` 或 dev 模式）。

**专项验收（必须在隔离库上做）**：

1. **纯函数层单测**：判定函数对典型卡（有标签 / 无标签 / 多标签 / 名称命中 / 无命中 / 同时命中两个分组）给出预期目标分组与命中原因；
2. **预览与执行一致性**：预览说移动 N 张，执行后实际移动数 = N（跳过项不执行）；
3. **路径派生键迁移**：**造一张带测卡会话 + 覆盖层 + 记忆的卡**，自动分组后三者**全部跟随**（抽查即可，这是本功能最容易静默丢数据的地方）；
4. **失败隔离**：故意让一张卡移动失败（如目标同名冲突），验证其它卡照常完成、失败项有明细、内存状态与磁盘一致；
5. **回滚**：执行后一键回滚，卡片回到原分组且**派生键也跟着回**（**与第 3 条同等标准**，因为回滚也是移动）；
6. **默认安全**：已是某分组的卡在**不勾选**覆盖时**一张都不动**；
7. **大库**：11k 卡库跑一次预览（只读）不卡死；执行选 1~2 个分组验证吞吐与中断；
8. **回滚变动检测**：回滚前**重命名原分组**、**手动移走一张卡**、**删除一张卡**，验证三种情况分别给出「无法自动回滚：卡片已变动」明细，**不静默跳过、不中断整批**；
9. **空分组被删后回滚**：删除已空的原分组 → 回滚 → 验证文件夹被**自动重建**且 UI 有说明；
10. **slim 大库标签可读**：11k **slim 库**在预览阶段能读到原生标签（复用 `extractCardTags`），**不触发正文还原、不卡死**；
11. **大小写口径**：标签大小写混排（如卡上 `Genshin`、条件写 `genshin`）仍能命中（`extractCardTags` 全小写 + `pattern` 小写化）；
12. **条件类型边界**：布尔条件（`hasLorebook` / `hasRegex`）无 `pattern` 时正常工作；`name-regex` 非法正则只跳过该条、不拖垮整表。

**新增静态检查（建议，机器可执行）**：
- 一条 `pychecks` 检查：**除 `useCardGroups.moveCardToGroup` 外，不得存在其它直接调用 `electronAPI.moveCardToGroup` 的地方**
  （防止后人绕过键迁移另写移动）—— **`include` 范围必须覆盖回滚代码路径**（§4.2）。这条是把 §4.4 第一条风险变成机器约束。
