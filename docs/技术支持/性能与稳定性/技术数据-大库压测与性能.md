## 五、PNG 内嵌提取缓存 A/B（同机交替、每次重启、同一大库）

| 方案 | fetch | worker | assemble | 首屏合计 | 缓存占盘 |
|---|---|---|---|---|---|
| **无缓存（现版本）** | 2.5 ~ 3.4s | 1.4 ~ 8.9s | 9.6 ~ 22.3s | **16.0 ~ 31.2s** | 0 |
| v1 `.json` 分片（24 片） | 9.3s | 2.0s | 11.0s | 36.9 ~ 43.3s | 1.17GB |
| v2 `.json.gz` 分片（23 片） | 29.1s | 1.6s | 52.8s | **85.3s** | 385MB |
| v8 二进制分片（过渡试验） | 62.5s | — | — | **137s** | 385MB |

**机理**：从 PNG 头部提取内嵌 JSON 本身只要 ~3s（自适应窗口 + 128 路并发 + 按需流式，GC 可回收）；
缓存把约 1.2GB 的**对象**一次性常驻主进程 → 堆压力/GC 抖动 + 额外 IPC 克隆，反而慢 2~5 倍。
压缩只减磁盘与读取量，**消不掉"对象常驻"这个根因**。
`v8.deserialize` 产出 **dictionary-mode** 对象，跨 IPC structured clone 与属性访问都明显变慢 —— 要交给渲染进程的数据，`JSON.parse` 反而是快路径。

**处置**：删除整块实现（-173 行）+ `cleanupLegacyEmbedCache()` 一次性回收（本机 **44 文件 / 758MB**）+ `.embed_cache_removed` 标记保证只扫一次目录。

## 六、冷启动 I/O 量化（`scripts/tools/png-head-io-probe.mjs`）

| 指标 | 数值 |
|---|---|
| 库合计 | 10,072 MB / 11,663 个 PNG+JSON |
| **每次启动读取量**（复刻主进程窗口逻辑） | **约 9,565MB（9.3GB）** |
| 文件打开次数 | **11,663 次** |
| 热缓存实读耗时 | 2.3s（等效 4,206MB/s —— 即 `fetch≈3s` 的真相） |
| 冷启动额外 I/O 估算 | 按 600MB/s 冷盘 ≈ **16~19s**；按 2~3GB/s NVMe ≈ **3~6s** |

**为什么读这么多**：`chara` 内嵌块位于**文件末尾附近**（块结束偏移 P50≈616KB / P90≈897KB / P99≈1010KB），
所以 ≤1MB 的卡（9,487 个，占大头）必然整文件读；>1MB 的卡里还有 1,902 个块不在前 1MB，只能走「读 8MB / 读整文件」兜底。
⇒ 「把首读窗口缩到 64KB 省 I/O」的设想**不成立**（64KB 只能命中 24%）。

**22k 库对账**：22,276 张 PNG 需读 ≈19.8GB，11k 库实测 9,565MB 翻倍正好对上。

**可选优化（未做）**
| 方案 | 预估 | 风险 |
|---|---|---|
| ① 尾读 + 标记搜索（`chara` 在末尾 → 只读最后 ~256KB 搜 `tEXt`/`chara\0`） | 读量 9.3GB → ~3GB | 块跨越尾窗、图像数据里撞标记 |
| ② 懒加载分片缓存（只缓存「path+mtime+size → 内嵌 JSON **文本**」，按需读单片） | 省重复提取 | 不要把对象常驻（这正是 85.3s 的锅） |
| ③ 什么都不做 | 冷启动多花几秒 | 换掉 1.17GB 磁盘 + 一堆缓存维护代码（**当前默认选择**） |

## 七、容量边界与安全上限

| 库规模 | 加载 | 堆占用（加载 + 索引后） | 判定 |
|---|---|---|---|
| 11,186 卡 / 9.76GB | 16.0 – 31.2s | 2.0 – 3.0GB（48 – 73%） | ✅ 日常可用 |
| **22,372 卡 / 19.85GB** | **85 – 117s**（P1a 后 72s） | **3.05 – 3.26GB / 4.19GB（73 – 78%）**，P1a 后 2,053MB | ⚠️ **能加载**（全部入库、索引可用、无崩溃），但「余量小」 |

**结论**：
- 2 万卡「能加载」，不是打不开；但处于「能跑、余量小」区间；
- **安全上限建议按 1.2–1.5 万卡规划**（对应堆 < 70%、首屏 < 60s）；
- 渲染进程堆上限 **4,192MB 是真的、抬不上去**（详见 [PK-10](../../bugs/BUG-性能与大库.md)），所以只能靠减少占用，不能靠抬上限。

### 9.4 T6 · 分级扫描并发（真实库 6 本大书 / 49.2MB）

| 并发 | 耗时 | 堆峰值增量 |
|---|---|---|
| 1 | 219ms | 74.4MB |
| **2（调参后生产值）** | 191ms | **58.7MB** ← 内存最低 |
| 3（原生产值） | 190ms | 118.1MB |

| 12 | 184ms | 117.7MB |

- 并发 2→12 耗时仅改善 **3%**，内存增量却从 **59MB → 118~146MB**。
  ⇒ **瓶颈在磁盘 I/O 与 `JSON.parse`，不在并发度**；提高并发只是白吃内存。
  → `SCAN_HEAVY_CONCURRENCY` **3 → 2**（内存减半、速度无损）。
- 常规档（放大到 240 本 / 25.2MB）：

  | 批次并发 | 耗时 | 堆峰值增量 |
  |---|---|---|
  | 4 | 185ms | 22.3MB |
  | 8 | 160ms | 26.4MB |
  | 16 | 157ms | 25.9MB |
  | **32（生产值）** | 154ms | 26.8MB |
  | 64 | 152ms | **44.3MB** |

  拐点在 16~32 → **`SCAN_JSON_BATCH = 32` 维持不动**。

- ⚠️ **探针踩坑**：首版用 `readFileSync` + `Promise.all` 包**同步**函数 → async 体内无 `await`，

  **教训：测并发必须确认被测函数真异步**（改用 `fs.promises.*` 后才生效）。

| 1 | **批量 `Promise.all(stat)` 后再统一判定** | **1164ms（更慢）** | ❌ 并发开销 > 收益，**已回滚** |

| 3 | **提高并发度**（T6 实验，并发 2→12） | 仅改善 **3%**，内存却 59→146MB | ❌ 瓶颈在磁盘 I/O，不在并发 |

**⇒ 最终结论：阶段 1 的 `stat` 占 83%，已是本机磁盘元数据操作的下限，无提速空间。**
代码保持**朴素的逐个 `stat` 实现**（不引入无收益的复杂度）。

**唯一真实的提速点是「热缓存跳过阶段 2」**（已是现状）：

| 场景 | 阶段 1 | 阶段 2 | 总计 |
|---|---|---|---|
| 冷缓存（首次） | ~780ms | **233.5s** | **~234s** |
| **热缓存（第二次起）** | ~780ms | **0ms** | **~0.8s** |

⇒ **热缓存提速 290×**（234s → 0.8s），且**阶段 2 在后台，本就不阻塞首屏**。

**⇒ 对用户问题的直接回答**：
- **5000 本「秒开」= 阶段 1 = ~780ms**（用户看到列表的时间）；
- **首次完整加载（含元数据 + L1 索引）= ~234s**（**后台**，不阻塞首屏）；
- **之后每次加载 = ~0.8s**（缓存全命中）；
- **无提速空间** —— 阶段 1 已是磁盘物理下限（83% 是 `stat`），阶段 2 已被缓存完全消除。
