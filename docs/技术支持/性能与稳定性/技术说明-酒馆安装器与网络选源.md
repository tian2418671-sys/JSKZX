## 一、安装流程与「先测网络，再选地址」

```text
① 探测 Node（缺失 → winget 安装 / 给官网下载按钮）
② 目录准备（<安装目录>\_jsk-runtime\）
③ 🌐 网络探测（并行，每个 4 秒超时）→ 选最快的下载源 + 最合适的 npm 源
④ 下载酒馆源码 zip（按③的顺序尝试；zip 魔数校验）
⑤ 解压（系统自带 bsdtar / tar）
⑥ 安装依赖（node + npm-cli.js；按③决定走官方 registry 还是国内镜像）
⑦ 写安装清单 runtime.json
```

### 探测目标（并行）

| 类别 | 目标 |
|---|---|
| 下载 · 直连 | `https://codeload.github.com/<repo>/zip/refs/heads/<branch>` |
| 下载 · 镜像 | `GH_MIRRORS` 里每个前缀 + 同一地址（当前：`ghfast.top` / `gh-proxy.com`） |
| npm · 官方 | `https://registry.npmjs.org/-/ping` |
| npm · 国内 | `https://registry.npmmirror.com/-/ping` |

判定只看**可达 + 耗时**（HEAD，403/405 也算可达 —— 不少镜像不支持 HEAD）。

### 决策（`main/networkPlan.js`，纯函数、已单测）

- **下载源**：只保留可达项，**按实测耗时升序**；同耗时直连优先（`priority=10`）。
  全不可达 ⇒ 直接报「❌ 网络不可用：GitHub 直连与所有加速镜像都连不上」，**不再白等一轮轮超时**。
- **npm 源**：可达项里**最快者胜**，同耗时官方优先；都不可达 ⇒ 官方兜底（让 npm 自己报错）。
- 结论会以一行日志回显给用户，例如：

  ```text
  🌐 网络检测：下载：GitHub 直连（最快）｜npm：国内镜像｜探测结果
  GitHub 直连 871ms｜ghfast.top 不可用｜gh-proxy.com 不可用｜npm 官方 3181ms｜npm 国内镜像 371ms
  ```

- 「🩺 检查环境」也**第一项就报网络**（空目录同样给结论，因为装不上往往就是网络问题）。

> ⚠️ **踩坑记录（别重犯）**：`--registry` 必须传**基地址**（`https://registry.npmmirror.com`），
> 不能传探针地址（`https://registry.npmmirror.com/-/ping`）—— 后者会让 npm 把包解析成
> `<base>/<pkg>/-/<pkg>.tgz` → **E404**（实测踩过一次，已在 `NPM_REGISTRY_BASE` 里固化基地址）。

## 二、调用外部命令（Windows 关键坑）

`main/spawnPlan.js` 统一收口，**禁止**在别处直接 `spawn('npm.cmd', …)`：

| 场景 | 做法 | 原因 |
|---|---|---|
| 首选 | `node.exe "<nodeDir>\node_modules\npm\bin\npm-cli.js" …` | 完全绕开 shell/批处理，路径带空格也安全（`pickNodeCli` 定位） |
| 兜底 | `cmd.exe /d /s /c npm.cmd …` + `windowsVerbatimArguments:true` | `.cmd` 在 `shell:false` 下会被 Node 拒绝（EINVAL，CVE-2024-27980） |
| 禁止 | 带路径的 `.cmd`（`C:\Program Files\...\npm.cmd`）经 cmd 传参 | `/s /c` 会剥外层引号 → 「'C:\Program' 不是内部或外部命令」 |

配套：`resolveNpm()` 会把 Node 目录**前置进子进程 PATH**（winget 刚装完 Node 时当前进程 PATH 不会刷新）。

## 三、依赖安装的可观测性

npm 在 `--loglevel=error --no-progress` 下**成功前零输出**，因此 `runStreamed` 提供心跳：

```text
⏳ 仍在执行（已用 5 秒）｜已装 0 个包
⏳ 仍在执行（已用 10 秒）｜已装 170 个包
```

- 包数 = `<root>/node_modules` 下一级目录数（纯本地计数，不联网）
- 「取消任务」：UI 传 `activeTaskId`；主进程对「未传 id 且只有一个任务在跑」也做兜底；
  取消统一翻译成退出码 `-3` → 界面显示「已取消」而不是「失败（退出码 1）」

## 四、下载阶段的数值进度读数（`main/downloadProgress.js`）

下载**不能**用 `resp.arrayBuffer()` 一次读完 —— 几十 MB 在慢网下要几分钟，期间零事件，
界面只有一个不动的进度条（AR-87）。现改为流式：

```text
下载中 35% · 12.8 MB / 36.7 MB · 142.9 KB/s
```

界面呈现（`StInstallModal.vue` ③ 进度）：

```text
35%                                    ← 数字用 font-mono/tabular-nums，一眼能读
12.8 MB / 36.7 MB · 142.9 KB/s         ← 已下 / 总量 / 实时速度
[████████░░░░░░░░░░░░░░]                ← 整条进度条按 10%→45% 区间平滑推进
```

要点：

| 关注点 | 做法 | 原因 |
|---|---|---|
| 推送节奏 | 250ms 节流（`shouldEmit`），首个数据块立即推 | 4/s 足够看出在动，又不打爆 IPC |
| 百分比封顶 | 未收完最高 99，收完才 100 | 避免「100% 却还在转」的假完成 |
| 总量未知 | `content-length` / `content-range` 都读不到 → `percent = -1`，界面改说「已下载 12.3 MB」 | 镜像常用 chunked，不装懂 |
| 速度 | 开始 0.2 秒内不报（`computeSpeed` 返回 0） | 否则开头抖出「几 TB/s」 |
| 落盘 | 先写 `<zip>.part`，校验通过再 `rename` | 中途失败/取消不留半个 zip 冒充安装包 |
| 坏镜像 | 首块验 zip 魔数（`PK`）；`content-length` 对不上视为不完整 → 掐掉响应体换下一个源 | 镜像偶发返回 200 的 HTML 错误页 |
| 取消 | 循环内每块检查 `cancelledTasks`，并 abort 掉 fetch | 与 AR-86 的取消语义一致 |

实测（本机 2026-11-16，GitHub 直连约 120 KB/s）：完整下载 36.7MB 收到 **1091 条**进度事件，
整体百分比单调递增 10 → 45，末条 `下载完成 100% · 36.7 MB / 36.7 MB · 120.5 KB/s`。

## 五、断点续传（`main/downloadResume.js`）

目标：**软件被意外关闭后，不该从头再下 36.7MB。**

做法：下载数据写 `<dest>.part`，旁边留 `<dest>.part.json`（版本 / 源地址 / 总大小 / ETag / Last-Modified）。
下次（哪怕重开软件）再下载同一目标时，用 HTTP `Range: bytes=<已下载>-` 继续。

### 关键事实（本机实测 2026-11-16）

| 源 | `Range: bytes=1000-1999` 的结果 | 能否续传 |
|---|---|---|
| `codeload.github.com`（直连） | **200**，`Content-Length: 38439126`，无 `Content-Range` | ❌ 不支持 |
| `gh-proxy.com`（镜像） | **206**，`Content-Range: bytes 1000-1999/38439126` | ✅ 支持 |
| `ghfast.top` / 多个其它镜像 | 连不上 / 403 / 200 全量 | ❌ |

⇒ **不能只对上"上次那个源"续传**：上次很可能走的直连（不支持 Range）。所以有残留片段时先并发探测一次
`Range: bytes=0-0`（4s 超时），挑「206 + 总量一致」的源来续传，探测只花 1 秒左右。

### 判定规则（全部是纯函数、已单测）

| 情况 | 处理 |
|---|---|
| 206 且 `Content-Range` 起点 == 本地片段长度 | `append`：追加写 |
| 200（源不支持 Range / 文件变了） | `restart`：截断重下，并在日志说明 |
| 416（范围越界，片段可能已完整） | 先验 zip 魔数，完整就直接用，否则重下 |
| 片段长度 == 元数据里的 total | 直接当「已下载完成」复用（崩溃在 rename 之前的情况） |
| 元数据版本不符 / JSON 坏了 | 当作没有 → 不冒险续传 |
| 跨源续传（源换了但 total 一致） | 允许，但**不带 `If-Range`**（各镜像 ETag 互不相同），收尾用 zip EOCD 校验兜底 |

收尾校验：下载完成后读文件尾部 128KB，找 `PK\x05\x06`（中央目录结束记录），并校验中央目录不越界。
失败就判定「片段拼接不一致」→ 丢弃重下，避免用户看到莫名其妙的「解压失败」。

### 中断即保留

- 用户点「取消任务」→ **保留** `.part`（这正是续传的前提），日志提示「已保留已下载的 X，下次会从这里继续」；
- 网络抖动 / 断流 → 同样保留；
- 只有「内容不是 zip」「结构校验失败」「所有源都不支持 Range」才删片段。

### 「续传会不会反而更慢？」——测速守卫

实测反例：直连能跑 **2.4 MB/s**，而支持 Range 的镜像只有 **~70 KB/s**；
硬续传 33MB 要 8 分钟，比直接重下 15 秒差得多。所以：

1. 中断时把**本次实测速度**记进 `.part.json` 的 `rateBps`；
2. 续传开始后先跑 **10 秒**测速，若低于上次速度的 **70%** ⇒ 判定「这个续传源不划算」，
   丢弃片段、回到原快源从头下（损失 ≤10 秒，换来正常速度）；
3. 没有历史速度、或测不出速度时**不切换**（不拿猜测当理由折腾用户网络）。

判定是纯函数 `shouldAbandonResume({ resumeRateBps, previousRateBps, factor })`，已单测。
