# 技术储备 · 渲染进程崩溃恢复闸门

> 状态：**已封存**（未合入主线，不影响 2.2.7 运行）
> 封存时间：2026-09-13
> 起因：大库压测时的观察，**不是**线上故障驱动
> 代码存放：`git stash`（条目名见第四节），本文件保留设计思路与结论

---

## 一、为什么值得留（结论先行）

这是一个**独立于内存问题的第二层兜底**，与已上线的内存守门员是**不同防线**：

| | 内存守门员（2.2.7 已上线） | 崩溃恢复闸门（本文档，已封存） |
|---|---|---|
| 层次 | **预防** | **兜底** |
| 时机 | OOM 之前，读内存占用主动降级 | 已经崩了之后，决定要不要再自动重载 |
| 能治什么 | 内存增长导致的崩溃 | **任何**原因导致的反复崩溃（不止 OOM） |
| 局限 | 只覆盖它能识别的内存模式 | 不能阻止第一次崩溃 |

**关键区别**：内存守门员防的是"它认得出的 OOM"。而崩溃可能来自别的原因
（实测遇到过两种不同 exitCode：`-36861` 与 `2`）。
只要崩溃是**反复发生**的，原本「崩了就无条件 reload」的兜底就会变成
**无限重载循环** —— 界面无限闪烁、用户点不到任何按钮、每轮还重扫盘重解析万卡。
闸门就是切断这个循环的。

> 边界说明：本文档记录的现象来自**开发期压测**（11,186 张 / 9.76GB 卡库），
> **没有证据表明线上正在发生**。因此它是"储备"，不是"待修缺陷"。

## 二、要解决的问题（原理）

### 2.1 原有兜底

`main.js` 的 `render-process-gone` 处理：

```js
if (details.reason === 'crashed' || 'oom' || 'killed') {
    setTimeout(() => { if (!win.isDestroyed()) win.reload(); }, 1500);
}
```

**对偶发崩溃是正确的** —— 用户几乎无感，比白屏好。

### 2.2 它假设了"崩溃是偶发的"

当崩溃是**确定性**的（例如库太大、某张卡必崩），就会形成：

```
加载 → 崩 → 1.5s 后 reload → 又加载 → 又崩 → 又 reload → …
```

三层后果：

1. **界面无限闪烁**，用户既看不懂也点不到按钮（比白屏更糟）
2. 每轮 reload 重扫盘 + 重解析（实测单次加载 17s、增量刷新可达 166s），CPU/磁盘被吃满
3. reload 会再触发一次**全量加载**；若崩溃时还有在途加载，两者并发重入同一个
   `library` 数组 → **会产生重复卡**（这条把"崩溃循环"与"重复卡"串成同一因果链）

第 3 条尤其值得记：**重复卡问题的成因不只一个**，崩溃重载是其中一条隐蔽路径。

## 三、方案要点（可复用的设计）

### 3.1 纯逻辑与副作用分离

状态机抽成 `main/crashRecovery.js`，**副作用全部由调用方注入**
（弹窗 / reload / 日志 / 时钟 / 定时器）：

```js
createCrashRecovery({ retryMax, windowMs, stableMs,
                      now, setTimer, clearTimer,
                      onGiveUp, onReloadPlanned, onStable })
  → { decide(), noteAlive(), snapshot(), reset() }

evaluateCrashWindow(stamps, nowTs, { retryMax, windowMs })
  → { inWindow, shouldGiveUp, total }

CRASH_DEFAULTS = { retryMax: 3, windowMs: 120000, stableMs: 60000 }
```

**收益**：可以用**假时钟 + 假定时器**单测，不必真崩渲染进程、也不必真等 60 秒。

> 该形态与项目既有约定一致：主进程纯逻辑抽到 `main/*.js` 再单测
> （先例：`main/memoryStore.js` ↔ `test/memoryStore.test.mjs`）。

### 3.2 核心语义

```js
const inWindow = stamps.filter(t => nowTs - t < windowMs).length;
const shouldGiveUp = inWindow > retryMax;   // 「超过」上限才放弃
```

`retryMax = 3` ⇒ 第 1/2/3 次仍自动恢复，**第 4 次停止**。

### 3.3 三个容易做错的点（这是最值得留的部分）

**① 崩溃计数必须按时间窗口滑动**
否则长期运行下计数只增不减，"越用越容易放弃"。旧记录要按 `windowMs` 剔除。

**② 「恢复成功」不能用 `did-finish-load` 判定**
那只是文档合成完成，紧接着仍可能在解析卡片时崩（大库就是这种情况）。
必须由**渲染层首屏流程真正走完**后主动上报（`app:ready`），
再由主进程计时「连续存活 `stableMs`」才算恢复成功、才清零计数。

**③ 放弃后要能重新开始**
用户手动重载成功后，计数必须清零、`givenUp` 复位，否则一次事故就让自动恢复永久失效。

### 3.4 验证方法论（踩过的坑，同样值得留）

- **不要用"CDP target 列表里页面是否消失"判定崩溃** —— 崩溃的 renderer
  仍可能留在 target 列表里，实测不可靠。要在主进程侧计数，再通过调试通道查询真实状态。
- **异步 IPC 必须等返回再断开连接** —— `debugCrash` 是异步 `invoke`，
  立刻关掉 WebSocket 会把在途请求掐断，主进程根本收不到，表现为"触发无效"。
- 调试通道要用 `app.isPackaged` 守卫，**不能成为打包版里可被页面脚本触发的自杀开关**。

## 四、封存的代码在哪、怎么取回

代码以 **git stash** 形式封存（不进主线，不影响任何已发布版本）。

```powershell
# 1) 查看封存列表（找到备注为「技术储备：渲染进程崩溃恢复闸门」那一条）
git stash list

# 2) 查看内容 —— ⚠️ 注意必须加 -u
#    新增的 4 个文件存在 stash 的「第 3 个 parent」（untracked 快照）里，
#    不加 -u 时 `git stash show` 只列已跟踪的 3 个文件，看起来像丢了（其实没丢）。
git stash show -u --name-only 'stash@{0}'
#    预期输出 7 项：
#      main.js
#      preload.js
#      js/components/App.vue
#      main/crashRecovery.js
#      test/crashRecovery.test.mjs
#      scripts/crash-throttle-test.mjs
#      docs/规格与计划/改动说明-崩溃恢复闸门.md

# 3) 检视差异（不动工作区）
git stash show -p 'stash@{0}'                 # 已跟踪的 3 个文件的改动
git show --name-only --format="" 'stash@{0}^3' # 确认 untracked 快照里的 4 个新文件

# 4) 应用到工作区（保留 stash 条目，可反复取）
git stash apply 'stash@{0}'

# 5) 应用并从 stash 列表移除
git stash pop 'stash@{0}'
```

> ⚠️ PowerShell 里 `stash@{0}` 的花括号会被解析，**务必加单引号**：
> `'stash@{0}'`。否则报 `Too many revisions specified`。

## 五、什么情况下该把它取出来用

| 触发条件 | 说明 |
|---|---|
| 用户报告"应用反复闪烁 / 打不开 / 要手动杀进程" | 这就是无限重载循环的典型症状 |
| `crash.log` 里出现**短时间内多条**记录（如 1 分钟内 ≥4 条） | 说明崩溃是确定性的，自动重载只会加重 |
| 新增了任何"崩溃后自动重载"类的兜底逻辑 | 都应套上这个闸门，避免重蹈覆辙 |
| 引入新的重内存特性（更大库 / 更多缓存） | 崩溃概率上升时，第二层兜底价值变大 |

## 六、附：完整判定链（复核用）

```
渲染层首屏跑完
   └→ app:ready 上报 → noteRendererAlive() → 起 stableMs 计时器
                        └→ 到期未被崩溃打断：stamps=[]、givenUp=false（恢复成功）

渲染进程崩溃
   └→ 'render-process-gone'
        ├→ 写 crash.log
        └→ decide()
             ├→ 剔除窗口外旧记录 → 压入本次 → inWindow = n
             ├→ n > retryMax → givenUp=true（首次弹窗）+ 返回 'giveup'
             │                 └→ 调用方 `if (verdict !== 'reload') return;` → 不 reload ✅
             └→ n ≤ retryMax → onReloadPlanned（日志）→ 返回 'reload'
                               └→ 1.5s 后 win.reload()
```
