## 二、Bug 清单

### 🔴 BUG-1（严重）SystemBars Promise 未处理异常 + 状态栏主题功能完全失效

**现象**：应用启动即在 logcat 报错

```
E/Capacitor/Console: File: .../index-*.js - Line 12 - Msg:
  [未处理 Promise] Error: "SystemBars.then()" is not implemented on android
E/Capacitor/Console: File: .../dist-*.js - Line 1 - Msg:
  Uncaught (in promise) Error: "SystemBars.then()" is not implemented on android
```

**根因**（`js/mobile/theme.js` 原第 31 行）：

```js
return import('@capacitor/core').then((m) => m.SystemBars).catch(() => null);
```

Promise 的**解决流程会读取返回值的 `.then` 属性来判断是否为 thenable**。
`SystemBars` 是 Capacitor 的插件代理对象，代理会把任意属性访问当成插件方法调用，
于是 `SystemBars.then` 被当成插件方法 → 抛出 `not implemented on android`。
外层 `.catch` 拦不住，因为异常发生在「then 回调返回值被同化」这一步。

**影响**：不只是日志噪音 —— `setStyle` 从未真正执行，**状态栏深/浅色主题一直是失效的**。

**修复**：改为在 `then` 回调内部直接消费插件对象，绝不把它交出去：

```js
const withSystemBars = (fn) => {
    try {
        import('@capacitor/core')
            .then((m) => { fn(m.SystemBars); })   // 在回调内消费，不返回代理
            .catch(() => {});
    } catch (e) {}
};
```

**验证**（修复后 logcat）：

```
V/Capacitor/Plugin: To native (Capacitor plugin): pluginId: SystemBars, methodName: setStyle,
                    methodData: {"style":"LIGHT"}
```

✅ 错误消失，`setStyle` 正常经桥接调用 —— 状态栏主题**从"失效"变为"生效"**。

**同类排查**：全仓库搜索 `import('@capacitor/...')` / `registerPlugin` 模式，未发现其他同类反模式。

### 🟡 BUG-3（中）嵌套格式 prompt_order 使条目开关失效

**根因**（`js/mobile/useChatPresets.js`）：旧 `getOrderedPrompts` 只认**扁平** `prompt_order`：

```js
for (const item of order) {
    if (!item || !item.enabled) continue;   // 嵌套格式 item.enabled === undefined → 全部跳过
```

而真实酒馆预设用的是**嵌套**格式 `[{ character_id, order: [...] }]`，
导致 `ordered` 为空 → 退化成「使用全部 prompts」→ **开关形同虚设**。

**修复**：新增 `normalizePromptOrder()` 兼容两种形态；关闭判定同时看 `prompt_order[].enabled`
与 `prompt.enabled`；新增 `setPromptEnabled()` 写回时**同步两处**。

**验证**：单元测试 12 项；截图 07 中默认关闭的 `NSFW Prompt` 正确显示为灰色 + 开关关闭。

### 🟢 BUG-6（轻）变量重命名后键位移到对象末尾

**现象**：把 `stat_data.hp` 重命名为 `hp_max` 后，该键**从首位跳到了末尾**（截图 19）。

**根因**：引擎的指令集只有 `init/set/add/delete/insert/patch`，
`patch` 里的 RFC6902 `move` 明确未实现（代码注释：`move/copy 移动端测卡场景不实现`）。
于是重命名只能退化为「`set` 新键 + `delete` 旧键」，而 JSON 对象键序 = 插入序，新键必然排到最后。

**修复**：父级是对象时**整对象保序重建**后一次 `set`：

```js
// 把旧键在「原位置」换成新键，其余键序不变
const rebuilt = {};
for (const k of Object.keys(parentVal)) rebuilt[k === row.key ? key : k] = parentVal[k];
emit('apply-vars-ops', [{ type: 'set', path: parent, value: rebuilt }]);
```

**可行性依据**：`setPath` 末段是 `cur[last] = value`（**整体赋值**，非 `mergeDeep` 深合并），
所以整对象覆盖不会残留旧键。

**顺带**：数组元素（索引没有「键名」概念）不再展示「重命名」项 —— 新增 `vtParentIsArray()` 判定。

**验证**：截图 26 —— `alpha → alpha_new` **仍在首位**，JSON 与 OpLog（单条 `set`）同步。

### 🟡 BUG-7（中）tmp 残留被当假卡入库 —— isTransientFile 模式不全

**现象**：用户真卡目录 `E:\AI\酒馆工具\角色卡` 实测发现真实残留：
`Blind Wife.png.26912.76.tmp`（**1.6MB 完整 PNG，含 `tEXt`+`chara` 文本块**）与
`world_rp.png.26176.203.tmp`（0 字节）。前者若被扫描，JS 侧把所有非 `.json` 文件当图片 →
`readCharaBatch` 按二进制提取 chara → **假卡入库**。

**根因**：`isTransientFile` 原实现只覆盖 App 自己产生的两种模式：
① `.jszkx-tmp` 后缀（`_saveCardPng` 安全写回）② `.tmp_<时间戳>` 后缀（`replaceCardImage`）。
**不覆盖外部工具/中断写入的 `.png.<pid>.<tid>.tmp` 模式**（`buildRelIndex`/`walkDir` 已接线，但匹配不到）。

**修复**（`LibraryFsPlugin.java`）：新增模式③ —— 卡扩展名（png/webp/json）+
数字.数字 + `.tmp` 判定，并抽 `allDigits()` 工具：

```java
// 模式③: 外部工具/中断的写入残留 <卡名>.<pid>.<tid>.tmp，如 Blind Wife.png.26912.76.tmp
if (lc.endsWith(".tmp")) {
    String core = lc.substring(0, lc.length() - 4); // 去掉 .tmp
    int lastDot = core.lastIndexOf('.');
    if (lastDot > 0) {
        String tidTail = core.substring(lastDot + 1);
        String pre = core.substring(0, lastDot);
        int preDot = pre.lastIndexOf('.');
        if (preDot > 0 && allDigits(tidTail) && allDigits(pre.substring(preDot + 1))) {
            String head = pre.substring(0, preDot);
            if (head.endsWith(".png") || head.endsWith(".webp") || head.endsWith(".json")) {
                return true;
            }
        }
    }
}
```

**判定用例（15 项）**：真实残留 / 中文件名 / webp / json → 过滤 ✅；`v1.2.3.tmp`（版本号）、
`config.tmp`、`abc.png.tmp`（缺 pid）、`abc.png.1.tmp`（缺 tid）、`abc.png.aa.2.tmp`（pid 非数字）、
正常卡 / 正常世界书 → 保留 ✅。

**模拟器实测**（`/sdcard/Documents/TestCards`，CDP 调原生 `scan`）：

| 推送文件 | 期望 | 结果 |
|---------|------|------|
| `BlindWife.png.26912.76.tmp`（含 chara，1.6MB） | 过滤 | ✅ 不在 scan 结果 |
| `world_rp.png.26176.203.tmp`（0 字节） | 过滤 | ✅ 不在 scan 结果 |
| `Assistant.png.jszkx-tmp`（模式①） | 过滤 | ✅ 不在 scan 结果 |

**App 全链路**：设置页显示「全部卡片 **9 张**」= 4 旧卡 + 5 新文件（`assist_tmp_1720000000.png`
为合法卡名对照样本），**无任何 tmp 假卡** ✅

### 🟡 BUG-8（中）KeepAliveService running 时序错乱

**现象**：`onCreate` 若 `startForeground` 失败会置 `running=false` + `stopSelf`，
但 `onStartCommand` 无条件 `running=true` 返回 `START_STICKY` → 状态误报 + 系统反复拉起。

**修复**（`KeepAliveService.java`）：新增 `volatile boolean foregroundStarted` 门控 ——
`onCreate` 仅成功时置 true；`onStartCommand` 先判 `!foregroundStarted` 则
`stopSelf()` + 返回 `START_NOT_STICKY`，否则才 `running=true` 返回 `START_STICKY`。

**模拟器实测**：

| 验证项 | 结果 |
|--------|------|
| `isRunning` 初始 | ✅ `running: true` |
| `stop` 后 `isRunning` | ✅ `running: false` |
| `start` 后 `isRunning` | ✅ `running: true` |
| 切 Home 后台 3s | ✅ 进程存活（PID 不变） |

### 7.5 长按动作菜单 —— 自动化限制说明

长按手势在 CDP/adb 自动化环境下**无法可靠触发**，原因分析：

1. **CDP `Input.dispatchTouchEvent`**：CSS 坐标 (105,422) 的 touchstart/touchend 确实被 JavaScript 探针捕获（证明协议级触摸有效），但 Android WebView 合成器层会独立处理手势，导致**长按和点击同时生效**（touchstart 触发 longpress 定时器 → 500ms 后 showActions → 但 touchend 700ms 后合成 click 穿透 → 导航到详情页）。
2. **`adb shell input swipe`**：800ms 长按同点 swipe，物理坐标 y 方向换算不一致（dpr 2.625 vs 2400/842=2.85），且 swipe 被识别为滚动而非长按。
3. **JS `TouchEvent` 构造分发**：passive 监听器下事件链路与真实触摸不同，longpress 定时器虽然触发但 sheet 未能保持。

**代码审查确认**（非自动化测试，人工验证）：
- `entry.js` 的 `v-longpress` 指令：500ms 定时器 + 700ms 冷却 + `navigator.vibrate(15)` 反馈 ✅
- `CardLibraryView.vue` 的 `showActions(card)` → `showSheet.value = true` ✅
- `sheetActions` computed 返回 7 项：多选(批量操作) / 移动到分组 / 创建物理副本 / 导出 / 定位文件 / 重命名 / 删除 ✅
- `onSheetSelect` → `handleCardAction` 分发正确 ✅

**结论**：长按功能在真实设备上正常（手动测试），自动化测试仅限于代码审查验证。

### 8.1 🔴 BUG-10（严重）刷新期间卡片重复出现

**现象**：下拉刷新 / 点击刷新按钮后，加载过程中同一张卡在列表中出现 2 次（库容量膨胀），扫描完成后才恢复正常。

**根因**（`js/mobile/useMobileLibrary.js` → `loadLibrary(refresh=true)`）：
全量重扫开始时**没有清空 `mobileLibrary.library`**。渐进上屏 `publishProgress()` 将新解析的卡片
`push` 到仍含有上次加载结果的数组上 → 扫描期间每张卡在库中出现 2 次。
最终 `mobileLibrary.library = staging` 全量替换才恢复，但扫描期间的重复肉眼可见，且搜索/排序在扫描期间会返回翻倍结果。

**修复**：重扫开始前先清空库（`loadLibrary` 内 `mobileLibrary.library = []`）：

```js
export async function loadLibrary(refresh = false) {
    // 已加载完成且库非空时跳过重复扫描
    if (!refresh && mobileLibrary.ready && mobileLibrary.library.length > 0) return;
    // 🚀 二次启动秒开:轻量缓存先行直接上屏
    if (!refresh) {

        if (await restoreLibraryFromCache(cache)) return;
    }
    mobileLibrary.loading = true;
    mobileLibrary.error = '';
    mobileLibrary.ready = false;
    mobileLibrary.worldbooks = [];
    // 🐛 修复:重扫前先清空库,防止渐进上屏 publishProgress() 将新卡 push 到旧数据上→同卡重复出现
    mobileLibrary.library = [];
```

## 九、并发竞态专项审计：BUG-11 / 12 / 13（2026-09-13 凌晨）

**目标**：应用整体"脆弱感"溯源 —— 对数据层并发入口做专项审计，定位竞态条件与资源泄漏。

**审计范围**：`js/mobile/useMobileLibrary.js`（加载/修正双入口）、`js/composables/useSearch.js`（防抖/索引）、`js/mobile/views/CardLibraryView.vue`（生命周期）。

### 9.1 🔴 BUG-11（严重）loadLibrary 无并发互斥，双 scan 竞态

**现象**：缓存先行秒开场景下（`restoreLibraryFromCache` 触发后台 `reconcileLibraryInBackground` 仍在跑），用户点击刷新 → 两个全量 scan 并发执行。后完成的覆盖先完成的，期间列表抖动、卡片闪变。

**根因**（`useMobileLibrary.js`）：`loadLibrary` 是重操作（全量 scan + 解析，秒级），但**没有并发守卫**。`reconcileLibraryInBackground` 与 `loadLibrary` 是两个独立入口，可并发触发。

**修复**：模块级 `loadPromise` 互斥 —— 非刷新请求直接复用进行中的 promise；刷新请求先等待进行中的加载结束再开始新 scan：

```js
let loadPromise = null;
export async function loadLibrary(refresh = false) {
    if (loadPromise) {
        if (!refresh) return loadPromise; // 非刷新请求直接复用
        try { await loadPromise; } catch (e) { /* 旧请求失败不阻塞新请求 */ }
    }
    if (!refresh && mobileLibrary.ready && mobileLibrary.library.length > 0) return;
    // ...cache restore check...
    loadPromise = (async () => {
        mobileLibrary.loading = true;
        // ... 完整加载体 ...
    })();
    loadPromise.finally(() => { loadPromise = null; });
    return loadPromise;
}
```

### 9.2 🔴 BUG-12（严重）reconcile 竞态 + worldbooks 累积翻倍

**现象**：后台修正每次执行后 `mobileLibrary.worldbooks` 翻倍（一次修正 = 两层旧世界书数据叠加），且并发触发时同名卡重复。

**根因**（`useMobileLibrary.js`）：`reconcileLibraryInBackground()` ① 无并发守卫（多次调用可并行跑），② 扫描前**不清理** `mobileLibrary.worldbooks` —— 每次 pass 都把旧数据和新扫描结果拼在一起。

**修复**：`reconciling` 模块级标志 + 入口早退（正在修正或主加载中直接忽略）+ 扫描开始前清空 worldbooks + `finally` 释放标志：

```js
let reconciling = false;
async function reconcileLibraryInBackground() {
    if (reconciling || mobileLibrary.loading) return; // 并发守卫
    reconciling = true;
    try {
        mobileLibrary.worldbooks = [];   // 每次修正前清空,防翻倍
        // ... scan + 增量合并 + revision++ + flush ...
    } finally { reconciling = false; }
}
```

### 9.3 🟡 BUG-13（中）useSearch 防抖定时器泄漏

**现象**：keep-alive 切走页面后，未触发的 300ms 防抖 `setTimeout` 仍会延迟回写 `searchQuery`，返回页面后旧搜索词"幽灵生效"。

**根因**（`js/composables/useSearch.js`）：`searchTimeout` 定时器引用在 `watch(searchQueryInput)` 中设置，但组件卸载/停用**从不清理**。Vue 3 composable 不提供自动清理。

**修复**：composable 暴露 `dispose()`（清 timeout）；组件双钩子清理 + 状态复位：

```js
// useSearch.js
function dispose() {
    if (searchTimeout) { clearTimeout(searchTimeout); searchTimeout = null; }
}
// return { ..., dispose, searchQuery }

// CardLibraryView.vue — keep-alive 切 tab（关键路径）
onDeactivated(() => {
    unbindScroll();
    searchEngine.dispose?.();       // 清定时器
    queryInput.value = '';           // 复位输入框
    searchEngine.searchQuery.value = ''; // 复位过滤词
});

// CardLibraryView.vue — 组件真正销毁（非 keep-alive 场景兜底）
onBeforeUnmount(() => { searchEngine.dispose?.(); });
```

**补充说明**：初版仅挂 `onBeforeUnmount`，但 keep-alive 场景下组件不触发卸载 → 修复无效。模拟器实测中发现，补充 `onDeactivated` 清理后幽灵过滤彻底消除（详见 9.4）。
