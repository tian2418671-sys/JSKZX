## 二、修复 1 · `refreshLibrary` 增量刷新缺 path 去重（高危）

**文件**：`js/composables/useDiskScan.js`（`refreshLibrary`）

**旧写法**的两条路径都没有去重：

```js
const next = [];
for (const f of result.files) {
    const old = oldMap.get(f.path);
    if (old && Number(old._mtime) === Number(f.mtime)) {
        next.push(old);        // ① 既没查重，也没登记任何 seen
    } else {
        toParse.push(f);
    }
}
library.value = next;
...
await Promise.all(batch.map(file => parseAndAddCard(file)));   // ② 没传 seenPaths
```

**触发条件**（任一即可让同一 path 进两条）：
- 扫描结果里同一 path 出现两次 —— 卡库目录内有 **junction / 符号链接**指向同一文件
  （`walkLibraryDir` 的 `realpath` 守卫只防目录环路，不阻止同一文件被两条不同路径列出）
- 目录里同时存在 `A.png` 与 `A.PNG`（Windows 不区分大小写，但 `realpath` 字符串不同 → 守卫拦不住）
- **并发刷新**：连点刷新、或刷新与启动期 `processElectronFiles` 重叠

**修复**：
1. `next` 构造时按 `path` 强去重（`seenPath` Set，首个胜出、保留原对象）
2. `parseAndAddCard` 调用补传 `seenPaths`，并把 `next` 里已有的 path 预填进去（`parseSeen`），
   避免「复用的旧对象」与「新解析对象」撞同一 path

## 三、修复 2 · `parseAndAddCard` 判重条件过窄（根因）

**文件**：`js/composables/useCardCrud.js`

**旧写法**：

```js
const inStaging = (opts.seenPaths instanceof Set)
    ? opts.seenPaths.has(file.path)
    : dupIn(opts.target || library.value);
if (inStaging || (opts.target && dupIn(library.value))) { ...跳过... }
```

问题在 **`opts.target &&` 这个短路**：增量刷新既没传 `target` 也没传 `seenPaths` 时，
- `inStaging` = `dupIn(undefined || library.value)` → 查的其实是 live library，但**已经被赋成 next 的副本**；
- 第二项 `opts.target && ...` → `target` 为空 → **直接 false**。

于是「live library 是否已有同 path」这一条**实际上永远不会被检查**，同一 path 进两次就写两条。

**修复**（两个维度无条件都查）：

```js
const seenHit = (opts.seenPaths instanceof Set) && opts.seenPaths.has(file.path);
if (seenHit || dupIn(opts.target) || dupIn(library.value)) { file._skippedExisting = true; return false; }
```

**外加最终防线**（push 处）：`liveList.findIndex(c => c.path === cardInfo.path)`，
命中即**替换**（顶层 mtime 变化本就走这条），绝不再新增一条 ——
这样即使将来又有新的调用方漏传 `seenPaths`，也不会再产生重复卡。

## 四、为什么其余集合库不用改（设计层面的原因）

本项目有一层很好的隐性保护：**「新建文件」类 IPC 都拒绝覆盖已存在文件**。

```js
// main.js —— wb:create
if (fs.existsSync(filePath)) return { success: false, error: '目标文件已存在，请换一个文件名。' };
// main.js —— preset:create
if (fs.existsSync(filePath)) return { success: false, error: '目标文件已存在，请换一个文件名。' };
```

而渲染层的 push 都写在 `if (res.success)` 之内 —— **磁盘拒绝 → 不 push → 内存不会重复**。
这是一条值得保留的约定：**新增任何「入库」类 IPC 时，务必保持「已存在即失败」语义**，
它同时也是防误覆盖的一道保险。

> ⚠️ 唯一例外是「先删文件、再调 create」的场景（内存里有旧条目、磁盘文件已被外部删除）——
> 此时 create 会成功，内存里就出现同一 path 两条。概率低，但确实存在。
> 如果今后要彻底根治，可给这几个 push 点统一套一个 `pushUniqueBy(list, item, keyFn)` 辅助函数。
