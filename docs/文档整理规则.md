# 🧹 文档整理规则（全仓库）

> **适用范围**：仓库根 6 份文档（`START-HERE.md` / `AGENTS.md` / `AI交接指导.md` / `README.md` / `RELEASE_NOTES.md` / `CHANGELOG.md`）

## 〇、一句话

**每份内容只有一个家；每个"活数字"只有一个权威来源；改了源头就要同步列表里所有引用点。**

整理文档不是"再写一遍"，而是**对账**：拿事实去比对文档里的声明，把声明改成事实。

### 一之二 · docs 各分类的分组规则（2026-09-25 起）

`docs/` 下**各分类不平铺**：按**项目 / 主题**建子文件夹，**同一项目/主题的全部文档必须放进同一组**（组名 = 项目/主题名，中文、无编号前缀）；分类根只留 `README.md` 索引。

各分类现有组：

| 分类 | 组 |
|---|---|
| `规格与计划/`（6 组） | `查重引擎/` · `世界书大库/` · `AI打标/` · `测卡工作区/` · `功能规格/` · `计划与记录/` |
| `技术支持/`（5 组） | `插件与扩展/` · `世界书与卡片/` · `AI打标/` · `性能与稳定性/` · `调试技术/` |
| `发布/`（2 组） | `规范与流程/`（内部） · `用户文档/`（可对外） |

> `bugs/` 按**领域代号**分文件（README 总表 + 6 份领域详述）——**等效分组**，不建子文件夹；`reference/`、`screenshots/` 是素材目录，保持扁平。

**链接层级**（改完必须跑 `node scripts/check-doc-links.mjs`，要求 **ALL RESOLVE**）：

| 场景 | 写法 |
|---|---|
| 组内互引 | 裸文件名 `xxx.md` |
| 分类根 README 引组内文档 | `<组>/xxx.md` |
| 跨组互引（子文件夹内） | `../<组>/xxx.md` |
| 引用 `docs/` 其他分类（`bugs/` `技术支持/` `发布/` …） | `../../bugs/xxx.md`（**多一级**） |
| 引用仓库根文件 / 代码（`CHANGELOG.md`、`js/` …） | `../../../CHANGELOG.md`（**多两级**） |

**拆分与新增**：同主题文档 ≥2 篇即建组；单篇先放最接近的组，成体系后再拆组。
各分类根 `README.md` 是**唯一索引**（不入子文件夹），登记时写清「组 / 文件名」两段路径。

## 二、五条硬规则

**R1 · 单一事实源（SSOT）**
同一段事实只允许在一处"展开写"，其它地方**只引用不复述**（写"详见 `docs/bugs/README.md` §二"，而不是把那张表再抄一遍）。

**R2 · 活数字必须同步**
下表列出的数字是"活数字"：源头一变，**所有引用点当次一起改**，不允许留到下次。

**R3 · 版本号联动**
改版本号不是只改 `package.json`，必须同步 §四 清单里的每一个位置。

**R4 · 新增文档必须登记**
新建任何文档，当次就要做齐四件事：

1. 在 `docs/README.md` 的对应分类表加一行；
2. 选择**正确的项目子文件夹**（`docs/规格与计划/`、`docs/技术支持/`、`docs/发布/`：按 §一之二 归组；跨组 / 出组引用按该节链接层级表写相对路径）；
3. 在**所属分类自己的 `README.md`**（`docs/bugs/`、`docs/技术支持/`、`docs/规格与计划/` 各有一份）加一行，含「约 N 行」与状态；
4. 在 `docs/README.md` 顶部把「上次整理」日期改成当天。

登记时链接必须是**相对路径**（`node scripts/check-doc-links.mjs` 会验）。

**R5 · 历史文档不追改**
`docs/规格与计划/计划与记录/回归测试报告-*.md`、`CHANGELOG.md` 的历史段落、`RELEASE_NOTES.md` 的历史版本段，记录的是**当时的实测口径**（例如当时"402 用例全绿"）——**不要把这类数字改成今天的值**，那会抹掉证据。
判据：**描述"当时发生了什么"的 → 保留原值；描述"现在是什么"的 → 必须更新。**

## 四、版本号联动清单（发版必改）

改 `package.json` 版本号时，**逐个文件核对**：

> 📌 **真实教训（2026-09-21）**：把 2.2.14 回退到 2.2.13 时改了 8 个文件，**漏掉 `AI交接指导.md`**（它一直还写着 v2.2.12，直到下一次整理才被发现）。版本号联动**不要靠记忆**，照下表逐行核对。

| # | 文件 | 具体位置 |
|---|---|---|
| 1 | `package.json` | `version` |
| 2 | `package-lock.json` | 顶层 `version` + `packages[""].version`（**两处**） |
| 3 | `RELEASE_NOTES.md` | 顶部版本段标题 `## SillyTavern 角色卡管理器 vX.Y.Z` + 该段主题行 |
| 4 | `README.md` | 「📥 下载」里的两个产物名、`### 📌 近期版本要点` 首条、构建产物路径示例 |
| 5 | `START-HERE.md` | 「⚡ 30 秒速览」的「当前版本」行 + 铁律里「已发布至 vX.Y.Z」 |
| 6 | `.github/copilot-instructions.md` | 顶部「当前版本」行 |
| 7 | `AI交接指导.md` | 顶部「最后更新 + 当前版本」行 |
| 8 | `CHANGELOG.md` | 标题「v1.0 → vX.Y.Z 更新汇总」+ 顶部摘要段 + 本次版本章节标题 |
| 9 | `docs/bugs/README.md` | 新增缺陷的「版本」列的归属版本 |
| 10 | 各文档顶部「最后更新 / 最后整理」日期 | 当次整理涉及到的每一份文档 |

**核对命令**（应返回空）：

```powershell
git grep -n "<旧版本号>" -- "*.md" "*.json" ":!package-lock.json"
```

## 五、命名与格式

| 项 | 规则 |
|---|---|
| 行尾 | 全仓库 **CRLF**（`core.autocrlf=true`，无 `.gitattributes`）——脚本写文件时用 `\r\n` |
| 编码 | UTF-8；**禁止**任何 `U+FFFD` 替换符（emoji 被工具链损坏时会出现，校验脚本一查就出） |
| 文件名 | 分类前缀 + 中文描述，全角/半角统一：`BUG-<领域>.md`、`代码片段-<主题>.md`、`方案-<主题>.md`、`<功能>-实现规格.md`、`技术数据-<主题>.md` |
| 子文件夹 | `docs/` 的三个文档分类（`规格与计划/` `技术支持/` `发布/`）按 §一之二 分组；组名 = 项目/主题名（中文、无编号），与各分类 `README.md` 的分组表一致 |
| 标题 | 每份文档 **一个 `#` 一级标题**；分类内的分节用 `##`；文档内编号用中文序号（`一、二、三`）或 `§` |
| 顶部元信息 | 每份文档顶部用 `> 引用块` 写清：**本文件是什么**、**与相邻文档的分工**、**最后更新日期** |
| BUG 编号 | `领域代号-序号`，序号按发现时间递增，**一经分配不再变更** |

**写完必须校验**（两条都要过）：

```powershell
node -e "const fs=require('fs');const t=fs.readFileSync(process.argv[1],'utf8');console.log('FFFD=',(t.match(/\uFFFD/g)||[]).length,'CRLF=',(t.match(/\r\n/g)||[]).length,'bareLF=',(t.match(/(?<!\r)\n/g)||[]).length)" <文件路径>
node scripts/check-doc-links.mjs
```

## 六、对外 / 内部边界

这是**最容易出事**的一条，细则见 [`发布/规范与流程/内部信息.md`](发布/规范与流程/内部信息.md) 与 [`发布/规范与流程/用户可看信息.md`](发布/规范与流程/用户可看信息.md)。速记：

- **对外**：`RELEASE_NOTES.md`、GitHub Release 正文、`README.md`、`docs/发布/用户文档/自动更新说明与常见问题.md`
- **内部**：`CHANGELOG.md`、`docs/**` 其余全部
- 对外正文**禁写**：文件名 / 函数名 / 脚本名 / 内存 MB 数 / 阶段耗时 / 崩溃原文 / 内部缺陷编号（`AR-38` 这种）/ 本机绝对路径
- 对外唯一数字例外：**用户拿来做判断的数字**（安装包体积、磁盘占用、库规模）
- Release 正文**必须**由 `node scripts/extract-release-notes.mjs vX.Y.Z` 从 `RELEASE_NOTES.md` 抽取，**不许手抄**

## 七、整理 SOP（按顺序做，别跳步）

**S1 取证** —— 先跑机器校验，拿到事实，别凭记忆改文档：

```powershell
node scripts/release-check.mjs          # 版本号 / 文档三件套 / 单测 / 构建
node scripts/check-doc-links.mjs        # 全部相对链接
python scripts/check.py                 # Python 侧一键检查
npm test                                # 取当前用例数
```

**S2 对账** —— 按 §三 活数字表逐项比"文档声明 vs 实际"，按 §四 清单逐项比版本号，按目录实际文件比索引登记。

**S3 修正** —— 只改"描述现在是什么"的地方（R2）；"描述当时发生了什么"的地方不动（R5）。

**S4 复验** —— 再跑一遍 S1 的命令；`git grep` 确认旧数字 / 旧版本号无残留。

**S5 留痕** —— 把本次涉及文档顶部的「最后更新 / 最后整理」日期改成当天；若结构性调整（增删分类），在 `docs/README.md` 顶部写明调整内容。

## 八、禁止事项

1. ❌ 新建"归档 / 旧版 / 备份 / 历史"目录保存被替代的文档（内容并入后**直接删除**）。
2. ❌ 同一段内容在仓库里存在两个"展开版"（只能一处展开，其余引用）。
3. ❌ 把历史报告 / 历史版本段里的实测数字更新成今天的值（破坏证据）。
4. ❌ 新增文档只创建文件、不登记索引（下次整理必然"找不到"）。
5. ❌ 只改 `package.json` 版本号就发版（§四 有 10 个位置）。
6. ❌ 用非相对路径写文档内链接（`check-doc-links.mjs` 只能验相对链接）。
7. ❌ 把内部细节写进对外文档（§六）。
8. ❌ 凭记忆填数字（一律现取，见 §三）。
