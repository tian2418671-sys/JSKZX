## 一、逐项取证要点（在移动版仓库执行）

### M1 · AR-39 差异弹窗崩溃
- **桌面版根因**：`diffText: null` + `path` 裸 `split`（无防御）。
- **取证**：移动版是否有「差异比对」弹窗？若有，检查 `path.split(/[\\/]/)` 是否对 `null`/无分隔符路径做过防御。
- **同步方式**：若同源 → 移植 `alignEntryLists` 的防御（见 `js/utils/entryAlign.js`）。

### M2 · DF-17 词条级对齐
- **桌面版修复**：`alignEntryLists`（带侧标识 + 一对一配对）。
- **取证**：移动版查重是否做「词条级」比对，还是仅文件级？
- **同步方式**：若做词条级 → 需同一套对齐算法，否则会出现「同名但错配」的假差异。

### M3 · DF-18 扫描闸门 / 静默丢弃
- **桌面版修复**：分级（≤5MB / 5~50MB 低并发 / >50MB 只回元数据）+ `skipped` 可见化 + 缓存不自愈固化。
- **取证**：移动版的扫描是否有一刀切体积上限？超限是否**静默**？
- **同步方式**：若静默丢弃 → 必须补可见化（静默丢弃 = 用户以为软件坏了，对照 AR-38）。

### M4 · DF-19 字典形态被判成角色卡
- **桌面版根因**：用 `Array.isArray(entries)` 判世界书，而 `entries` 可能是对象字典（V2 老格式）。
- **取证**：移动版判定世界书用的是 `Array.isArray` 还是兼容字典？
- **同步方式**：改为「`entries` 存在即为世界书」+ 字典归一化。

### M5 · PK-18 检索准确性
- **桌面版修复**：索引就绪后补短语复核（此前只做 token 交集，会漏「短语必须连续」的语义）。
- **取证**：移动版是否用同一 `searchIndex`？检索是否做短语复核？
- **同步方式**：若共用同一算法文件 → 直接同步；若各自实现 → 按同一语义补齐。

### M6 · PK-19 拉丁前缀全表回退
- **桌面版修复**：bigram 候选剪枝（实测快 20~70 倍，结果与全表扫逐条一致）。
- **取证**：移动版是否有倒排索引？是否有「精确命中失败 → 全表扫」的退化路径？
- **同步方式**：若同源 → 移植 `_buildBigram` / `_getMatches`；注意 `bigramDirty` 的降级保障（脏时回退全表扫，只慢不错）。

### M7 · AR-40 子组件绑定缺失
- **桌面版根因**：模板调用 `wbEntryCount(wb)` 但没进 `setup()` 的 return → 渲染期 TypeError → **整个组件被卸载**。
- **取证**：移动版是否有同款「`provide/inject` 四步链」？其子组件模板调用的函数是否都在 `setup` 暴露？
- **同步方式**：若同源 → 移植静态检查思路（见 `test/sidebarBindings.test.mjs`）。
- ⚠️ **移植时注意**：该检查器本身有两个坑（必须 `lastIndexOf('</template>')`、必须剥注释再提取键名），
  直接抄会得到「假绿」的检查器。详见 [`../bugs/BUG-架构与渲染.md`](../../bugs/BUG-架构与渲染.md) AR-40。

## 二、同步完成后的落档规则

移动版结论**不回写本仓库的移动版专属文件**（那会让本仓库出现无法验证的二手信息）。
按领域拆开归位：

| 结论类型 | 落到本仓库哪里 |
|---|---|
| 移动版**确认有**同一缺陷 | 对应领域文档（`bugs/BUG-*.md`）加一行「移动版同源，已在移动版仓库修复（日期）」 |
| 移动版**确认没有**该路径 | 本文对应行标注「✅ 不适用（已取证：<理由>）」，**不要**删行（留证） |
| 移动版新发现的缺陷 | 若与桌面版无关 → **只记在移动版仓库**；若同源 → 本仓库按领域登记 |
| 移动版实测数字 | 只进移动版仓库文档；本仓库不收录（口径不可比：Android vs Electron） |
