## 一、用户建议原文与解读

> **用户建议**：让我们自定义提示词和破限，分成 system、assistant、user 三类。这样就可以在提示词里面设置思维链来约束 AI。
> 然后 AI 输出后，软件自动截取固定的标签例如 `<标签>[XX, XX]</标签>` 这样作为标签，打标签也不会乱。
>
> **用户想法**：增加一个思维链模式与原来的隔离，或者融合进入。

| 诉求 | 真实问题 | 落点 |
| --- | --- | --- |
| 分 `system` / `assistant` / `user` | ① 想控制**消息角色**；② 想用 `assistant` 段写**思维链示例**或**预填充** | R2 |
| `<标签>` 截取 | 打标结果**乱**（模型加解释 / markdown / 思维链污染） | R1 |
| 思维链模式隔离 | 想区分「严格模式」与「思维链模式」 | ⚠️ 见 §五：**用 R2 表达即可，不需要模式开关** |

## 三、关键技术洞察（决定方案设计）

### 洞察 1 · 现有解析在**思考型模型**上不可靠 ★

`rawReply.match(/\[[\s\S]*\]/)` 是**贪婪匹配**：取「第一个 `[`」到「最后一个 `]`」。

| 场景 | 后果 |
| --- | --- |
| 模型输出 `好的，分析如下：["奇幻","冒险"]` | 侥幸能解析（只有一个方括号组） |
| 模型输出 `标签含义说明 [1]：[奇幻]；[2]：[冒险]` | ❌ **取到错误区间** |
| **思考型模型**先输出思维链（含方括号）再给 JSON | ❌ **思维链污染**，取到思维链里的方括号 |
| JSON 被 max_tokens 截断 | ❌ 无 `]` → 匹配失败 → 走暴力拆分（可能拆出垃圾） |

> ⚠️ **这是本方案的核心收益点**：用户常用的 **GLM-5.3 / DeepSeek-V4 / 商汤 6.8** 都是**思考型**模型，
> 思维链里出现方括号（如 `["奇幻", "冒险"]` 的示例、编号列表 `[1]`）会让现有正则**取错区间**。

### 洞察 2 · `assistant` 预填充是最强的格式约束

在 messages 末尾放一条 `assistant` 消息，模型会**接着它往下写**：

```js
messages: [
  { role: 'system',    content: '...' },
  { role: 'user',      content: '...' },
  { role: 'assistant', content: '<标签>[' }     // ← 预填充
]
// 模型输出将从 `"奇幻", "冒险"]</标签>` 开始，天然不含解释
```

**兼容性限制（必须处理）**：

| 后端 | 预填充支持 | 说明 |
| --- | --- | --- |
| Anthropic 原生 | ✅ | 叫 "prefill"；⚠️ **结尾不能是空白字符** |
| OpenAI 官方 | ✅ | — |
| **部分中转 / 聚合站** | ⚠️ **可能忽略或报错** | 用户环境有多个中转站（B.AI / 逍遥 / InferAI 等） |
| **思考型模型**（reasoning） | ❌ **常不支持** | 需先输出 `reasoning_content`，预填充会冲突 |

⇒ **必须有降级**：预填充失败/被忽略时，自动退回「只用 system + user」并仍能正确解析（靠 R1 的标签截取兜底）。

### 洞察 3 · 「思维链」现在**已经能做**，只是没有显式控制

用户现在就可以在 `systemPromptPresets` 里写"请先分析性格，再判断世界观，最后给标签"——
但推理过程与输出格式**混在同一条 system**，无法分开控制，也无法用 `assistant` 预填充强制格式。

⇒ **R2 的"分角色"正是为此**：把推理引导放 `system`、把输出格式示例放 `assistant`，职责分离。

## 四、候选方案对比

### R1 · 结构化输出契约（`<标签>` 包裹）★ 推荐先做

```
改动：
1. promptText 输出规则改为：必须用 <标签>[标签1, 标签2]</标签> 包裹
2. 解析改为**三层降级**：
   ① /<标签>\s*([\s\S]*?)\s*<\/标签>/   （非贪婪，精确边界；同时兼容 <tags>）
   ② 回退现有 /\[[\s\S]*\]/             （旧格式 / 模型不遵守时）
   ③ 回退暴力拆分                        （最后兜底）
```

| 项 | 评估 |
| --- | --- |
| 改动量 | **小**（约 30 行，集中在 `useAITools.js` 一处） |
| 风险 | **低**（三层降级；旧格式仍可解析，不影响既有行为） |
| 收益 | **高**（彻底隔离思维链污染；边界明确，非贪婪） |
| 可验证性 | **强**（跑一次打标即可对照） |
| 缺点 | 未解决"用户想控制消息角色" |

**标签名建议**：默认用 **`<tags>`**（英文，模型训练数据里常见 XML 风格，遵守率高），
**解析时同时兼容 `<标签>`**（照顾中文用户手写）。**不做成可配置**（增加认知负担，收益低）。

### R2 · 提示词预设分角色

```
数据模型（向后兼容）：
systemPromptPresets: [{
  id, name, expanded,
  system:    '你是一个专业的角色卡分析助手...',   // 主提示词
  assistant: '',      // 🆕 可选：示例推理 / 输出格式示范
  user:      '',      // 🆕 可选：留空 = 用程序生成的默认（候选池 + 卡片数据）
  prefill:   '',      // 🆕 可选：assistant 预填充（如 '<tags>['）
  // 旧字段 content 保留：读取时自动迁移到 system（老配置零破坏）
}]

消息组装：
messages = [
  { role: 'system', content: preset.system + 破限 },
  { role: 'user',   content: preset.user || 程序默认 promptText },
  ...(preset.assistant ? [{ role: 'assistant', content: preset.assistant }] : []),
  ...(preset.prefill   ? [{ role: 'assistant', content: preset.prefill   }] : []),
]
```

| 项 | 评估 |
| --- | --- |
| 改动量 | **中**（数据模型 + 组装 + UI + 旧配置迁移） |
| 风险 | **中**（预填充在中转站可能失效 → 需降级；旧配置需迁移） |
| 收益 | **高**（用户可控制消息角色；预填充是格式约束最强手段） |
| 缺点 | 需处理兼容性与迁移 |

**UI 呈现**（接在布局重构的「③ 提示词与破限」页签内）：

```text
┌ 提示词预设 ──────────────────────┐
│ ● 默认分析助手（当前生效）          │
│ ○ 严格模式                         │
├────────────────────────────────────┤
│ [System] [Assistant] [User]  ← 三个小页签 │
│ ┌────────────────────────────────┐ │
│ │ 你是一个专业的角色卡分析助手... │ │
│ └────────────────────────────────┘ │
│ 💡 Assistant 段可写示例推理或预填充 │
└────────────────────────────────────┘
```

### R3 · 「思维链模式」独立开关 ❌ 不推荐

> ✅ **2026-09-24 更新**：用户最终**明确要求**加思维链（「写思维链破限次提示词为默认版，提供自定义模式」）。
> 落地方式**不是**新开一个全局模式开关，而是**做成预设内的第 5 小页签**（三档：默认版 / 自定义 / 关闭）——
> 即原方案说的「用 R2 表达即可」，只是**多给了一个内置默认版**（省得用户自己写）。见 §九 9.6。

| 项 | 评估 |
| --- | --- |
| 改动量 | **大**（两套流程 + UI 切换 + 各自测试） |
| 风险 | **中高** |
| 收益 | **低** —— **功能与 R2 重复** |
| 缺点 | **两套代码要各自维护**；用户还要理解"模式"概念 |

> **为什么多余**：R2 里「`assistant` 段留空」= 严格模式；「`assistant` 段填示例推理」= 思维链模式。
> **同一个字段的填写与否就能表达两种模式，不需要额外开关**——而用户的痛点恰恰是「UI 乱」，加开关只会更乱。

## 九、✅ 落地记录（2026-09-24）

### 9.1 用户追加的启用条件（关键约束）

> **用户原话**：「LLM 层在给他加一层组成新的 llm 打标结构，在窗口合适位置添加插入点。
> 挡规则，向量不启动时只启动 llm 的打标机制，则进行三层的思维链就是方案中说的，
> **当只有 LLM 层单独启动时才启动 R1 的结构截取功能**。」

⇒ 落地时新增**唯一启用条件**：`isLlmOnlyPlan(plan)` = **①规则关 且 ②向量关 且 ③LLM 开**。
其他组合（如 规则+LLM 同开）**保持原有打标链路不变** —— 零回归风险。

> **为什么这样切**：分角色结构是为「纯 LLM 打标」设计的；规则/向量层命中时会直接写入标签，
> 混用两套解析语义会让「标签来源」不可预测 ⇒ **按执行计划分流**。

### 9.3 解析三层降级（实测语义）

| 层 | 手段 | 实测要点 |
| --- | --- | --- |
| ① | `<tags>…</tags>` / `<标签>…</标签>` **精确边界 + 取最后一个有效包裹** | ⚠️ **必须从后往前找**：思考型模型常在思维链里先给「示例：`<tags>["示例"]</tags>`」，取第一个会**把示例当结果** |
| ② | JSON 数组正则（**从后往前找第一个能解析成数组的方括号组** → 再贪婪兜底处理嵌套） | 思维链里的 `[1]` / `["示例"]` 会被自动跳过（非数组 / 非法 JSON）；嵌套数组用贪婪兜底 + `flat(Infinity)` 展平 |
| ③ | 按 `[,，、\n]` 暴力拆分 | 最后兜底，**无法区分标签与解释文字**（命中时会打 `⚠️` 日志，让用户知道模型没遵守格式） |

### 9.6 🧠 思维链（CoT）+ 破限 + 🔌 连通性测试（2026-09-24 第二批追加）

> **用户原话**：「测试是否联通并写思维链破限次提示词为默认版，提供自定义模式，在 R1 中加入这些功能」

#### 9.6.1 消息结构（最终版）

```text
[ system ]    主提示词 + 破限词（破限必须在末尾 —— 注意力权重最高）
[ user   ]    预设 user 段 或 程序默认（卡片内容 + 输出要求）
[ assistant ] 预设 assistant 段（few-shot 示例，可选）
[ assistant ] 🧠 思维链提示词（默认版 / 自定义；cotMode='off' 时无）
[ assistant ] ⚡ 预填充（默认 `<tags>[`，放最后 —— 紧邻输出位置）
```

⚠️ **所有 `assistant` 消息必须排在 `user` 之后** —— 这是 **Anthropic 协议的硬要求**：
`main.js` 的 `chat:send` 挑出 `system` 后原样透传 messages，而 Anthropic 要求
**第一条非 system 消息必须是 `user`**。把思维链放在 `user` 之前会直接报错。

#### 9.6.2 思维链三档模式（`preset.cotMode`）

| 模式 | 值 | 行为 |
| --- | --- | --- |
| 🟢 **默认版** | `'default'`（**默认值**） | 注入内置 `DEFAULT_COT_PROMPT`（只读展示，开箱即用） |
| ✏️ 自定义 | `'custom'` | 用 `preset.cot`；**留空则回退默认版**（不静默失效） |
| ⚪ 关闭 | `'off'` | 不注入 |

**默认版内容**（`DEFAULT_COT_PROMPT`）同时做两件事（为什么融合在一起）：

1. **思维链引导**：让模型先在心里过一遍「题材 / 身份 / 性格 / 关键词 / 归纳」再产出标签；
2. **破限**：角色卡常含 NSFW / 暗黑 / 病娇设定 ⇒ 模型容易直接拒答。
   把「这是虚构文本特征归纳、不受内容审查影响」与推理引导写在**同一段**，比分开写更稳
   （模型先接受「这是分析任务」的前提，再顺着推理往下走）。

🔑 两个关键设计：**明确要求「推理过程不要输出」**（否则白烧 token）；**把最终格式写死在末尾**
（与 `outputFormatRule()` / `prefill` 三处呼应，形成「提示词 + 示例 + 预填充」三重格式约束）。

#### 9.6.3 🧹 解析前先剥「思考块」（思维链模型的第二道防线）

`parseStructuredTags` 现在会先调 `stripThinkingBlocks()` 剥掉：

| 形式 | 例子 |
| --- | --- |
| 尖括号 | `<thinking>…</thinking>` / ` thinking…` / `<reasoning>` / `<thought>` / `<analysis>` |
| 中文方头括号 | `【思考】…【/思考】` / `【推理】…【/推理】` / `【分析】…【/分析】` |

🛡️ **防御性设计**：剥完若解析失败，**回退用原始文本再解析一次** ——
防止模型把真结果写在思考块里被误剥掉（单测已覆盖此用例）。

#### 9.6.4 🛡️ 降级阶梯（原「只降预填充一次」升级为三级）

预填充与思维链都是「末尾 assistant 消息」，部分中转站 / 思考型模型会拒收。
原来的「只降预填充一次」不够（若连思维链也被拒就整卡失败）⇒ 改为**逐级剥离**：

| 档 | 内容 | 应对 |
| --- | --- | --- |
| ① | 全量（预填充 + 思维链） | 正常情况 |
| ② | 去预填充（保留思维链） | 只有预填充被拒 |
| ③ | 去预填充 + 去思维链 | 所有末尾 assistant 都被拒 |

⚠️ 只保留**实际会用到**的档位（没开预填充 / 思维链就不白跑一趟）；
降级发生时日志会写明「「全量」被拒（原因），降级为「去预填充」重试…」，跑完还会提示「本次实际使用「X」模式」。

#### 9.6.5 🔌 测试连通性（`testApiConnection`）

**为什么需要**：打标是**批量**操作，Endpoint / Key / Model 任一配错，
都会在跑了几十张卡之后才暴露（每张还带 1.5s 间隔 + 重试退避）⇒ 白等很久。

**怎么做**：发一条**最小请求**（`messages:[{role:'user',content:'hi'}]` + `max_tokens:8` + `temperature:0`），
立刻验证三要素是否真的通，并回显耗时 + 当前模型名（便于确认没选错模型）。

- 走 `sendChatMessage` 通道（主进程转发）—— 渲染层直接 fetch 会被 CORS 拦；
- 不写入任何配置、不改状态，只回 `{ok, message, ms}`；
- 支持 `{silent:true}`（供将来「批量前静默预检」复用）；
- 位置：**API 引擎设置区**，与「拉取模型列表」并列。
