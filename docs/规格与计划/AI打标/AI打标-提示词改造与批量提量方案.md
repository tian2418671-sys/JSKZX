## 一、问题与来源（用户原话驱动）

### 1.1 提示词「套娃」

> 用户原话：「系统提示词库中的预设词本身就带有 System，但是在里面又加了 System，什么意思，不重复了套娃么」

现状：`系统提示词预设库（N 条）` → 点开某条 → 内部再分 `System / Assistant / User / 预填充 / 思维链` 五个小页签。

问题：**预设本身就是 System 的内容**，再放一个 System 页签 = 同一件事写两遍；且「选哪条」与「每条里写什么」混在一起，认知负担大。

### 1.2 破限词的位置

> 用户原话：「在 System 上加一个破限词栏」

破限词发送时本来就拼在 System 末尾（`buildTaggingSystemPrompt` / `buildLlmMessages` 落地），却放在左侧独立的「强制破限」分区 —— 位置与语义不一致。

### 1.3 批量吞吐（十万卡 = 月级）

> 用户原话：「若是以张一张的跑，十万卡跑到那一年去你说」

现状（代码事实）：**一张卡一次请求 + 每张间隔 1.5s**（`AI_TAG_DELAY_MS = 1500`），且**没有断点续跑** —— 中途关窗后队列需重新发起。

| 模型类型 | 单张 | 1.2 万张 | 10 万张 |
| --- | --- | --- | --- |
| 快模型 | ≈5 秒 | ≈18 小时 | ≈6 天 |
| 一般 | ≈12 秒 | ≈1.5 天 | ≈13 天 |
| 思考型 | ≈30 秒 | ≈4 天 | ≈36 天 |

（24 小时不停地跑的账；每天只跑几小时会再翻数倍。）

> 用户裁决：**并发不做**（「第一个不可控不使用」—— 用户可能接各种中转站，速率规则不可枚举）；**打包做**（「一次十张卡提供滑块让用户选择一次几张卡」）；**断点续跑做**（「3. 可以」）。

### 1.4 超长卡与候选池

> 用户原话：「（软件自动填卡片内容）：若是用户批量十万卡片，大模型收的住么，需要一个分段机制」

先澄清：软件是**一张卡一次请求**（十万张 = 十万次，不会一起送）。决定"收不收得住"的是两件事：① 单张卡大小；② 候选池大小。

代码现状（`useAITools.js`）：描述截断 **1500 字** / 首句 **500** / 性格 **300**（**只取开头、其余直接丢**）；**候选池无上限**。

## 三、提示词链路化（设计）

### 3.1 界面

```text
📝 系统级微调全局提示词 (System Prompts)
┌ 🧠 System ────────────────────────────────┐
│ ⚠️ 破限词（发送时自动拼在主提示词最后）  ［开关］ │
│ 📚 预设套用：原 3 预设 ＋ 末项「✏️ 自定义」      │
│ [破限词输入框：选预设自动填入 / 自定义手写]      │
│ ─────────────────────────────────────────── │
│ 📚 系统预设：🎯标准 / 🧭深度 / ✂️精简 / 末项「✏️自定义」 │
│ [主提示词：你是「角色卡标签分析助手」…（默认全文见 §3.5）] │
└───────────────────────────────────────────┘
                     ↓
┌ 👤 User ──────────────────────────────────┐
│ [留空 = 程序自动（卡片内容 + 候选池 + 输出要求）] │
│ 📦 每请求打包卡数  [——●———] 3 张（短卡成组）    │
└───────────────────────────────────────────┘
                     ↓
   ⚡ 预填充（高级 · 折叠）  [<tags>[          ]

   🟢 分角色结构已生效（仅「只有 LLM 层」组合时）
```

### 3.2 数据与迁移

- 新数据（全局**单套**）：`llmRolePrompts = { system, assistant, user, prefill }`（字段名实现时定）
- 迁移规则：

| 新字段 | ← 旧来源 |
| --- | --- |
| System | 旧「当前生效预设」的 `system`（无则 `content`）；无旧值 → §3.5 新默认文案 |
| ~~Assistant~~ | **已取消（D14）**：旧 `assistant` / `cot` 内容并入 System（无旧值 → §3.5 第 5 条默认推理句） |
| User | 旧 `user`（空 = 程序自动） |
| 预填充 | 旧 `prefill`（空 = 默认 `<tags>[`） |

- `systemPromptPresets` / `activeSystemPromptId` 不再读写；**旧数据保留在配置文件**（不删、可回滚）
- `cotMode` / `cot` 字段废弃（思维链文本并入 Assistant 框）

### 3.3 消息组装（两种模式）

| 模式 | 消息序列 |
| --- | --- |
| 非「仅 LLM」组合（零回归） | `system（主提示词 + 破限词）` → `user（程序默认 promptText）` |
| 「仅 LLM」组合 | `system（主提示词 + 破限词 + 推理句）` → `user（自定义 或 程序默认）` → `prefill（默认 <tags>[；可清空关闭）` |

> 🧩 **组装链路**（每张卡）：破限（拼入 System 末尾）→ System（含推理句）→ User（本卡信息 + 候选池）→ 预填；**分段与打包都作用在「User = 本卡信息」这一步**（见 §四 / §五）。

- 降级重试**简化为两级**（全量 → 去预填充）—— Assistant 取消后「去思维链」档不再需要
- `<tags>` 三层解析、剥思考块、连通性测试：**全部不动**

### 3.4 删除 / 保留清单

| 删除 | 保留 |
| --- | --- |
| 预设列表、新增/删除/单选/命名/展开折叠 | 🟢 分角色徽标（仅 LLM 层提示） |
| 五小页签 与 `cotMode` 三档 | `<tags>` 结构化截取（三层降级） |
| `activeSystemPromptId`（界面层） | 降级重试（两级）、剥思考块 |
| 「强制破限」独立分区（内容搬进 System 栏） | 破限功能本体（开关 + 预设套用 + 词栏） |
| | 「附加自定义提示词」（本次打标区内，不动） |
| Assistant 框（推理句并入 System，D14） | ⚡ 预填充（折叠高级，D14） |

### 3.5 System 默认文案（重构版 · 结合实际卡）

编写依据（**真实库实测**，`E:\AI\酒馆工具\角色卡` 抽查 10 张）：

- **性格字段几乎为空** —— 信息主要靠「描述 + 首句」承载；提示词不得假设性格可用；
- **描述常含结构化设定行**（全名 / 别名 / 种族 / 年龄 / 外貌）+ 世界观段落；
- **卡名常含身份或称号**（如「【Amily2号助手】客服」）；
- **世界书词条是信息大户**（实测常见 14~110 条）——⚠️ **用户澄清（2026-09-25）：卡内嵌世界书不在打标范围**；需打标的是**世界书库的独立世界书**（独立需求，见 §八 Q10）；
- **既有标签爱用「大类/子类」写法**（如「仙侠/修真」「古代/宫廷」）与少量双语 —— 默认文案引导与卡库风格一致；
- **推理句并入 System（D14）**：原独立「思维链」段取消（System + User 已构成完整链路）；⚡ 预填充保留作格式保险。

默认文案（迁移无旧值 / 新装时使用；实现时用它替换各处旧默认）：

```text
你是「角色卡标签分析助手」，为 SillyTavern 角色卡生成便于检索的标签。
你会收到以下几类材料：
- 描述（description）：主要信息源；常含结构化设定（全名 / 别名 / 种族 / 年龄 / 外貌）与世界观段落；
- 首句（first_mes）：开场剧情 —— 用于判断场景、氛围与互动基调；
- 性格（personality）：可能为空，有则参考；
- 卡名：常含身份或称号；
- 如另附对话示例 / 世界书内容，一并参考。
打标原则：
1. 只依据材料中真实出现或可直接推断的内容，不脑补、不臆造；
2. 标签为简短中文词或词组（2~6 字），不写句子、不堆同义词；
3. 覆盖维度：题材 / 世界观、身份与职业、性格与气质、外貌特征、能力与特殊设定、关系与阵营、氛围与风格；
4. 避免过泛（如「女性」「有趣」）；卡库常用「大类/子类」写法（如「仙侠/修真」），候选池里有的优先复用，没有再用自己的词。
5. 输出前先在内部完成推理（题材 → 身份 → 关键词 → 归纳），只输出最终标签，不输出推理过程。
```

> 📚 **System 预设套用**（D12）：内置「🎯 标准打标（=上文默认）/ 🧭 深度解析（长卡，输出 10~15 个细标签）/ ✂️ 精简标签（只留核心 5~8 个）」+ 末项「✏️ 自定义」。选预设 = 覆盖填入；选自定义 = 用手写内容。**3 个变体文案为草案，待定稿。**

## 四、批量提量（设计）

### 4.1 打包（一次请求多张卡）

- 控件：**滑块「每请求打包卡数」1~10**，默认 1（= 与现状完全一致；建议甜蜜区 3~5）
- 位置：**挂在 👤 User 框下**（卡信息入口处；与「⚙️ 执行管线」页的滑块两处同步、共用同一状态）
- 适用：**只打包短卡**（长卡、超长卡不参与，防超限）
- 输出：一次请求内按编号出结果（格式实现时定），**逐卡校验**
- 兜底：包内某卡解析失败 → **自动拆回单发重试**（不丢卡）
- 节流：1.5s 间隔从"每卡"改为"**每请求**"（请求数变少、节奏不变 → 限流风险不升反降）
- 进度：仍按"卡"计数显示

### 4.2 断点续跑

- 记账：处理进度（目标卡清单 + 已完成清单 + 统计）落盘；**每 N 张 + 暂停/退出时**补记（N 待议）
- 续跑：再开工时提供入口「继续上次未完成的 X 张」→ **跳过已完成**
- 与打包兼容（整包完成才记该包内的卡）

### 4.3 明确不做

- ❌ 并发请求（用户裁决：不可控）
- ❌ 模型白名单硬编码（沿用「失败即重试」的通吃方案）

### 4.4 效果预期

| 场景 | 10 万张 | 1.2 万张 |
| --- | --- | --- |
| 现状（单发） | 6~36 天 | 18 小时~4 天 |
| + 打包 5 + 续跑 | ≈3~4 天（可断开续跑） | ≈4~5 小时 |
| 再 + 规则/向量先行过滤 | 常见 1~2 天 | 常见 <1 小时 |

## 五、超长卡分段 + 候选池上限（设计 · 细节待议）

### 5.1 超长卡分段

```text
普通卡（不超阈值） → 照旧单发
超长卡 → 按段落边界切段 → 逐段请求打标 → 合并去重（出现次数多者排前）
```

- 触发阈值：建议 4000 字（**待议**）
- 作用对象：**User 里的「本卡信息」**（与打包同一层；短卡不切，走 §4.1 打包）
- 备选（默认不做）：先摘要再打标（多 1 次请求、质量略低）

### 5.2 候选池上限

- 加"上限"（建议 300 个，**待议**）；超出时提示精简
- 阈值内仍全量拼入 prompt（现状行为）

## 六、风险与防线

| 风险 | 防线 |
| --- | --- |
| 打包后模型串号 / 偷懒 | 逐卡校验 + 失败拆单发；只打包短卡；默认 1 可随时退回 |
| 打包拉大后质量下降 | 滑块由用户自选；出问题滑回 1 即恢复现状 |
| 迁移丢配置 | 旧数据不删、自动搬运、可回滚 |
| 分段合并引入噪声 | 出现次数排序 + 候选池上限；普通卡不受影响 |
| 续跑与手动改动冲突 | 续跑仅跳过"已完成 ID"（卡被改动/删除时的行为见 §八 Q8） |

## 七、验收标准（可测）

- [ ] 滑块 = 1 时：行为与现状**完全一致**（请求数、提示词内容不变）
- [ ] 滑块 = N 时：请求数按预期减少；含"坏卡"的包自动拆单发、最终不丢卡
- [ ] 续跑：跑到一半强制结束 → 重开 →「继续」跳过已完成，无重复请求
- [ ] 两框 + 预填：老配置打开不丢字段（旧 Assistant / 思维链内容并入 System）；改字生效；清空「⚡ 预填充」= 不注入；恢复默认一键还原
- [ ] 破限词：开/关行为与现状一致（拼接位置不变）
- [ ] **UI 文字审计**：正式版不得出现任何讨论 / 预览标记（「静态演示 / 方案新增 / 现状机制 / 已按裁决 / 示例数字 / 此处只是摆放位置」等设计说明式文案）
- [ ] 超长卡：造一张超长卡验证分段合并；普通卡耗时不变
- [ ] 全程 `npm test` 全绿 + 真实库冒烟无错
