## 二、现状取证（2026-10-03 代码事实）

> ⚠️ 行号仅供参考，动工前请重新 grep 校对。

### 2.1 发送链路（卡片 / 世界书**共用同一条**）

```text
[ system    ] buildTaggingSystemPrompt() = llmRolePrompts.system + 破限（拼末尾）
[ user      ] 程序材料 promptText（= 任务说明 + 候选池与规则 + 输出要求 + 目标材料）
[ assistant ] 预填充（默认 <tags>[，可留空关闭）
```

出处：`js/composables/useAITools.js`（`../../../js/composables/useAITools.js`）
`requestTaggingShared` L403-488、`buildTaggingSystemPrompt` L105-111。

`promptText` 由 `buildCardPromptParts` / `buildWbPromptParts` L387-394 **分段构建后拼接**
（`parts.map(p => p.body).join('')`）——这也是「📨 程序自动材料（发送预览）」的数据源（发送与预览同源）。

### 2.2 世界书材料 = 书名 + `【触发词】` + 正文（**词条名丢了**）

`buildMaterial` L271-288：

```js
const parts = [`书名：${name}`];
for (const e of entries) {
    const key = Array.isArray(e.key) ? e.key.join('、') : String(e.key || '');
    parts.push(`【${key || '无标题'}】\n${content}`);   // ← 只用 key，没有 e.comment
}
```

| 事实 | 后果 |
| --- | --- |
| 词条标题用的是 **`key`（触发词）**，不是 **`comment`（词条名 / 备注）** | 触发词常是 `{{user}}`、`你`、`我` 这类**无信息量**的词；而 `comment` 通常是作者写的一句话摘要（如「世界观-魔法体系」）—— 这是**最大的信息丢失点** |
| 书级 `description` **没送** | 整本书的定位说明（作者写的简介）被丢掉 |
| `keysecondary`（次级触发词）、`constant`（常驻）、`enabled`（启用）**都没体现** | 常驻的核心设定与临时词条**在提示词里长得一样**；被禁用的词条**照样送**去打分 |
| 大幅书分段：> 4000 字走分段（`SEGMENT_THRESHOLD_CHARS` L158），最多 **40 段**（`WB_SEGMENT_MAX_SEGMENTS` L1193），超出**均匀采样** | 真实库实测（2026-10-03 探针）：材料均值 **14 万字**、最大 **96 万字**；**28/35 本会走分段**、其中 **7 本超过 40 段**。最大的那本 96 万字 ≈ 275 段 → 采样 40 段 ≈ **只送 14.6%**（其余 60 万+ 字完全不进提示词）。每段还各自带一遍任务说明 + 候选池 + 输出要求 |

> 📌 真实库口径：世界书 `H:\01\全局世界书`（41 本，含 6 本 ≥6MB）—— **大幅书是常态，不是边角**。

### 2.3 世界书用的是「角色卡」System 文案 ★

`DEFAULT_SYSTEM_PROMPT`（`js/utils/llmPromptRoles.js` L68-80）开头是：

```text
你是「角色卡标签分析助手」，为 SillyTavern 角色卡生成便于检索的标签。
你会收到以下几类材料：
- 描述（description）…
- 首句（first_mes）：开场剧情…
- 性格（personality）…
- 卡名：常含身份或称号；
```

`useAITools.js` L148-151 写明「**世界书打标与角色卡打标是同一条系统**」——
⇒ 打世界书时，AI 被告知「材料是描述 / 首句 / 性格 / 卡名」，实际收到的却是 `【世界书材料】书名 + 词条`。
**口径错配**，且用户无法分开设置（只有一套 `llmRolePrompts`）。

### 2.4 自定义模式：程序材料固定拼进「最后一条 USER 段」

`buildCustomMessages`（`js/utils/customPromptSegments.js` L95-115）：

```js
// 材料（候选池+卡数据+输出要求 = defaultUser）：拼进**最后一条 user 段**；无 user 段时作为独立 user 消息
msgs[li] = { role: 'user', content: msgs[li].content + '\n\n' + mat };
```

| 事实 | 后果 |
| --- | --- |
| 材料是**一整块**（任务说明 + 池 + 输出要求 + 目标材料）拼进去的 | 想只去掉「任务说明」做得到（覆盖成空串），想**把材料挪到 SYSTEM 段**做不到 |
| 段内容里**没有任何占位符机制** | 用户只能「在材料前面加话」，不能「让材料出现在我写的位置」 |
| 分流条件：`isCustomMode = llmOnly && tagPromptMode === 'custom'`（L409-411） | 自定义模式**只在使用「仅 LLM」组合时生效**（与既有设计一致，本方案不改） |

### 2.5 顺带发现的两处隐患（本方案顺手修，或另立 BUG）

| # | 现象 | 取证 |
| --- | --- | --- |
| H1 | **① 规则层在世界书未加载正文时静默失效** | `startWbTagging` 的规则循环（L1282-1307）**没有** `ensureWorldbookLoaded`，而向量层（L1315）与 LLM 层（L1381）都有。世界书是**懒加载**（`scanWorldbookDir` 只 `fastListOnly`，正文按需读；`releaseWorldbookBody` 会把 `wb.data` 置 `null`）⇒ 未加载的书 `buildMaterial` 只返回 `书名：X`，规则**必然**不命中，日志却显示「未命中规则」（看起来很正常） |

## 三、问题定性

| 编号 | 问题 | 性质 | 用户能感知的后果 |
| --- | --- | --- | --- |
| **P1** | 世界书材料**丢字段**（`comment` / `description` / `keysecondary` / `constant` / `enabled`） | 打标准确性缺陷 | 打出来的标签泛、偏、漏（尤其触发词是 `{{user}}` 的词条） |
| **P2** | 世界书走**角色卡口径**的 System + 任务说明 | 打标准确性缺陷 | AI 按「角色卡」的思路理解世界书设定 ⇒ 维度错位 |
| **P3** | 程序材料**不可关、不可挪位**（只能整段覆盖） | 自由度缺陷 | 用户写了完整预设，程序仍塞 145 字进去；材料只能出现在 USER 尾部 |

> P1/P2 是「**AI 拿到的东西不对**」；P3 是「**AI 拿到的东西放得不对**」。两者独立，可分两批做。

## 四、方案设计

### 4.1 材料占位符（R3 的核心）

**语义**：自定义模式的**段内容**里出现占位符 → 发送时替换成对应材料，且该材料**不再自动附加**；
没被任何占位符引用的材料 → 照旧尾随（= 今天的零回归行为）。

**建议的占位符表**（`{{...}}` 与现有宏风格一致，见 `chat/useChatMacros.js`）：

| 占位符 | 展开为 | 复用的现有段 key |
| --- | --- | --- |
| `{{材料}}` | **当前目标**的材料（卡片视图 = 卡材料；世界书视图 = 书材料） | `card` / `wb` |
| `{{卡片}}` / `{{世界书}}` | 精确指定某一种（一般不需要，做兜底） | 同上 |
| `{{候选池}}` | 候选池 + 规则（池关时为空） | `pool` |
| `{{附加要求}}` | 附加要求正文 | `extra` |
| `{{任务说明}}` | 程序任务说明（用户想保留但想换位置时用） | `task` |
| `{{输出要求}}` | 输出格式强制规则 | `output` |
| `{{破限}}` | 破限词（现在固定拼在 System 末尾） | — |

**替换规则（关键约束）**：

1. **只替换「段内容」**，绝不替换材料正文 —— 世界书正文里本来就带 `{{user}}` / `{{char}}` 宏，
   不能在里面二次替换（否则会污染原文）。
2. 材料里若含 `$1` 之类的字面量，**不会被当占位符**（同理只认段内容）。
3. 数字别名：支持用户建议的 **`$1` = `{{材料}}`**（见 §十 Q1）；同一个占位符写几次就插几次，
   **不做去重**（用户显式写了两次就是想要两次）。
4. 占位符名不区分大小写（`{{材料}}` / `{{ 材料 }}` 容忍空格）。
5. 未知占位符（如 `{{随便写的}}`）**原样保留**，但预览区给 `⚠️ 未识别的占位符` 提示。

**实现方式（纯函数，可单测）**：

```js
// js/utils/tagPromptVars.js（新增）
//   parseVarsInSegments(segments) → { usedKeys: string[], unknown: string[] }
//   applyVarsToSegments(segments, vars) → 新段数组（替换后）
// 复用现有 buildCustomMessages：把「未被引用的材料」作为 defaultUser 传进去（行为不变）
```

> 这样 `buildCustomMessages` 的现有语义（拼进最后一条 USER 段 / 无 USER 段时独立成 USER）**保持不动**，
> 单测 `test/customPromptSegments.test.mjs` 不受影响；新增能力落在新文件里。

**UI**：段编辑器每段下方加一排「插入材料」小按钮（`＋ 材料` / `＋ 候选池` / `＋ 输出要求`），
点击即在光标处插入占位符 —— 用户不用记写法。

### 4.2 「自动附加」改成可关（R2 的核心）

把现在**硬编码**的自动附加改成**每类材料一个状态**（逐类独立，互不影响）：

| 材料类 | 段 key | 默认 | 关闭后 |
| --- | --- | --- | --- |
| 任务说明 | `task` | 自动附加（与今天一致） | 不送（用户自己在段里写） |
| 候选池与规则 | `pool` | 自动附加 | 不送（或改用 `{{候选池}}`） |
| 输出要求 | `output` | 自动附加 | 不送（用户自己写格式要求） |
| 目标材料 | `card` / `wb` | 自动附加 | 不送（必须用 `{{材料}}`，否则 AI 收不到内容 —— 预览要给**红色警告**） |

**三档全局预设**（放在自定义模式页顶部，一个单选圈）：

| 档 | 行为 | 适合 |
| --- | --- | --- |
| 🟢 **兼容（默认）** | 全自动附加（= 今天行为），占位符仍可用（用了就接管对应那一类） | 老用户零回归 |
| 🟡 **半自动** | **只不送「任务说明」与「输出要求」**；目标材料 / 候选池与规则 / 附加要求照旧自动附加 | 想自己写角色与格式、又不想管材料插入点 |
| ⚪ **全手动** | 一类都不自动附加，全靠占位符 | 完全自己编排（用户的批注 ② 指的就是这一档） |

> 📌 **落地偏差（半自动的边界）**：原方案写的是「只有目标材料自动附加」；落地时**保留「候选池与规则」与「附加要求」**
> （候选池是打标一致性的关键输入，跟着材料一起走更合理），只砍「任务说明 / 输出要求」——
> 实现即 `splitPartsByVars()` 的 `DROP_SEMI = ['task','output']`，UI 文案与之一致。

**「一键生成默认模板」**按钮：把当前生效的三类程序材料**内联成段**（SYSTEM/USER 角色按今天的实际发送位置生成），
让「全手动」也可以一键还原成等价的可编辑内容 —— 这样「关掉自动附加」不会让人不知道从哪写起。

> ⚠️ **落地偏差（「一键生成默认模板」未做）**：本批**未实现**该按钮（已有「⟸ 映射当前提示词」把系统提示词链路映射为段，
> 但**不含**程序材料段）。用户如需「全手动 + 一键还原」，当前路径是：先切回 🟢 兼容档看一遍预览，再把预览里的文字抄进段里。
> 该按钮列入后续可选增强。
>
> ⚠️ **去掉输出要求 = 少了格式约束**：解析层仍是 `<tags>` 三层降级（`parseStructuredTags`），不会崩，
> 但命中第 ③ 层（暴力拆分）的概率会上升。落地时**在日志里提示一次**（「本次未附加输出要求，模型未遵守格式时会走兜底解析」）。

### 4.3 世界书材料「直发」（R1 的核心）

**目标形态**（保持纯文本，不改成 JSON —— 见 §十一）：

```text
书名：<worldbook name>
简介：<data.description>                      ← 新增（有则送）
词条数：1234

【<comment 或 触发词>】                        ← comment 优先（新增）
触发词：a、b、c · 次级：d · 常驻            ← key + keysecondary + constant（新增）
<content>
```

| 改动 | 说明 | 待拍板 |
| --- | --- | --- |
| 加 `comment` | **第一优先**，收益最大 | Q4 |
| 加书级 `description` | 有则送 | — |
| 触发词 / 次级 / 常驻标注 | 帮助 AI 判断词条性质 | — |
| **跳过 `enabled === false`** 的词条 | 被禁用的词条不该参与打标 | Q5 |
| 大幅书分段**上限 40 → 可调** | ✅ **已拍板（Q8 = (c)，2026-10-03）**，设计见 §4.3.1 | ✅ 已拍板 |

> 💡 **为什么加 `comment` 不算「送酒馆看不到的东西」**：`comment` 在酒馆里对模型不可见（仅作者标识），
> 但它正是**作者自己写的摘要**，对「打标」这种**归纳任务**价值极高；我们不是在做「角色扮演上下文」，
> 是在做「内容归类」。这一条要用户明确点头（Q4）。

#### 4.3.1 大幅书分段上限可调（Q8 拍板 (c)）

**现状（常量，用户改不了）**：`WB_SEGMENT_MAX_SEGMENTS = 40`（`useAITools.js:1193`）——
材料 > 4000 字（`SEGMENT_THRESHOLD_CHARS`）即分段，单段目标 3500 字（`SEGMENT_CHUNK_MAX_CHARS`），
段数超过 40 就**均匀采样 40 段**（`stride = 实际段数 / 40`）。

**改成**：

```text
⚙️ 大幅书分段（世界书打标）
   最多分段数  [——●————] 40 段      （范围 10 ~ 300，步进 10；默认 40 = 与今天一致）
   ⓘ 本次每本最多 40 次请求（≈ 40 × 1.5s 间隔 + 模型耗时）
```

| 项 | 设计 |
| --- | --- |
| 语义 | 与今天**同一算法**（`segments.length > 上限` → 均匀采样 `上限` 段），只是上限不再写死 |
| 取值 | 10 ~ 300，步进 10；默认 **40**（= 现状 ⇒ 老用户零变化） |
| 位置 | AI 打标窗「⚙️ 执行管线」页（与打包滑块、增量开关同组）；世界书打标范围处显示当前生效值 |
| 落盘 | `ui.tagWbSegmentMax`（老配置无此字段 → 40） |
| 成本可见 | 拖动时实时显示「每本最多 N 次请求」；日志沿用现有那条并补一句「（上限 = 你的设置值，可在「执行管线」页调整）」 |
| **不做** | 单段字数（3500）与分段阈值（4000）**仍为常量** —— 改它们会同时改变「每段送多少」和「要不要走分段」，影响面远大于「多分几段」；用户要的「提高覆盖度」**一个上限旋钮就够**（上限↑ = 采样更密） |
| 顺带观察（本次不改） | **卡片**侧分段**没有**上限（`processSegmentedCard` 逐段全跑）：50 万字的卡 ≈ 143 次请求，目前无闸门 —— 建议同批登记为观察项，日后复用同一个设置位 |

### 4.4 世界书专用默认文案（P2）

**现状**：`llmRolePrompts` 只有一套（`system` / `user` / `prefill`），卡与书共用。
**建议**：链路按目标分叉，但**不逼用户维护两份**：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **S-A（推荐）** | `llmRolePrompts` 增加可选的 `wb` 覆盖：`{ system, user, prefill, wb: { system, user } }`；未填 `wb.*` 时**回落**到主套 | 老配置零破坏；世界书想分开写就填，不想管就留空 |
| S-B | 只把**默认值**换掉：卡视图默认卡文案、书视图默认书文案 | 改动最小，但用户改过一次后就分不开了 |
| S-C | 完全独立两套（当前视图各记一套） | 认知负担最大，不推荐 |

> ✅ **落地形态（Q7，与 S-A 的偏差已按「显式优于隐式」修正）**：
> `llmRolePrompts.wb = { mode: 'default' | 'inherit' | 'custom', system: '' }`——
> · `default`（**新默认**）：用内置 `DEFAULT_SYSTEM_PROMPT_WB`；
> · `inherit`：沿用主套 System（一套通吃的用户显式选择）；
> · `custom`：用 `wb.system`；**留空自动回退 `default`（不静默失效）**。
>
> ⚠️ **为什么不照搬「留空 = 隐式回落主套」**：老用户的主套 System 是**角色卡口径**（「你是角色卡标签分析助手…描述/首句/性格/卡名」），
> 隐式回落会让口径错配（AI-15）**对老用户继续存在**——等于病根没修。改成显式三态后：
> 默认就修好；想一套通吃的人在 UI 上点一下 `inherit` 即可。老配置无 `wb` 字段 → 自动补 `default`（**加法式，不删旧键 ⇒ 可回滚**）。
> `wb.user` **未实现**：`user` 段是「本次任务指令」（与目标类型无关），卡与书共用即可，不复制第二套字段。
> 打标日志会显式告知本次世界书用的是哪一套（`🌍 世界书 System：…`）。

新增内置默认文案 `DEFAULT_SYSTEM_PROMPT_WB`（草案）：

```text
你是「世界书设定标签分析助手」，为 SillyTavern 世界书（世界观 / 设定集）生成便于检索的标签。
你会收到一本世界书：书名、简介、若干词条（每条含词条名 / 触发词 / 正文）。
打标原则：
1. 只依据材料里真实出现或可直接推断的内容，不脑补、不臆造；
2. 标签为简短中文词或词组（2~6 字），不写句子、不堆同义词；
3. 覆盖维度：题材 / 世界观、势力与阵营、地点与场景、人物与身份、能力与体系、事件与剧情、风格与氛围；
4. **词条名与触发词是定位线索**：词条名说明作者如何归纳该词条，触发词反映它在对话里何时被唤起；
5. 避免过泛（如「设定」「内容」）；卡库常用「大类/子类」写法，候选池里有的优先复用；
6. 输出前先在内部完成推理（主题 → 势力 → 地点 → 关键词 → 归纳），只输出最终标签，不输出推理过程。
```

任务说明也同步分叉：`buildTaggingTaskText('wb', …)` 的现文案是
「你是一个专业的世界书设定标签分类助手。请根据以下世界书内容进行打标。」——保留，但**只在没有 `wb.system` 时兜底**
（避免与新的 `wb.system` 重复说同一件事）。

### 4.5 预览与透明化必须同步（不变式）

现有的唯一不变式是：**预览 = 实发（逐字）**。
引入占位符后新增两条不变式：

1. 预览里显示的段内容 = **已替换后**的实际文本（不能显示 `{{材料}}` 原文而不展开 —— 否则「完全透明」就断了）；
2. 预览里每类的状态要看得见：`程序自动生成` / `已修改` / **`已由占位符接管（不自动附加）`** / `已关闭`。

> 预览的「目标材料」用**第一个目标**的正文展开（多目标时其余目标的段文字不同 —— 沿用现有多目标展示思路：
> 逐张/逐本列组），并在段头标注「本段由占位符接管」。

## 九、验收标准（可测）

- [ ] **保真**：任取一本真实世界书，材料里能看到**词条名（comment）**、**触发词**、**书级简介**；被禁用的词条**不出现**（Q5 定后）
- [ ] **口径**：世界书打标的 System 是**世界书文案**（不是「角色卡标签分析助手」）；卡片侧文案**一字未变**
- [ ] **零回归**：默认档下，同一张卡 / 同一本书的**实发 promptText 与升级前逐字一致**（可用预览 + 日志对照）
- [ ] **占位符**：`{{材料}}` 放在 SYSTEM 段能生效（材料真的出现在 system 消息里）；写与不写占位符，材料**不重复送**
- [ ] **全手动档**：只用段 + 占位符完成一次真实打标，日志里 System / User / 预填充与预期一致
- [ ] **预览不变式**：预览文本 = 实发文本（逐字）；接管 / 关闭 / 已修改三种角标正确
- [ ] **解析**：去掉输出要求 + 预填充被中转站拒绝时，仍能解析出标签（走三层降级）且日志有提示
- [ ] **规则层**（H1）：未打开过的世界书，① 规则层也能命中（正文按需加载 + 用后释放，内存不涨）
- [ ] **分段上限可调**（Q8）：默认 40 时与升级前**逐字一致**；设 5 / 200 各跑一本，请求数分别 ≤ 5 / min(实际段数, 200)，日志与进度可核对
- [ ] **真实库冒烟**：卡库 `E:\AI\酒馆工具\角色卡`（89 张）+ 世界书 `H:\01\全局世界书`（41 本，含 6 本 ≥6MB）各跑一轮；`npm test` 全绿；`npm run build:web` + 真实启动无 `[Vue 错误]`

> 📌 **批注 ① 的意思最终按「补全 + 口径修正」实现**（不加「原样直贴」模式）：材料仍是「书名 + 简介 + 词条（带词条名/触发词）」的**可读结构**，
> 但用户可以在自定义模式里用占位符 + 自己的提示词完全接管措辞与位置。若日后确实要「连 `【词条】` 标记都不要、原文照贴」，
> 属于新需求（需另立方案，见 §十一 的「不做」清单）。

## 十一、明确不做 / 范围边界

| 不做 | 原因 |
| --- | --- |
| ❌ 把世界书材料改成 **JSON / 结构化投喂** | 用户要的是「**直接送内容**」，JSON 反而是又一层加工；且会与分段、打包、预览三处口径打架 |
| ❌ 改 `<tags>` 三层解析 / 剥思考块 | 与本方案无耦合；已有 824 用例覆盖，不动 |
| ❌ 改三层漏斗（规则 / 向量 / LLM）协议与落盘（`wbTagMap`） | 只修 H1 的「加载对齐」，不改语义 |
| ❌ 引入并发请求 / 模型白名单 | 用户既有裁决：并发不做、不硬编码模型名 |
| ❌ 让占位符替换发生在**材料正文**里 | 世界书正文天然含 `{{user}}` 等宏，替换会污染原文 |
| ❌ 自动替用户改写 / 生成预设正文 | 只在用户点「一键生成默认模板」时给出**可编辑**的段，不隐式覆盖 |
