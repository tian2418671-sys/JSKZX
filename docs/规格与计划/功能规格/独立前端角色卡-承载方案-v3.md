## 零、实测验证记录（v3 与 v2 / v2.1 的根本差别）

v2 与 v2.1 均有若干"基于推测"的技术判断。本文在动手设计前先跑了一次实机探针，结论如下。

**探针环境**：Electron **43.4.1**（本项目 `package.json` 实际版本），Windows，独立 `--user-data-dir`。

| # | 验证项 | 实测结果 | 影响 |
| --- | --- | --- | --- |
| V1 | `WebContentsView` 可用性 | ✅ `typeof WebContentsView === 'function'` | **可用**，无需 `webviewTag` |
| V2 | `WebContentsView` 能否指定独立 partition | ✅ 创建成功，独立 session 生效 | 容器方案成立 |
| V3 | `session.getStoragePath()` 是否存在 | ✅ 存在且**返回精确路径** | 无需猜测 `Partitions/` 路径 |
| V4 | 精确路径返回值 | `...\userData\Partitions\heavycard-probe_g1` | 与预期一致 |
| V5 | `flushStorageData()` 是否存在 | ✅ 存在 | 备份前刷盘方案成立 |
| V6 | 落盘后真实目录内容 | `Local Storage` / `Session Storage` / `Network` / `Cache` / `Code Cache` / `GPUCache` / `DawnGraphiteCache` / `DawnWebGPUCache` / `blob_storage` / `Shared Dictionary` / `DIPS` / `Preferences` | **备份白名单可按此精确定义** |
| V7 | `Local Storage` 实际文件 | `leveldb/{000003.log, CURRENT, LOCK, LOG, MANIFEST-000001}` | **证实必须跳过 `LOCK`，但 `CURRENT` / `MANIFEST-*` 必须保留** |

| V9 | 一次空 partition 的体积 | 39 个文件 / **1.75 MB** | 一卡一 partition 的固定成本可接受 |

> **这张表是 v3 的核心价值**：后续所有设计不再出现"需实测确认"的占位符。

### 零之三、评审批复的三项实战细节（实现要求，不可省略）

| # | 主题 | 要求 |
| --- | --- | --- |
| **D1** | **原生层遮挡** | `WebContentsView` 位于 OS 合成层，**`z-index` 对它无效**。任何主界面 Modal / 右键菜单 / 子弹窗打开，或离开 `heavycards` 模式时，必须 IPC 通知主进程 `setVisible(false)`；关闭后恢复 |

## 一、v2 / v2.1 → v3 的修正对照

| # | v2 做法 | v2.1 做法 | v3 做法 | 判定依据 |
| --- | --- | --- | --- | --- |
| 1 | `<iframe>` + 主窗口换 partition | `<webview>` + `webviewTag: true` + 守门 | **`WebContentsView`**（主进程创建，独立 session） | V1/V2 实测可用；`webviewTag` 属 Electron 官方"not recommended"，且需给渲染层开创建能力 |
| 2 | 备份直接复制目录，等 300ms | `flushStorageData()` + 跳过 `LOCK` + 世代轮换 | **保留 v2.1 全部要点**，补充：等待 `destroyed` 事件而非固定延时；`CURRENT` / `MANIFEST-*` **不可**跳过；容忍目录缺失 | V5/V7/V8 |
| 3 | 未考虑退出备份 | `before-quit` + `Promise.race` 5 秒超时 | **保留拦截**，但改为「**原子备份**」（临时目录 → 完成 → rename）+ 超时 15 秒 + 断点标记 | `Promise.race` 不取消任务，5 秒必产半截备份 |
| 4 | `archiver` / `zlib` 打包 | `fs.cpSync` 目录快照 | **保留目录快照**，但用**逐文件遍历**（复用 `fullBackup.js` 范式）而非 `cpSync` | 项目无 zip 依赖（已查 `package.json`）；逐文件可发进度、可取消 |

## 二、定位与边界（沿用定稿，未改）

### 2.1 一句话定位

**重型卡是"能玩的收藏品"，软件是它的展柜兼管理员 —— 不碰内容，只管摆放和保管。**

### 2.2 四项职责

| 职责 | 具体表现 | 用户价值 |
| --- | --- | --- |
| **A 启动器** | 侧边栏入口、列表选卡、一键打开 | 不用记网址、不用翻书签 |
| **B 保险柜** | 一卡一存档、自动/手动备份、免重启恢复、迁移、删除 | 几十小时存档不因清缓存/换电脑而丢 |
| **C 统一入口** | 统一列表：名称/图标/备注/上次玩/占用/备份状态 | 几十张卡也不会乱 |
| **D 展示游玩** | 整块渲染、可交互、切走再回来状态还在 | 在软件里真的能玩 |

### 2.3 红线（不做）

| 不做 | 原因 |
| --- | --- |
| 解析卡内存档（剧情/变量/角色/时间线） | 碰芯，格式随作者变，逆向维护成本极高 |
| 编辑卡内任何数据 | 只做整包/目录级操作 |
| 注入 API Key / 接管 AI 推理 | 密钥风险 + 逻辑耦合 + 随版本失效 |
| 修改/镜像站点源码 | 产物 hash 化、持续更新、授权问题 |
| 让卡获得 Node / preload 能力 | 安全红线 |

### 2.4 与现有功能的边界

| 现有功能 | 关系 |
| --- | --- |
| 测卡工作区（`chatEngine`） | 完全独立 |
| 插件工作区（`usePlugins`） | 完全独立 |
| 卡内插件页签 | 无关 |
| 整库冷备（`main/fullBackup.js`） | **复用其范式**（逐文件遍历 / manifest 权威 / 保留轮转），但目录与通道独立 |

## 四、总体架构

```text
┌────────────────────── 主进程 (main.js + main/heavyCards/) ──────────────────────┐
│  · WebContentsView 宿主管理器（创建 / setBounds / 销毁）                        │
│  · 安全基线：sandbox=true, contextIsolation=true, nodeIntegration=false         │
│             不注入 preload；渲染层无法创建任何 WebContents                       │
│  · 独立 session：persist:heavycard-<id>_g<gen>                                  │
│  · 外链：该 view 的 setWindowOpenHandler → shell.openExternal（仅 http/s）      │
│  · 导航：will-navigate 仅放行该卡 URL 同源                                       │
│  · 备份引擎：flushStorageData + 逐文件快照 + 原子写入 + 保留轮转                  │
│  · 恢复引擎：解压至新世代 g(N+1) → 切 partition → 启动期清理旧世代               │
│  · 退出前备份：before-quit preventDefault + 15 秒上限 + 原子性保证               │
└──────────────────────────────────────────────────────────────────────────────────┘
                       ↕ IPC（preload.js 白名单：heavycard:*）
┌────────────────────── 渲染进程 (Vue 3) ─────────────────────────────────────────┐
│  SidebarPanel ── Dock 第 5 按钮 🎬                                              │
│  HeavyCardWorkspace ── 工具条 + 一个「视图占位框」（不渲染任何容器元素）         │
│      · 占位框用 ResizeObserver / 滚动监听 → 上报 rect 给主进程                   │
│  useHeavyCards.js ── 清单 CRUD / 备份编排 / 世代切换 / 持久化                    │
│  useConfigPersistence ── ui.heavyCards 落盘 app_config.json                     │
└──────────────────────────────────────────────────────────────────────────────────┘
                       ↕
        mainWindow.contentView.addChildView(view)  ← 视图层级在主进程
```

### 4.1 为什么是 `WebContentsView` 而不是 `<webview>`

| 对比项 | `WebContentsView`（v3） | `<webview>`（v2.1） |
| --- | --- | --- |
| 独立 session | ✅ 构造参数 `webPreferences.partition` | ✅ `partition` 属性 |
| 谁能创建 | **仅主进程** | 渲染层任意脚本（需 `webviewTag: true`） |
| 安全基线 | ✅ 无需开关，无降级 | ⚠️ 必须开 `webviewTag`，等于给 XSS 一条创建通道 |
| 守门依赖 | 架构层面无入口 | 依赖 `will-attach-webview` 守门代码永不出错 |
| Electron 官方态度 | 推荐（`BrowserView` 的现代替代） | 文档标注 **not recommended** |
| 布局 | 主进程 `setBounds`（需同步坐标） | DOM 直接排版 |

**结论**：多写约 30 行坐标同步代码，换取"渲染层根本无法创建被控容器"。这符合本项目"安全基线不放松"的铁律。

### 4.2 坐标同步设计（v3 唯一新增的复杂度）

```text
渲染层 HeavyCardWorkspace：
  · 放一个空的 <div ref="hostBox">（只做占位与测量）
  · ResizeObserver + scroll + window resize → 计算 getBoundingClientRect()
  · 节流 16ms → ipcRenderer.invoke('heavycard:setBounds', { id, rect })

主进程：
  · 直接 view.setBounds({ x: Math.round(r.left), y: Math.round(r.top),
                         width: Math.round(r.width), height: Math.round(r.height) })
  · 切换 appMode / 窗口最小化 → setVisible(false) 而非销毁
```

> ⚠️ **D3 铁律（V14 实测）**：`getBoundingClientRect()` 与 `setBounds()` **都是 DIP 逻辑像素**。
> **绝不乘 `devicePixelRatio`**（125%/150% 缩放下会放大越界）。仅当主窗口自身调过
> `webContents.setZoomFactor()` 时才需乘该 zoomFactor（本项目主窗口未设置，故为 1）。

**失败兜底**：若 rect 获取异常，视图不显示但**数据不丢**（数据在 partition 里）。

### 4.3 原生图层遮挡（D1 · 必须在 P0 就做）

`WebContentsView` 挂在 `mainWindow.contentView` 上，处在 **OS 合成层**，高于整个 Vue DOM 树。
因此 `z-index: 9999` **完全无效** —— 主界面的弹窗会被重型卡画面盖住。

**触发隐藏的时机（必须全覆盖）**：

| 场景 | 处理 |
| --- | --- |
| 主界面任何 Modal 打开（API 设置 / 命令面板 Ctrl+K / 重命名 / 恢复确认 / 质量检查…） | `setVisible(false)` |
| 重型卡自身弹窗（恢复备份选择器 / 右键菜单） | `setVisible(false)` |
| 离开 `appMode === 'heavycards'` | `setVisible(false)` |
| 窗口最小化 / 失焦到其他窗口 | `setVisible(false)` |
| 上述全部结束 | `setVisible(true)` |

**实现方式（不污染现有弹窗代码）**：在 `HeavyCardWorkspace.vue` 用 `MutationObserver` 监听 `document.body`
的弹窗容器变化（本项目所有弹窗都在根级渲染），或直接监听 `ctx` 里已有的弹窗状态聚合。
**优先后者**，避免全局 DOM 观察。

**视觉无缝（可选增强，P1 再做）**：隐藏前 `const img = await view.webContents.capturePage()`（V13 已证实存在），
把截图作为 `hostBox` 背景；恢复时再切回真视图。

### 5.3 备份白名单（**必须精确，V6/V8 实测得出**）

| 目录 | 备份 | 理由 |
| --- | --- | --- |
| `Local Storage` | ✅ | 存档主载体之一 |
| `Session Storage` | ✅ | 部分卡依赖会话态 |
| `IndexedDB` | ✅（**缺失时跳过，不报错**） | 存档主载体；V8 证实可能不存在 |

| `Local State` / `Preferences` | ⚠️ 可选 | 建议不备份（含全局偏好，恢复会串） |
| `Cache` / `Code Cache` / `GPUCache` | ❌ | 纯缓存，体积大且无意义 |
| `DawnGraphiteCache` / `DawnWebGPUCache` | ❌ | GPU 缓存 |
| `blob_storage` | ⚠️ P2 再定 | 卡若存图片 blob 则需要；体积未知 |
| `Shared Dictionary` / `DIPS` | ❌ | 浏览器内部状态 |

### 5.4 leveldb 文件处理（V7 实测）

```text
复制时：跳过 LOCK          （锁文件，必须跳过）
保留：  CURRENT           （指向当前 MANIFEST，缺了库打不开）
保留：  MANIFEST-*        （元数据）
保留：  LOG / LOG.old     （可保留，体积小）
保留：  *.log / *.ldb     （数据文件）
```

> v2.1 只写了"跳过 LOCK"，**未强调 `CURRENT` 与 `MANIFEST` 不可丢**。这是 v2.1 的潜在缺陷，v3 已明确。

## 六、备份系统

### 6.1 三种触发

| 类型 | 时机 | 默认 |
| --- | --- | --- |
| 自动 · 退出前 | 软件关闭 | ✅ 开 |
| 自动 · 定时 | 游玩期间每 N 分钟 | ✅ 30 分钟 |
| 手动 | 工具条 / 右键菜单 | — |

### 6.2 备份流程（修正版）

```text
① 前置：isWebviewMounted = false → 等待 view.webContents 的 'destroyed' 事件
      （不是固定 200ms / 300ms —— 固定延时不可靠）
② 主进程：await session.fromPartition(partition).flushStorageData()
      （可选补 cookies.flushStore()）
③ 目标：heavycard-backups/<cardId>/<stamp>_<kind>.part
      （用 .part 后缀，未完成即不可见）
④ 按 §5.3 白名单逐文件复制（复用 fullBackup.js 的遍历范式）
      · 跳过 LOCK
      · 单文件 EBUSY 重试 3 次（100ms 间隔），仍失败则记录并跳过该文件
      · 发送进度事件（文件数 / 字节数）
⑤ 写 _manifest.json（最后一步，含 cardId / url / gen / createdAt / kind / 文件清单 / 总字节）
⑥ rename <stamp>_<kind>.part → <stamp>_<kind>
⑦ 执行保留策略（永不删最后一份 manual）
⑧ 前端重新挂载 view
```

**原子性保证**：`_manifest.json` 最后写 + `.part` 未完成不暴露 ⇒ 即使进程被强杀，也不会产生"可被误认为有效"的半截备份。

### 6.3 恢复流程（世代轮换，免重启）

```text
① 先对当前状态做一次 kind = 'pre-restore' 的快照（防呆）
② 卸载当前 view
③ nextGen = card.gen + 1
   nextPartition = persist:heavycard-<id>_g<nextGen>
   targetDir = path.join(app.getPath('userData'), 'Partitions', `heavycard-<id>_g<nextGen>`)
   ⚠️【D2】此处**绝对禁止**调用 session.fromPartition(nextPartition) ——
      该调用会让 Chromium 立即初始化 Storage Service 并持有该目录，
      后续写入会与运行时状态冲突。（V10：纯拼接路径与 getStoragePath() 完全一致）
④ 纯文件操作：把备份内容 fs 拷到 targetDir（此刻 Chromium 100% 未触碰该目录，V11 已验）
⑤ 记录旧世代到 orphanPartitions，更新 card.gen / card.partition / storagePath
⑥ **拷贝完成后**才创建 WebContentsView({ webPreferences: { partition: nextPartition } })
   并用 getStoragePath() 校验路径与 targetDir 一致
⑦ 加载卡 URL；用户看到"已恢复到 <时间> 的存档"
```

### 6.4 旧世代清理（必须保守）

```text
启动期（app.whenReady 早期，任何 view 挂载前）：
  扫描 Partitions/ 下所有 heavycard-<id>_g<N>
  保留：
    · 任何卡当前使用的 gN
    · 任何卡当前 gN - 1（留一代回滚，防"恢复两次误删"）
  删除其余
```

> v2.1 说"删除所有不在活跃列表中的旧世代"，**在多世代快速切换时会误删刚回滚需要的目录**。v3 保留 `gN-1`。

### 6.5 退出前备份（修正 `Promise.race` 缺陷）

```js
let quittingAfterHeavyBackup = false;
app.on('before-quit', (event) => {
  if (quittingAfterHeavyBackup) return;
  const cards = getHeavyCardsNeedingExitBackup();
  if (!cards.length) return;

  event.preventDefault();
  Promise.race([
    runExitBackupsForHeavyCards(cards),          // 内部由原子性保证安全
    delay(15000)
  ]).finally(() => {
    quittingAfterHeavyBackup = true;
    app.quit();
  });
});
```

**关键认知**：超时**不取消**备份任务。所以安全性不来自超时，而来自 §6.2 的原子性 —— 超时后退出，最坏结果是"这次没备份成功"，**绝不会产生损坏的备份**。超时情况写入日志，下次启动提示"上次退出备份未完成"。

项目现状：`main.js` 目前**没有** `before-quit` 监听（仅第 4930 行有 `window-all-closed` → `app.quit()`），所以本项是纯新增，**无回归风险**。

## 七、安全设计

| 风险 | 措施 | 与 v2.1 差异 |
| --- | --- | --- |
| 卡内脚本读写文件 | 不注入 preload + `sandbox: true` + 不提供任何 Node 能力 | 同 |
| 渲染层创建被控容器 | **架构上不可能**（`WebContentsView` 只能主进程创建） | **优于 v2.1**（v2.1 需开 `webviewTag`） |
| 卡把软件导航走 | 该 view 的 `will-navigate` 只放行同源；无 top-navigation 能力 | 同 |
| 卡弹窗 | 该 view 的 `setWindowOpenHandler` 拦截 → `shell.openExternal`（仅 http/s） | 更精确（按 view 隔离，不影响主窗口） |
| CSP 冲突 | **无需改动主窗口 CSP**：`WebContentsView` 是独立 webContents，继承的是**该卡自己的响应头** | 与 v2.1 同（但 v2.1 的理由"iframe 被 CSP 拦"是错误归因，v3 不依赖此前提） |
| 卡偷偷外联 | 在线模式不拦；离线模式在该卡专属 session 上 `webRequest` 拦截 | 同 |
| 路径穿越 | 不提供本地目录加载（P2 若做，协议 handler 强制前缀校验） | 同 |

**主窗口改动量**：`createWindow` 仅需在 `createWindow` 返回后保留 `mainWindow` 引用供 `contentView` 使用 —— **`webPreferences` 一行不改**，安全基线零降级。

## 附录 A：关键技术决策速查

| 决策点 | 选择 | 依据 |
| --- | --- | --- |
| 容器 | **`WebContentsView`** | V1/V2 实测可用；零安全降级 |
| 排除 `iframe` | 无法独立 session | Electron 限制（同一 webContents 共用 session） |
| 排除 `<webview>` | 需开 `webviewTag`，官方 not recommended | 安全基线铁律 |
| 排除 `BrowserWindow` | 变成"另一个软件"，失去统一管理意义 | 产品定位 |
| 存储隔离 | 一卡一 `persist:heavycard-<id>_g<N>` | 同 origin 仍会串档 |
| 路径获取 | `session.getStoragePath()` | V3/V4 实测精确返回 |
| 备份格式 | 目录快照（逐文件，非 `cpSync`） | 项目无 zip 依赖；需进度与取消 |
| 备份原子性 | `.part` → manifest → rename | 防强杀产生半截备份 |
| 恢复 | 世代轮换 `gN+1` | V5/V7：leveldb 锁不可释放 |
| 退出备份 | `preventDefault` + 15 秒 + 原子性兜底 | `Promise.race` 不能取消任务 |

| 7 | `Network/Cookies` 复制报 `EBUSY` | Chromium 持有 Cookie 句柄，`flushStorageData` 不释放 | 重试 4 次（10/40/120ms 退避）+ 标注为「可忽略」降级 |

#### 已知限制

- `Cookies` / `Cookies-journal` 在卡正处于打开状态时可能复制失败（警告里带 `[可忽略]` 前缀）。影响仅为「恢复后需重新登录站点」，不影响存档本体。

### E.5 定时自动备份（2026-10-18 补齐）

**实现**：`useHeavyCards.js` 中的 `startAutoBackupTimer` / `stopAutoBackupTimer` / `applyAutoBackupSettings`。

设计取舍（改动前先读）：

| 取舍 | 原因 |
| --- | --- |
| 用 `setTimeout` 链，**不用** `setInterval` | 备份耗时可能超过间隔；链式调度保证「上一次做完再排下一次」，不会堆积并发备份 |
| 只在「卡已打开 && 状态 `ready`」时计时 | `loading` / `error` 时备份无意义，且刷盘可能撞上正在写入的 leveldb |
| 每轮触发前**重新校验**卡 id / gen / 配置 | 期间可能已切卡、恢复（世代变化）、或用户改了设置 |
| 与手动备份互斥 | `heavyCardBackupBusy` 为 true 时跳过本轮，避免并发写同一目录 |

**UI**：备份面板顶部新增自动备份设置区（开关 / 关闭软件前 / 间隔 0·5·10·30·60 分钟 / 保留 3·5·10·20 份），改动即时生效（无需重开卡）。

**实测**：间隔设为 1 分钟后等待 70 秒 → 备份目录新增 `_auto` 快照 ✅（测试后已复位为用户默认 30 分钟 / 5 份）。

### E.6 P2 增强（2026-10-18 全部落地）

| 功能 | 实现要点 | 入口 |

| **📴 离线模式** | 每卡 `session.webRequest.onBeforeRequest` 拦截；只放行入口域名（含子域）+ 白名单；`app:` / `local-file:` / `ws:` 放行；被拦记录进环形缓冲（200 条） | 工具条「📴 离线」 |

| **😴 闲置隐藏** | 10 分钟无操作 → `setCardVisible(false)`；**不销毁**，点任意处瞬间恢复（不重载 2 MB） | 自动；覆盖层点击恢复 |

#### P2 关键设计约束

- **离线拦截按 session 装**：每卡独立 partition ⇒ 拦截器天然只影响这张卡，不会误伤主界面（这是 iframe 方案做不到的）
- **tar 而非 zip**：项目无 zip 依赖；`tar -a` 依赖系统 bsdtar 且中文路径易踩坑；自研 tar 只写不压缩，任何机器可自解
- **导入不直接覆盖**：迁移包里可能是另一台机器的存档，直接覆盖风险大 ⇒ 导入成"新快照"，由用户再确认恢复
- **闲置只隐藏不销毁**：销毁会丢失页面状态（未保存的命卷），隐藏则零成本恢复
