## 一、目标

给「配置备份 💾」与「单卡/单书/单预设快照（`userData/jsTavern_Backups`）」之上，补一层**整库级冷备**：

- 一键把**当前库的整个目录树**（含子文件夹）冷备到用户指定目录（可指向备份盘）；
- 保留最近 N 份自动轮转，可浏览 / 恢复 / 删除；
- 恢复采用**改名 + 复制**策略（当前库先改名保留，防呆），全程可追溯。

典型场景：改一批卡/世界书前先冷备；换机/迁移前全量导出；误操作后整体回滚。

## 二、现状与缺口

| 层 | 现有能力 | 粒度 | 缺口 |
| --- | --- | --- | --- |
| 配置备份 | 💾 备份配置 / 恢复配置（`app_config.json`） | 配置 | — |
| 内容快照 | 保存前自动快照 + 手动快照（`jsTavern_Backups/{cards?,worldbooks,presets}`，`snapshotConfig` 轮转） | **单文件级** | 无「整库时间点」 |
| 回收站 | `jsTavern_Trash`（`trashFiles`，目录亦可） | 单次操作 | — |
| 冷备 | **本次新增** | **整库级** | — |

## 三、设计

### 3.1 主进程 IPC（`main.js`，命名沿用现有风格）

| 通道 | 入参 | 出参 | 说明 |
| --- | --- | --- | --- |
| `backup:full:create` | `{ libraryPath, destRoot, keep, label? }` | `{ ok, backupDir, fileCount, bytes }` | 全量复制 + manifest + 轮转 |
| `backup:full:list` | `{ destRoot }` | `{ items: [{ dir, name, createdAt, fileCount, bytes, libraryPath, appVersion }] }` | 扫描 `_manifest.json` |
| `backup:full:restore` | `{ backupDir, libraryPath }` | `{ ok, safeCopyPath }` | 改名 + 复制回 |
| `backup:full:delete` | `{ backupDir }` | `{ ok }` | 走 `shell.trashItem`（支持目录） |
| `backup:full:progress` | （事件） | `{ phase, done, total, bytesDone, bytesTotal }` | 仿 `onScanProgress` 的流式事件 |

### 3.2 目录布局与 manifest

```text
<destRoot>/
  JSK-FullBackup/
    <库文件夹名>__20261003-1530/
      _manifest.json          ← 元数据（唯一权威，list 只认它）
      <库目录树…>             ← 库里原样复制（含子文件夹）
```

`_manifest.json` 字段（v1）：

```json
{
  "schema": 1,
  "appVersion": "2.3.5",
  "libraryPath": "E:\\AI\\酒馆工具\\角色卡",
  "createdAt": "2026-10-03T15:30:00.000Z",
  "fileCount": 102,
  "bytes": 12345678,
  "files": [{ "rel": "sub/a.png", "size": 123, "mtimeMs": 1700000000000 }]
}
```

- **复制实现**：**逐文件循环**（不用 `fs.cp` 整树静默）——便于发进度事件、可取消、可跳过噪音文件。
- **排除规则**：隐藏目录（`.` 开头，与扫描口径一致）、`*.tmp`、回收站目录（实现时按实际名核实，如库内 `.trash`）。

### 3.3 轮转与防呆

- 保留份数 `keep`（默认 **3**，范围 1~10）；超出时**最旧**一份走 `shell.trashItem`（不是硬删）。
- 防呆（全部在**主进程**校验，不信任渲染层）：
  1. `destRoot` 不能是库目录自身或库内子目录（`path.relative` 检查）；
  2. 目标盘可用空间 < `bytes × 1.2` → 阻断并回报（`fs.statfs`，Node ≥18.15 提供）；
  3. 同一时刻只允许一个备份任务（主进程内存标志）；
  4. 备份进行中禁止触发恢复。

### 3.4 恢复策略（安全优先）

1. 选一份备份 → 校验 `_manifest.json` 可读、`fileCount > 0`；
2. 当前库**原地改名**为 `<库名>_恢复前_<时间戳>`（同盘 rename，秒级、零拷贝，失败即中止）；
3. 把备份内容复制为原库名路径；
4. 刷新扫描（`rescanLibrary`），提示：「已恢复。旧库体保留在 `<安全副本路径>`，确认无误后可自行删除（或点按钮移入回收站）」。
5. 恢复完成前**不删**任何备份（幂等可重试）。

## 四、验收口径

1. **真实库**（77 张）：冷备 → 临时改一张卡 → 恢复 → 卡内容回滚、`_恢复前_` 副本存在；
2. **大库**（11k 压测库，只读场景）：冷备中途进度事件连续、可取消（取消后无半成品残留或半成品被清理）；轮转正确（第 4 份出现时最旧一份进回收站）；
3. 空间不足 / 目录嵌套 / 并发触发 → 三个防呆均有明确错误提示；
4. 冷备目录配置持久化：重启后恢复；
5. 单测：manifest 生成与解析、排除规则、轮转选择（纯函数抽取后覆盖）。

## 五、风险与注意事项

- **还原是写操作**：联调与验收一律**用隔离副本库**，严禁对真实库执行恢复演练；
- Windows 长路径：库深目录 + 冷备路径叠加可能超 260 字符，复制失败要给出「路径过长」的明确提示（不是泛化 IO 错误）；
- 大库冷备耗时/体积大——UI 必须显示进度与预估剩余（按 bytesDone/bytesTotal），并允许取消；
- 与「启动自动任务」联动：自动冷备复用本通道（见 [`启动自动任务-实现规格.md`](启动自动任务-实现规格.md)），需接受「同一时刻仅一个任务」标志的约束；
- 不引入 zip 依赖（项目无打包库）：v1 为目录直拷；如需 zip 压缩包另开决策（Compress-Archive / 引依赖都要单独拍板）。
