# 🧹 查重 · 批量清理与规则化勾选 · 可执行方案（v1，待评审）

> **问题**：查重结果窗口现在只有「每组点一次『保留此版，清理其余』」。
> 真实库能扫出上千组重复，等于上千次点击 + 上千个原生确认框，且批量过程中容易报错、报错也说不清是哪几个文件。
> **目标**：在同一个窗口里用「勾选规则 + 组级勾选 + 一键清理选中」把上千组一次做完，
> 并且**每一步都可预演、可中止、可追溯、失败项可重试**。

```text
└─────────────────────────────────────────────────────────────────────────┘
```

要点：

1. **两段式**：先「👁 预演」（纯只读，零写入）→ 看清「删哪些 / 留哪些 / 跳过哪些及原因」→ 再「🧹 清理选中」。
2. **组级勾选**：每组标题左侧新增复选框（默认勾选 = 参与批量），单组的「保留此版」按钮保留不动 —— 想精细时仍可单组处理。
3. **保留单选 + 范围多选**：保留策略互斥单选；处理范围多选；三者组合即生成删除清单。
4. **默认安全档**：只有「L0 内容完全一致」默认勾选；`high` / `nameonly` 必须用户显式勾，且确认框追加红字警告。

## 三、规则语义（`buildBatchPlan` 纯函数口径）

### 3.1 保留策略（每组留谁，单选）

| 代号 | 名称 | 判定 |
| --- | --- | --- |
| `center` | 👑 推荐版（默认） | 取 `group.cards[0]`（簇心，与界面「👑 综合最优推荐」完全同源） |
| `tokens` | 📝 Token 最多 | `_tokens` 降序；并列回退 `center` |
| `newest` | 🕒 修改时间最新 | `_dateStr` 降序；并列回退 `center` |
| `clean-name` | 📄 文件名最干净 | 无 `(1)` / `_copy_` / `_移动_数字` / 纯时间戳 后缀者优先，并列回退 `center` |
| `size` | 💾 文件最大 | `_sizeKb` 降序；并列回退 `center` |

> 所有策略都必须**保证组内至少留 1 张**：策略算不出来时一律回退 `center`。

### 3.2 处理范围（多选，决定哪些组进清单）

| 代号 | 名称 | 默认 | 说明 |
| --- | --- | --- | --- |
| `exact` | ✅ 内容完全一致（L0） | ✅ 勾 | `group.type === 'duplicate'` 且 `level === 0`，最安全 |
| `similar` | ⚠️ 高度相似（L1/L2） | ⬜ 不勾 | `group.type === 'high'` |
| `nameonly` | ⚠️ 仅名称相同 | ⬜ 不勾 | `group._nameOnly`，内容与推荐版无关 |

### 3.3 保护闸门（默认全开；`keep-one` 不可关闭）

| 代号 | 名称 | 行为 |
| --- | --- | --- |
| `keep-one` | 每组必留 1 张 | **硬闸门**，任何策略都不得把一组删空 |
| `skip-open` | 跳过已打开/编辑中的卡 | 该卡在 `keep-one` 之外时**整组跳过**（避免删掉正在编辑的文件） |
| `skip-outside` | 跳过不在库内的卡 | 预检剔除（`isPathAllowed` 口径由主进程把关，渲染层先用 `libraryPath` 前缀预判） |
| `skip-empty-group` | 成员 < 2 的组不处理 | 硬闸门 |

### 3.4 输出结构（`dedupeBatch.js`）

```js
buildBatchPlan(groups, {
  keepBy: 'center',                 // 3.1
  scopes: { exact: true, similar: false, nameonly: false },  // 3.2
  guards: { skipOpen: true, skipOutside: true },
  maxGroups: 500, maxFiles: 2000,   // 单次上限（超出分批）
  isOpenCardPath: (p) => boolean,
  libraryPath: 'E:\\AI\\酒馆工具\\角色卡'
})
// → {
//   deletions: [{ path, groupIndex, groupName, keepPath, why }],
//   keepList:  [{ groupIndex, groupName, keepPath, keepName }],
//   skipGroups:[{ groupIndex, groupName, reason }],   // 仅同名 / 高风险 / 已打开 / 不在库内 / 未勾选范围
//   stats: { groups, files, bytes, skipByReason: {…} }
// }
```

理由字符串固定枚举（便于统计与测试）：`范围未勾选` / `仅名称相同` / `已打开卡片` / `不在库目录内` / `成员不足` / `已达单次上限`。

## 四、执行流程（`useDedupe` 新增三个方法）

```text
previewDedupeBatch(opts)          // 只读：调 buildBatchPlan，写 dedupeBatchPlan ref，UI 出摘要
      ↓ 用户确认（原生 confirmDialog，含数量/体积/前 5 个示例；含 nameonly/similar 时追加红字二次确认）
executeDedupeBatch(opts)          // 分批 trashFiles(200/批) → 汇总 failed[]
      ↓ 每批后 await 让出主线程（进度可刷新、可中止）
applyTrashedPaths(kind, trashed, failed)   // 一次性内存同步（替代现在"每组一次"）
      ↓
      ├─ 组数据同步：全删净的组移除，有残留的只剔已删项
      ├─ cleanupEmptyCategories() / 世界书/预设对应清理（**整批只跑 1 次**）
      └─ 写批量清单（userData/dedupe_batch_last.json：时间 / 策略 / 删除路径 / 失败原因）
```

### 4.1 关键改动（相对现状）

| # | 改动 | 原因 |
| --- | --- | --- |
| 1 | `trashFiles` 由「每组一次」改为「每 200 个一次」 | 1000 组 → 约 10 次 IPC，而不是 1000 次 |
| 2 | `library.value.filter` 由「每组一次」改为「整批一次」 | 每次替换整库都会触发全库 computed 重算（大库会卡死） |
| 3 | `cleanupEmptyCategories` 整批只跑 1 次 | 同上 |
| 4 | 新增 `dedupeBatchAbort` | 上千组执行要能中途停（已完成的不回退，剩余保留在清单里） |
| 5 | 失败项结构化保留（`{path, groupName, error}`） | 支撑「重试失败项」，不再一句 alert 了事 |

## 五、「会报错」的归因与治理

| 可能原因 | 现状表现 | 本方案对策 |
| --- | --- | --- |
| 路径不在授权白名单（库换过盘 / 配置迁移） | 整批可能全失败，只弹一句「清理失败」 | 预演阶段就按 `libraryPath` 预判并**单列**「不在库目录内」；执行期仍以主进程 `failed[]` 为最终依据 |
| 文件被占用（EBUSY / EPERM） | 混在总失败里 | 主进程对 `EBUSY/EPERM/EACCES/DELETE_PENDING` **退避重试 2 次**（120ms）；仍失败则按原因单列 + 「↻ 重试失败项」 |
| 文件已不存在（被手动删/移动） | 计入失败，看起来像"报错"，且条目永远留在列表 | 逐项展示原因；**全部失败原因都是「文件不存在」**时追问「是否从列表移除失效条目」（`removeGhostEntries`，只动列表不动磁盘）；批量面板另有「🧹 移除失效条目」按钮 |
| 组数据被重扫刷新 → 下标错位 | 可能删错组 | 批量计划**按路径 + 组 id 固化**，不使用 `groupIndex` 作为唯一依据；执行前校验 `group.id` 仍存在 |
| 一次删太多触发 UI 卡顿/假死 | 用户以为"报错" | 分批 + 每批让出主线程 + 进度条 + 可中止 |

> **DF-33 教训（2026-11-15 用户反馈截图）**：`sys:trashFiles` 的 `success:false` **只代表「一个都没删成」**，
> 真实原因在 `failed[]{path,error}`。前端读 `res.error`（该场景恒空）⇒ 一律显示「未知错误」，把三类原因全吞掉。
> 现在的契约：**任何清理失败都必须逐项说出「哪个文件 + 什么原因」**，并给出可操作建议。

## 九、风险与不做的事

- **不新增删除通道**：一律走 `sys:trashFiles`（白名单 + 分项失败 + 回收站），不写 `fs.unlink` 直删。
- **不改聚类与判定阈值**（`dedupeGates.js` / `dedupeCluster.js` 一行不动）：本方案只做"怎么批量执行"，不重新定义"谁是重复"。
- **不静默删任何组**：每组的删除都会体现在预演清单与批量日志里。
- 最大风险 = 误把 `nameonly` / L1-L2 当重复删掉 → 默认不勾 + 红字二次确认 + 回收站可捞。

**实现期微调（与 §四 的差异）**：

1. **批量清单不落盘**：`userData/dedupe_batch_last.json` 未做（需新增 IPC），改为「日志 + 失败清单可复制（📋 复制清单）」；落盘留到 P5 与「一键撤销」一起做。
2. **新增 `retryDedupeBatchFailures`**：对上一轮失败路径单独重跑，不必重新生成计划。
3. **`excludeIds` 双写**（组 id + 下标）：组有 id 用 id，重扫后下标漂移也不会错删。
4. **失败原因分布**：执行完的原生提示按「文件被占用 / 其他错误」聚合，不再只报一个总数。
5. **DF-33 补强（用户反馈截图驱动）**：
   - 单组与批量都**逐项**展示 `failed[]{path,error}`（列 8 条 + 其余计数），并按原因给可操作建议
     （不存在 → 重扫；被占用 → 关预览/杀毒后重试；越界 → 重新授权目录）；
   - 新增 `removeGhostEntries` / `purgeDedupeBatchMissing`：**只从列表移除**磁盘上已不存在的失效条目（不动磁盘），
     批量失败面板出现「🧹 移除失效条目（N）」按钮；
6. **AR-80（用户实测「四个窗口预演按钮全灰」）**：
   - `executeDedupeBatch` 改 `try/finally`：异常 / 中止 / 超时都**必解锁** `exec.running`，并同步失败清单；
   - 每批 IPC **30 秒超时**（`withTimeout`，超时按整批失败记账后继续下一批）；
   - 「⏹ 中止」2 秒后强制复位；「👁 预演」是只读操作，**不再受 `running` 限制**；
   - 预演点击后**toast + 日志**反馈（同规则二次预演不再是「没反应」）；
   - 四个弹窗的组块加 `v-memo="[group, excludedGroups]"`：预演/进度更新不再重画上千组列表。
