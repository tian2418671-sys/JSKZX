## 二、落码前的 3 处微调建议（可直接吸收，无需二次评审）

在进入 Phase 0 接线前，针对代码细节做最后几处严谨对齐，防止编码阶段踩坑：

### 1. 语料统计挖掘的“单字主干”防过度剥离（§4.3）

- **现象**：如果全库有大量类似《鬼 1.0》、《鬼 状态栏版》、《鬼 终极版》或者《龙 A》、《龙 B》，主干会被识别为单字（`鬼`、`龙`）。此时若某些卡名叫《鬼王》、《龙神》，可能会被误当成“主干 `鬼` + 尾缀 `王`”。
- **补丁策略**：在语料统计抽取尾缀时，增加约束：**“只有当剩余主干长度 ≥ 2 个字符时，才允许登记/剥离统计尾缀”**。单字主干强制不参与尾缀剥离，统一交由【内容轨】与【keys 轨】兜底判定，彻底消除中文字词误切。

### 2. MinHash-96 采样维度的初始化种子（§5.1 & §12）

- 建议将 96 个固定的 FNV-1a 哈希种子直接以 `const MINHASH_SEEDS = new Uint32Array([...])` 常量数组形式硬编码在 `js/utils/simhash64.js` 或专门的特征工具中，避免运行时动态循环生成素数引发的潜在随机数/浮点漂移，确保跨进程、跨轮次计算的严格幂等（TC-SYS-02 两轮一致性要求）。

### 3. 瘦身卡正文读回的并发压制（§3.1）

- 卡片全量态虽然需要读回正文（`ensureFullBody`），但在处理超大卡库（11k 张卡，其中可能 9k 张处于瘦身态）时，不要使用 `Promise.all` 全量并发唤起 IPC。
- 建议沿用旧实现的**滑动窗口分批（Chunking）机制**：每批次处理 50~100 张卡，读回、算完指纹并释放内存正文后，再进行下一批，防止渲染进程内存暴涨至 1GB+ 触发 Chromium 堆警告。
