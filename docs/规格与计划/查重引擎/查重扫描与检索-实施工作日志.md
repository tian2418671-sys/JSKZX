## 一、Phase 1（P0 止崩 + 词条级对齐）

### 1.1 动工前的取证结论（决定方案怎么改）

| 发现 | 影响 |
|---|---|
| `diffText: null` + 模板直读 `.masterLines` | **崩溃根因**：`isSame === false` 时必崩，词条数相同才不崩（解释了"有的书能开有的崩"） |
| `path` 裸 `split` | 次要崩点，`path` 缺失时同样抛错 |

| `mapB` 用 Map + Set 会漏渲染 | 重复 `comment` 时两条 A 配同一条 B，B 侧另一条永不渲染 → 条数对不上 |

## 二、Phase 2（扫描闸门 + 检索准确性）

### 2.1 检索准确性（PK-18）—— 优先级最高，先做

**问题本质**：索引对 CJK 按单字建 token，所以「系统」在索引路径下退化为「含『系』**且**含『统』」的单字 AND，
把正文「体**系** 传**统**」的卡误命中；而旧代码的短语校验条件是 `... && searchIndex.cardCount === 0` —— **索引一就绪整条被跳过**。

| 改造点 | 说明 |
|---|---|
| **就绪判定** | `cardCount > 0 && !building && cardCount >= library.length`（替代裸 `cardCount > 0`）→ 杜绝「构建中/覆盖不足」漏卡 |
| **查空回落** | 索引返回空不再 `|| []` 硬空，回落内存匹配 |
| **候选集短语复核** | 新增 `needPhraseCheck`，索引路径下**对候选集**复算文本做 `includes`；同卡文本用 Map 缓存避免多关键词重复复算 |

> 代价有界 —— 只对候选集复算，照抄 `excludeKeywords` 分支的既有范式；**不需要 bigram、不涨索引体积**。

### 2.2 扫描闸门分级 + 缓存自愈（DF-18）

**问题本质**：旧写法 `if (st.size > 5 * 1024 * 1024) return;` 是**静默丢弃**（无日志 / 无 UI / 不进统计）；
且 512KB 头部预检未命中会写 `cache = { valid: false }` → **误杀被永久固化**，修了逻辑也不自愈。

| 改造点 | 说明 |
|---|---|
| **分级常量** | `SCAN_INLINE_MAX_BYTES = 5MB` / `SCAN_PARSE_MAX_BYTES = 50MB` / `SCAN_HEAVY_CONCURRENCY = 3` / `SCAN_CACHE_VERSION = 2` |
| **分级处理** | ≤5MB 常规（32 并发内联）/ 5~50MB 低并发（3）/ >50MB 不 parse 只回元数据 |
| **元数据** | 结果补 `size / mtime / entryCount / heavy / dataLoaded` |
| **跳过可见化** | 返回体新增 `skipped: [{path, size, reason}]`；渲染层 `reportSkipped` 落日志（计数 + 文件名 + 原因） |
| **缓存自愈** | 预检未命中改写 `valid: null`（不固化否定）；`scanCache` 加版本号，升版即整体失效 |
| **两侧同改** | **世界书 + 预设**（`preset:scan` 是同一段写法、同一个 cache） |
| **懒加载** | `wbEntryCount` / `selectWorldbook` / `ensureWorldbookLoaded`；侧栏 `heavy && !dataLoaded` 显示「按需」徽标 |

> ⚠️ **为什么不能一刀切 50MB**：`wb:scan` 是 32 路并发 `Promise.all` 且每任务 `readFile + JSON.parse`，
> 50MB × 32 会把 OOM 从渲染进程**搬到主进程**（主进程崩 = 整体消失）。分级 + 大文件降并发才安全。

## 三、踩坑与返工记录（过程信息，供下次避雷）

### 3.1 生产构建剥离 `__vueParentComponent`（Phase 1 踩到）

**现象**：生产模式（`vite build` 产物）下 CDP 里找不到 Vue 组件实例，`app._instance` 为 `undefined`，`__vueParentComponent` 也不存在。

**结论**：**UI 级断言必须在 dev 模式下做**（`VITE_DEV_SERVER_URL` + Vite dev server），
从 `#app` 下的 `el.__vueParentComponent.setupState` 取应用真实实例（键数 > 500 的那个是根组件）。

### 3.2 CDP 内 `import('vue')` 失败（Phase 2 踩到）

**现象**：`Failed to resolve module specifier 'vue'` —— 裸模块说明符在 CDP 的 `import()` 里解析不了。

**结论**：不要试图在 CDP 里重建应用实例；**从 `setupState` 取应用已有的实例**（含 `library` / `filteredLibrary` 等）。

### 3.3 主进程改动必须重启 Electron 实例（Phase 2 踩到）

**现象**：改完 `main.js` 后跑冒烟仍失败，`heavy` 字段值还是旧的。

**结论**：主进程代码**不走 Vite 热更新**，改完必须杀掉实例重启（渲染层改动才热更）。

### 3.4 `heavy` 字段语义混淆（**被端到端断言当场抓出**）

**初版写法**：`heavy: !inlineData` —— 语义错位（`inlineData` 是"是否走内联路径"，不是"是否大文件"）
→ 6MB 书被标记 `heavy: false`。

**修正**：`heavy: st.size > SCAN_INLINE_MAX_BYTES`。随后顺手简化了 `handleOne(fullPath, inlineData)` 签名
（`inlineData` 已无用，留着会误导）。

> 💡 **教训**：布尔参数的语义要与字段名一致；`!inlineData` 这种"间接推导"极易写错，直接用原始判据（size）最稳。

### 3.5 测试的等价实现漏了实现细节（**被测试自己抓出**）

**现象**：`test/scanGate.test.mjs` 的 `loadCacheEquivalent` 初版直接 `return { __v, worldbook: {}, preset: {} }`，
漏了 main.js 里「先版本判定、再补齐分支」的顺序 → 「缓存结构补齐」用例失败。

**修正**：等价实现按 main.js 的真实顺序重写。

> 💡 **意义**：这说明这组测试**确实在约束实现**，而不是走过场。

### 3.6 测试有效性反向验证（主动做的一次）

**做法**：临时把 `needPhraseCheck` 置为 `false`（回退成旧逻辑），重跑 `searchPhrase.test.mjs`。

**结果**：多词 AND 用例从 `['卡A']` 变成 `['卡A','卡C']`（卡C = 「体系 传统 监控」）→ **失败**。

**结论**：**证明该用例确实能抓到 PK-18**，不是"测了个不会崩的场景"。随后恢复修复代码。
