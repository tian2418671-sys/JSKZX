## 一、目标 / 非目标 / 衡量标准

### 1.1 目标

1. 角色卡 / 世界书 / 预设三库查重全部可用（四入口 + 三合一分发保持现状 UI 契约）。
2. **改名同源可召回**（内容轨）；**版本家族可召回**（名字形状 + 内容轨分工）。
3. 结果可解释：每个组、每个成员给出「证据级别 + 相似度 + 建议」；高风险一律降级提示。
4. 清理安全：回收站 + 文件名清单 + 二次确认 + 部分失败如实呈现。
5. 算法通用：零案例字面量；阈值全部来自标定表（§13）。

### 1.2 非目标（本版不做，防范围蔓延）

- 繁简全量映射（不做任何繁简转换；理由与影响见 §16）。
- 图连通分量 / 标签传播聚类（PK-29 病根，沿用「星型 + 簇心回归校验」）。
- 句级对齐（09-24 实测只能改善 1 条词条 = 0.02%，已否决）。
- Python / 原生二进制 / 向量服务（零原生依赖约束）。
- 昵称/拼音/emoji 的专用规则（由名字形状与语料统计自然覆盖，出不来就如实漏报）。

### 1.3 衡量标准（验收时逐条实测，真实库口径）

| 指标 | 目标 | 口径 |
| --- | --- | --- |
| 四入口冒烟 | 全部可开、结果可渲染、无控制台错误 | 真实库 + 隔离 profile |

### 1.4 评审问答：为什么是“重构判定层”，而不是“在旧代码上改造”？

> **问题背景**：旧实现（含单文件 211KB 的 `useDedupe.js`，共 59 个文件）已于 2026-09-25 整体删除，备份可完整恢复（`%USERPROFILE%\jsk-dedupe-backup-20260925\`，含 `working-tree.patch`）。评审自然会问：为何不恢复后原地修？

**结论（先给答案）**：就本项目的实测历史与缺陷分布——

1. **「接口/工程契约层沿用 + 判定与分组层重写」（本 v4）成功率最高**；
2. 「在旧实现上打补丁」次之，且**大概率复发**（已有 4 天连续修复仍复发的实证）；
3. 「全部从零重写（含 UI 与契约）」成功率低于 v4（接口需重新摸索，试错面大）。

#### 依据一：旧缺陷的主体是“架构性”的，不是“局部 bug”

（缺陷全表见[查重-全量资料汇编.md](查重-全量资料汇编.md) §五）

| 缺陷群（合计 35 条） | 数量 | 形态 | 打补丁能消除吗 |
| --- | --- | --- | --- |
| AR 架构与 UI（AR-39~52） | 13 | 名字驱动分组 / 展示与判定脱钩 / 静默降级 / 进度多源 | ❌ 病根在「判定-分组-展示」架构里，补丁只能逐例防 |
| DF 数据与口径（DF-17~26） | 10 | 字段层级 / 多套相似度 / DF 两字段 / trim 不一致 | ❌ 口径不统一时修一处漏一处（实测反复复发） |
| PK 性能与内存（PK-18~32） | 12 | 全量两两比对 / OOM / 索引失效 | ⚠️ 个别可修，但分散在旧结构各处 |

#### 依据二：“改造路线”的失败已被本项目自己验证过

- 时间线：09-21 启动全链路修复 → 09-23/24/25 仍在修（AR-49/50/51/52、PK-31/32…）→ 09-25 用户判定「推倒重来」。
- 用户原话（汇编 §六）：「已经多次修复问题依旧存在」「算了让你改BUG越改越多」。
- 即：改造路线的真实成功率已用 **4 天连续修复 + 35 条缺陷 + 停不下来** 验证过——这不是概率预测，是实测结果。

#### 依据三：v4 的“重构”不是从零（复用面清单）

| 层 | 处置 | 证据 |
| --- | --- | --- |
| UI 六弹窗 + 三合一切换 | **沿用**（不动） | 组件保留；入口调用不变（§11.3） |
| 清理 / 进度 / 差异机制 | **沿用**（按备份恢复） | 备份 L802 / L530 / L1581（§10 / §9.4） |
| L1 基础设施（keys / simhash / exact） | **沿用**（单一实现） | main.js:1093-1400（§12） |
| 数据契约（三库形态 / 瘦身卡） | **沿用**（补降级上报） | 现壳 + 备份注入清单（§3 / §11.1） |
| 判定与分组算法 | **重写** | §4~§8（新增纯函数模块，可独立测试） |

⇒ 工作量集中在「最需要重写的那一层」；**不需要重新摸索接口**（32 项注入、四弹窗契约、清理流程全部有源码与备份对表）——这是“改造派的复用”与“重构派的正确性”兼得。

#### 依据四：成功率差异的量化视图

| 维度 | 旧实现打补丁 | **v4（契约层沿用 + 判定层重写）** | 全部重写（含 UI/契约） |
| --- | --- | --- | --- |
| 架构匹配 | 低（病根不动） | **高** | 高 |
| 遗留债承接 | 全额承接（59 文件） | 只承接契约层 | 无（但重新试错） |
| 回归风险 | 高（修复 A 看见 B，实测） | **中**（标注集 + 守卫 + 契约测试抵扣） | 中高（接口重新摸索） |
| 测试与验收 | 难（无标注集） | **易（先立标注集与守卫）** | 易 |
| 评审可验证性 | 低（“改了哪 35 处”说不清） | **高（G1~G8 对照 + 源码索引）** | 高 |
| 预计复发概率 | 高 | **低** | 低-中 |
| 首版交付成本 | 低（表面） | 中（P0~P2 计划见 §15） | 高 |

**兜底（若评审强制要求先改造旧实现）**——必须先行 3 个架构级前置，否则无效：

1. 分组从「名字驱动」改为「证据驱动」；
2. 相似度/打分收敛为**单一口径**（展示 = 判定）；
3. 静默降级全部改为上报。

完成这三项后，改动已覆盖旧实现核心——与「重写判定层」等价，只是多背 59 个文件的历史包袱。这就是 v4 选择「重构判定层、保留契约层」的根因。

## 三、数据契约层（三库统一归一化）

### 3.1 角色卡

- **数据源**：App.vue 的 `library`（当前库数组）。条目字段按现状：`path / name / data / dateStr / sizeKb / tokens / avatar / tags`（DedupeModal 消费 `customTags`、DiffModal 消费 `avatar`、`fileNameOf` 取 `path`）。
- **正文取法**：`const base = cardItem.data?.data || cardItem.data`（DF-17 口径，v3.1 已修对，沿用）。
- **瘦身态**：大库（≥3000 张）正文可能已被 `cardSlim` 移出内存 → **必须先读回再算指纹**：走 `isSlim/ensureFullBody`（备份 L30-60 段注明 AR-50 第五项：查重口径与内存状态解耦；用完交还，收尾后由 App.vue 补跑瘦身，§11.4）。**读回必须分批（滑动窗口，每批 50~100 张：读回 → 算指纹 → 立即交还 → 下一批）**——禁止全量 `Promise.all` 并发触发 IPC（评审微调 #3；P0 实现取 `CHUNK_SIZE=64`），防渲染进程内存 1GB+ 触发 Chromium 堆警告。
- **字段池（全字段，用于文本与 DF）**：
  `description / personality / scenario / first_mes / mes_example / system_prompt / post_history_instructions / creator_notes` + `alternate_greetings[]` + `character_book.entries[].content`（内嵌书正文）+ 内嵌书键 `entries[].key | entries[].keys`（**两形态都读**，备份 L530段 `e.key` 优先、`e.keys` 回退——DF-19 教训）。
- **三个派生指纹**（每张卡一次计算，供全流程复用）：
  1. `fullText`（上列字段池拼接）→ `fullMinHash`（96 维，§5.1）、`fullSig`（simhash，§12）。
  2. `coreText`（5 字段：description/personality/scenario/first_mes/mes_example）→ `coreSig`（simhash）。
  3. `keyHashes`（内嵌书键 → 规范化 → FNV-1a 32 → 升序去重 Uint32Array，cap 2000）。
- **exact 直通**：`exactTextHash` = `fnv1a64(fullText)`（双 32 位 FNV-1a；跨进程口径见 §12）。

### 3.2 世界书（**只读 L1，永不重读正文**）

- **数据源**：App.vue 的 `worldbooks`；条目字段：`path / wbName / entryCount / size / mtime / keyHashes / exactContentHash / simhash`（main.js 落盘；`simhash` 受 `WB_STORE_SIMHASH` 开关控制）。
- **归一化**：直接复用既有三个注入函数（**不得重定义**）：
  - `hasKeyIndex(wb)` —— 无索引 → 该本进入 `degraded='L1_INDEX_NOT_READY'`（**不得填 `[0,0]`**；v3.1 已修对，沿用）。
  - `compareKeyHashes(a, b)` —— 返回 `{jaccard, inter, union} | null`（`useWorldbooks.js:112-142`；null = 缺少索引，**不得静默当 0**）。
  - `isExactSame(a, b)` —— `exactContentHash` 相等（`useWorldbooks.js:144`）。
- **显示字段**：`wbEntryCount(wb)` / `wbDisplayName(wb)`（PK-26 轻量字段，`data` 可能为 null）。
- **正文语义**：世界书查重**不读 L2 正文**（PK-27 成果）；内容证据只有 `simhash`（预筛）+ `exactContentHash`（直通）+ keys（精确）。已知限制见 §16。

### 3.3 预设

- **数据源**：App.vue 的 `presets`；条目 `{ path, name, data }`；结构字段：`data.prompts`（**数组 / 字典双形态**）+ `data.prompt_order` + 采样参数（`temperature / max_tokens / max_context / rep_pen / top_p / top_k / min_p / openai_model` —— DiffModal 预设分支字段，DiffModal.vue:295+）。
- **派生结构**（通用统计维度，非案例规则）：
  - `identifierSeq`（prompts 的 `identifier || name`，**保序**）；
  - `identifierSet`（去重排序）；
  - `enabledRatio`（`prompt_order` 中启用条目数 / 总条目数）；
  - `sampler`（上列参数向量）。
- **文本指纹**：`contentText` = 各 prompt `content` 拼接（用于 MinHash，与卡片同轨）。

### 3.4 降级与上报（**如实，绝不静默**）

契约对象统一带 `degraded: { code, detail } | null`。**管线必须对每个 degraded 条目记录到 `skippedRecords`，并在完成提示与日志中呈现**（数量 + 理由分布 + 前若干样例名）：

| code | 触发 | 上报文案示例 |
| --- | --- | --- |
| `EMPTY_DATA` | 卡片 `data` 为空 | 「3 张卡缺少数据，已跳过（样例：xxx）」 |

## 四、名字层（G1 / G2）：形状规则 + 语料统计，**零案例词**

### 4.1 规范化（纯函数，可单测）

```text
normName(s) = NFKC → lower → 去 [\s\p{P}\p{S}] → trim
```

- **不做繁简映射**（见 §16-3）；不做拼音；不做 Unicode 近似折叠。
- 输出仅用于比较与统计，**不用于清理判定**（名字永不单独决定分组/清理）。

### 4.2 形状规则（**只描述形状，不枚举词汇**）

对名字做「可剥离段」检测，全部为**形状**（正则描述字符构成，不含具体词）：

| 形状 | 正则（示意，实现时固化） | 例（形状级） |
| --- | --- | --- |
| 数字版本 | `(?:^\|[\s_\-])v?\d+(?:[.\-]\d+)*[a-z]?(?=$\|[\s_\-])` | `xxx 2.2`、`xxx v1.0b` |
| 括号副本 | `\(\d+\)$`、`（\d+）$` | `xxx (1)` |
| 时间戳 | `[_\-]?\d{4}[-_]?\d{2}[-_]?\d{2}(?:[T_\-]\d{2,6}Z?)?$` | `xxx_20250925` |
| 长数字尾 | `[_\-]\d{6,}$` | `xxx_2025092501` |
| 拉丁副本词形状 | 前缀 `[_\- ]` + `(?:copy\|backup\|bak\|old\|new)` + `(?:[_\-\d]+)?$` | `xxx copy`、`xxx_old` |
| 独立附加段 | 名字主体后的 `[_\-][A-Za-z0-9]{2,12}$`（**候选级，须过 §4.3 语料检验**） | `xxx-CDN` |

**使用方式**：剥离后得 `stem`；`stem` 等值 → 名字轨候选（§5.3）。
**注意**：`状态栏版 / 终极版 / 重置版` 这类**语义修饰词不属于形状**——它们由 §4.3 语料统计决定是否剥离（跨主干出现才剥；只在单一家族出现则**不剥**，交给内容轨——**这正是“不针对案例打补丁”的落点**）。

### 4.3 语料统计（数据驱动发现「可剥离修饰词」）

对全库名字（三库合流后的当前库）：

1. 先做 §4.2 形状剥离 → `stem0`；再对 `stem0` 切「主段 + 尾缀」：尾缀 = 末尾连续的中文 1~4 字 or 拉丁 1~12 字符（不跨标点）。
2. 统计：`tailFrequency[tail] = 出现该尾缀的**不同主干数**`（主干 = 去掉尾缀后的名字）。
3. **判定**：`tailFrequency[tail] ≥ K_tail` 且 `尾缀长度 ≥ 2` → 该尾缀进入「本库可剥离修饰词集」（**运行时从当前库发现，不落盘、不写死**）。
4. 应用：名字比较与名字轨候选使用 `stemFinal = stem0 去尾缀（若尾缀在集合中）`；`_nameOnly` 等展示文案里注明「已剥离修饰词：xx（全库 N 个主干共用）」。

**单字主干保护（评审微调 #1，已吸收）**：仅当剩余主干长度 ≥ 2 字符时，才允许登记/剥离统计尾缀；单字主干（如「鬼」「龙」）强制不参与尾缀剥离，统一交由内容轨 / keys 轨兜底——消除「鬼王 → 鬼+王」类中文字词误切。

初始 `K_tail = 3`（**启发式，待标定**：§13）；标定方法：11k 库对其扫描，人工抽检 50 个尾缀判定，调节至误剥 ≤ 1/50。
**守卫**：静态检查禁止 `dedupe*` 模块源码出现任何示例卡名/书名/预设名（§14.2）。

### 4.4 名字相似度（仅候选与展示用）

```text
nameSim(a, b) = 1                     若 stemFinal 互相包含
              = LCS(a,b) / min(len)   否则（>0 的最小证据）
```

**用途**：① 名字轨候选（§5.3）；② 判定层否决②的输入（§6.2）；③ 展示（「名似 0.5」）。**不单独决定分组与清理**。

### 4.5 「3 字 vs 4 字」版本家族如何被召回（评审点名场景）

- `唐清露 2.2版 ↔ 唐清露 2.0版`：形状剥离数字版号 → `stemFinal` 相同 → **名字轨**直配候选；判定仍走证据（§6）。
- `鬼 1.1版 ↔ 鬼 1.2版`：形状剥离后 `鬼`（1 字）——**1 字主干不做尾缀/前缀统计**（防过度剥离），靠内容轨召回。
- `艾莎终极版 ↔ 艾莎状态栏版`：若「终极/状态栏」两类尾缀在全库跨主干常见（K_tail 达标）→ 剥离后命中名字轨；否则 → **内容轨**（内嵌书 keys / MinHash）兜底。
- 结论：**名字轨负责“同主干换皮”，内容轨负责“改主干甚至改名”**；两者缺一不可（v3.1 缺内容轨 → 改名同源漏报的根因）。

## 五、候选层（G3）：三轨 + 桶上限 + 抽样 + **上报**

> 总约束：任何“跳过/丢弃”必须进 `report.notices`（含轨道名、桶键样例、跳过数量），完成时汇总输出。**禁止静默**。

### 5.1 内容轨（卡片 / 预设）：MinHash-96 + 分带 LSH

**签名**（每项一次）：

```text
shingles = Set of 4-gram（对 normText：NFKC→lower→去空白，保持字符序）
sampled  = 按序每 4 个取 1（step=4）
sig[96]  = min over sampled of( h_i(shingle) )   // h_i：fnv1a32(shingle, seed_i)；seed_i 为**硬编码常量数组**（`MINHASH_SEEDS`，见 §12；评审微调 #2）
```

- **先去重（Set）再采样**——修复 v3.1 的最大性能点（其实现为逐字符位置 ×96 维）。
- `normText` 为空或 <20 字符 → 该项 `degraded='NO_TEXT'`。

**LSH 分带**：`b=16 band × r=6 row`（96 维恰好 16×6）。碰撞概率 `P(s)=1-(1-s⁶)¹⁶`（s=0.85 → 99.95%；s=0.70 → 86.7%）——0.85（本判定门）近全召回，参数与推导一并入 §13 表。
**桶键**：6 个 32 位值转 16 进制串接（**字符串键，零碰撞**；不用数值混合——会造假候选）。
**桶深**：>200 → **按入库序保留前 200 + `report.notices` 记录**（“桶 X 深 1234，已抽样 200，可能漏召”）。<2 的桶忽略。

### 5.2 keys 轨（卡片 / 世界书）

- 卡片：`keyHashes`（cap 2000，§3.1）取**前 30 个最小 hash** 建倒排；每条倒排链（bucket）深度 >100 → 跳过 + 上报（高频泛用词特征）。
- 世界书：`keyHashes` 同法（来自 L1）。
- 世界书另加 **simhash 分桶**：64 位取高 16 位做粗桶，邻桶（±1）同查（避免边界漏配）——**仅生成候选，不判定**。

### 5.3 名字轨（三库）

- `stemFinal`（§4.2/4.3）的 **char-2gram** 倒排（不用“前缀 slice”——旧实现的前 2/3 字符切片是拍脑袋，弃用）。
- 倒排桶深 >200 → 上报；生成候选时要求 `nameSim ≥ 0.5` 才入列（桶只是粗筛）。

### 5.4 合并与工程上限

- 三轨合并去重（`i<j` 规范键）；总候选数打印与上报。
- **上限保护**：若候选对 > 500,000 → 按轨道轮转抽样（各轨保底采样）并**显式上报“候选超限已抽样”**（宁可明说，不可悄悄吞）。
- 判定阶段逐对 `await yield`（`setTimeout 0` 每 200 对）保持 UI 响应；进度按 §9.4。

### 5.5 世界书特殊路径（**不读正文**）

- 有 `exactContentHash` 相等 → L0 直通（无需其他信号）。
- 其余走 keys 轨 + simhash 粗桶候选 → 判定层用 exact keys Jaccard 精确量（§6.3）。
- **无 `keyHashes` 也无 `simhash`** → 该本 `degraded='L1_INDEX_NOT_READY'` 上报。

## 六、判定层（G4）：证据分级 + 否决族 + 同名家族

### 6.1 证据分级（**判定只用被命中的最高级证据**）

| 级 | 证据 | 适用 | 通过条件（见 §13 标定表） |
| --- | --- | --- | --- |
| **L0** | `exactTextHash` / `exactContentHash` 相等 | 三库 | 直接通过（`_simPct=100`，`_simType='duplicate'`） |
| **L1** | keys 精确 Jaccard（世界书用 `compareKeyHashes`；卡片用 `keyHashes` 双指针） | 卡片/世界书 | `≥ KEYS_PASS=0.90`（与旧定稿一致） |
| **L2** | MinHash 相似度（96 维匹配率） | 卡片/预设 | `≥ CONTENT_PASS=0.85` |
| **L3** | simhash 汉明距离 | **仅分桶/预筛**（世界书粗桶、卡片粗筛）；**永不单独定夺** | —（不产出通过） |

- `_simPct` = **最强命中证据的百分比**（L0=100；L1=keys×100；L2=MinHash×100）。
- **长度惩罚不混入百分比**：`lenPenalty = 0.7 + 0.3 × min/max`（字符数；世界书用 `entryCount` 并在展示标注口径）**只用于排序与「长度 ×0.78」类独立徽标**（弹窗字段 `_lenPenalty`）。⇒ 从机制上消灭「19% 却同组」。

### 6.2 否决族（每一条都有**前提**与**反例回归样本**）

按顺序执行，命中即不出组（产出 `reason` 计入统计）：

| # | 否决 | 条件（全部满足才否决） | 前提/反例（回归样本） |
| --- | --- | --- | --- |
| ① | 触发词严重矛盾 | 两侧 `keyCount ≥ 2` 且 `keyJaccard < KEYS_CONFLICT=0.05` | 样本：`（淫力）斗罗大陆 ↔ 斗罗淫师`（实测 0.15%） |
| ② | 共用世界书但不同角色 | `keyJaccard ≥ 0.50` 且 `nameSim < 0.30` 且 `hamming(coreSig) > CORE_DIFF=24` | 样本：`神里绫华 ↔ 纳西妲`（共用设定书）；**反例**：同名家族不适用（nameSim=1 不进此条） |
| ③ | 全字段/5 字段分歧 | **仅当任一侧内嵌词条数 = 0**（前提！）且 `fullSim / coreSim < RATIO_DIVERGE=0.40`（simhash 相似度） | 反例：`作为贵族管家… ↔ 作为管家…`（比值 0.17 但真同源）——**有前提才不会误杀**（v3.1 缺此前提，回归案例保留在测试集） |
| — | TYPE 不同 | 库类型不同 | 结构性防呆 |

### 6.3 世界书判定（无 MinHash 的替代路径）

1. L0：`isExactSame` → 直通。
2. L1：`compareKeyHashes(a,b)`（或注入函数）→ `jaccard ≥ KEYS_PASS` → 通过；`jaccard === null`（缺索引）→ 该对跳过并计入 degraded 上报。
3. 否则不通过。**simhash 只用于把对带进这条路径，不产出分数**（废除 v3.1 的 `(16-d)/16×0.3+0.7` 映射）。

### 6.4 分数与建议（展示同源）

```text
_simPct   = 最强命中证据百分比（§6.1）
_simType  = 由证据级别与补充判据生成（§9.3 枚举表，与弹窗 isRisky 白名单一一对应）
_simAdvice / _pctAdvice / _pctBadge = 由 _simPct 走同一张分档表产出（单一来源）
recommend 排序键 = (证据级别 desc, _simPct desc, lenPenalty desc, path asc)  // 确定性
```

### 6.5 同名家族通道（G7 / AR-48）

- 输入：`normName`（§4.1，**不含形状剥离**——精确同名）相同但**未通过任何证据级**的对。
- 产出：进入卡片/世界书的**同名家族组**（`_nameOnly=true`、`_nameOnlyDist = hamming(coreSig)` 或世界书「键交集为空」判据）。
- 展示与保护：
  - DedupeModal / WbDedupeModal 的 `_nameOnly` 分支/按钮降级（现有 UI 已实现，仅需字段）；
  - 清理确认框**必带警示**（沿用备份 L802-812 / L1160-1167 的文案结构：列前 5 个文件名 + “建议先对比再清理”）；
  - **不进“安全清理”语义**：`resolve*` 检测到 `_nameOnly` 组时，确认框文案含「⚠️ 仅同名」段落（防误删，与旧实现同口径）。

## 七、分组层：星型 + 簇心（确定性、无传递）

### 7.1 构图与顺序

- 输入：判定通过的边集合 `edges = [{a, b, level, simPct, type}]`。
- **确定性排序**：`(level desc, simPct desc, min(pathA,pathB) asc)`——保证跨轮一致（红线：大库口径跨轮一致）。
- 聚合（与 PK-29 教训对齐，**禁止连通分量**）：
  1. 双方均未入组 → 新组；中心 = 推荐键更高者（§6.4）。
  2. 仅一侧入组 → **与中心重算** `evaluateGate(center, 新成员)`：通过才加入；不通过 → `crossNotices:'判定通过但与中心不符，未合组'`。
  3. 两侧在不同组 → **不合并**（记录 crossNotices；合并需全员重校验，本版不做，如实提示）。
- **中心升迁**：新成员推荐键高于中心 → 与**全体成员**回归校验全通过才升迁（沿用 A7 修法）；任一失败放弃升迁并记录。

### 7.2 组元数据（数字必须诚实）

- `minScore = 组内所有边的最小 simPct`，**每次加成员后更新**（v3.1 病点：不更新 ⇒ 字段名撒谎）。
- `type / advice / _pctAdvice / _pctBadge` 一律从 §6.4 同源产出；组内排序：推荐版在 **index 0**（弹窗契约：`group.cards[0]` / `group.list[0]` 即推荐版）。

### 7.3 字段文案（沿用旧文案档）

- DedupeModal `_diffType`：由字数差产出（'推荐版 / 可能包含更多设定 / 设定可能有缺失 / 设定细节不同 / 设定完全一致'，备份 L763-770 同款档位）。
- WbDedupeModal `_diffInfo`：按组证据产出（如 `🧬 指纹 × ｜ 🔑 触发词 92%`）——数字与 §6.4 同源。
- 任何字段不得出现“与 `_simPct` 不同源”的数字（单一来源红线）。

## 十二、simhash 单源化（口径一致性）

- 现状：`main.js:1345-1400` 的 `computeSimhash64 / simhashInputOf` 是世界书 L1 落盘的**权威实现**；旧卡片查重是渲染层自算（本就是两套；v3.1 又造了第三套——“对齐口径”实为第三口径）。

- 常量锁死：`FNV_OFFSET=0x811c9dc5`、`FNV_PRIME=0x01000193`、双流同序（**非逆序**）、4-gram、`step=4`——全部写进 parity 测试断言（防未来“优化”跑偏）。
- **`MINHASH_SEEDS`（96 项）为硬编码常量数组**（评审微调 #2，已吸收）——不在运行时动态循环生成，保证跨进程、跨轮次幂等（两轮一致性验收项）；同样锁进 parity / 一致性测试。
- `WB_STORE_SIMHASH` 开关语义不变（默认关）；卡片侧 `fullSig / coreSig` 由渲染层调用同一模块计算。
