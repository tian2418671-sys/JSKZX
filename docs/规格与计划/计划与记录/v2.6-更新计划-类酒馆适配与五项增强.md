## 一、现状与约束

### 1.1 当前只有「一种酒馆」——写死在代码里

识别逻辑全部集中在 `js/utils/stInstallCore.js`，且**硬编码 SillyTavern**：

| 位置 | 现状 | 问题 |
| --- | --- | --- |
| `ST_MARKERS` | 固定 6 项：`server.js` / `package.json` / `public` / `src` / `data` / `config.yaml` | 换一个 fork 微调目录就识别不到 |
| `detectSillyTavern()` | `packageName === 'sillytavern'` 视为高置信 | fork 改了 `name` 就直接漏判 |
| `isStRootStrict()` | 只认 `name === 'sillytavern'` 或 `server.js + public` | 全盘扫描时最严格，同样只认一种形态 |
| `countStData()` | 统计 `data/` 下的 cards / worldbooks / chats | fork 若改数据布局（如多用户/多 profile）会统计为 0 |
| `checkUpdate()` | `git ls-remote https://github.com/SillyTavern/SillyTavern` | fork 的版本号与官方对不上，升级提示会误报 |
| `startServer()` | 固定 `node server.js --port N` | 少数 fork 入口不是 `server.js` |

**结论**：`df-76 / df-77 / df-78` 那几个「统计恒为 0」「状态判定错误」的历史缺陷，本质都是**把一种项目的形态当成唯一真理**。加适配器层不是锦上添花，而是消除这一类缺陷的根因。

### 1.2 不能被破坏的东西（硬约束）

1. 现有 SillyTavern 用户的行为**逐字节不变** —— 识别、启动、统计、升级、体检结果全部保持一致；
2. 真实库口径不变 —— 本机 `E:\AI\SillyTavern`（v1.19.0，40 卡 / 108 世界书 / 170 会话 / 3.75 GB）与压测库 `I:\03\角色色卡`（11,849 张）统计值必须与改造前一致；
3. `build.files` 白名单机制不变（新增文件必须落在已通配的目录里）；
4. 不引入新的运行时依赖。

## 二、主线 A：类酒馆项目适配器

### 2.1 目标形态

把「酒馆」抽象成一个**可注册的适配器**，内核只认接口、不认具体项目。

```text
js/utils/tavernAdapters.js   ← 纯函数，零 IO，可单测
  ├─ ADAPTERS: TavernAdapter[]         内置适配器注册表
  ├─ matchAdapter(entries, pkg, opts)  → { adapter, confidence, hits }
  ├─ listAdapters()                    供 UI 展示
  └─ validateAdapter(custom)           校验用户自定义适配器

主进程（stManager.js）只负责：
  用 matchAdapter 判定 → 用 adapter.dataLayout 统计 → 用 adapter.entry/scripts 启动
```

### 2.2 适配器数据结构

```js
/**
 * @typedef {object} TavernAdapter
 * @property {string}   id           唯一标识，如 'sillytavern'
 * @property {string}   name         展示名，如 'SillyTavern'
 * @property {'builtin'|'custom'} kind
 * @property {object}   detect       识别规则
 * @property {string[]} detect.packageNames   命中即 high（大小写不敏感的正则源）
 * @property {string[]} detect.required       必须同时存在（如 ['server.js','public']）
 * @property {string[]} detect.anyOf          任选 2 个即 medium
 * @property {string}   entry        入口文件，默认 'server.js'
 * @property {string[]} startScripts 原版启动脚本候选，如 ['Start.bat','start.sh']
 * @property {number}   defaultPort  默认端口，默认 8000
 * @property {object}   dataLayout   数据子目录映射（相对 data/）
 * @property {string}   dataLayout.characters  默认 'default-user/characters'
 * @property {string}   dataLayout.worlds      默认 'default-user/worlds'
 * @property {string}   dataLayout.chats       默认 'default-user/chats'
 * @property {string}   dataLayout.groups      默认 'default-user/groups'
 * @property {string}   dataLayout.settings    默认 'default-user/settings.json'
 * @property {object}   [version]    版本来源
 * @property {'git'|'package'|'file'} version.source
 * @property {string}   [version.repo]   git 源，如 'SillyTavern/SillyTavern'
 * @property {RegExp}   [version.pattern] file 源时的匹配正则
 */
```

### 2.3 内置适配器（P1 交付）

| id | 名称 | 识别要点 | 数据布局 | 说明 |
| --- | --- | --- | --- | --- |
| `sillytavern` | SillyTavern（官方） | `name==='sillytavern'` 或 `server.js+public` | `default-user/*` | **现有行为原样保留** |
| `sillytavern-fork` | 酒馆衍生版（通用兜底） | 存在 `server.js` + `public/` 且 `config.yaml` 或 `data/` | 自动探测 `data/*/characters` | 覆盖汉化版 / 魔改版 / 私有分支 |
| `st-portable` | 便携版（免安装） | 目录内自带 `node.exe` + `server.js` | 同上 | 便携包常见形态 |

> **关键设计：`dataLayout` 要能自动探测而不是写死。**
> 官方是 `data/default-user/characters`，但多用户 fork 可能是 `data/<用户名>/characters`。
> 落地方式：先按声明路径找，找不到则**扫 `data/` 下一层目录**，命中 `characters` 的那层即为用户根。
> 这条规则同时解决历史上「世界书/会话统计恒为 0」的 `DF-76`。

### 2.4 自定义适配器（P2）

面向「小众 fork / 自建版本」，给用户一个表单：

| 字段 | 说明 | 必填 |
| --- | --- | --- |
| 名称 | 展示用 | ✅ |
| 识别特征 | 目录里必须存在的文件/文件夹（多选，至少 1 个） | ✅ |
| 入口文件 | 默认 `server.js` | ✅ |
| 默认端口 | 默认 8000 | ✅ |
| 数据目录 | characters / worlds / chats 相对路径 | 选填（留空则自动探测） |
| 版本来源 | git 仓库地址 或 package.json | 选填 |

存到 `app_config.json → tavern.adapters[]`，支持**导入 / 导出 JSON**（社区可互相分享）。

### 2.5 改动清单

| 文件 | 改动 | 风险 |
| --- | --- | --- |
| `js/utils/tavernAdapters.js` | **新增**（纯函数 + 注册表 + 校验） | 低 |
| `js/utils/stInstallCore.js` | `detectSillyTavern` / `isStRootStrict` 改为**委托给 `matchAdapter`**，保留同名导出（向后兼容） | 中 |
| `main/stManager.js` | `findStRoot` / `countStData` / `startServer` / `checkUpdate` 读取 `adapter.*` | 中 |
| `js/components/StInstallModal.vue` | 显示识别到的项目类型徽标 + 「⚙️ 适配器」入口 | 低 |
| `test/tavernAdapters.test.mjs` | **新增**，覆盖识别/布局探测/自定义校验 | 低 |

### 2.6 验收标准

1. **零回归**：SillyTavern 的识别结果、统计数字、启动参数、升级判断与 v2.5.0 **完全一致**（用真实库 `E:\AI\SillyTavern` 对比前后输出）；
2. 手工造 3 个假目录（改 name 的 fork、多用户布局、便携版）均能正确识别；
3. 自定义适配器导入导出往返一致；
4. 单测新增 ≥ 20 条，全量用例不减少。

### 2.7 明确不做

- ❌ **不兼容**数据格式完全不同的项目（RisuAI `.risum`、在线服务 Agnai/Chub）—— 那是另一套数据模型，硬套只会做出半成品；
- ❌ 不自动下载/安装第三方 fork（来源不可信）；
- ❌ 不改动 `app_config.json` 的既有字段结构（只**新增** `tavern.adapters`）。

## 三、附带建议项

> 下列五项按「对用户的实际价值 / 工作量」排序，建议 **B、C** 进 v2.6，其余看排期。

### 三-B：常驻资源治理 ⭐ 建议优先

#### 痛点（实测依据：2026-11-15 现场采样）

| 进程 | CPU | 内存 |
| --- | --- | --- |
| 本软件 · 某渲染进程 | **13.3%** | **481 MB** |
| 本软件 · 主进程 | 3.1% | 196 MB |
| 酒馆（node） | 0.8% | 237 MB |

系统内存已用 **71.4%**（31.7 GB 中只剩 9.1 GB）。也就是说：**挂机时软件比酒馆本身更吃资源**，这正是用户反馈「软件里启动酒馆后 AI 回复变慢」的真实原因之一（并非管道阻塞 —— 实测酒馆 HTTP 响应仍为 17 ms）。

#### 方案

1. **窗口不可见即降频**：`document.visibilityState === 'hidden'` 时暂停所有 `setInterval` 轮询、CSS 动画、ECharts 渲染；
2. **缩略图按需加载 + 内存上限**：大库（万级）只保留可视区附近的 `objectURL`，超限 LRU 回收；
3. **酒馆运行时让路**：检测到酒馆进程在跑，自动降低自身后台任务（扫描/缩略图/向量）的并发与优先级；
4. **资源面板**：设置里显示「本软件占用 vs 酒馆占用」，让用户自己看到差异。

**验收**：空闲 5 分钟平均 CPU < 1%，内存 < 250 MB。

**工作量**：中（3~5 天）

---

### 三-C：卡片分享包 `.jskpack` ⭐ 建议优先

**痛点**：把自己的调好的成品分享出去，现在要手动翻 4 个地方找文件：角色卡 PNG、它引用的世界书、卡内正则、配套预设/状态栏。少一个对方就跑不起来。

#### 方案

- **导出**：自动收集依赖闭包 → 打包成 `.jskpack`（zip + `manifest.json` 记录来源/版本/文件清单/SHA256）；
- **导入**：解析 manifest → 冲突检测（同名卡/同名世界书/正则 UID 冲突）→ 给出「跳过 / 覆盖 / 保留两份」三选；
- **完整性校验**：导入时校验 SHA256，损坏文件单独标红而不是整体失败。

**价值**：这是当前功能矩阵里**完全空缺**的一环，且是社区高频动作。

**工作量**：中（3~4 天，可复用现有 `fullBackup` 的打包与 `inventory` 的清单能力）

---

### 三-D：插件权限摘要（安全）

**痛点**：插件是能直接跑的 JS 脚本，可读本地文件、发网络请求。现在用户点「链接安装」时**完全不知道它会做什么**。

**方案**：静态扫描插件源码，产出一张「权限卡」：

| 检测项 | 说明 |
| --- | --- |
| 🌐 网络 | 出现 `fetch` / `XMLHttpRequest` / `WebSocket`，列出目标域名（能从字面量看出时） |
| 📁 文件 | 出现 `fs` / `require('path')` / `FileReader` |
| ⚙️ 进程 | 出现 `child_process` / `exec` —— **高危，默认红标** |
| 🔑 凭据 | 读取 `apiKey` / `token` / `localStorage` 的模式 |
| 📦 依赖 | 是否请求外部 CDN（离线环境会失效） |

只做**静态提示**，不阻止、不沙箱（沙箱会破坏插件生态兼容性）。

**工作量**：小~中（2 天）

---

### 三-E：酒馆换机迁移包

**痛点**：换电脑 / 重装系统时，要手工搬 `data/`、`config.yaml`、已装扩展列表，还容易漏。

**方案**：一键导出「酒馆完整状态包」（数据 + 配置 + 扩展清单 + 版本信息），新机一键还原并按清单重装扩展。

**与现有能力的边界**：`整库冷备` 是**本机快照**（回滚用），这个是**跨机器迁移**（带来源版本校验与目标环境检查）。

**工作量**：小（1~2 天，复用 `fullBackup` 的打包思路）

---

### 三-F：库健康报告（可导出 HTML）

**痛点**：库乱了不知道从哪下手 ——「我有 3000 张卡，但不知道哪些是坏的」。

**方案**：一键体检并生成可分享的 HTML 报告：重复卡（复用现有 simhash）、缺图/坏图、超大卡、无标签、孤立世界书（没有任何卡引用）、命名不规范、文件与索引不一致。每条都带**一键修复入口**（跳回对应界面并预置筛选）。

**工作量**：小（2 天，几乎都是现有能力的聚合）

## 五、风险与预案

| 风险 | 影响 | 预案 |
| --- | --- | --- |
| 适配器抽象改坏现有识别 | 老用户扫描不到酒馆（**严重**） | 改造前后用真实库跑同一份快照对比，数字必须逐项一致；`detectSillyTavern` 保留同名导出作为兼容层 |
| 自定义适配器被填错 | 识别到假酒馆 | 保存前用「试识别」按钮在真实目录验证一次，失败不给保存 |
| 资源治理改出「该刷新时不刷新」 | 数据不更新（**用户会当成 bug**） | 降频只针对「不可见/空闲」，任何用户交互立即恢复全速；加开关可关闭 |
| `.jskpack` 依赖收集不全 | 对方导入后仍跑不起来 | manifest 记录「未解析依赖」清单并在导出时明示，不假装完整 |

## 六、附：为什么不做「支持所有 AI 前端」

社区里常被提到但**明确不支持**的：

| 项目 | 不支持的原因 |
| --- | --- |
| RisuAI | 自有 `.risum` 二进制格式，与 PNG/JSON 卡体系不通用 |
| Agnai / Chub | 纯在线服务，没有本地库可管 |
| text-generation-webui / KoboldCpp | 是**推理后端**，不是角色卡前端，没有卡库概念 |

判断标准：**只要它遵循 `characters/*.png|json` + `worlds/*.json` 这套数据布局，就能用适配器接进来；否则不接。**
