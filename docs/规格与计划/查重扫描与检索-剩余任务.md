## 二、T2 · 真进度条（P2）—— ⚠️ 用户明确要求**不降级**

### 为什么不是「复用现成心跳范式」那么简单
规格原本设想「复用 `onScanProgress` 心跳范式」，但**角色卡那条链路本身是分多次 IPC 调用才推得动心跳**；
而 `wb:scan` 现状是**单次 IPC 一次性返回**，渲染层在 `await` 期间拿不到任何进度。

**所以真进度条 ≡ `wb:scan` 的 IPC 协议改造**，不能藏在别的任务里。

### 要做什么
1. **主进程**：把 `wb:scan` 的单次返回改成**分批推送**
   - 新增 `wb:scanStream`（或给现有通道加 `onProgress` 回调参数）：主进程按目录 / 批次推
     `{ phase: 'scanning'|'parsing', done, total, current }`；
   - 渲染层用 `window.electronAPI.onWbScanProgress(cb)` 接收（参考 `onScanProgress` 的既有实现）。
2. **渲染层**：世界书扫描 / 查重弹窗顶部渲染进度条 + 当前项名，平滑前推至 100%。

### 依赖与复用
- **依赖 T3（分级扫描）已落地** —— 分级天然把文件分成「常规 / 大文件」两批，可直接作为分批推送的粒度。
- 世界书扫描已有 `reportSkipped` 落日志，可与之共用同一条进度通道。

### 验收（对应最终方案 TC-07）
- 上百本世界书执行查重：有进度条 + 当前项名，平滑前推至 100%，结束有 Toast；期间窗口不白屏。

## 三、T3 · 拉丁前缀全表回退优化（PK-19，P1 速度）

### 问题本质（已实测定性）
`searchIndex._getMatches(keyword)` 先 `index.get(keyword)` 精确命中，**miss 时退化为遍历整个倒排表**：

```js
for (const [word, cards] of this.index) {
    if (word.includes(keyword)) matches.push(...cards);
}
```

- **中文按单字建 token** → 单字查询必精确命中（**不走这里**，实测 0~0.2ms）；
- **拉丁词是整词 token** → 用户输前缀（`syst`）时整词 `system` 命中不了 → **每次都全表扫**（实测 **19~36ms/次**，随 token 表线性增长）。

### 必须先实测（决定方案）
见 §四 #1。**不要在没实测前就选方案。**

### 候选方案（实测后择一）
| 方案 | 说明 | 风险 |
|---|---|---|
| (a) 前缀专用结构 | 建 `token → 前缀` 的有序结构做二分查找 | 索引体积与构建耗时上升，需压测 |
| (b) 首字母桶 + 桶内过滤 | 按 token 首字母分桶，只在桶内 `includes` | 只削减常数，不改变量级 |
| (c) 候选上限 + 提示 | 超过 N 张时截断并在 UI 标注「结果可能不完整」 | 会牺牲完整性，需用户可接受 |

> ⚠️ 已证否：`matches.push(...cards)` 的 `RangeError` **不成立** ——
> `_indexCardInto` 的 `buf.cards.has(card)` 幂等保证**单个桶大小 ≤ 卡数**，22k 库不可能触发展开上限。

### 验收（对应最终方案 TC-06）
- 万卡级库输入拉丁前缀（每敲一个字母）无可感知冻结；实测前后数字记入
  [`../技术支持/技术数据-大库压测与性能.md`](../技术支持/技术数据-大库压测与性能.md)。
