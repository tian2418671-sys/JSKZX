## 二、T2 · 真进度条（P2）—— ⚠️ 用户明确要求**不降级**

### 为什么不是「复用现成心跳范式」那么简单
规格原本设想「复用 `onScanProgress` 心跳范式」，但**角色卡那条链路本身是分多次 IPC 调用才推得动心跳**；
而 `wb:scan` 现状是**单次 IPC 一次性返回**，渲染层在 `await` 期间拿不到任何进度。

**所以真进度条 ≡ `wb:scan` 的 IPC 协议改造**，不能藏在别的任务里。

### 要做什么
1. **主进程**：把 `wb:scan` 的单次返回改成**分批推送**
   - 新增 `wb:scanStream`（或给现有通道加 `onProgress` 回调参数）：主进程按目录 / 批次推
     `{ phase: 'scanning'|'parsing', done, total, current }`；
   - 渲染层用 `window.electronAPI.onWbScanProgress(cb)` 接收（参考 `onScanProgress` 的既有实现）。
2. **渲染层**：世界书扫描 / 查重弹窗顶部渲染进度条 + 当前项名，平滑前推至 100%。

### 依赖与复用
- **依赖 T3（分级扫描）已落地** —— 分级天然把文件分成「常规 / 大文件」两批，可直接作为分批推送的粒度。
- 世界书扫描已有 `reportSkipped` 落日志，可与之共用同一条进度通道。

### 验收（对应最终方案 TC-07）
- 上百本世界书执行查重：有进度条 + 当前项名，平滑前推至 100%，结束有 Toast；期间窗口不白屏。

### ✅ 完成情况（2026-09-21）

**四步接线全部落地**（与角色卡 `onScanProgress` 是**两条独立通道**，因为世界书扫描是单次 IPC）：

## 三、T3 · 拉丁前缀全表回退优化（PK-19，P1 速度）

### 问题本质（已实测定性）
`searchIndex._getMatches(keyword)` 先 `index.get(keyword)` 精确命中，**miss 时退化为遍历整个倒排表**：

```js
for (const [word, cards] of this.index) {
    if (word.includes(keyword)) matches.push(...cards);
}
```

- **中文按单字建 token** → 单字查询必精确命中（**不走这里**，实测 0~0.2ms）；
- **拉丁词是整词 token** → 用户输前缀（`syst`）时整词 `system` 命中不了 → **每次都全表扫**（实测 **19~36ms/次**，随 token 表线性增长）。

### 必须先实测（决定方案）
见 §四 #1。**不要在没实测前就选方案。**

### 候选方案（实测后择一）
| 方案 | 说明 | 风险 |
|---|---|---|
| (a) 前缀专用结构 | 建 `token → 前缀` 的有序结构做二分查找 | 索引体积与构建耗时上升，需压测 |
| (b) 首字母桶 + 桶内过滤 | 按 token 首字母分桶，只在桶内 `includes` | 只削减常数，不改变量级 |
| (c) 候选上限 + 提示 | 超过 N 张时截断并在 UI 标注「结果可能不完整」 | 会牺牲完整性，需用户可接受 |

> ⚠️ 已证否：`matches.push(...cards)` 的 `RangeError` **不成立** ——
> `_indexCardInto` 的 `buf.cards.has(card)` 幂等保证**单个桶大小 ≤ 卡数**，22k 库不可能触发展开上限。

### 验收（对应最终方案 TC-06）
- 万卡级库输入拉丁前缀（每敲一个字母）无可感知冻结；实测前后数字记入
  [`../技术支持/技术数据-大库压测与性能.md`](../技术支持/技术数据-大库压测与性能.md)。

### ✅ 完成情况（2026-09-21）

**选型实测（`scripts/_probe-latin-prefix-options.mjs`，11k 卡 / 112 万 token）**——三方案对照，**正确性优先**：

| 方案 | 正确性 | 常见前缀耗时 | 内存 |
|---|---|---|---|
| (a) 有序数组 + 前缀二分区间 | ❌ **破坏子串语义**（`aster`/`yst`/`el` 结果与基线不一致） | 1.28ms | +8.6MB |
| (b) 首字母桶 + 桶内过滤 | ❌ **破坏子串语义** | 4.18ms | +18.5MB |
| **(c) bigram 桶 + 桶内精筛** | ✅ **20 个查询全部与基线逐条一致** | **0.54ms** | +18.9MB |

⇒ 采用 **(c)**：唯一不改变 `includes` 语义的方案，且比现状（全表扫 **19~44ms**）快 **20~70 倍**。
> ⚠️ (a)(b) 会让用户搜到**更少或更多**的卡 —— 属不可接受的回归，故即使更快/更省内存也不用。

**实现（`js/utils/searchIndex.js`）**：
- 新增 `_buildBigram()`（token 二元组 → token **下标** `Int32Array`；token 字符串不复制，直接引用 `index` 的 key），
  在 `_swap()` 换表时同步重建（与活跃表**严格同代**，绝不指向旧 token）。
- 重写 `_getMatches(keyword)`：精确命中 → 直通；否则取查询串里**最稀有**的 bigram 候选集做 `includes` 精筛；
  任一 bigram 桶不存在 → **精确剪枝**直接返回空。
- **降级保障（正确性优先，绝不返回错误结果）**：单字符查询（无 bigram 可用）/ `bigramDirty`（`add`/`remove` 后下标失效）/
  下标越界异常 → **一律回退全表扫**（只是慢，不会错）。
- **顺带修掉展开上限风险**：`_scanAllFor` 与精筛路径的 `push(...cards)` 改为**循环追加**
  （超大桶会触碰引擎参数个数上限 → `RangeError`）。
- `stats()` 增加 `bigramCount` / `bigramDirty`（可观测性）。

**防再犯（`test/latinPrefix.test.mjs`，10 条全绿）**：
把「结果必须与基线**逐条一致**」钉死 —— 含拉丁前缀逐字母、**词中片段**（`aster`/`yst`/`el`，正是 (a)(b) 会挂的用例）、
中文单字、无命中词、端到端 `search`（分词 + 交集语义）、`add`/`remove` 后降级正确性、
重建后恢复快路径、`clear()` 同生死、大桶不触发展开上限。
> 📌 写测试时踩过的坑（已记入测试文件注释）：`search(str)` 会**先分词再做 AND 交集**，
> 而 `_getMatches(kw)` 是 **token 级**函数 —— 对比必须在**同一层级**做，否则会得出「实现错了」的误判。

**T6 常规档**：`SCAN_JSON_BATCH` 维持 **32**（放大到 240 本 / 25.2MB 实测，拐点在 16~32；

> ⚠️ **探针踩坑（记录下来避免复现）**：T6 首版探针用 `readFileSync` + `Promise.all` 包同步函数 →
> async 函数体内无 `await`，body 同步跑完 → **实际是串行执行**，所有并发档耗时几乎相同（244~262ms），
> 数据「看起来很稳」但**完全没测到并发**。改用 `fs.promises.*` 后并发才真正生效。
> **教训：测并发必须确认被测函数真异步。**
