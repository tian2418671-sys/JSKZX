### 2.3 落盘链路（决定 P0-1 / P0-2 怎么接）

```text
wb:scan  →  main.js walk 深度递归（5MB 上限 / 512KB 头部预检）
            →  返回 [{ path, name, data }]  ← entries 全量内联
渲染层    →  useWorldbooks.scanWorldbookDir 归一化 entries（数组化）
保存      →  wb:save → stripInternalFields → 快照(backupWorldbookSnapshot) → 原子写(tmp+rename)
```

- `isPathAllowed` 白名单：`wb:scan` 通过指纹验证后 `addAllowedRoot(dirPath)`（`main.js:2546`）→ 本会话内可读写；**重启后白名单为空**（懒加载 / 直写 meta 都要处理这个前提）。
- 白名单安全模型曾修过两次越权（`main.js` 的注释明确写了「无条件 `addAllowedRoot` = 后门」）→ **新 IPC 不得**为了写 meta 就无脑扩权。

## 三、必须先拍板的 3 个决策点（不拍板不要动工）

### 决策 1 · 元数据的单一真相源（SSOT）放哪？

| 方案 | 优势 | 代价 |
|---|---|---|
| **A · 留在配置文件**（改现状：把 `wbCategoryMap` 补上 tags） | 零风险；不动用户文件；不产快照；不碰第三方格式 | 换机 / 库外复制**不随书走**；「双源漂移」问题**没解决**（方案 P0-1 的初衷） |
| **B · 写进世界书文件** `extensions.jskzx`（原方案） | 随书走，单源真相 | 每个 JSON 被改写；改标签 → 新快照；第三方工具/酒馆是否会保留未知扩展字段（**待实测**，见 §七） |
| **C · 文件为写入源 + 配置只读缓存**（推荐） | 兼顾；离线也能起界面 | 需要一次性迁移 + 冲突仲裁规则（首次扫描时文件优先还是配置优先） |

> 无论选哪个，**必须写迁移**：升级后若新逻辑只读 `extensions.jskzx`，存量用户的分组看起来会「全部消失」（数据还在 `wbCategoryMap` 里）。这是本次最高概率的升级事故。

### 决策 2 · 哨兵值怎么统一？

- 现状：`'全部'`（视图）/ `'默认'`（未分组默认名）。
- 原方案：`'__all__'` / `'__ungrouped__'` + `__` 前缀保留。
- 必须定：① 是否迁移到英文哨兵；② 存量用户自建的「全部」「默认」分组名如何处置（**改名** / **视为保留名** / **原样保留但加前缀区分**）。三者都要落成可执行规则，不能只拦新输入。

### 决策 3 · 标签存储口径：卡片 vs 世界书是否统一？

- 卡片：`customTags`（内存）+ 配置覆盖层落盘（`useCardCrud.js:223-257`），**不写进卡片文件**。
- 世界书（原方案）：写进文件。
- 若不统一，需在 `docs/bugs/` 与交接文档里明确记录「两套口径并存」的理由，避免后续被当成 bug 反复「修复」。
