### 2.2 P0-1：世界书差异查看必崩 —— 根因已定位

**现象**：查重结果里点「查看词条差异」，**词条数不同**的世界书打开即渲染报错。

**根因（两处叠加）**：

1. `useDedupe.js` 的「📚 世界书词条总数 (Entries Count)」字段构造为
   `isSame: entries1.length === entries2.length`，**且 `diffText: null`**。
2. `DiffModal.vue` 模板在 `isSame === false` 时走 `v-else` 分支，直接读 `f.diffText.masterLines` / `.compareLines`
   → `null.masterLines` → **TypeError（渲染期）**。

**推论（可用于验收）**：**词条数相同**的世界书**不会崩**（`isSame: true` 走「已自动折叠」文案分支）。这解释了「有的书能开、有的书一开就崩」。

**次要崩溃点**：`DiffModal.vue` 的 `masterItem.path.split(/[\\/]/).pop()` / `compareItem.path...` **未判空** —— `path` 缺失时同样崩。

### 2.3 P0-2：世界书差异看不到「哪个词条变了」+ `keyOf` 定稿

现状世界书比对只有三行，都无法回答「删了哪个词条」：

| 行 | 现状 | 局限 |
|---|---|---|
| 📚 词条总数 | 只比 `entries.length` | 差异不可展开（且见 §2.2 必崩） |
| 🔑 触发词池覆盖 | `key` 集合的交 / 差 | 只看 `key`，不看正文；`keysecondary` 未参与 |
| 📝 词条正文总集 | 把两侧全部词条正文拼成一条大字符串再做句级比对 | `computeTextDiffLines` 用 `Set` 判 same/added/removed，**不保留归属与顺序** → 只能看到「一大坨文本里某几句变红变绿」 |

**解法**：`alignEntryLists` 外连接对齐（Full Outer Join），把「不对称增删」表达成 `only-a` / `only-b` / `both` 三类。

**词条字段口径**（取证自 `useWorldbookExtras.js`、`useWorldbookEntries.js`、`App.vue`）：

- 独立世界书（库）：`uid` / `key`（数组） / `keysecondary`（数组） / `comment` / `content`
- 角色卡内嵌：`uid` / `keys` / `secondary_keys` / `comment` / `content`
- **没有 `name`**（`comment || name` 只是别处的兜底写法）

**`keyOf` 定稿（三级回退 + 带侧标识）**：

```js
// 对齐主键：能跨源稳定识别的只有「词条名 / 触发词指纹」，uid 只做同源加速
const norm = (v) => String(v == null ? '' : v).trim().toLowerCase();
const keyOf = (e, side, idx) => {
    if (!e || typeof e !== 'object') return `anon:${side}:${idx}`;   // 脏数据不参与配对（必须带侧标识）
    const label = norm(e.comment || e.name);
    if (label) return 'c:' + label;                                   // ① 词条名（最稳，跨源可用）
    const keys = Array.isArray(e.key) ? e.key : (Array.isArray(e.keys) ? e.keys : []);
    const fp = norm(keys.join('|'));
    if (fp) return 'k:' + fp;                                         // ② 触发词指纹
    return e.uid ? 'u:' + e.uid : `anon:${side}:${idx}`;             // ③ 最后才用 uid
};
```

**三个必须同时满足的约束**（少一个就会退化 / 误配）：

1. **带侧标识**：脏数据 key 必须带 `side`（`anon:a:3` / `anon:b:3`）。两侧共用下标会让 A 侧脏数据与 B 侧第 3 条**无关**脏数据配成 `both`，与"不参与配对"的目的正好相反。
2. **一对一配对**：`mapB` 必须是 `key → 数组 + 已消费标记`（或 key 追加出现序号）。同书内重复 `comment` / 重复 `key` 集合**现实存在**，若用 `Map` + `Set`：两条 A 会配到同一条 B，且 B 侧那一条永远不被渲染 → 两侧条数对不上，用户看到"漏了一条"。
3. **不认 `uid` 当主键**：`uid` 逐条随机生成（同源复制保留，但经「导入词条到角色卡」这类字段转换会**重新生成**）→ 拿 uid 当主键会把同一条词条判成「两侧各缺一条」。

> 若两侧都填写了 `comment` 但同一词条改了名，会显示成「一条缺失 + 一条新增」——这是**可接受且可解释**的结果（改名在语义上确实是删 + 增），**不要**为此加模糊匹配。

### 2.4 🟡 字典形态 `entries` 判定（顺手加固，不投入验收资源）

`openDiffDetailModal` 判定世界书用 `Array.isArray(masterItem.data.entries)`，而 `isValidWorldbook`（`main.js:2489`）**明确兼容** `entries` 为对象字典 `{"0":{...}}` 的 V2 老格式（DF-02）。

**复核结论：逻辑成立，但当前不是活路径**，不应排在 §2.2 之前：

- `isValidWorldbook` **第 3 步原地** `Object.values()` 归一化 → 返回的 `data.entries` **已经是数组**；
- 启动入口再洗一次；网址导入、文件夹导入也都洗过；
- 内容级查重的世界书源就是 `worldbooks.value`，进去的已全部是数组。

**建议**：加两行归一化防御不亏（防未来新增入口绕过清洗），定位是**顺手加固**，**不投入验收资源**，也不作为"更隐蔽的错"记账。

### 2.6 P1：关键词检索 —— 现状与真实短板（⚠️ 病根已实测改写）

**已经具备（不要再重写）**：倒排索引（分片构建 / 双缓冲 / 跨代沿用 / MessageChannel 让步）、索引接入搜索、300ms 输入防抖、多词 AND + `-` / `tag:` / `author:` / `file:` / `wb:` 语法、卡片级 try/catch 兜底。

**三条短板**：

- **短板 A · 漏卡（"明明有却搜不到"）**
  分流条件是 `searchIndex.cardCount > 0`，即「索引里有东西」就当成**完整索引**。索引**构建中 / 半建 / 刷新未收尾**的窗口里，候选集只有部分卡；只有 `cardCount === 0` 才回落到全量内存匹配。
  **落档口径**：改为「索引就绪 **且** 覆盖当前库」才走索引（`searchIndex.js` 已有 `building` / `cardCount` / `stats()` 可观测字段）。

- **短板 C · 索引查空即空列表**
  `useSearch.js` 的 `|| []`：索引查询返回空 → 候选集空 → **没有回落到内存匹配**，用户直接看到「0 结果」。

- **短板 B · 病根原判断有误，已实测改写（2026-09-21）**

  **❌ 错误的前档论断**：「中文双字词 `index.get('系统')` 必然 miss → `_getMatches` 退化为全表 `word.includes`」。
  **为什么错**：漏了 `search()` 的第一行 —— **查询字符串本身也会被 `_tokenize()` 拆开**，而 `_tokenize` 对 CJK 按**单字**切：
  `"系统"` → `['系','统']` → `index.get('系')` **精确命中**，**不触发全表扫描**。

  **实测**（5001 卡 / 150 万 token / 含一张文本为「体系 传统 经典文字」的卡）：

  | 查询 | 命中 | 耗时 | 走的路径 |
  |---|---|---|---|
  | `系统` / `体系` / `经典`（中文双字） | 1 | **0~0.2ms** | 单字桶精确求交 |
  | `syst` / `sys` / `st`（拉丁前缀） | 0 | **23~36ms** | **全表 `word.includes`** |
  | `e`（单字母） | 0 | 19.5ms | 同上 |
  | `false_positive_by_系统` | — | **true** | 文本「体系 传统」的卡被「系统」**误命中** |

  **修正后的两个真短板**：

  1. **慢**：**拉丁子串 / 前缀**才触发全表扫描。用户每敲一个字母扫一次全表，且 token 表越大越慢（实测 150 万 token 上 23~36ms/次，配合 300ms 防抖在万卡库上足以感到迟滞）。
  2. **不准（比慢更严重）**：索引就绪后**没有短语复核**，于是「系统」= 单字 AND → 命中「体系 传统」这类的卡。而且
     `useSearch.js` 的全文多词必含校验条件是 `... && searchIndex.cardCount === 0` —— **索引一就绪，短语校验整条被跳过**，
     同一句查询的结果在索引建好前后**不一致**。

  > ⚠️ 连带影响：**"仅展示同时命中两个词的条目"这个判据按现状必然失败**（TC-05）。

### 2.8 P2：进度反馈现状

- 查重的耗时**主要在两个地方**：主进程 `wb:scan` 的 I/O + `JSON.parse`（目录内 **32 路并发**，`SCAN_JSON_BATCH = 32`）与渲染层聚类。
- 世界书扫描**当前没有任何进度心跳**；角色卡扫描已有现成范式：主进程推 `onScanProgress`，渲染层 `window.electronAPI.onScanProgress(cb)`。
- 结论：进度应挂到**扫描阶段**，而不是原方案设想的「两两比对计数」；但**真进度条等价于 `wb:scan` 的 IPC 协议改造**（现状单次 IPC 一次性返回，await 期间渲染层拿不到心跳），见 §四 Phase 3 的降级口径。

## 四、分阶段实施

### Phase 1 · P0（差异查看不再崩 + 词条级对齐）

**S1-1 `alignEntryLists`（Full Outer Join，按 §2.3 定稿）**

```js
/**
 * 组级词条对齐：comment → key 指纹 → uid 三级回退 + 带侧标识 + 一对一配对
 * 目标：把「不对称增删」表达成 only-a / only-b / both 三类，规避大字符串拼接比对
 */
export function alignEntryLists(listA = [], listB = []) {
    // keyOf 见 §2.3 定稿；mapB 用「key → 数组 + 已消费标记」保证一对一
    const buckets = new Map();                       // key -> []
    listB.forEach((e, i) => {
        const k = keyOf(e, 'b', i);
        if (!buckets.has(k)) buckets.set(k, []);
        buckets.get(k).push({ entry: e, used: false });
    });
    const pairs = [];
    listA.forEach((a, i) => {                         // Pass 1：以 A 侧（推荐保留版）为主
        const k = keyOf(a, 'a', i);
        const bucket = buckets.get(k);
        const free = bucket && bucket.find(x => !x.used);
        if (free) { free.used = true; pairs.push({ side: 'both', a, b: free.entry, key: k }); }
        else pairs.push({ side: 'only-a', a, b: null, key: k });
    });
    listB.forEach((b, i) => {                         // Pass 2：收集 B 侧独有（未配对的 = 新增）
        const k = keyOf(b, 'b', i);
        const bucket = buckets.get(k) || [];
        if (bucket.some(x => !x.used)) {
            const free = bucket.find(x => !x.used);
            free.used = true;
            pairs.push({ side: 'only-b', a: null, b, key: k });
        }
    });
    return pairs;
}
```

**S1-2 单项安全清洗**：`prepareDiffPayload(entryA, entryB)` —— `name` 取 `comment || name || '未命名条目'`，`content` 强制 `String(...)`，`keys` 兼容 `key` / `keys` 数组与逗号串，并补 `keysecondary` / `secondary_keys` 兜底。

**S1-3 差异弹窗空值防御（崩溃的直接修复）**

**S1-4 新增词条级分支**

### Phase 2 · P1（大文件 + 检索）

**S2-1 闸门分级 + 跳过可见化（⚠️ 不要一刀切 50MB）**

`main.js` 提常量，替换写死的 5MB，**按文件大小分级**：

| 文件大小 | 处理方式 |
|---|---|
| ≤ 5MB | **维持现状**（内联 `data`）—— 绝大多数世界书在这一档，零行为变化 |
| 5MB ~ 50MB | 仍 `readFile`，但**降并发**（该档单独一个低并发批次，如 2~4 路，**不占用 32 并发**）；`data` 仍返回但标记 `heavy: true` |
| > 50MB | **不 parse**，只回 `size / mtime / entryCount`（大小用 stat 已知；`entryCount` 可轻量估或首次打开时才算），正文按需 `readText` |

**为什么必须分级**：`wb:scan` 是 **32 路并发** `Promise.all` 且每任务 `readFile` + `JSON.parse`。若一刀切 50MB 且 `entryCount` 仍在主进程算 → **50MB × 32 并发的 JSON.parse 直接打爆主进程**（主进程 OOM 是进程整体消失，比渲染进程崩溃更难看）。

超限时**不再静默 `return`**：记 `console.warn` + 汇总进返回值的 `skipped: [{ path, size, reason }]`；
渲染层把 `skipped.length > 0` 显示为「N 个文件因超过 50MB 被跳过」+ **可展开文件名**。

**S2-2 元数据**：`wb:scan` 结果补 `size`（`st.size`）/ `mtime`（`st.mtimeMs`）/ `entryCount`。

**S2-3 `scanCache` 误杀自愈（⚠️ 新增，必须与 S2-1 同批）**

修头部预检时必须同时让缓存自愈，否则用户机器上已有的误杀记录不会消失：

- 要么给 `scanCache` 加结构版本号使其失效；
- 要么把「头部预检未命中但不大于上限」的结果标成 `valid: null`（未知，下次仍重试），而不是 `valid: false`。

> 🔴 **预设侧 `preset:scan` 同款写法、同一个 cache** —— 只修世界书那一半，预设库的误杀依旧不自愈。**两侧一起改、一起测。**

**S2-4 检索改造**

```js
// ① 就绪判定：building 中或覆盖不足 → 回落内存匹配（杜绝漏卡）
const indexReady = searchIndex.cardCount > 0
    && !searchIndex.building
    && searchIndex.cardCount >= library.value.length;
// ② 查不到结果也要回落，不要 || [] 硬空
```

**S2-5 候选集短语复核（准确性修复，优先于速度）**

索引返回候选集后，**对候选集**（不是全表）复算文本做短语 `includes` 校验：

- 修的是**准确度**（「体系 传统」被「系统」命中、索引前后结果不一致）；
- 代价**有界且有先例** —— `excludeKeywords` 分支本来就是「只对候选集复算 `this._extractText(card)`」，照抄即可；
- **不需要 bigram、不需要常驻正文**，22k 卡库的堆压力不变；
- 落点：`useSearch.js` 第 7 步条件去掉 `&& searchIndex.cardCount === 0`（改为始终复核，但只对候选集）。

**S2-6 拉丁前缀（速度，优先级低于准确度）**：方案待 §七 #1 实测后定（候选上限 / 前缀专用结构）。

## 十一、Phase 2 落地记录（2026-09-21）

### 11.1 检索准确性（PK-18）—— 优先级最高，先做

| 文件 | 变更 |
|---|---|
| `js/composables/useSearch.js` | ① **就绪判定**：`cardCount > 0 && !building && cardCount >= library.length`（替代裸 `cardCount > 0`）；② **查空回落**：索引返回空不再 `|| []` 硬空，回落内存匹配；③ **候选集短语复核**：新增 `needPhraseCheck`，索引路径下**对候选集**复算文本做 `includes`（同卡文本 Map 缓存避免重复复算），并去掉第 7 步的 `&& searchIndex.cardCount === 0` |

> 代价有界 —— 只对候选集复算，照抄 `excludeKeywords` 分支的既有范式；**不需要 bigram、不涨索引体积**。

### 11.2 扫描闸门分级 + 缓存自愈（DF-18）

| 文件 | 变更 |
|---|---|
| `main.js` | ① 新增常量 `SCAN_INLINE_MAX_BYTES=5MB` / `SCAN_PARSE_MAX_BYTES=50MB` / `SCAN_HEAVY_CONCURRENCY=3` / `SCAN_CACHE_VERSION=2`；② **分级**：先 stat 再分「常规（32 并发）/ 大文件（3 并发）」两档，`>50MB` 不 parse 只回元数据；③ 结果补 `size / mtime / entryCount / heavy / dataLoaded`；④ 返回体新增 `skipped: [{path, size, reason}]`；⑤ **预检未命中改写 `valid: null`**（不再固化 `valid:false`）；⑥ **`scanCache` 加版本号**，升版即整体失效；⑦ **世界书 + 预设两侧同改** |
| `js/composables/useWorldbooks.js` | ① `reportSkipped`（计数 + 文件名入日志）；② `wbEntryCount`（未解析时用 `entryCount`）；③ `ensureWorldbookLoaded` / `selectWorldbook`（超大书点击时 `readText` 懒加载） |
| `js/composables/usePresets.js` | `reportSkipped`（预设侧同款） |
| `js/components/SidebarPanel.vue` | 词条数改用 `wbEntryCount`；点击改走 `selectWorldbook`；`heavy && !dataLoaded` 显示「按需」徽标 |
| `js/components/App.vue` | 按**四步约定**接入新方法（解构 / ctx 暴露 / 子组件可用） |

> ⚠️ **为什么不能一刀切 50MB**：`wb:scan` 是 32 路并发 `Promise.all` 且每任务 `readFile + JSON.parse`，
> 50MB × 32 会把 OOM 从渲染进程**搬到主进程**（主进程崩 = 整体消失）。分级 + 大文件降并发才安全。
