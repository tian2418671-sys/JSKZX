# v2 评审意见

## 一、总评

**v2 完成了从“方向正确的提案”到“数字可信的方案”的跃迁，可以进入拍板流程——但有三个问题需要在动工前修掉：一个顺序缺陷（simhash 参数依赖倒挂）、一个算法落地不精确（§6.1 第 2 步）、一个流程死胡同（oversized 书的查重处置）。** 其中 P0-2 如果不修，PK-25 的“桶爆炸”会换个形式重演。
先确认 v2 做对的五件事（不展开）：

| # | v2 的进步 | 评价 |
| --- | --- | --- |
| 1 | **实测推翻估算**（353.7MB vs 原估 11~22MB） | 这是本次修订最大的价值。若照 v1 动工，等于把“重读正文的 OOM”换成“摘要常驻的 OOM” |
| 2 | **摘要改在主进程算**（D5） | v2 最好的新决策。它把渲染进程从“数据加工方”降级为“数据消费方”，结构性解决了渲染层内存问题——这比“顺序化”高一个层级。且复用 `wb:meta` 既有通道、零新增 IPC，工程上干净 |
| 3 | **发现 `wb:meta` 无体积守卫**（§3.4） | 主动扩大了取证范围，避免“比 PK-27 崩得更早”的第四次事故 |
| 4 | **S3' 拆出本轮** | 正确。阈值未定不该动工 |
| 5 | **§12 评审意见处理表** | 逐条可追溯，这本身是好的工程文化 |
以下全部是增量问题。

## 二、P0：动工前必须修的

### P0-1 simhash 参数依赖倒挂：S1' 将落盘一个 S3' 才能定的值

**问题**：S1' 要在 L1 里落盘 `simhash64`，但 simhash 的**特征选择方案**（分词方式？n-gram 宽度？输入是触发词还是词条正文？中文无空格怎么切？）被归入 S3' 才实验。
**后果链**：S3' 实验若得出“char 3-gram 应改 4-gram”或“应剔除触发词只算正文”——**S1' 已落盘的全库 simhash 全部作废**，意味着 34.8GB 重读一遍。这正是本方案要消灭的东西，会以“索引重建”的形式回来。
**修法**：在 S1' 之前插入一个**半天量的离线实验**（不碰线上代码）：

```text
S0.5：simhash 方案实验（离线脚本）
  样本：s1000 已采样的 92 本 + 正负样本组（同源副本 = 正；跨组书 = 负）
  变量：① 特征方案（char 3-gram / 4-gram / 触发词+正文混合，2~3 种）
        ② 阈值 T（跑两组的汉明距离分布，取分界点）
  产出：特征方案定稿 + 阈值初始值（S3' 上线时只需线上复核）
```

S3' 剩下的就只是“改查重代码 + 线上验证”，不再有返工风险。v2 把“阈值实验”排进了 S3'，但**比阈值更上游的“特征选择”没有任何安排**——这是排期表上的一个洞。

### P0-2 §6.1 第 2 步“排序 + 相邻窗口”算法描述不成立，且漏掉了高频桶爆炸

**问题一：描述不精确**。第 3 步（组内双指针求交）是清楚且正确的；但第 2 步“keyHashes 排序 + 相邻窗口比较”作为“把名字不同但触发词重合的书聚到一起”的机制，**含混到无法实现**。如果指“把 5401 本书按某种方式排序后只比较相邻的”——这不成立：Jaccard 相似度不是全序关系，排序无法保证相似的书相邻，召回率会失控。
**问题二：正确做法里藏着 PK-25 的翻版**。这一步的唯一正确落地是**倒排共现**：`key_hash → [bookId...]`，共享触发词的书自然落入同一桶。但注意——**一个高频触发词（如“你”）出现在 5000 本中，它的桶就是 5000，桶内两两共现 = 1250 万对；50 个这样的高频词 = 6.25 亿对计数，共现 Map 最坏 1350 万条目（数百 MB）**。这就是 PK-25“全同源→单桶爆炸”在 keys 域的精确复刻。v2 在 §6.2 对 simhash 分桶专门防了这个问题，却在 §6.1 对 keys 倒排完全没有设防。
**修法：bottom-k 签名 + 倒排共现 + 全量精算的两层设计**：

```text
候选生成（O(Σk)，k=64）：
  每本书 signature = keyHashes.slice(0, 64)   // keyHashes 已排序，取最小 64 个 = bottom-k sketch
  建倒排 Map<hash, bookId[]>，共现计数
  高频桶（bucket > 500）跳过或降权 —— 高频词对 Jaccard 区分度贡献极小（stopword 思路）
精算（仅候选对）：
  共现 ≥ 阈值（如 8）的书对 → 用全量 keyHashes 双指针算精确 Jaccard
```

三点理由：

1. **bottom-k 是 MinHash 的标准变体**（不是自研 MinHash LSH，保留了你“不引入重算法”的原则），每本书取最小 k 个 hash 做签名，交集/并集比是 Jaccard 的无偏估计。实现上就是 `slice(0, 64)`，一行。
2. **bottom-k 天然抑制桶爆炸**：64 × 5401 ≈ 35 万个倒排条目，且只有“hash 值恰好的高频词”才会进签名，爆炸面大幅收窄，再配 bucket 上限双保险。
3. **组内同样适用**：最坏同名组 200 本 → C(200,2) ≈ 2 万对全量精算没问题；但若将来出现 1000 本的组（C(1000,2) = 50 万对 × 1137 双指针 ≈ 5.7 亿次比较），bottom-k 预筛同样兜得住。
**顺带指出一个 v2 没意识到的巧合**：D6 的 `MAX_KEYS_PER_BOOK = 2000` 截断“保留前 N 个（最小的 hash）”，**数学上恰好就是 bottom-k(2000)**——截断后书与书之间的 Jaccard 仍是无偏估计。这个性质应该写进文档。但它引出一个**微妙的正确性坑**：一本截断书（2000）与一本未截断书（如 1137 个全量）比较时，若直接用“截断集 vs 全集”求交，Jaccard 会**系统性低估**。正确口径是**双方都截断到 min(k, 自身大小) 再比较**。这条要加进 §7 约束清单。

### P0-3 oversized 书的查重处置是死胡同

**矛盾链**：`wb:meta` 加 50MB 守卫（§3.4，正确）→ 超限书返回 `oversized: true`、**不算摘要** → S2' 的回退策略是“摘要缺失时仍走顺序读正文”（§10）→ 但 S4' 的内存守卫**恰恰会拒绝批量读超大书**。
**结果**：超大书既没有 L1 摘要，也不能走 L2 回退——**永远无法参与指纹查重，且没有任何机制告诉用户这件事**。这是 PK-26“静默 = 坏了”教训的再犯形态：查重结果里 silently 少了几本书。
**修法（按成本递增，至少做 A）**：

| 选项 | 做法 | 成本 |
| --- | --- | --- |
| **A（底线，必做）** | 超限书标记 `dedupeExcluded: true`，查重结果 UI 明确显示“N 本超大书未参与查重，点击查看清单” | 极低 |
| **B（增强）** | 对超限书做**流式 keys 提取**（stream-json 类流式解析，只捕获 `entries[].keys` 字段，不物化整个 JSON）。keys 提取不需要完整 parse——超大书的 keys 摘要依然可以在 MB 级内存内产出。仍在主进程做 | 中 |
另外注意与扫描主路径对齐：`wb:scan` 遇到超过 `SCAN_PARSE_MAX_BYTES` 的书现有处置是什么（跳过？`valid` 标记？），`wb:meta` 的 oversized 处置应复用同一套语义，避免出现“扫描认为有效、查重认为排除”的口径分裂。

## 三、P1：拍板前应明确的问题

### P1-1 23.4MB 是内存形态，不是 JSON 落盘形态——落盘体积会膨胀 1.3~2.6×

`Uint32Array` 在内存中每 hash 占 4 字节；但 `JSON.stringify` 后变成十进制数字数组，每个 uint32 平均 9~10 位数字 + 逗号 ≈ **10.5 字节/hash，膨胀 2.6×，落盘 ≈ 60MB+**。

| 落盘形态 | 体积 | 加载成本 |
| --- | --- | --- |
| 纯数字数组 JSON | ~61MB | JSON.parse ~1s |
| **base64(Uint32Array) 字符串（建议）** | ~31MB | atob + new Uint32Array，<100ms |
| 二进制 .bin + JSON 头 | ~24MB | 需自写解析 |
**建议**：base64 编码 TypedArray（改动最小），并把两条写进 D2 的细则：

1. **懒加载**：`wb_index.json` 只在查重/统计首次触发时载入，秒开路径完全不碰它——否则 31~61MB 的加载耗时直接吃掉 PK-23 的秒开预算；
2. **每条摘要内嵌 `{mtime, size}`**：v2 §10 说“摘要与 scan_cache 用同一 mtime+size 判据 → 天然同步”，但两个独立文件之间**没有事务性**（崩溃时可能一新一旧）。正确做法是 wb_index 每条自带判据、加载时与磁盘 stat 独立对账——两个文件彻底解耦，任一损坏不牵连另一个。

### P1-2 hash 不可逆 → 查重结果无法展示“具体重合了哪些词”

L1 只存 hash 后，“这两本书 87% 触发词重合”这个数字**对用户是不可解释的**——用户判断“是否安全清理”时最想看的是“重合的到底是哪些词”。按 v2 现设计，只能回读 L2 正文（又绕回读正文）。
**建议**：L1 增加可选字段 `sampleKeys: string[]`——每本存 8~20 个**特征词原串**（选法：跨书出现频次最低的优先，即区分度最高的词）。体积：20 词 × 6.1 字符 × 2 字节 × 5401 本 ≈ **1.3MB**，可忽略。查重详情页用它展示“重合样例词（前 N 个）+ 总重合度”，让数字可解释。这是 PK-26 教训的直接延伸：**算出的数字无法解释，与算出 0 是同一类缺陷**。

### P1-3 主进程没有守卫，且并发可以更聪明

v2 的守卫只覆盖渲染层。但摘要计算移到主进程后，**主进程被 OOM killer 杀 = 整个应用消失**，后果更重。两个补充：

1. **主进程用 `process.memoryUsage().rss` 做守卫**——它包含 Buffer 外部内存，比渲染层的 `performance.memory` 更接近内核视角（OOM killer 看的就是 RSS）；
2. **`WB_META_CONCURRENCY = 8` 改为自适应**：按当前批次最大单本体积降档（批次内多本 >20MB → 降 4 → 2）。粗算：8 并发 × (50MB 磁盘 buffer + ~110MB parse 后) ≈ 1.28GB 峰值——主进程可承受但值得记录，自适应降档能把这个数字压到 300MB 级。

## 四、P2：实现约束清单的补充（进 §7）

| # | 补充约束 | 说明 |
| --- | --- | --- |
| 7 | **`exactContentHash` 的 canonical 序列化定义** | “对排序后的 entries 做 SHA-256”不够：① 键序不同但逻辑相同的对象，`JSON.stringify` 输出不同 → 必须 canonical JSON（递归键排序）；② 明确覆盖范围（只 `entries` 还是整个 `data`）与顺序语义（**建议：条目顺序不同 → hash 不同，视为不同版本**。“顺序不同内容同”是 simhash 的职责，别混进 exactHash）；③ 内容不做 NFC/大小写规范化——“完全相同”就该字节级 |
| 8 | **截断比较口径** | 跨“截断/未截断”书比较 Jaccard 时，双方都截到 `min(2000, 自身)`，否则系统性低估（P0-2 末尾） |
| 9 | **IPC TypedArray 透传验证** | Electron `invoke` 走 structured clone，理论支持 TypedArray；但若链路上任何一环有 JSON 边界，Uint32Array 会退化成 `{"0":123,...}` 对象（体积暴涨数倍）。写一条集成测试断言 IPC 后仍是 TypedArray，不过则 base64 兜底 |
| 10 | **CI 规则改白名单制** | 黑名单 grep（`Promise.all` + `ensureWorldbookLoaded`）有假阴性：`for...of` 里嵌 `Promise.all` 抓不住；也有假阳性：`Promise.all(paths.map(invoke('wb:meta')))` 是合法的主进程侧并发。白名单制更稳：`ensureWorldbookLoaded` 只允许出现在清单文件里（`consumeWorldbookBodies` 内部 / 差异比对 / 编辑器加载点），其余文件出现即 CI fail |
| 11 | **体积系数口径标注** | §4.1 的 0.57 是“字符串净字符量/磁盘字节”，而 13.2MB 总驻留含对象开销（≈2×磁盘）。两个系数并存但不加说明，后人拿 0.57 算内存预算会漏掉 3.5× 的对象开销。守卫注释里两个都要写 |
| 12 | **快照合并语义** | 约束 #5 的“结束再合并”要定义为：**只写入本次新算出的摘要，快照中的旧值不回写**；失效以各条内嵌 mtime+size 对账为准 |
| 13 | **`tokenEstimate` 本轮砍掉** | 标注“可选”却没有消费方 = YAGNI。版本号机制支持未来加字段，等统计功能立项再加 |
| 14 | **归档而非删除评审稿** | §12.1 的“未采纳”决策（不引入 SQLite）将来可能被推翻——届时需要回看当时的完整理由。建议归档，不删 |

## 六、修订后的落地顺序

```text
S0   ✅ 止血（已完成并验证，s5000 存活是决定性证据）
S0.5 ★ 新增（半天，离线脚本，不碰线上代码）
     simhash 方案实验：92 本采样 + 正负样本 → 定特征方案 + 阈值初始值
S1'  L1 落地：wb:meta 守卫（含 oversized 处置 A）+ base64 落盘 + 内嵌 mtime/size + 懒加载
S2'  同名查重改读 L1：bottom-k 候选 + 倒排共现 + 全量精算（P0-2 的算法）
S4'  守卫（渲染层 + 主进程双侧）+ CI 白名单 + 规范化/截断口径单测
S3'  （下轮）内容查重：S0.5 已定方案，只改代码 + 线上复核阈值
```

## 七、一句话结论

**v2 的病根诊断、三层模型、主进程算摘要、实测文化全部成立，S0 的 s5000 存活验证是硬证据；剩余风险集中在三处——simhash 参数依赖倒挂（S0.5 半天可解）、指纹分组算法落地不精确（bottom-k + 倒排共现可解，且不解则 PK-25 换形式重演）、oversized 书处置死胡同（至少做 UI 明示）。修掉这三处，本方案可以拍板动工。**
