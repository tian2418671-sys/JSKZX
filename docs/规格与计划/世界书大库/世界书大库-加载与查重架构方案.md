## 一、事故取证：不是「卡死」，是「进程被内核杀掉」

### 1.1 实测事实

| 事实 | 证据 |
| --- | --- |
| 应用**不是卡死**，是**进程消失** | CDP 连不上；**无 `crash.log`**；无 `Crashpad/*.dmp` |
| 这是 **OOM killer** 特征 | 渲染进程被内核直接杀死，来不及写任何日志（与内容级查重注释记录的 `reason:"killed"` 同款） |
| 崩在**同名查重的「读正文」阶段** | `useDedupe.js` 用 `Promise.all` **整组并发**载入正文 |
| **库规模是决定性变量** | s1000：每组 40 本 ≈ 528MB 峰值（**侥幸存活**）；s5000：每组 **200 本** ≈ **2.6GB**（**被杀**） |

**量化**（磁盘实测）：

| 库 | 本数 | 总量 | 单本均 | 单本 parse 后 | 同名查重每组 | 组内并发峰值 |
| --- | --- | --- | --- | --- | --- | --- |
| s1000 | 1081 | 7.0GB | 6.60MB | ~13.2MB | 40 本 | **~528MB**（存活） |
| **s5000** | **5401** | **34.8GB** | 6.60MB | ~13.2MB | **200 本** | **~2.6GB**（**被杀**） |

> ⇒ **「小库测不出、大库必崩」**：这是本次事故最危险的性质。

### 1.2 真因：**「查重」没有数据源，只能反复重读全部正文**

这是**架构问题**，不是算法问题：

```text
扫描（wb:scan）已经 parse 了整本书 ──┐
                                    ├─→ 但只把 {mtime,size,name,entryCount} 写进缓存
entriesArr 就在手边 ────────────────┘   ★ 触发词被丢掉了 ★

       ↓ 于是

同名查重需要「触发词集合」 → 缓存里没有 → 只能重新读 34.8GB 正文
差异比对需要「词条正文」   → 缓存里没有 → 只能重新读
内容级查重需要「全文」     → 缓存里没有 → 只能重新读
```

**关键证据**（`main.js:2855`）：

```js
metaCache[fullPath] = { mtime: mt, size: st.size, name: wbDisplayName, entryCount: entriesArr.length };
//                     ↑ 只有这 4 个字段，没有 keys
```

**⇒ 三次 OOM 事故（PK-20 / 内容查重 / PK-27）都是同一个病根**：
**「数据在扫描时被 parse 出来，却被丢掉；下游需要时再重新读一遍」**。
每加一个「需要正文」的功能，就多一次 34.8GB 重读 + 一次 OOM 风险。

### 1.3 评审对定位的修正（已采纳）

> 用户判断「已经有很多 BUG 或者算法问题不是很完整」——**部分成立，但定位需要修正**：
> · ❌ **不是「卡死」** —— 是进程被 OOM killer 杀掉；
> · ❌ **不是「很多 BUG」** —— 根因是**一个**（数据供给架构）；
> · ❌ **不是「算法不完整」** —— MinHash+LSH 是标准做法；
> · ✅ **「需要新架构」完全正确**。

## 二、S0 止血（已完成，可独立验证）

### 2.1 唯一入口原则

新增 `consumeWorldbookBodies()`（`useWorldbooks.js`）—— **唯一**的「批量读正文」入口：

| 契约 | 说明 |
| --- | --- |
| **顺序消费**（默认 `concurrency: 1`） | 内存峰值 ≈ **单本正文**，**与库大小无关** |

同名查重、内容查重**都改走它**（删掉各自的 `Promise.all` 与手写 `for` 循环）。

> 代码评审时 `grep` `Promise.all` + `ensureWorldbookLoaded` 即视为违规（→ §7 约束 #4 要进 CI）。

## 三、方案总览：**扫描即建索引，查重只读索引**

### 3.1 核心思想

> **正文（重、一次）与摘要（轻、可常驻）分离。**
> 扫描时正文已经在内存里 —— **顺便把「查重需要的那一小部分」抽出来持久化**，
> 之后所有查重/检索都**只读摘要，永不重读正文**。

### 3.2 三层数据模型

| 层 | 内容 | 体积（**实测外推**） | 常驻？ | 谁用 |
| --- | --- | --- | --- | --- |
| **L0 元数据** | `{path, mtime, size, wbName, entryCount, valid}` | 5401 × ~200B ≈ **1.1MB** | ✅ 常驻 | 列表 / 筛选 / 统计 |
| **L1 摘要**（**新增**） | `{keyHashes: Uint32Array, keyCount, exactContentHash, simhash64, tokenEstimate}` | 5401 × ~4.5KB ≈ **23.4MB** | ✅ 常驻（可落盘） | **同名查重 / 内容查重 / 统计** |
| **L2 正文** | 完整 `data` | 34.8GB | ❌ **按需单本** | 编辑器 / 差异比对 / 导出 |

> **L1 是本次方案的核心**：它把「查重」从 **L2 依赖**降级为 **L1 依赖**。
> ⚠️ **L1 体积是实测过的**（§4），不是估算 —— 且 **`keys` 必须存 hash 而非原字符串**（15.1× 差距）。

### 3.3 ★ 关键设计：摘要**在主进程算**（渲染进程零正文）

> **这是本方案与「只把并发改成顺序」的本质区别。** 若摘要由渲染进程算，它**仍要读 34.8GB**，
> 只是不再同时读 —— 那只是「慢」，没有解决「渲染进程不该碰这么多数据」这个根本问题。

**已取证的事实**：`wb:meta` **本来就是「主进程读全文 → parse → 只回轻量字段」**（`main.js:2928`）：

```text
渲染进程 ──invoke('wb:meta', paths)──→ 主进程
                                        ├─ fs.readFile（读全文）
                                        ├─ JSON.parse（已在内存）
                                        └─ 只回 { path, wbName, entryCount, valid }   ← 正文就地丢弃
        ←──── 轻量数组 ────────────────┘
```

**⇒ 摘要只需「扩展这个已有通道的返回字段」，渲染进程无需任何新机制、无需读一个字节正文。**

| 方案 | 渲染进程读到什么 | 渲染进程内存峰值 |
| --- | --- | --- |
| **v1（仅顺序化）** | 每本正文（顺序） | ≈ 13.2MB（但**仍要读 34.8GB 磁盘**） |
| **v2（主进程算摘要）** | **只有摘要（~23MB 一次 IPC）** | **≈ 23MB，且与库大小无关** |

**主进程侧的并发安全性**：`wb:meta` 现有 `WB_META_CONCURRENCY = 8`（`main.js:1041`），
8 × 13.2MB ≈ **105MB 峰值** —— 主进程可承受。
且这是**已上线并验证过**的通道（PK-23 秒开阶段 2 实测 5001 本正常）。

**⇒ 结论**：**不需要新建任何通道**，只需在 `wb:meta` 的 `handleOne` 里**多算几个字段**。

### 3.4 ⚠️ 但必须同时给 `wb:meta` 加**体积守卫**（评审盲区，已取证为真）

**取证**：`wb:meta`（`main.js:2946`）**没有单本体积守卫**（不像扫描主路径有 `SCAN_PARSE_MAX_BYTES = 50MB`）：

| 路径 | 单本体积守卫 | 并发 | 最坏峰值 |
| --- | --- | --- | --- |
| 扫描主路径（`wb:scan`） | ✅ `SCAN_PARSE_MAX_BYTES = 50MB` | 2（heavy 档） | ~100MB |
| **`wb:meta`（阶段 2）** | ❌ **无** | 8 | **8 × 单本**（若遇 200MB 合并书 → **1.6GB**） |

**⇒ 本方案要在 `wb:meta` 里算摘要（多读一遍正文），会放大这个盲区。必须同时补守卫**：

```js
// wb:meta 的 handleOne 内（S1' 必做，不可省）
if (st.size > WB_META_MAX_BYTES) {            // 建议 50MB，与扫描主路径同口径
    // 超限：只回元数据 + 标记 oversized，不读正文、不算摘要
    return { path: p, wbName: null, entryCount: null, valid: true,
             oversized: true, cached: false };
}
```

**为什么不可省**：若不加，S1' 上线后遇到超大合并书会在**扫描阶段** OOM ——
比 PK-27 崩得更早、更难定位（用户会以为「扫描坏了」，实际是「为算摘要而读爆」）。

### 3.5 摘要字段设计（主进程侧）

```js
// main.js · wb:meta 的 handleOne 内（示意，非最终代码）
const entriesArr = Array.isArray(data.entries) ? data.entries
    : (data.entries && typeof data.entries === 'object' ? Object.values(data.entries) : []);
const keyHashes = buildKeyHashes(entriesArr);   // ★ Uint32Array（实测 4.44KB/本）
return {
    path: p, wbName: nm, entryCount: cnt, valid: true,
    // ★ L1 摘要（全部由已在内存的 entriesArr 算出，**零额外读盘**）
    keyHashes,                                    // 去重小写触发词的 32 位 hash
    keyCount: keyHashes.length,
    exactContentHash: sha256Of(entriesArr),       // 确定性「完全相同」判定
    simhash: simhash64(entriesArr),               // 64 位内容指纹（内容查重预筛）
    tokenEstimate: estimateTokensOf(entriesArr)   // 统计用（可选）
};
```

**设计要点**：

| 要点 | 理由 |
| --- | --- |
| `keys` 去重 + 小写 + NFC | 与现有 `getWorldbookKeysSet` **同口径**（但**规范化函数必须统一且写成单测**，见 §7 #2） |
| **★ 存 `Uint32Array` hash 而非原字符串** | **实测 15.1× 体积差距**（67.1KB → 4.44KB/本）；**必须项，非优化项** |
| **★ 另存 `exactContentHash`**（SHA-256） | 把「两本完全一样」变成**确定性**判定（text-dedup 的 ExactHash 层） |
| **设 `MAX_KEYS_PER_BOOK` 上限** | 防「异常书有 10 万触发词」把摘要撑爆（**摘要必须体积可控**） |
| `simhash` 用 64 位整数 | 每本 8 字节；比较只需异或 + popcount（**阈值待实测，见 §6.2**） |
| 全部由 `entriesArr` 现算 | **零额外读盘**；且与正文**同源同版本**（不会出现摘要与正文不一致） |

> ⚠️ **hash 碰撞评估**：32 位 hash 在 1137 keys/本下，单本内碰撞概率 ≈ $1137^2 / 2^{33} \approx 1.5\times10^{-4}$；
> 全库（5401 × 1137 ≈ 614 万 keys）必然存在跨本碰撞。
> 但碰撞的后果只是「触发词集合比较时多算一个交集元素」，**对 Jaccard 相似度的影响 < 0.1%**，
> 且**绝不会造成「误判为重复」**（重复判定还需要 `entryCount` 与重合度同时达标）。**可接受**。

### 3.6 缓存分层落盘

| 文件 | 内容 | 体积（实测外推） | 失效策略 |
| --- | --- | --- | --- |
| `scan_cache.json`（现有） | `{__v, worldbook:{path:{mtime,valid}}, wbMeta:{path:{...}}}` | 1.4MB | mtime+size 变化即失效单条 |
| 建议拆出 `wb_index.json`（新） | L1 摘要（keyHashes/simhash/exactContentHash） | **~23.4MB**（实测） | 同上；**升版本号整体失效**（沿用 DF-18 自愈机制） |

> 为什么建议拆开：`scan_cache.json` 是「扫描正确性」的缓存（含 `valid` 否定判定，DF-18 有专门自愈设计）；
> L1 是「查重索引」，**失效语义不同**（索引过期只是查重结果旧，不影响扫描正确性）。混在一起会让两者互相牵制。

### 4.1 L1 摘要体积实测（`scripts/probes/_probe-l1-size.mjs`，s1000 采样 92 本真实数据）

| **原字符串方案 单本** | 2~4KB | **67.1KB**（P95 92.1KB） | 🔴 **高估 17~33×** |
| **原字符串方案 全库（5401 本）** | 11~22MB | **353.7MB** | 🔴 **会压垮渲染进程** |
| **hash 数组方案 单本** | — | **4.44KB** | ✅ |
| **hash 数组方案 全库** | — | **23.4MB** | ✅ 可常驻 |
| 压缩比（原串 → hash） | — | **15.1×** | — |
| 体积系数（parse 后字符/磁盘字节） | 假设 ×2 | 平均 **0.57** ｜ P95 **0.89** | ✅ `×2` 够用 |
| 含非 BMP（emoji）的书 | 担心 | **0/92** | 本库无此风险（守卫仍按 2.2 系数留余量） |
| parse 耗时/本 | — | **31.0ms** | 主要成本 |
| **hash 计算耗时/本** | 担心变慢 | **0.04ms**（parse 的 **0.13%**） | ✅ 可忽略 |

**⇒ 三条写死的实现约束**（已验证）：

1. **`keys` 存 `Uint32Array`（FNV-1a 32 位 hash）**，不存原字符串 —— **必须项不是优化项**。
2. **规范化统一为 `trim().toLowerCase().normalize('NFC')`**，全库所有比较点共用同一函数（写成单测断言）。
3. **另存 `exactContentHash`**（对排序后的 entries 做 SHA-256）—— 用于「完全相同」的**确定性**判定。

> 🔴 **若不实测就动工**：L1 会是 **353.7MB 常驻** → 把「重读正文的 OOM」
> 换成「摘要常驻的 OOM」，**同一个坑换个入口再踩一次**。

## 五、加载架构（世界书库从大到小）

### 5.1 现状（PK-23 已做对的部分，保留）

```text
阶段 1：readdir + stat                    → 43~326ms  ✅ 秒开
阶段 2：后台读元数据（wb:meta）            → ~160s（5001 本，读全文只取 4 个字段）
```

**阶段 2 的问题**：它**读了全文**（`fs.readFile` + `JSON.parse`）**只为拿 4 个字段** —— 这是最大的浪费。

### 5.2 方案：**阶段 2 顺带产出 L1 摘要**（主进程内完成）

```text
阶段 1：readdir + stat                    → 秒开（不变）
阶段 2：wb:meta 读全文 → parse → 抽 {元数据 + L1 摘要} → 写缓存 → 丢弃正文
        └─ 耗时不变（本来就在读），但**产出从 4 个字段变成「元数据 + 查重所需全部信息」**
        └─ ★ 全程在主进程，渲染进程只收到轻量摘要（**零正文**）
```

**⇒ 净收益**：阶段 2 的 160s **同时完成了「秒开补元数据」与「查重建索引」两件事**。
之后所有查重**再也不需要碰正文，也再也不需要渲染进程参与读取**。

### 5.3 内存预算守卫（建议新增）

```text
读取前：估算 单本 parse 后体积 ≈ 磁盘 size × 2.2（留 emoji 余量）
      若 单本 > 阈值 → 拒绝批量读，提示用户单独处理
运行时：每本读取后检查 usedJSHeapSize
      若 > 可用堆 × 70% → 中止并提示「内存不足，已中止（已处理 N/M 本）」
```

**两处关键修正**（评审 §3.7）：

| 评审意见 | 采纳后的做法 |
| --- | --- |
| 阈值用**绝对值 64MB** 不妥 | 改为 **可用堆的百分比**（`limit × 70%`） |
| `usedJSHeapSize` **不含 ArrayBuffer 外部内存**（`fs.readFile` 的 Buffer 不计入） | 守卫阈值留出 **Buffer 余量**；并补「**读前按 `size × 2.2` 预估**」的**预检**（不依赖 `performance.memory`） |
| `performance.memory` 只在 Chromium 可用 | 守卫逻辑**不得写死依赖**它 —— 缺失时降级为「计数器 + 估算」模式 |

**为什么需要**：本次 OOM 是**内核直接杀进程**，应用**没有任何机会提示用户**。
有了守卫，至少能**优雅中止并说明原因**（符合 PK-26 的「静默 = 坏了」教训）。

## 六、查重算法（在 L1 之上重写）

### 6.1 同名查重（改名：**指纹查重**）

**算法选型论证**（评审要求）：

| 维度 | simhash | MinHash + LSH | **本方案选择** |
| --- | --- | --- | --- |
| 适用对象 | 长文本（>500 词）特征加权 | **集合**的 Jaccard 相似度 | 见下 |
| 触发词集合（**是集合**） | ❌ 不合适 | ✅ **天然匹配** | **不引入 MinHash，用更简做法** |
| 整本正文（**是长文本**） | ✅ 合适 | 可用但偏重 | **simhash**（§6.2） |

**⇒ 分工正确，但落地方式采纳评审建议**（不自研 MinHash LSH —— JS 生态无成熟库，自研易出 bug）：

```text
输入：L1 摘要（keyHashes: Uint32Array + keyCount + entryCount）
算法：
  1. 候选分组：按 wbName 归一化分组（现有逻辑，保留）
  2. ★ 新增：keyHashes 排序 + 相邻窗口比较（sorted-neighborhood）
     —— 名字不同但触发词高度重合的书也能聚到一起；
     工程量比自研 MinHash LSH 小一个数量级，5000 本规模下效果足够。
     （keyHashes 本就是排序数组 → 求交集只需 O(n) 双指针，无需哈希表）
  3. 组内两两比较：双指针求 keyHashes 交集（整数比较）→ Jaccard，不读正文
  4. 输出：重合度百分比 + 「可安全清理」判定
复杂度：O(总触发词数 × log n)（排序）而非 O(总字节数)
```

> 📌 **若将来走 SQLite 路线**（§10 D2 备选），第 2 步可退化为一行 SQL：
> `SELECT key_hash, GROUP_CONCAT(book_path) FROM keys GROUP BY key_hash HAVING COUNT(*) > 1`
> —— 倒排表天然避免「每本重复存高频词」。

### 6.2 内容级查重（改名：**内容指纹查重**）

**🔴 汉明距离阈值必须实测，不能拍脑袋。**

```text
输入：L1 的 64 位 simhash
算法：
  1. 预筛：汉明距离 ≤ T 的视为候选（整数异或 + popcount，每对 < 1μs）
  2. 分桶：按 simhash 高 16 位分桶 → 桶内比较（避免 PK-25 的「全同源 → 单桶爆炸」）
  3. 精算：仅对候选对，按需读正文做精确比对（候选通常极少）
复杂度：O(n × 桶内大小) 而非 O(bucket²)
```

**⚠️ 阈值 T 的确定方式**：

| 项 | 说明 |
| --- | --- |
| 理论背景 | 64 位 simhash 下，两本**完全无关**的书期望汉明距离 = **32** |
| 为什么不能沿用「≤3」 | 那是拍脑袋值；T 偏小 → **漏报**，T 偏大 → **误报** |
| **必做的实验** | 准备**两组标注样本**：① 已知「同源不同版本」② 已知「完全无关」；各跑一遍 simhash，看**两组汉明距离的分布**，取「能分开两组的分界点」作为 T（通常取 ① 的 P95） |
| 前置条件 | **本项属 S3'，已拆到下一轮** —— 因为阈值未定就不该动工 |

> ⇒ **S3' 的第一步是「写一个离线阈值实验脚本」，不是「改查重代码」**。
> 样本可取自现有压力库（同源副本 = 正样本；跨组不同书 = 负样本）。

### 6.3 差异比对（保持现状）

差异比对**本质上需要正文**（要逐行展示差异），所以它**必须**读 L2 —— 但只需 **2 本**，
用现有的 `ensureWorldbookLoaded`（单本）+ 用后释放即可，**不需要架构改动**。

> ⚠️ 现状已正确（`openDiffDetailModal` 有 `diffLoadAttempted` 防重入），**本次无需改动**。

### 8.3 ⚠️ 落地时实测踩到的两个真 bug（已修，务必记住）

**bug ①：热缓存下 L1 摘要全丢**（`withKeyHashes: 0`）

- **根因**：`wb:scan` 阶段 1 的**缓存命中分支**只回 `entryCount`/`wbName`，**没带 `keyHashes`**；
  且 `metaPending: !hit` → 命中即 `false` → **阶段 2 被跳过** → 摘要永远拿不到。
- **表现**：「首次扫描正常、再次扫描全丢」—— **极难定位**（因为首次是对的）。
- **修法（两处，缺一不可）**：
  ① 阶段 1 命中时**一并返回 `keyHashes`**，且 `metaPending: !(hit && Array.isArray(cached.keyHashes))`
  （老缓存无摘要字段 → 必须回落 `true` 让阶段 2 补算）；
  ② **`wbMeta` 子结构升版**（`WB_META_CACHE_VERSION = 2`）—— 只丢 `wbMeta`，**不动 `worldbook` 的 valid 缓存**
  （后者一起丢会触发全量重扫）。

**bug ②：「bottom-k + 倒排共现」在极端同源库下彻底失效，且重演 PK-25**

- **过程**：先按评审 P0-2 实现「bottom-k(64) + 倒排共现（桶上限 500）+ 门槛 8」→ **探针卡死**。
- **分析**：
  · 极端同源库 → 所有书 keys 几乎相同 → bottom-k 的 64 个 hash **全落在同样的书上**
    → 每桶顶到上限 → C(500,2) × 64 ≈ **800 万对** → **卡死**（正是评审警告的「PK-25 换形式重演」）；
  · 改成「高频桶**整桶跳过**」→ 但**所有桶都是高频** → **候选集为空**。
- **⇒ 最终设计修正**：**组内直接全量精算**（不预筛）。
  理由：**同名分组本身已把范围缩到组内**（实测 s1000：25 组 × 40 本 = **975 对**；
  s5000：每组 200 本 ≈ 2 万对）→ 全量精算是 O(组内对数 × keys 长度)，**纯整数无读盘，实测 9ms**。
  简单、正确、**零召回损失**（预筛反而会漏）。
- **⚠️ 教训**：评审给的算法（bottom-k + 倒排）**在「桶大且均匀」时有效**，
  但**极端同源库是它的退化情形**（所有桶都高频）。
  ⇒ **「分组已缩范围」时应优先用简单全量**，不要为了「看起来更快」引入预筛 —— **预筛的失效模式比慢更糟**。

## 十、风险与回退

| 风险 | 评估 | 缓解 |
| --- | --- | --- |
| **摘要体积失控** | 异常书可能有 10 万+ 触发词 | 设 `MAX_KEYS_PER_BOOK`（如 2000）上限，超出只保留前 N + 记 `keyCount` 真实值 |
| **缓存文件损坏** | `wb_index.json` 写坏 → 查重读不到 | 沿用 DF-18 机制：**版本号不符即整体丢弃重建**；写入用「临时文件 + 改名」保证原子性 |
| **摘要与正文不一致** | 用户在别处改了文件 | 摘要与 `scan_cache` 用**同一 `mtime+size` 判据**，同一时刻失效 → 天然同步 |
| **`wb:meta` 变慢** | 多算 keys/simhash 增加主进程 CPU | keys 提取是 O(总触发词数)，simhash 是 O(总字符数)；**相对 `JSON.parse` 可忽略**（实测 hash 仅 parse 的 0.13%） |
| **IPC 传输变大** | 摘要 23MB 一次传给渲染层 | 分批（`wb:meta` 本就是 8 并发分批 + 进度回调）；且 23MB 相对原 34.8GB 可忽略 |
| **首次扫描变慢** | 多算摘要 | 实测可忽略；且**只需算一次**，之后走缓存命中（0 次读盘） |
| **改动面** | `main.js` + `useDedupe.js` | **不新增通道、不新增 IPC**；`wb:meta` 只加返回字段，向后兼容 |

**回退策略**：
· **S1'** 只**新增**字段 → 出问题可让渲染层忽略（一行判断）；
· **S2'** 改同名查重数据源 → 保留旧路径为 `fallback`（摘要缺失时仍走顺序读），**可随时切回**。

## 十三、附录：事故的完整教训

> **同一个病根，三次事故**：
> ① PK-20（全量内联 3.56GB → 退出）→ ② 内容级查重（全文本 3GB → 被 OOM killer 杀）→ ③ PK-27（整组并发 2.6GB → 被 OOM killer 杀）
>
> 每次修的都是**「这一次的入口」**，从没修**「为什么会需要一次性读这么多」**。
> 直到这次才看清：**根因是「数据供给架构」—— 扫描时 parse 出的信息被丢弃，下游只能重读。**

**⇒ 教训一**：连续两次同款事故（PK-20 / 内容查重）之后，就该问「**是不是缺一层架构**」，
而不是继续在调用点打补丁。

**⇒ 教训二（来自评审）**：**方案里的每个数字都必须是实测的**。
本方案原估「L1 = 11~22MB」，实测 **353.7MB（差 16~32 倍）** —— 若照原估算动工，
会把「重读正文的 OOM」换成「摘要常驻的 OOM」，**同一个坑换个入口再踩一次**。

**⇒ 教训三**：**「静默长耗时」与「静默算出 0」是同一类缺陷** —— 用户都无法区分「在算」和「坏了」。
（来自 PK-26：查重时「触发词重合度 0%」会**误导用户误删正确的书**。）
