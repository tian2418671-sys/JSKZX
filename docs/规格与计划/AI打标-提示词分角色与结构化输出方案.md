## 一、用户建议原文与解读

> **用户建议**：让我们自定义提示词和破限，分成 system、assistant、user 三类。这样就可以在提示词里面设置思维链来约束 AI。
> 然后 AI 输出后，软件自动截取固定的标签例如 `<标签>[XX, XX]</标签>` 这样作为标签，打标签也不会乱。
>
> **用户想法**：增加一个思维链模式与原来的隔离，或者融合进入。

| 诉求 | 真实问题 | 落点 |
| --- | --- | --- |
| 分 `system` / `assistant` / `user` | ① 想控制**消息角色**；② 想用 `assistant` 段写**思维链示例**或**预填充** | R2 |
| `<标签>` 截取 | 打标结果**乱**（模型加解释 / markdown / 思维链污染） | R1 |
| 思维链模式隔离 | 想区分「严格模式」与「思维链模式」 | ⚠️ 见 §五：**用 R2 表达即可，不需要模式开关** |

## 三、关键技术洞察（决定方案设计）

### 洞察 1 · 现有解析在**思考型模型**上不可靠 ★

`rawReply.match(/\[[\s\S]*\]/)` 是**贪婪匹配**：取「第一个 `[`」到「最后一个 `]`」。

| 场景 | 后果 |
| --- | --- |
| 模型输出 `好的，分析如下：["奇幻","冒险"]` | 侥幸能解析（只有一个方括号组） |
| 模型输出 `标签含义说明 [1]：[奇幻]；[2]：[冒险]` | ❌ **取到错误区间** |
| **思考型模型**先输出思维链（含方括号）再给 JSON | ❌ **思维链污染**，取到思维链里的方括号 |
| JSON 被 max_tokens 截断 | ❌ 无 `]` → 匹配失败 → 走暴力拆分（可能拆出垃圾） |

> ⚠️ **这是本方案的核心收益点**：用户常用的 **GLM-5.3 / DeepSeek-V4 / 商汤 6.8** 都是**思考型**模型，
> 思维链里出现方括号（如 `["奇幻", "冒险"]` 的示例、编号列表 `[1]`）会让现有正则**取错区间**。

### 洞察 2 · `assistant` 预填充是最强的格式约束

在 messages 末尾放一条 `assistant` 消息，模型会**接着它往下写**：

```js
messages: [
  { role: 'system',    content: '...' },
  { role: 'user',      content: '...' },
  { role: 'assistant', content: '<标签>[' }     // ← 预填充
]
// 模型输出将从 `"奇幻", "冒险"]</标签>` 开始，天然不含解释
```

**兼容性限制（必须处理）**：

| 后端 | 预填充支持 | 说明 |
| --- | --- | --- |
| Anthropic 原生 | ✅ | 叫 "prefill"；⚠️ **结尾不能是空白字符** |
| OpenAI 官方 | ✅ | — |
| **部分中转 / 聚合站** | ⚠️ **可能忽略或报错** | 用户环境有多个中转站（B.AI / 逍遥 / InferAI 等） |
| **思考型模型**（reasoning） | ❌ **常不支持** | 需先输出 `reasoning_content`，预填充会冲突 |

⇒ **必须有降级**：预填充失败/被忽略时，自动退回「只用 system + user」并仍能正确解析（靠 R1 的标签截取兜底）。

### 洞察 3 · 「思维链」现在**已经能做**，只是没有显式控制

用户现在就可以在 `systemPromptPresets` 里写"请先分析性格，再判断世界观，最后给标签"——
但推理过程与输出格式**混在同一条 system**，无法分开控制，也无法用 `assistant` 预填充强制格式。

⇒ **R2 的"分角色"正是为此**：把推理引导放 `system`、把输出格式示例放 `assistant`，职责分离。

## 四、候选方案对比

### R1 · 结构化输出契约（`<标签>` 包裹）★ 推荐先做

```
改动：
1. promptText 输出规则改为：必须用 <标签>[标签1, 标签2]</标签> 包裹
2. 解析改为**三层降级**：
   ① /<标签>\s*([\s\S]*?)\s*<\/标签>/   （非贪婪，精确边界；同时兼容 <tags>）
   ② 回退现有 /\[[\s\S]*\]/             （旧格式 / 模型不遵守时）
   ③ 回退暴力拆分                        （最后兜底）
```

| 项 | 评估 |
| --- | --- |
| 改动量 | **小**（约 30 行，集中在 `useAITools.js` 一处） |
| 风险 | **低**（三层降级；旧格式仍可解析，不影响既有行为） |
| 收益 | **高**（彻底隔离思维链污染；边界明确，非贪婪） |
| 可验证性 | **强**（跑一次打标即可对照） |
| 缺点 | 未解决"用户想控制消息角色" |

**标签名建议**：默认用 **`<tags>`**（英文，模型训练数据里常见 XML 风格，遵守率高），
**解析时同时兼容 `<标签>`**（照顾中文用户手写）。**不做成可配置**（增加认知负担，收益低）。

### R2 · 提示词预设分角色

```
数据模型（向后兼容）：
systemPromptPresets: [{
  id, name, expanded,
  system:    '你是一个专业的角色卡分析助手...',   // 主提示词
  assistant: '',      // 🆕 可选：示例推理 / 输出格式示范
  user:      '',      // 🆕 可选：留空 = 用程序生成的默认（候选池 + 卡片数据）
  prefill:   '',      // 🆕 可选：assistant 预填充（如 '<tags>['）
  // 旧字段 content 保留：读取时自动迁移到 system（老配置零破坏）
}]

消息组装：
messages = [
  { role: 'system', content: preset.system + 破限 },
  { role: 'user',   content: preset.user || 程序默认 promptText },
  ...(preset.assistant ? [{ role: 'assistant', content: preset.assistant }] : []),
  ...(preset.prefill   ? [{ role: 'assistant', content: preset.prefill   }] : []),
]
```

| 项 | 评估 |
| --- | --- |
| 改动量 | **中**（数据模型 + 组装 + UI + 旧配置迁移） |
| 风险 | **中**（预填充在中转站可能失效 → 需降级；旧配置需迁移） |
| 收益 | **高**（用户可控制消息角色；预填充是格式约束最强手段） |
| 缺点 | 需处理兼容性与迁移 |

**UI 呈现**（接在布局重构的「③ 提示词与破限」页签内）：

```text
┌ 提示词预设 ──────────────────────┐
│ ● 默认分析助手（当前生效）          │
│ ○ 严格模式                         │
├────────────────────────────────────┤
│ [System] [Assistant] [User]  ← 三个小页签 │
│ ┌────────────────────────────────┐ │
│ │ 你是一个专业的角色卡分析助手... │ │
│ └────────────────────────────────┘ │
│ 💡 Assistant 段可写示例推理或预填充 │
└────────────────────────────────────┘
```

### R3 · 「思维链模式」独立开关 ❌ 不推荐

| 项 | 评估 |
| --- | --- |
| 改动量 | **大**（两套流程 + UI 切换 + 各自测试） |
| 风险 | **中高** |
| 收益 | **低** —— **功能与 R2 重复** |
| 缺点 | **两套代码要各自维护**；用户还要理解"模式"概念 |

> **为什么多余**：R2 里「`assistant` 段留空」= 严格模式；「`assistant` 段填示例推理」= 思维链模式。
> **同一个字段的填写与否就能表达两种模式，不需要额外开关**——而用户的痛点恰恰是「UI 乱」，加开关只会更乱。

## 五、推荐路径（分两步，可独立验收）

```text
第 1 步 · R1 结构化输出契约（P0）
  ├ 改动：promptText 输出规则 + 解析三层降级
  ├ 验收：真实打标一次；构造「模型带解释」「带思维链」两种输出，均能正确截取
  └ 收益：立刻解决思考型模型的思维链污染

第 2 步 · R2 提示词预设分角色（P1）
  ├ 改动：数据模型（+迁移）+ 消息组装（+预填充降级）+ UI（三小页签）
  ├ 验收：① 旧配置读入不丢；② 填 assistant 段生效；③ 预填充被中转站忽略时自动降级
  └ 收益：用户可控制消息角色；预填充强化格式约束

（R3 不做）
```

**与布局重构的关系**：R2 的 UI 落在「③ 提示词与破限」页签内，**建议与布局重构同批做**（都在 `AITagModal.vue`，省一次回归测试）；
R1 只动 `useAITools.js`，**可与布局重构并行**。

## 七、风险与防线

| 风险 | 防线 |
| --- | --- |
| 模型不遵守 `<标签>` 格式 | **三层解析降级**（标签 → JSON 正则 → 暴力拆分），任一层成功即可 |
| 预填充在中转站失效 | 捕获异常 → **自动去掉 `assistant` 消息重试**（或直接降级为 system+user） |
| 旧配置读入丢数据 | `content` → `system` **自动迁移**；新字段缺失时回落默认（**不抛错**） |
| 思考型模型与预填充冲突 | 检测到 reasoning 类模型 → **自动禁用预填充**（或由用户手动关） |
| 改动影响既有打标行为 | `test/` 补解析用例（含思维链污染、markdown 包裹、截断）；真实打标端到端对照 |
