---

预设查重和世界书/角色卡查重有本质区别：**预设的核心价值不在文本内容，而在提示词（prompts）的编排结构和采样参数（samplers）的配置**。同一套 prompt 换个顺序、改一个 `enabled` 状态，行为可能完全不同；而两个预设的 `temperature` 差 0.05，不应该被判定为“重复”。所以预设查重不能简单套用文本相似度。

---

## 一、预设的三种类型与结构

SillyTavern 的预设系统按 API 后端分为多个类别，每种的结构和查重重点不同：

| 预设类型 | 存储键 | 查重重点 |
|---|---|---|
| **OpenAI / Chat Completion** | `openai_settings` | `prompts[]` 数组的块级结构、`prompt_order` 排序、采样参数 |
| **Text Completion** | `textgenerationwebui_presets` | `instruct` 模板 + `context` 模板 + 采样参数 |
| **Context Template** | `context_presets` | `story_string` 模板的字段编排顺序 |
| **Instruct Template** | `instruct_presets` | 序列符号（`input_sequence` / `output_sequence` 等） |
| **System Prompt** | `system_prompts` | 纯文本内容 |
| **Reasoning Template** | `reasoning_templates` | 思维链提取逻辑 |

**Chat Completion 预设**（最复杂）的核心结构：

```json
{
  "temperature": 0.85,
  "top_p": 1,
  "prompts": [
    { "identifier": "main", "name": "Main Prompt", "role": "system",
      "content": "...", "enabled": true, "injection_depth": 0 },
    { "identifier": "worldInfoBefore", "name": "WI Before", "role": "system",
      "content": "", "enabled": true, "system_prompt": true },
    ...
  ],
  "prompt_order": [ { "character_id": 100000, "order": [...] } ]
}
```

`prompts[]` 数组中每一项是一个**提示词块**，有自己的 `identifier`、`role`、`content`、`enabled` 状态和 `injection_depth`。`prompt_order` 则定义了这些块在最终 prompt 中的排列顺序。

**Text Completion 预设** 则是另一种结构，包含 `instruct`（序列模板）、`context`（story_string 模板）和顶层采样参数。

## 二、预设查重的核心策略：结构指纹 + 块级对齐

### 2.1 预设指纹（结构性）

预设的“身份”由以下要素共同决定，按重要性排序：

```text
预设指纹 = {
  prompts 的 identifier 集合,        // 有哪些块
  prompts 的 enabled 状态映射,       // 哪些块是启用的
  prompt_order 的排序,              // 块的排列顺序
  prompts 的 content 指纹,          // 块的内容
  采样参数的归一化向量               // 行为参数
}
```

**两个预设的 `identifier` 集合和 `enabled` 状态完全一致，但 `content` 不同**——这是最常见的“换皮预设”，应该被标记为高度相似。

**两个预设的 `identifier` 集合不同**——一个是 60+ 模块的 mega-preset，一个是 10 个块的精简预设——即使 `content` 有重叠，也不应判为重复。

### 2.2 块级内容指纹

对每个提示词块独立计算：

```text
对 prompts[] 中每个块：
  · content 的 MinHash 签名（字符 n-gram，n=2~4）
  · content 的 SimHash 指纹
  · content 的字符数

对采样参数（temperature, top_p, top_k, repetition_penalty, ...）：
  · 归一化到 [0,1] 或标准化为 z-score
  · 形成一个数值向量
```

### 2.3 结构相似度

```text
结构相似度 S_struct 由三部分组成：

1. identifier 集合的 Jaccard：
   J_id = |ID_A ∩ ID_B| / |ID_A ∪ ID_B|

2. enabled 状态的一致性：
   对两个预设共有的 identifier，统计 enabled 状态相同的比例：
   S_enabled = |{id ∈ ID_A ∩ ID_B : enabled_A[id] == enabled_B[id]}| / |ID_A ∩ ID_B|

3. prompt_order 的 Kendall tau 距离（仅对共有 identifier）：
   将共有 identifier 在两个预设中的顺序提取出来，计算 Kendall tau 相关系数 τ ∈ [-1, 1]，
   归一化为 S_order = (τ + 1) / 2。
```

### 2.4 内容相似度

对共有 identifier 的块，逐块比较 `content`：

```text
对每个共有 identifier id：
  sim_content[id] = J_minhash(content_A[id], content_B[id])

S_content = Σ_id [ w_id * sim_content[id] ] / Σ_id w_id

其中 w_id 建议按块的类型赋予不同权重：
  · main / system_prompt 等核心块：权重高（如 2.0）
  · worldInfoBefore / worldInfoAfter 等注入块：权重中（如 1.0）
  · 用户自定义的辅助块：权重低（如 0.5）
```

### 2.5 采样参数相似度

```text
将两个预设的采样参数向量分别标准化（z-score），计算余弦相似度：

S_sampler = cos(z_A, z_B)

注意：采样参数的差异通常不决定“是否重复”，而是决定“行为是否一致”。
两个预设的 prompts 完全相同但 temperature 差 0.2，应该被标记为
“结构重复，行为参数不同”，而不是直接判为重复。
```

## 三、融合打分与相似类型分类

### 3.1 融合公式

```text
S_raw = w_struct * S_struct
      + w_content * S_content
      + w_sampler * S_sampler

其中 S_struct 本身是 identifier Jaccard、enabled 一致性、order 相似度的加权组合。
```

**建议权重**（预设查重中结构比内容更重要）：

```text
S_struct   权重 0.50   ← 结构决定行为
S_content  权重 0.35   ← 内容反映意图
S_sampler  权重 0.15   ← 参数反映风格
```

### 3.2 相似类型分类（预设特化）

```text
类型判定规则：

完全重复     S_raw ≥ 0.95，且所有 prompts 的 content 都 ≥ 0.95
结构相同换皮 S_struct ≥ 0.90，但 S_content < 0.60
              → identifier 和 enabled 几乎一致，但块内容不同
内容相同重排 S_content ≥ 0.85，但 S_order < 0.60
              → 块内容高度相似，但排列顺序不同
参数变体     S_struct ≥ 0.90，S_content ≥ 0.90，但 S_sampler < 0.70
              → prompts 几乎一样，但采样参数差异大
部分重叠     S_struct 在 0.50 ~ 0.90 之间
              → 共享部分块，但整体结构不同
不相关       S_struct < 0.50
```

**“结构相同换皮”** 是预设查重中最有价值的发现——这类预设通常是某个热门预设的衍生版，用户可能只想保留一个。

## 四、聚类：簇心校验

**坚持你 PK-29 修复的思路**，不用连通分量。预设查重中链式误聚风险更高——预设 A 和 B 共享 60% 的块，B 和 C 共享另外 60% 的块，但 A 和 C 可能只有 20% 重叠。

```text
1. 候选对按 S_raw 降序排列
2. 每对检查：
   · 与簇心的 S_raw ≥ T_cluster
   · 或簇内两两 S_raw ≥ T_cluster（小簇时）
3. 不满足则开新簇
4. 弹窗给可验证依据：identifier Jaccard + content Jaccard + 采样参数差异
```

## 五、字段级差异报告

聚类后，对同簇内每对预设输出**块级差异表**：

```text
预设 A: "MyPreset-v3.json"  (OpenAI 预设, 42 个块)
预设 B: "MyPreset-v2.json"  (OpenAI 预设, 40 个块)

块级差异：
  identifier          状态        content 相似度    备注
  main                ✅ 一致     0.98            ⚠️ 高度相似
  worldInfoBefore     ✅ 一致     1.00            完全一致
  worldInfoAfter      ✅ 一致     0.95
  jailbreak           ⚠️ A启用/B禁用 —               A 新增了此块
  custom_chain_of_thought ✅ 一致  0.12            ❌ 内容完全不同
  ... (其余 37 个块一致)

采样参数差异：
  temperature:   0.85 → 0.92   (+0.07)
  top_p:         1.00 → 1.00   (无变化)
  repetition_penalty: 1.10 → 1.15 (+0.05)

相似类型判定：内容相同重排（37/42 块内容一致，但 custom_chain_of_thought 位置从第 10 位移到第 25 位）
```

块级差异对齐可以复用项目 `textDiff.js` 的 **token 级高亮**，把“行”换成“块”。

## 六、纯 JS 实现路径（零新依赖）

### 6.1 读取与解析

**`parsecard`** 是当前最合适的选择：

```js
import { OpenAIPreset } from 'parsecard';

// 自动兼容 SillyTavern Chat Completion 预设
const preset = OpenAIPreset.fromJSON(jsonData);

// 访问 prompts
preset.prompts.forEach(p => {
  console.log(p.identifier, p.enabled, p.content);
});

// 采样参数
console.log(preset.temperature, preset.top_p);
```

`parsecard` 是 TypeScript 实现的面向对象库，零外部依赖，支持 Node.js 和浏览器双环境，覆盖 OpenAI 预设的 prompts 增删改查、启用状态和排序管理。

对于 Text Completion 预设（`instruct` + `context` 结构），可以直接 `JSON.parse` 后按字段访问——结构相对简单，不需要额外解析库。

### 6.2 可复用的项目能力

```text
已有能力                        复用方式
──────────────────────────────────────────────────────────────
minhash / simhash               块级 content 指纹
textDiff.js (token 级高亮)      块级差异对齐
簇心校验逻辑                    聚类阶段直接复用
```

### 6.3 分阶段落地

**第 1 阶段（1~2 天，零新依赖）**

```text
1. 实现预设类型检测（OpenAI / TextCompletion / Context / Instruct）
2. 提取 prompts 的 identifier 集合 + enabled 状态 + order
3. 逐块算 MinHash 指纹
4. 结构相似度 + 内容相似度 + 采样参数相似度融合
5. 簇心校验聚类
6. 输出块级差异表
```

**第 2 阶段（按需）**

```text
7. 接入 vectorManager 做块级 content 的语义精排（仅 top-N）
8. 支持 Text Completion 预设的 instruct/context 模板字段级对齐
9. 支持多语言块内容（如中文预设 vs 英文预设）的跨语言比较
```

**明确不做**：

- ❌ 不把采样参数纳入“是否重复”的核心判据（采样参数差异 ≠ 预设重复）
- ❌ 不用连通分量聚类
- ❌ 不索引全库向量
- ❌ 不引入 Python 工具链

## 七、特殊场景处理

### 7.1 OpenAI 预设 vs Text Completion 预设

两者结构完全不同（`prompts[]` vs `instruct`/`context`），**不应跨类型比较**。在查重时先按类型分组，组内再比较。

### 7.2 `prompt_order` 的 character_id 变体

`prompt_order` 数组可能包含多个 `character_id` 的条目（`100000` 是全局默认，其他是角色专属）。查重时应**只比较全局默认的顺序**（`character_id: 100000`），忽略角色专属的排序变体——否则同一预设在不同角色下会被判定为不同。

### 7.3 预设导出格式差异

SillyTavern 导出的预设可能包含 `extension_settings` 等额外字段，这些是扩展的私有配置，**不应参与相似度计算**。在解析后只提取核心字段（`prompts`、`temperature` 等），丢弃扩展字段。

### 7.4 采样参数的 null 值

预设 JSON 中采样参数可能为 `null`（表示使用默认值）。比较时应将 `null` 归一化为该参数的默认值，而不是当作 0 处理。

---

## 八、阈值建议

预设查重的阈值应**比角色卡更严格**，因为预设的结构差异（块增删、顺序变化）对行为影响更大：

```text
场景                              建议 T_similar    说明
─────────────────────────────────────────────────────
同类型预设，完整比较              0.85             结构 + 内容综合
仅比较结构（快速筛查）            0.75             只看 identifier + enabled
跨大版本（如 v1 精简 → v3 完整）  0.65             块增删较多
```

`T_cluster` 建议设为 `T_similar + 0.05`。

**这些阈值必须从真实预设库标定**。你先跑一轮单参数扫描，观察 precision/recall 曲线再定。

---

## 九、一句话总结

预设查重的核心是**结构优先**：先看 `identifier` 集合和 `enabled` 状态，再看 `prompt_order` 排序，最后看块内容。采样参数差异标记为“参数变体”而非“重复”。用 `parsecard` 的 `OpenAIPreset` 类做解析（纯 JS、零依赖），用项目已有 `minhash` 算块级指纹，用 `textDiff.js` 做块级差异对齐，聚类坚持**簇心校验**。**不要**把预设当成一堆文本去算整体相似度——那会丢失结构信息，把“换皮预设”和“真正不同的预设”混为一谈。

# 角色卡跨版本查重对比方案（V1 → V2 → V3）

## 一、先分清三类差异

跨版本查重比世界书查重多一层复杂度：**同一个角色在不同版本规范下，承载信息的字段位置和数量都不同**。直接拿 V1 卡和 V3 卡做字段级对比会大量误报。必须先做**版本归一化**。

### 1.1 V1 字段（兼容层，不在公开规范中）

V1 没有 `spec`/`spec_version`/`data` 嵌套结构，字段直接平铺在根对象上。六个核心字段：

```text
name, description, personality, scenario, first_mes, mes_example
```

V1 兼容字段不在 `spec_v2` / `SPEC_V3` 任何公开规范里，是 SillyTavern `src/character-card-parser.js` 的导出兼容层——旧前端只读顶层字段。

### 1.2 V2 字段

V2 引入 `spec: 'chara_card_v2'` + `spec_version: '2.0'` 的包装，所有角色字段移入 `data` 对象：

```text
data: { name, description, personality, scenario, first_mes, mes_example,
        creator_notes, system_prompt, post_history_instructions,
        alternate_greetings[], character_book?, tags[], creator,
        character_version, extensions }
```

关键行为差异：`system_prompt` 替换前端系统提示（空串回落用户设置），`post_history_instructions` 替换 ujb/jailbreak 位，两者必须支持 `{{original}}` 宏。`creator_notes` **不进 prompt**。

### 1.3 V3 字段（V2 超集）

V3 在 V2 基础上**只增不减**，`spec` 改为 `'chara_card_v3'`，`spec_version` 为 `'3.0'`。新增字段：

```text
assets?: Array<{type, uri, name, ext}>   // icon/background/user_icon/emotion
nickname?                                 // 存在则 {{char}} 替换为它
creator_notes_multilingual?: Record<ISO639-1, string>
source?: string[]
group_only_greetings: string[]            // MUST 存在，可空
creation_date? / modification_date?       // Unix 秒
```

V3 还引入**世界书装饰器**（`@@depth`、`@@position`、`@@role`、`@@activate_only_after`），这是跨版本查重中最容易被忽略的差异点。

### 1.4 载体差异（影响读取方式）

| 载体 | V1 | V2 | V3 |
|---|---|---|---|
| PNG/APNG | tEXt chunk `chara`（部分旧工具） | tEXt chunk `chara` | tEXt chunk `ccv3`；并存时优先 `ccv3` |
| JSON | 根对象平铺 | 根对象含 `spec`/`data` | 同 V2 |
| CHARX | — | — | ZIP 包，根目录必含 `card.json`；资源按 `embeded://` 引用 |

ST 导出行为：同时写 `chara`（V2）+ `ccv3`（V3 副本）两个 chunk，读取时 `ccv3` 优先。

---

## 二、核心策略：版本归一化 → 统一比较

跨版本查重的第一步不是算相似度，而是**把 V1/V2/V3 都映射到同一个规范化的比较视图**。

### 2.1 归一化映射

```text
归一化字段 → 来源（优先级：V3 > V2 > V1）

CORE_FIELDS = {
  name:                V3.nickname ?? V3.name ?? V2.data.name ?? V1.name
  description:         V3.data.description ?? V2.data.description ?? V1.description
  personality:         V3.data.personality ?? V2.data.personality ?? V1.personality
  scenario:            V3.data.scenario ?? V2.data.scenario ?? V1.scenario
  first_mes:           V3.data.first_mes ?? V2.data.first_mes ?? V1.first_mes
  mes_example:         V3.data.mes_example ?? V2.data.mes_example ?? V1.mes_example
  system_prompt:       V3.data.system_prompt ?? V2.data.system_prompt ?? ''
  post_history:        V3.data.post_history_instructions ?? V2.data.post_history_instructions ?? ''
  alternate_greetings: V3.data.alternate_greetings ?? V2.data.alternate_greetings ?? []
  character_book:      V3.data.character_book ?? V2.data.character_book ?? null
  tags:                V3.data.tags ?? V2.data.tags ?? []
}
```

**`nickname` 的处理要小心**：V3 的 `nickname` 存在时会替换 `{{char}}`，但 `name` 仍是原始角色名。查重时应该**同时保留两者**作为独立比较字段——两个卡 `name` 不同但 `nickname` 相同，可能是有意区分；`name` 相同但 `nickname` 不同，可能是同一角色的不同变体。

### 2.2 版本感知的字段权重

不同版本规范下，同一字段的信息密度不同。例如 V1 的 `description` 通常比 V2/V3 更长（因为 V1 没有 `creator_notes`/`system_prompt` 等字段分流信息）。建议按版本调整权重：

```text
字段权重表（按卡自身版本选择）：

字段            V1权重   V2/V3权重   说明
description      0.30     0.25       V1 中 description 是信息主载体
personality      0.25     0.20
scenario         0.15     0.10
first_mes        0.15     0.15       first_mes 是角色声音的直接体现
mes_example      0.10     0.10
system_prompt      —      0.10       V2+ 才有，V1 无此字段不参与
post_history       —      0.05
alternate_greetings —     0.05

跨版本比较时（如 V1 卡 vs V3 卡）：
  缺失字段不参与加权平均，权重按剩余字段归一化。
  例如 V1 卡没有 system_prompt，则 V3 卡的 system_prompt 不与 V1 卡的空串比较，
  而是从 V3 卡的总权重中剔除该维度。
```

### 2.3 V3 新增资源的处理

`assets` 数组包含 `uri`（可能是 `embeded://`、`ccdefault:`、https 或 data URL）。**不应把 `assets` 纳入相似度计算**——两张卡用同一张素材图不代表内容重复。但可以作为一个**辅助信号**：如果两张卡的核心字段高相似 + `assets` 的 `name` 和 `ext` 完全一致，强烈提示其中一张是另一张的派生版本。

`creator_notes_multilingual` 同理：多语言笔记是元数据，不参与内容相似度，但可作为“同作者/同角色”的佐证。

## 三、跨版本查重算法流程

### 3.1 整体架构

```text
读取（PNG/JSON/CHARX 自动识别）
→ 版本检测（V1/V2/V3）
→ 归一化到统一比较视图
→ 字段级特征提取（每字段独立指纹 + 向量）
→ 多路召回（字段级指纹 + keys 集合 + 向量）
→ 版本感知融合打分
→ 簇心校验聚类
→ 字段级对齐与差异报告
```

### 3.2 字段级特征提取

**不要**把整张卡的所有文本拼成一个字符串再算指纹——这会丢失字段结构信息。应该**每个字段独立**计算：

```text
对每个归一化字段 f：
  · 字符 n-gram 集合（n=2~4）
  · MinHash 签名
  · SimHash 指纹
  · 稠密语义向量（复用项目 vectorManager 的 MiniLM，仅用于精排）
```

`character_book`（内嵌世界书）单独处理，走你已有的世界书查重管线，结果作为**辅助维度**回传。

### 3.3 字段级相似度

对候选对 A、B 的每个字段：

```text
sim_f(A, B) = w_literal * J_minhash(f_A, f_B)
            + w_semantic * cos(vec(f_A), vec(f_B))   // 仅精排阶段启用

如果某字段在一方中缺失（版本差异）：
  该字段不参与相似度计算，权重从总分中剔除。
  但在差异报告中标记为 "版本差异：B 卡无此字段"。
```

### 3.4 融合打分

```text
S_raw = Σ_f [ weight_f(version_A, version_B) * sim_f(A, B) ]
        / Σ_f weight_f(version_A, version_B)

S = S_raw * (0.7 + 0.3 * p_len)
```

其中 `p_len = min(total_chars_A, total_chars_B) / max(...)`，`total_chars` 为所有参与比较字段的字符数之和。

**为什么不直接用 8 维权重**：你之前已经证明，用 8 对正样本拟合 8 个权重会过拟合。这里的字段权重建议**先固定**，只标定一个总阈值 `T`。字段权重来自“该字段在 prompt 中的重要性”这一先验，而非数据拟合。

### 3.5 聚类：簇心校验，不用连通分量

**这一点必须坚持你 PK-29 修复的思路**。跨版本查重中链式误聚风险更高——V1 卡 A 与 V2 卡 B 在某字段相似，B 与 V3 卡 C 在另一字段相似，A 与 C 可能完全不相关。

```text
1. 候选对按 S 降序排列
2. 每对检查：
   · 与簇心的 S >= T_cluster
   · 或簇内两两 S >= T_cluster（小簇时）
3. 不满足则开新簇
4. 弹窗给可验证依据：各字段的 Jaccard 值 + 版本差异说明
```

### 3.6 字段级对齐与差异报告

聚类后，对同簇内每对卡输出**字段级差异表**：

```text
字段              相似度    状态
name              1.00     完全一致
description       0.92     ⚠️ 高度相似（差 3 处）
personality       0.88     ⚠️ 高度相似
scenario          0.45     不同
first_mes         0.98     近乎一致
system_prompt     —        V1 卡无此字段
alternate_greetings —      V1 卡无此字段
character_book    0.76     内嵌世界书部分重叠
tags              0.60     标签部分重叠

版本标记：A=V2, B=V3
差异摘要：B 卡在 description 中新增了 2 段外貌描写，
          其余字段为 V3→V2 降级时的字段迁移。
```

字段级对齐可以复用项目 `textDiff.js` 的**行级 LCS + token 高亮**，把“行”换成“段落”或“句”。

### 4.2 与项目现有能力的对接

### 4.3 分阶段落地

**第 1 阶段（1~2 天，零新依赖）**

```text

3. 固定字段权重，融合打分
```

- ❌ 不引入 Python 工具链（FAISS / ColBERT / Cross-Encoder）

## 五、特殊场景处理

### 5.1 V1 → V2/V3 的字段迁移

V1 升级到 V2/V3 时，`description`、`personality` 等字段通常**原样迁移**，但 `system_prompt`、`creator_notes`、`alternate_greetings` 在 V1 中不存在，升级时会填充为空串或空数组。查重时，**V1 卡与 V2/V3 卡的这些“新增字段”不应作为差异点**——标记为“版本差异，非内容差异”。

### 5.2 V3 → V2 降级

降级是有损的：`assets` 中的非 icon 资源会丢失，`nickname` 会被合并回 `name` 或丢弃，`group_only_greetings` 被忽略。如果两张卡中一张是 V2、一张是 V3，且 V3 卡有大量 `assets` 而 V2 卡没有，**不应因此降低相似度**。在融合打分中，`assets` 不参与计算；在差异报告中单独列出。

### 5.3 同一角色不同 `character_version`

`character_version` 是作者自定的版本字符串，**不同作者格式不同**（`"1.0"`、`"v2-final"`、`"2026-09-23"`）。不要用字符串比较来判断“哪个更新”，而是用 `modification_date`（V3 才有）或文件修改时间。查重时，`character_version` 相同只作为辅助信号（+0.02 左右的 bonus），不作为核心判据。

## 六、阈值建议

跨版本查重的阈值应**比同版本查重更宽松**，因为版本差异本身会引入噪声：

```text
场景                        建议 T_similar    说明
─────────────────────────────────────────────────────
同版本（V3 vs V3）           0.80             直接比较
同版本（V2 vs V2）           0.80
跨版本（V1 vs V2/V3）        0.72             字段迁移导致部分字段无法比较
跨版本（V2 vs V3）           0.75             V3 新增字段不参与计算
```

`T_cluster`（聚类连边）建议设为 `T_similar + 0.05`，即同版本 0.85、跨版本 0.77~0.80。

**这些阈值必须从真实卡库标定**，不要凭感觉定。你已有的 35 本真实库 + 8 对真重复，可以先跑一轮单参数扫描，观察 precision/recall 曲线再定。

---

## 七、一句话总结

跨版本查重的核心是**先归一化再比较**：V1/V2/V3 的字段位置不同，必须映射到统一视图；缺失字段不参与计算而是标记为“版本差异”；`assets` 和 `creator_notes_multilingual` 不纳入相似度；聚类坚持**簇心校验**不用连通分量；字段级差异报告复用 `textDiff.js`。纯 JS 库（`@lenml/char-card-reader` + `parsecard`）即可完成读取和归一化，零 Python 依赖，符合项目“零原生依赖”约束。
