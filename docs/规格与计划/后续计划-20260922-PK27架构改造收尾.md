## 二、本轮实测数据（可复现）

### 2.1 加载速度（用户问「5000 本多少秒 + 有无提速空间」）

**s5000（5401 个 `.json` / 34.8GB）：**

| 阶段 | 冷缓存（首次） | 热缓存（第二次起） |
|---|---|---|
| **① 阶段 1（秒开）** `readdir`+`stat`，**零读盘** | ~780ms | **~780ms** |
| **② 阶段 2（后台）** 读全文+`JSON.parse`+L1 | **233.5s（3.9 分钟）** | **0ms**（零读盘） |
| **总计** | **~234s** | **~0.8s** |

**瓶颈定位**：阶段 1 的 **83% 是 `stat`**（649ms / 5001 文件）= **磁盘元数据物理下限**。

**⚠️ 已验证无效的三条优化（全部实测排除，代码已回滚）：**

| # | 尝试 | 实测 | 结论 |
|---|---|---|---|
| 1 | 批量 `Promise.all(stat)` 后统一判定 | **1164ms（更慢）** | ❌ 并发开销 > 收益 |
| 2 | 跳过指纹验证（`rescan:true`） | 1550 vs 1580ms | ❌ **指纹验证不是瓶颈** |
| 3 | 提高并发（T6 实验 2→12） | 仅改善 **3%**，内存 59→146MB | ❌ 瓶颈在磁盘 I/O |

**⇒ 结论：无提速空间**。阶段 1 已到磁盘下限；阶段 2 已被热缓存完全消除。

## 三、本轮踩到的坑（已修，务必记住）

| # | 坑 | 教训 |
|---|---|---|
| 1 | **热缓存下 L1 摘要全丢**（首次正常、再次全丢） | 阶段 1 缓存命中分支**没带 `keyHashes`** 且 `metaPending: !hit` → 命中即跳过阶段 2 |
| 2 | **「bottom-k + 倒排共现」在极端同源库下失效**（且重演 PK-25） | 所有桶都高频 → 整桶跳过 → 候选为空；**分组已缩范围时应优先用简单全量** |
| 3 | **simhash 位向量不能用 `estimateSimilarity`** | 对 `[lo,hi]` 只返回 0 或 1 → **假阳 + 假阴同时存在** |
| 4 | **多阶段进度条各阶段自己 reset** | → 横跳 / 倒退 / 变光条；**必须有统一状态机**（各阶段只推进，出口负责收尾） |
| 5 | **探针判据把「收尾归零」误判为「倒退」** | 判据必须只在 `scanning === true` 窗口内检查单调性 |
| 6 | **压力库是硬链接放大产物**（40 组全是同一本书） | 不能用于阈值实验（首次跑出「汉明距离全 0」） |
| 7 | **BigInt simhash 太慢**（1387ms/本 → 全库 124.9 分钟） | 改 number 双 32 位 + 采样 step=4 → **43ms/本** |
| 8 | **AR-46：进度条探针只采了「条宽」**（没采数字） | ⇒ **5/5 通过是假绿**；用户二次报出才发现。**探针必须采「用户实际看到的东西」（渲染后 DOM 文本）**，不是内部变量 |
| 9 | **同一个 UI 元素的两部分走了两条数据源**（条宽 ← `dedupeScanPercent`；数字 ← 透传 `wbScanProgress`） | AR-43 / AR-46 是**同一缺陷的两次爆发**（前者数字恒 0 / ?，后者扫描结束数字掉 0 / ?）⇒ **必须收敛到唯一写入入口** |
| 10 | **散落的进度赋值点**（8 处，其中 2 处漏了 `Math.max`） | 漏保护的 2 处（同步定时器 / 阶段初始化）正是**倒退来源** ⇒ 收敛到 `applyDedupeProgress()` |
| 11 | **阈值复核用「自动标注」在硬链接库上失效**（误报率虚高 66%） | s1000 里「同族不同副本」被误标为无关 ⇒ **必须 MD5 去重 + 前缀精确标注**（`_probe-simhash-verify2.mjs`） |
| 12 | **压测探针的判据会随架构演进过期**（S2' 后查重**不再读正文**，而旧断言要求「必须逐本载入再释放」） | 旧断言把**正确行为判为失败** ⇒ 探针判据必须跟架构同步；**看到失败项先取证是「真缺陷」还是「探针过期」** |
| 13 | **文档记录的「待办」可能早已解决**（git 代理、PK-19、`performance.memory` 降级、P2/P3 等 8 项） | 接活前**必须逐项 grep 源码核实**，否则会白做已完成的工作 |
| 14 | **`requestAnimationFrame` 等「渲染完成」在窗口不可见时被节流**（**第二次踩**） | 实测**假耗时 9.41s / 6012.74s**（真实仅 1.00s）⇒ **判性能必须用 `setTimeout(0)` + DOM 节点数** |
| 15 | **「分批」如果 `await` 首批，会把首屏一起阻塞** | s5000 冷缓存首批 120 本要 **5.13s** ⇒ 首屏从 782ms 恶化到 **5.51s**。修：**两批都不 `await`**（列表先渲染，元数据到了就地更新） |
