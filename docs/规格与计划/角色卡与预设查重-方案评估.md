## 一、预设查重方案

### 1.1 ✅ 核实为真的部分

#### ① `parsecard` 的 `OpenAIPreset` 真实存在（库选型准确）

```text
npm view parsecard  →  v2.0.4 ｜ 零 dependencies（真纯 JS）
导出：export { OpenAIPreset, DEFAULT_PROMPT_ORDER_CHARACTER_ID,
              DEFAULT_OPENAI_PROMPTS, DEFAULT_OPENAI_PROMPT_ORDER } from './OpenAIPreset.js';
公开 API：prompts / promptOrder / temperature / topP / hasPrompt / getPrompt /
         isPromptEnabled / listPromptEntries / movePrompt / isPromptEnabled ...
```

方案对 `parsecard` 的描述（TypeScript、面向对象、覆盖 prompts 增删改查 + enabled + 排序）**逐条属实**。

#### ② ★ 结构指纹判别力**充足**（实测跨度 96.6 个百分点）

方案主张「`identifier` 集合 Jaccard 作为 S_struct 主成分（权重 0.50）」。真实库实测：

| 对比 | 结构 Jaccard | 内容 Jaccard |
|---|---|---|
| `A.U.T.O.预设 v1.0` ↔ `万象枢机 2.5` | **99.3%** | **57.0%** |
| 其余 9 对（无关预设） | 2.6% ~ 4.9% | 0.0% ~ 1.5% |

⇒ **判别力来自「自定义块」**：5 个预设合计 **685 个去重 identifier / 858 个块位**，
远超 12 个默认骨架块，骨架造成的「基础分」被稀释。

> 对照实验（剔除 12 个骨架块后重算）：无关对 `3.6% → 0.0%`（更干净），同源对 `99.3% → 99.2%`（几乎不变）
> ⇒ 剔除骨架是**可选优化**，非必需。

#### ③ ★★ 「改名同源」是真实现漏洞，方案精准命中

**实测坐实**：`A.U.T.O.预设 v1.0.json` ↔ `万象枢机 2.5.json` —— **文件名完全不同**，
但结构 **99.3%** 相同（正文 840KB vs 2.66MB）。

而当前实现（`useDedupe.js` `startPresetDedupeScan`）**只按 `data.name` 聚类**：

```js
// 1. 按预设名称聚类（data.name 优先，兜底文件名）
presets.value.forEach(p => {
    const name = ((p.data && p.data.name) || (p.name || '')...).trim();
    groups[name].push(p);
});
const potentialGroups = Object.entries(groups).filter(([_, list]) => list.length > 1);
```

⇒ **不同名的同源预设永远不会进入比较**（漏报）；且有同名的才会比 ⇒
这是 **AR-48「聚错组」的镜像缺陷**（那个是聚错，这个是漏聚）。

**方案主张的「结构优先」正是这个缺口的正解。**

#### ④ 「采样参数不纳入核心判据」—— 自洽且正确

实测 5 个预设的采样参数**全部存在、无 null**（`temperature` / `top_p` / `top_k` /
`repetition_penalty` / `min_p` / `top_a` / `frequency_penalty` / `presence_penalty` / `openai_max_tokens` 均 5/5）。

方案自己指出「参数差异标记为『参数变体』而非重复」—— 与项目「不把参数只差 0.05 判为重复」的判断一致。

#### ⑤ 簇心校验（不用连通分量）—— 与 PK-29 一致

方案两处主动写「坚持 PK-29 的簇心校验思路」，并对链式误聚风险做了正确描述。

### 1.2 ⚠️ 需修正的部分

#### ① `character_id` 处理**不完整**（方案只写 100000，parsecard 常量是 100001）

| 来源 | 值 |
|---|---|
| 方案 §7.2 | `100000` 是全局默认 |
| `parsecard` 导出常量 | `DEFAULT_PROMPT_ORDER_CHARACTER_ID = 100001` |
| **真实库实测** | **两者并存**：`100000` → 2 组 ｜ `100001` → 5 组 |

⇒ **必须两者都处理**（或干脆「取该预设所有 order 组中覆盖度最高的那个」），
不能按任一单一常量写死。

#### ② 块数规模**低估一个数量级**

| 指标 | 方案断言 | 真实库实测（5 个 OpenAI 预设） |
|---|---|---|
| 块数 | 「60+ 模块的 mega-preset」 | min=**118** ｜ p50=**138** ｜ max=**261** |

⇒ 规模假设需按 100~300 量级重估（影响算法复杂度与 UI 展示设计）。

#### ③ 权重与阈值**无法从真实库标定**（样本量不足）

| 需要标定 | 方案建议值 | 可用样本 |
|---|---|---|
| S_struct / S_content / S_sampler | 0.50 / 0.35 / 0.15 | **仅 5 个 OpenAI 预设** |
| T_similar | 0.85 / 0.75 / 0.65 | **仅 1 对同源** |
| T_cluster | T_similar + 0.05 | 同上 |

⇒ **3 个权重 + 4 个阈值，用 1 对正样本标定 = 必然过拟合**（与项目 PK-29 的教训同型：
S0.5 用合成样本定 T=19，真实库实测误报 10/18）。

**建议**：先按**方案给的经验值**上线（明确标注「启发式、未标定」），
待预设库积累到 **20+ 个 OpenAI 预设 / 10+ 对同源**再回头标定。

#### ④ 「跨类型不比较」在当前库**无法验证**

方案主张「OpenAI 预设 vs Text Completion 预设不应跨类型比较」。
真实库实测：**23 个 JSON 中只有 5 个是 OpenAI 预设**，其余 17 个是**非预设文件**
（`credential_*.json` / `regex-*.json` / `SPMv6.0 (世界书)` / `TavernDB_template` 等），
**没有一个 Text Completion / Context / Instruct 预设样本**。

⇒ 该分支属「防御性设计」，可保留，但**无真实样本可验证**（落地时需构造合成样本）。

## 二、角色卡跨版本查重方案

### 2.1 ✅ 核实为真的部分

#### ① V1/V2/V3 **真实并存**（跨版本查重是真需求）

真实卡库实测（45 张可解析）：

| 版本 | 数量 | 占比 |
|---|---|---|
| V1 | 1 | 2.2% |
| V2 | 21 | 46.7% |
| V3 | **22** | **48.9%** |
| 未知 | 1 | 2.2% |

⇒ 近半数卡是 V3，「必须做版本归一化」的判断成立。

#### ② ★★ **当前查重忽略 71.7% 的文本信息**（重大缺口，实测坐实）

现有 `extractContentText`（角色卡分支）只取 **5 个字段**：

```js
return [d.description, d.personality, d.scenario, d.first_mes, d.mes_example]
    .filter(Boolean).join('\n');
```

真实库字段填充率与字符量对比：

| 字段 | 填充率 | 是否参与查重 |
|---|---|---|
| `description` | 21/45 | ✅ |
| `first_mes` | 38/45 | ✅ |
| `scenario` | 8/45 | ✅ |
| `mes_example` | 6/45 | ✅ |
| `personality` | 5/45 | ✅ |
| **`character_book`** | **36/45（80%）** | ❌ **完全忽略** |
| `creator_notes` | 15/45（33%） | ❌ |
| `alternate_greetings` | 13/45（29%） | ❌ |
| `system_prompt` | 2/45（4.4%） | ❌ |
| `post_history_instructions` | 2/45（4.4%） | ❌ |

```text
当前查重用（5 字段）： 30,958 字符  (28.3%)
被忽略（5 字段）：   130,167 字符  (71.7%)
```

⇒ **`character_book`（内嵌世界书，80% 的卡都有）完全不参与角色卡查重** ——
这是方案最有价值的发现，且与项目既有能力**天然可接**（世界书查重管线已成熟）。

#### ③ 「8 维权重会过拟合」—— 诚实且与项目结论一致

方案明确写「你之前已经证明，用 8 对正样本拟合 8 个权重会过拟合」，
并主张「字段权重固定（来自『字段在 prompt 中的重要性』先验），只标定一个总阈值 T」。
**这个取舍是对的。**

#### ④ 缺字段「不参与加权」而非「按空串比较」—— 正确

方案：

> 缺失字段不参与相似度计算，权重从总分中剔除。但在差异报告中标记为「版本差异」。

这正是 V1↔V3 比较时最容易做错的地方（按空串比 → 系统性低估）。

### 2.2 ❌ 事实错误（会直接导致实现踩坑）

#### ① ★★★ 「读取时 ccv3 优先」与真实库**相反**

方案 §1.4 与 §七：

> PNG/APNG：V1 = `chara`（部分旧工具）｜V2 = `chara`｜V3 = **`ccv3`；并存时优先 `ccv3`**
> ST 导出行为：同时写 `chara`（V2）+ `ccv3`（V3 副本），**读取时 `ccv3` 优先**。

**实测（43 张 PNG，逐 chunk 解析）**：

| chunk 组合 | 数量 | spec |
|---|---|---|
| `chara` 单独 | 21 | `chara_card_v2` |
| `chara` 单独 | **20** | **`chara_card_v3`** |
| `ccv3` 单独 | **1** | `chara_card_v3` |
| 其他（含 `Title`/`Software` 等元数据块） | 3 | 含 1 个 V3 |

```text
V3 数据在 chara chunk：21  ｜  在 ccv3 chunk：1
```

⇒ **V3 数据 95% 存在 `chara` chunk 里**。「ccv3 优先」若实现成「只读 ccv3」，
会**漏掉 21/22 的 V3 卡**；正确的判据是**解析 `spec` 字段**，与 chunk 名无关。

> ✅ **好消息**：项目现有 `pngParser.js` 已正确处理
> （`if (keyword === 'chara' || keyword === 'ccv3')` 同时收两个 chunk），**此处不需要改**。
> ⚠️ 但**必须写进文档**，否则后续维护者可能按「ccv3 优先」的思路「优化」掉 chara 分支。

#### ② V3 新字段与真实库**完全不符**

方案用了大量篇幅讨论 V3 新增字段。真实库实测出现率：

| V3 新字段 | 方案定位 | 真实库实测 |
|---|---|---|
| `assets` | 「不纳入相似度，但可作辅助信号」 | **0 / 45** |
| `nickname` | 「查重时应同时保留 name 与 nickname」 | **0 / 45** |
| `creator_notes_multilingual` | 「不参与内容相似度，可作佐证」 | **0 / 45** |
| `source` | — | **0 / 45** |
| `group_only_greetings` | 「MUST 存在，可空」 | 32 / 45 ✅ |
| `creation_date` / `modification_date` | — | 4 / 45 |

⇒ `assets` / `nickname` / `creator_notes_multilingual` 的处理逻辑**在真实库中无样本可验证**，
优先级应**降到最低**（或先不做）。

#### ③ `system_prompt` 权重 0.10 **偏高**

方案字段权重表给 `system_prompt: 0.10` / `post_history: 0.05`。
真实库实测这两项各只有 **2/45（4.4%）** 填充。

⇒ 对 95% 的卡这两个维度权重会被「剔除后归一化」逻辑吃掉，
建议**降权或不分权重**（直接按填充情况动态归一化即可）。

### 2.3 ⚠️ 库选型与项目现有能力**高度重叠**

方案的库建议：

| 推荐库 | 项目现状 | 评价 |
|---|---|---|
| `@lenml/char-card-reader` | 已有 `pngParser.js`（PNG tEXt/iTXt + **WebP 深度扫描** + 损坏 PNG 提取） | ❌ **功能重复** |
| 同上 | 已有 `cardLoader.normalizeCardData`（V1→V2 归一化 + tags/alternate_greetings/extensions 兜底） | ❌ **归一化重复** |
| 同上 | 已有 `isCharacterCardData` / `getCardRejectReason`（V1/V2/V3 鉴定 + 拒绝原因诊断） | ❌ 鉴定重复 |
| `parsecard`（角色卡类） | 同上 | ❌ 重复 |
| `@character-foundry/normalizer` | 同上 | ❌ 重复 |
| `@character-foundry/charx` | **CHARX 完全未实现**（源码 0 处引用） | ⚠️ 唯一真缺口，但真实库 **0 个 CHARX 文件** |
| `@overworks/chara-card-core` | 同 `char-card-reader` | ❌ 重复 |

🔴 **最大风险：两套归一化口径并存**

项目 `normalizeCardData` 已在**所有加载路径**生效（`cardParseWorker` / `useCardCrud` /
`useSnapshots` / `App.vue` 三处加载点）。若再引入 `@lenml/char-card-reader` 做归一化，
会出现**同一张卡在两条路径下字段口径不同** —— 正是项目 **DF-17「字段口径」坑**的土壤，
且该坑在历史上出现过多次（`wb.data` / `v3` 字段迁移等）。

**结论**：**不建议引入任何读卡库**。项目缺的不是「读卡」，而是
「**字段级指纹 + 结构归一化视图**」这一**纯算法层**（可在 `js/utils/` 自写纯函数）。

### 2.4 ✅ 方案里**真正有价值但未被强调**的一点

**JPEG 支持不一致**（我核查时发现的）：

| 位置 | 声明/行为 |
|---|---|
| `HeaderBar.vue:20`（导入对话框） | `accept=".png,.webp,.jpg,.jpeg,.json"` ← **声明支持 JPEG** |
| `cardLoader.js:240`（注释） | 「用户选择的文件（.json / .png / .webp / .jpeg / .jpg）」 |
| `main.js:1424`（磁盘扫描） | `if (ext !== '.png' && ext !== '.webp' && ext !== '.json') return []` ← **跳过 JPEG** |
| `main.js:4929` | 同上 |

⇒ **导入对话框允许选 JPEG，但磁盘扫描会跳过它们**（扫描不到 = 库不加载）。
这是一个**独立于两份方案的真实缺陷**，值得单独登记。

## 四、口径与约束（落地时不得违反）

1. **`character_id` 必须同时兼容 `100000` 与 `100001`**（真实库两者并存），
   且**不得**按任一常量写死。
2. **PNG 版本判定必须解析 `spec` 字段，不得依赖 chunk 名**
   （V3 数据 21 个在 `chara`、仅 1 个在 `ccv3`）。
   现有 `pngParser.js` 同时收两个 chunk 的做法**是正确且必需的**，不得「优化」掉。
3. **不得引入第二套卡片归一化逻辑** —— 一切归一化走 `cardLoader.normalizeCardData`。
4. **聚类必须用簇心校验**（`unionFindGated`），不得用连通分量。
5. **阈值/权重若采用方案经验值，必须在代码与文档中标注「启发式、未标定」**，
   并在样本量达标后回头标定（参照 PK-29 的教训：未标定阈值会造成 10/18 误报）。
6. **判定只产出标签，不决定分组**（与 `similarityType.js` 的既有契约一致）。
