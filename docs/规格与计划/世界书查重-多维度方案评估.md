## 一、评估结论（30 秒版）

**方向对，栈不对。**

| 方案要点 | 评估 | 理由 |
|---|---|---|
| ① 多维度加权（keys / content / title / meta） | ✅ **采纳** | 真缺口：内容查重**完全没用 keys** |
| ② 长度惩罚 `0.7 + 0.3×min/max` | ✅ **采纳** | 真缺口，且成本极低 |
| ③ 相似类型分类（触发重复 / 内容可合并 / 设定冲突） | ✅ **采纳** | 可解释性核心，数据全在手 |
| ④ 酒馆特化判定规则（§4） | ✅ **采纳** | 最有洞察，**零额外成本** |
| ⑤ 句级对齐（Smith-Waterman） | ❌ **否决** | 实测收益 ≈ 0（见 §四） |
| ⑥ 开源工具表（7 个 Python 项目） | ❌ **不可用** | 全是 Python/R，本项目是 Electron/JS，且**零原生依赖**是既定决策 |
| ⑦ FAISS / ColBERT / Cross-Encoder / LLM 精排 | ❌ **不可行** | 量级错配（见 §三-2） |
| ⑧ 8 维权重 + 4 档阈值 | ⚠️ **需标定** | 真实库仅 8 对真重复，拟合 8 个权重 = 过拟合 |
| ⑨ 「连通分量」聚类 | 🚫 **危险** | **正是 PK-29 刚修掉的病根**，照搬会复现同一 bug |

## 二、已落地：类型判定 + 长度惩罚（第 1 步）

### 2.1 落地内容

| 文件 | 改动 |
|---|---|
| `js/utils/similarityType.js`（**新增**） | 纯函数模块：`classifySimilarity()` / `lengthPenalty()` / `SIM_TYPE` / `SIM_TYPE_META` |
| `js/composables/useDedupe.js` | 内容查重分组构造处接入：算 keys 相似度（复用 L1a）+ 判定类型 + 挂展示字段 |
| `js/components/ContentDedupeModal.vue` | 展示类型标签 / 触发词重合度 / 长度惩罚 / 可执行建议；**高风险类型降级清理按钮** |
| `test/similarityType.test.mjs`（**新增**） | 19 例：6 类型边界 + 长度惩罚 + 降级路径 + 健壮性 + **契约断言** |

### 2.2 六种类型与处理建议

| 类型 | 判据 | 用户该做什么 |
|---|---|---|
| 🔁 **完全重复** | `exactContentHash` 一致 | ✅ 可安全清理 |
| 🔑 **触发重复** | keys 高 + content 低 + 长度相近 | ⚠️ 触发条件撞车 → 合并 keys 或改写，**别直接删** |
| 🔀 **内容可合并** | content 高 + keys 低 | 🔀 合并为一本 |
| 🚨 **设定冲突** | keys 高 + content 低 + **长度悬殊** | 🚨 **需人工裁决**（按钮已降级警示） |
| 🔍 **高度相似** | 其余（如两者都高但指纹不同） | 🔍 逐条对比后再决定 |
| ⚠️ **仅名称相同** | 两侧都低 | **请勿清理**（按钮已降级警示） |

### 2.3 为什么成本≈0

方案所需的四类数据**全部已在手**，本模块只做**组合与判定**：

| 数据 | 来源 | 是否已落盘 |
|---|---|---|
| keys 相似度 | L1a `keyHashes` + `compareKeyHashes()`（纯整数双指针） | ✅ `main.js:1100` |
| content 相似度 | 查重时已算的 MinHash 估计值 | ✅ 内存 |
| 完全相同 | `exactContentHash` | ✅ `main.js:1296` |
| 长度 | 查重时已算的 `textLen` | ✅ 内存 |

### 2.4 ⚠️ 关键设计约束（防误删）

**类型判定只产出「标签」，绝不参与「是否同组」的判定。**

- 「是否同组」仍由 PK-29 修复后的**三闸门**负责（simhash 预筛 + MinHash 复核 + 簇心校验）；
- 单测里有一条**契约断言**：`classifySimilarity()` 的返回值**不得**包含任何分组/清理决策字段
  （`inGroup` / `sameGroup` / `keep` / `remove`），防止后人误用。

> 理由：真实库实测过「反向结论最危险」—— 一旦类型判定影响分组，
> 就会重演 PK-29 / AR-48 那类「一键误删真书」的事故。

## 三、否决理由（附实测证据）

### 3.1 「连通分量」聚类 = PK-29 病根

方案 §3.6 推荐「连通分量：最简单快速」。这正是 2026-09-23 修掉的缺陷：

```text
连通分量（朴素并查集）只要「每对」合法就合并
⇒ A~B ≤ T、B~C ≤ T，但 A~C = 29（T=16）时三者仍被串成一组
⇒ 真实库实测：6 本一组，含与主项距离 29 的《鬼物》（真实 Jaccard 0.1%）
   而弹窗标「⚠️ 高度相似」+ 按钮「清理其余」⇒ 一键误删真书
```

**修法**：簇心校验（合并前要求双方**都与对方簇心**通过闸门）。**方案若照搬连通分量，等于重新引入该 bug。**

### 3.2 ColBERT / 稠密向量量级错配

| 项 | 实测 |
|---|---|
| 压测库 | **s5000 = 5001 本 / 34.8GB** |
| ColBERT 需要 | **token 级**嵌入矩阵 |
| 估算 | 34.8GB 中文 ≈ 8~11B tokens × 768 维 × 4B ≈ **24.6 TB** |
| 退到句级（500 字/块） | 23M chunks × 384 维 × 4B ≈ **35GB 常驻**，本地 MiniLM 推理 ≈ **数十小时** |

> 项目 `vectorManager.batchMatch` 是为「**标签池**」（几十~几百标签）设计的，**不是**全文检索引擎。

### 3.3 开源工具表整表不可用

| 方案推荐 | 语言 | 落地方式 |
|---|---|---|
| `codomyrmex/data_curation` / `DedupKit` / `SemHash` / `Semantic-Text-Deduplicator` | Python | ❌ 需 Python sidecar |
| `textreuse` | **R** | ❌❌ 需装 R |
| `RAGatouille`（ColBERT） / `mxbai-rerank` / `RankLLM` | Python | ❌ 需 sidecar（+ GPU） |

**项目既定决策**（`世界书大库-加载与查重架构方案.md` §十二）：

> 「本项目至今**零原生依赖**（纯 Electron + Vue）。引入 better-sqlite3 会增加打包复杂度、跨平台二进制风险」

连 SQLite 都因「原生依赖」被列为备选，而方案要引入 **4 个 Python 栈**。

### 3.4 权重与阈值未标定（过拟合风险）

方案给出 8 个「经验权重」与 4 档阈值，**均无标定数据**。且方案**自身矛盾**：

| 位置 | content | keys | title | meta |
|---|---|---|---|---|
| §3.4（8 维） | ≈0.75 | 0.15 | 0.05 | 0.05 |
| §4（酒馆特化） | **0.6** | **0.2** | 0.1 | 0.1 |

而项目刚吃过「凭感觉定阈值」的亏：

> S0.5 声称「负样本 min 31」→ 定 T=19 → **真实库实测无关对低至 17** → 10/18 对纯误判。

**真实库目前只有 8 对真重复** —— 用 8 个正样本拟合 8 个权重是教科书级过拟合。
**建议**：维度砍到 3 个（content / keys / 长度），权重从**扩标后的真实库**标定。

### 3.5 一处技术细节错误

方案写 `sim = 1 - Hamming/B` 当相似度 —— **在位向量语义下不成立**。
项目实测：把 simhash 的 `1 - d/64` 当相似度展示会严重误导（**距离 19 → 显示 70%，真实重叠 0.1%**）。
已于 PK-29 改为「simhash 只做预筛，展示值走 MinHash 真实 Jaccard」。

## 四、为什么否决「句级对齐」（实测数据）

### 4.1 实测：真实库 7,424 条词条

| 指标 | 实测值 |
|---|---|
| 单行词条（无换行） | 5,716 条（**77.0%**） |
| 单行长度 | p50 = **122** / p90 = 331 / p99 = 391 / max = 1,643 |
| **长度 > 500 字符**（行内 LCS 的降级门槛） | **仅 1 条** |

### 4.2 关键：行级 diff 对单行**不是**整段标记

`js/utils/textDiff.js` 的 `diffOneLine` 会「剥公共前后缀 + **行内 token 级 LCS**」
（CJK 按单字、拉丁按整词），单行词条照样细粒度对比：

```js
const MAX_INLINE_PRODUCT = 250000;   // 行内 LCS 规模积上限 → 单行 ≳ 500 字符才降级
```

| 覆盖情况 | 条数 |
|---|---|
| 行内 token 级**正常**覆盖 | **5,715 / 5,716（99.98%）** |
| 行内也降级（>500 字符） | **1** |

### 4.3 结论

> 句级切分只能改善 **1 条词条（0.02%）**，成本却是：改造 diff 引擎 + 新增切句/对齐算法 +
> 处理中文标点边界 + 大量回归测试。
>
> **⇒ 否决。** 真要改，也是先改 `diffOneLine` 的超长降级策略（按标点二次切分），
> **而不是**引入 Smith-Waterman（O(n·m)，真实库最大单本 898,436 字符 → 8×10¹¹ 单元/对，完全不可行）。

### 5.1 ✅ 第 2 步落地详情（2026-09-24）

**实际做了两件事，第三件刻意没做：**

| # | 事 | 位置 |
|---|---|---|
| 1 | keys 相似度接入**打分**（`0.75×内容 + 0.25×keys` × 长度惩罚） | `js/utils/similarityType.js` 的 `classifySimilarity()` |
| 2 | **综合分排序**（组内按 `_score` 降序）+ **弹窗展示综合分** | `useDedupe.js` / `ContentDedupeModal.vue` |
| ❌ | **权重标定** —— **刻意不做**（真实库仅 8 对真重复，拟合 3 个权重 = 过拟合） | — |

**排序实现的两个约束（踩过才知）**：

- ⚠️ **排序不能动 `master`** —— 类型判定是逐项 vs `list[0]`（内容最长者），若把它排走，基准版会变、`_simPct` 全错 ⇒ 做法是**先摘出 master、只排其余项、再拼回开头**；
- ⚠️ **排序必须在 `_score` 算完之后** —— 否则排到 `null`。

**修复的真缺口**：`_score` 原本**算了却从未被消费**（不排序、UI 不显示）—— 属于「算了不用」的死代码。

### 5.2 第 3 步的前置条件（未变）

⚠️ **必须先扩标注集**。真实库当前只有 8 对真重复 —— 在这个基础上调权重，
只会把权重拟合到那 8 对样本上。**扩标到 50+ 对之后**再谈权重标定。

## 六、给外部方案的正面回应

方案最有价值的三点**已被采纳**（多维度、长度惩罚、类型分类 + 酒馆特化规则），
且落地成本极低（数据全在手、零新依赖、1~2 小时）。

**未被采纳的部分不是「不好」，而是「与项目约束不匹配」**：

- 技术栈：Python/R 工具链 vs 项目「零原生依赖」；
- 量级：ColBERT/FAISS 面向「万级文档的语义检索」vs 项目「34.8GB 正文的本地去重」；
- 标定：8 维权重需要标注集支撑，而项目当前只有 8 对真样本。

**若未来出现以下信号，可重新评估被否决项**：

| 信号 | 可重开项 |
|---|---|
| 落盘索引 > 150MB 或出现「按触发词搜书」需求 | SQLite（D2 第三选项） |
| 标注集 > 500 对 且 需要跨语言/改写识别 | 语义召回（复用已有本地 MiniLM，**不引入 FAISS**） |
| 用户明确要求「句级差异报告」 | 改 `diffOneLine` 的超长降级策略 |
