# 🔒 内部信息 — 写什么、写在哪

> **本文规定「内部可见信息」的边界与载体**：哪些内容属于内部、应当写进哪些文件、绝对不可以出现在对外内容里。
> 配套：[`用户可看信息.md`](用户可看信息.md)（对外怎么写）、[`一条龙-发布流程.md`](一条龙-发布流程.md)（流程本身）。
> 由来：2026-09-13 用户明确要求「要分清内部文件和外部用户可以看的更新内容文件」。
> 最后更新：2026-09-13

---

## 一、判据（一句话）

> 句子里出现 **文件名 / 函数名 / 脚本名 / 内存 MB 数 / 阶段耗时 / `crash.log` 原文 / 内部坑记录 / 未发布计划** → **属内部**，不得进对外内容。

反过来，**用户能感知的现象**（变快了 / 不再崩 / 位置变了 / 修好了哪个毛病）才允许出现在对外内容里。

---

## 二、载体清单（内部信息写在这些地方）

| 载体 | 定位 | 里面写什么 | 可见性 |
|---|---|---|---|
| `CHANGELOG.md`（仓库根） | **版本技术总表** | 每个版本的完整技术细节：改了哪些文件、机制、实测数字、验证命令与结果、踩坑与教训 | 内部（在仓库里，但**不粘进 Release 正文**） |
| `docs/bugs/**` | **缺陷库** | 现象 / 根因 / 修复 / 验证 / 来源，按领域编号（AR/DF/PK/RL/CT） | 内部 |
| `docs/技术支持/**` | **技术资产** | 完整代码片段、实测技术数据、外部 API 参考、格式规范 | 内部 |
| `docs/**` 其余 | 规格与计划 | 实现规格、移植检查报告、升级计划、测试日志 | 内部 |
| `AI交接指导.md`（仓库根） | 指导 | 架构、工作流、铁律、缺陷地图（**导航**性质，不含具体数字细节） | 内部（面向接手者） |
| `README.md`（仓库根） | 半对外 | 功能说明、截图、下载与构建说明、产物名与版本号、开发指南 | **用户/开发者都能看** → 其中的**功能描述**可以，**内部排查记录不行** |
| 仓库记忆 `/memories/repo/**` | AI 私有笔记 | 约定、构建命令、踩坑、修复结论 | 内部（不进 git 文档） |

### 允许写进内部文档的内容（示例）

- 具体文件与函数：`js/utils/cardSlim.js`、`slimLibraryIfNeeded()`、`buildAsync(..., { reuse: true })`
- 精确数字：堆 2,891MB → 2,053MB；首屏 79.9s → 43s；22,372 卡 / 349,648 token
- 探针与脚本：`scripts/_cdp-mem.mjs`、`capacity-check.ps1 -ReplicaDir`
- 崩溃原文：`render-process-gone {"reason":"oom","exitCode":-536870904}`
- 内部坑与教训：「`requestIdleCallback` 在隐藏窗口永不回调」「不要为便宜的数据加缓存」
- 未发布的计划：P1b、冷启动真机复测、移动版未同步

## 三、`CHANGELOG.md` 结构规范

```markdown
# SillyTavern 角色卡管理器 · v1.6.2 → vX.Y.Z 更新汇总

## 🚀 vX.Y.Z（一）<专题名>
### 🔴 修复 1：<一句话现象>
- 文件 / 机制 / 根因 / 修复
### 🔬 验证
- `npm test` → N/N；端到端脚本 → 结果；实测数字
```

- 一个版本可以有多个 `（一）（二）（三）…` 专题段（按主题拆，不按时间）；
- 每段结尾**必须有「🔬 验证」**，写命令 + 结果数字 —— 这是后人判断「能不能信」的依据；
- 页首的**版本区间**（`v1.6.2 → vX.Y.Z`）必须同步更新；
- 未发布时先写「未发布」段，发版时再改为正式版本段。

## 四、发布前「内部信息不外泄」自查

```powershell
# ① 对外文件（RELEASE_NOTES.md）里是否混入内部痕迹
Select-String -Path RELEASE_NOTES.md -Pattern '\.js|\.vue|\.mjs|\.ps1|MB|ms\b|crash\.log|heap|堆' -Encoding utf8

# ② 取出的 Release 正文再扫一遍（就是即将公开的那段）
Select-String -Path "$env:TEMP\jsk-notes-X.Y.Z.md" -Pattern '\.js|\.vue|\.mjs|\.ps1|MB|crash\.log' -Encoding utf8

# ③ 确认正文与 RELEASE_NOTES 对应版本段一致（不是手抄的）
```

**命中即视为需要改写**（例外：面向用户的「约 106 MB 完整包」这类**用户需要知道的体积信息**是允许的 —— 见 `用户可看信息.md` 的例外清单）。

## 五、常见的越界写法（反面例子）

| ❌ 越界（内部细节泄漏） | ✅ 改成用户可感知 |
|---|---|
| 「索引不再为每张卡常驻一份小写全文，堆从 2,891MB 降到 2,053MB」 | 「万卡大库内存占用明显下降，打开卡片时才读取它自己的设定」 |
| 「`_tokenize` 改用 `charCodeAt` 区间比较，索引构建快一个量级」 | 「大库的搜索索引能正常建完了（此前会长时间卡在 0 进展）」 |
| 「写盘判据改为基于 `diskTagsBefore`，重写张数 3,415 → 0」 | 「库加载明显变快，不再每次启动重写数千张卡片」 |
| 「`latest.yml` 必须上传否则 OTA 404」 | （这条**根本不该出现在对外正文**，属于内部流程） |
| 「`render-process-gone {"reason":"oom"}` 已修复」 | 「刷新 / 搜索时程序崩溃已修复」 |

## 六、维护责任

1. **改代码的人**：同一轮改动要**同时**更新 `CHANGELOG.md`（内部）+ `RELEASE_NOTES.md`（对外，若影响用户）；
2. **发现新缺陷的人**：先在 `docs/bugs/README.md` 加一行 + 在对应领域文档加完整条目，再写修复；
3. **发版的人**：按 [`一条龙-发布流程.md`](一条龙-发布流程.md) 第 1 步与第 9 步检查单执行分工检查；
4. **接手的人**：读 `AI交接指导.md` → 按需查 `docs/bugs/` 与 `docs/技术支持/`，不要从 `RELEASE_NOTES.md` 反推技术细节（那里面**故意没有**）。
