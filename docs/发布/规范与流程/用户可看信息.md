# 👥 用户可看信息 — 写什么、写在哪

> **本文规定「对外可见内容」的写作规范**：哪些文件用户会看到、能写什么、禁写什么、怎么写才有用。
> 配套：[`内部信息.md`](内部信息.md)（内部写在哪）、[`一条龙-发布流程.md`](一条龙-发布流程.md)（发布流程）。
> 由来：2026-09-13 用户明确要求「要分清内部文件和外部用户可以看的更新内容文件」。
> 最后更新：2026-09-13

---

## 一、哪些文件用户会看到

| 用户会看到的地方 | 说明 | 写什么 |
|---|---|---|
| **`RELEASE_NOTES.md`**（仓库根） | **最主要**：粘进 GitHub Release 正文；应用内点「检查更新」看到的也是这段 | 只写用户能感知的变化 |
| **GitHub Release 正文** | 实际公开的那段（由 `RELEASE_NOTES.md` 对应版本段抽取） | 同上，**且必须与 RELEASE_NOTES 一致**（用 `--notes-file` 抽取，不手抄） |
| **`README.md`**（仓库根） | 下载页首屏、功能介绍、安装与使用说明、常见问题入口 | 功能说明、截图、下载链接、构建与产物名、**版本号** |
| **`docs/发布/用户文档/自动更新说明与常见问题.md`** | 用户点更新出问题时会看的说明 | OTA 机制、为什么时快时慢、重启失败怎么办（面向用户措辞） |
| 应用内提示（角落更新浮标、对话框、日志摘要） | 运行时文案 | 一句话说清「发生了什么 + 我该做什么」 |

## 二、能写什么 / 禁写什么

### ✅ 可以写（用户能感知）

- **修好了什么现象**：「搜索后刷新，同一张卡重复出现」「刷新后整个库从界面上消失」「添加正则后要切选项卡才看到」
- **变快了（用可对比的量级或生活化描述）**：「库加载从最慢 79.9s 降到 16~31s」「重复写入量逐步收敛到 0」
- **位置 / 操作变了**：「新增现在立即生效」「删除现在有二次确认」
- **体积 / 兼容性等用户需要知道的客观事实**：「每次要下载约 106 MB 的完整包」「升级后首次启动会自动回收旧缓存，帮你省回磁盘空间」
- **回归覆盖范围**（不写方法细节）：「在 11,186 张卡的真实大库上完成完整回归」

### ❌ 禁止写（内部细节）

| 禁写项 | 例子 |
|---|---|
| 文件名 / 函数名 / 类名 | `js/utils/cardSlim.js`、`slimLibraryIfNeeded()`、`buildAsync` |
| 脚本 / 探针名 | `scripts/tools/_cdp-mem.mjs`、`capacity-check.ps1` |
| 内存 / 堆数字（MB、GC、堆占比） | 「堆 2,891MB → 2,053MB」「常驻文本 1,459MB」 |
| 阶段耗时（内部口径） | 「fetch=2.9s worker=1.5s assemble=9.9s」 |
| 崩溃原文 / 内部错误码 | `render-process-gone {"reason":"oom","exitCode":-536870904}` |
| 内部坑与教训 | 「`requestIdleCallback` 在隐藏窗口永不回调」 |
| 未发布 / 未验证的内容 | 计划中的 P1b、未做的冷启动实测 |
| 内部流程 | 「`latest.yml` 必须上传否则 OTA 404」、打包命令、Release 操作步骤 |

> ⚠️ **唯一例外**：当某个数字是**用户需要用来做判断的**（如安装包体积、磁盘占用变化、库规模），可以写 —— 判据是「用户看到它会不会更明白」，而不是「它看起来像不像技术参数」。

## 三、`RELEASE_NOTES.md` 版本段模板

```markdown
## SillyTavern 角色卡管理器 vX.Y.Z

本地优先、完全离线可用的角色卡管理与解析工具（Electron + Vue3 + Tailwind + ECharts）。

### 🔧 vX.Y.Z 更新 —— <一句话主题>

> 全部结论都在真实大库（N 张卡 / X GB）上复现、修复并回归验证。

#### 🔴 修复
- **<用户描述的现象>** —— 已修复（<补一句原因层面的、用户能懂的话>）

#### 🚀 性能
- **<什么场景>变快了**：<可对比的量级>

#### 🪶 <专题名，可选>
- <针对大库 / 特定场景的能力说明与操作影响>

#### 🔬 回归
- <覆盖范围>；<结果>
```

**写作要点**
1. **先说现象，再说结论** —— 用户是按"我遇到的问题"来找的，不是按模块名。
2. **一句一条**，短句；不要嵌套 bullet 超过两层。
3. **每条尽量带上"对用户的影响/操作变化"**（例如「打开卡片时多一次读取，大库首次打开可能略有停顿（预期行为）」）。
4. **不确定的不写**；未验证的不写"已修复"。
5. 版本段之间保留历史段（用户会往前翻）。

## 四、抽出 Release 正文（不手抄）

```powershell
# 用仅 ASCII 的正则从 RELEASE_NOTES.md 抽「第一个二级标题之后到下一个二级标题之前」的版本段
# 输出到 ASCII 路径，避免编码问题
# 然后：gh release create vX.Y.Z --title "vX.Y.Z" --notes-file "$env:TEMP\jsk-notes-X.Y.Z.md" <assets...>
```

抽完**必须回读一遍**确认：标题、版本号、段落完整、无内部细节（对照 §二 禁写表）。

## 五、发布前自查（对外内容专用）

- [ ] `RELEASE_NOTES.md` 顶部已加本版段，**版本号与 `package.json` 一致**
- [ ] 通读一遍：**没有**文件名 / 函数名 / 脚本名 / MB 数 / 阶段耗时 / `crash.log` 原文 / 内部坑
- [ ] 每条"修复"都能对应一个**用户能描述出来的现象**
- [ ] 每条"性能"都有**可对比的量级**（或明确说"明显变快"）
- [ ] 涉及行为变化的地方写清了**用户要做什么**（或"不需要做任何事"）
- [ ] Release 正文是从 `RELEASE_NOTES.md` **抽取**的（不是手抄、不是另写一版）
- [ ] `README.md` 的版本号与产物名同步（用户按 README 找安装包）
- [ ] 更新说明与常见问题（`自动更新说明与常见问题.md`）里的措辞仍是面向用户的

## 六、常用替代写法（把内部话翻译成用户话）

| 内部事实 | 用户可看的写法 |
|---|---|
| 索引不再常驻全卡全文 + P1a 正文懒加载 | 「内嵌世界书设定改为"打开才加载"，列表与搜索不再常驻这些重数据；打开某张卡时才把它的设定读回来」 |
| 写盘判据改为基于磁盘标签（幂等） | 「消除了每次启动重写数千张卡片的循环，加载明显变快」 |
| `generation` 代次号 + 幂等 + `Set` 去重 + 合并重建 | 「搜索后刷新出现重复卡已修复」 |
| 扫描返回空数组被当空库 | 「刷新后整个库从界面上消失已修复（异常的扫描结果不再被当成"库是空的"）」 |
| 内存守门员 + `--expose-gc` | 「新增内存水位监测，逼近上限时自动释放可重算的缓存并主动回收，而不是等它崩」 |
| 移除 PNG 内嵌提取缓存（`cleanupLegacyEmbedCache`） | 「移除了一个实测反而更慢的缓存机制；升级后首次启动会自动回收旧缓存文件，帮你省回磁盘空间」 |
| `migrateChatKeys` 整键子串迁移 | 「移动分组 / 重命名分组 / 换卡图后，聊天测试的会话与变量树不再消失」 |
