### 6.2 🔴 渲染进程崩溃（稳定复现 ×3 次）—— 最可能的真正病根

### 6.3 🎯 因果链（这解释了重复卡的来源）

`main.js:906` 的崩溃兜底会**自动 reload**：

```js
win.webContents.on('render-process-gone', (event, details) => {
    console.error('[renderer] 渲染进程崩溃:', JSON.stringify(details));
    fs.appendFileSync(crashLogPath(), ...);
    if (details && (details.reason === 'crashed' || details.reason === 'oom' || details.reason === 'killed')) {
        setTimeout(() => { try { if (!win.isDestroyed()) win.reload(); } catch (e) {} }, 1500);
    }
});
```

于是形成这条链：

```
大库加载 / 刷新（11k 卡，9.76 GB）
      ↓ 渲染进程 OOM / 崩溃（exitCode -36861）
崩溃兜底自动 win.reload()（1.5s 后）
      ↓
新页面启动 = 又一次「全量加载」
      ↓ 若此刻还有未完成的加载/刷新在跑
「加载 + 加载」/「加载 + 刷新」并发重入
      ↓
两次循环交错操作同一个 library 数组 → 同一 path 入两条 → **列表出现重复卡**
      ↓ 崩溃瞬间的中间态
侧栏显示一个「不完整」的卡片数（如 478）→ 正是用户截图看到的样子
```

**这解释了为什么用户只在「大库 + 反复刷新/搜索」时才看到重复卡**：小库（75 张）
根本不会触发 OOM，也就不会走这条自动 reload 链。

### 6.4 已就位的防护（能挡住重复，但挡不住崩溃）

第 2 轮复测全程（基线 + 1 次刷新 + 3 次崩溃恢复）**未观测到任何重复卡**，
`dupPaths=0 / dupIds=0`，说明已有的 6 项修复在挡重复这条线上是有效的。
但**崩溃本身仍未解决** —— 这才是要根治的。

### 6.5 附带发现

  `20456 / 13632 / 35224`…）——`atomicWriteJson` 中途失败/进程退出留下的垃圾，

### 8.1 复现（修复前，单元测试级）

### 8.2 四个根因

| # | 缺陷 | 根因（一句话） |
|---|------|----------------|
| 1 | **搜索时同一张卡出现两次** | `searchIndex` 的构建无代次保护、也不保证「同对象只索引一次」；刷新期间 `watch(library)` 被反复触发 → 多个 11k 重建**重叠**运行：旧对象在新构建 `clear()` 后被写回倒排表、同一对象被重复 push 进同一桶。**只有「精确 token」分支会原样返回倒排桶 → 中文单字搜索最易复现** |

## 九、库加载变慢：根因与优化（2026-09-13 晚）

**现象**：11,186 卡库启动加载 **79.9s**（此前同库为 22.5s），且每次启动日志都有
`⏳ 后台落盘自动打标卡片: 3,415 张` —— 数千张卡被反复重写。

### 9.1 根因：写盘判定看错基准 → 无限重写循环

`useCardCrud.parseAndAddCard` 的写盘判据原本是：

```js
const nativeCleared = oldNativeTagsLen > 0 && （清洗后的 tags 为空）;   // ← 基于「清洗后」内存状态
if (newTags.length > 0 || nativeCleared) { …写盘… }
```

而 `processAutoTagsAndCategory` 在「🧹 导入时忽略卡片自带标签」**开启时每次加载都会清空** `data.tags`：

```
加载 → 盘上有作者标签 → 开关把它清空 → 判定「需要物理清洗」→ 写盘（把 customTags 写回 PNG）
     → 下次启动：这些 customTags 又成了「原生标签」→ 又被清空 → 又判定需要写盘 → …… 无限循环
```

代价：每次启动重写 **3,415 张 PNG**（每张含整图读回 + 重写 + 快照备份），且 mtime 全变
→ 下次「刷新」按 mtime 差分又把这批卡全量重解析。

### 9.2 修复：基于「磁盘原有标签」判定（幂等）

```js
// 记录清洗前的磁盘标签（数组/逗号串两种形态）
const diskTagsBefore = …;
const desiredSet = new Set(customTags);
const newTags = desiredTags.filter(t => !new Set(diskTagsBefore).has(t));
// 只有「盘上真的存在不该保留的标签」或「确有新标签要补」才写盘
const needsPhysicalClean = sanitizeImportedTags.value && diskTagsBefore.some(t => !desiredSet.has(t));
if (newTags.length > 0 || needsPhysicalClean) { … }
// 写盘内容也改为幂等：忽略开关开 → 盘上只留 customTags；开关关 → 保留作者标签 ∪ 规则标签
```

### 9.3 实测数据（`I:\03\角色色卡`，11,186 卡 / 9.76GB，dev 模式）

| 轮次 | 重写卡数 | 主进程扫描 | fetch | worker | assemble | 蒙版淡出总耗时 |
|---|---|---|---|---|---|---|
| 修复前 | **3,415** | 2.4s | 9.3s | 18.3s | 58.3s | **79.9s** |
| 修复后·第 1 次 | 971（真正的残留清洗，一次性） | 2.4s | 8.1s | 6.1s | 26.9s | **40.6s** |
| 修复后·第 2 次 | **0** | 2.8s | 11.8s | 6.6s | 19.0s | **41.8s** |
| 修复后·最终回归 | **0** | 2.7s | 6.9s | 7.2s | 31.0s | **43.3s** |

**结论**：加载时间 **≈1.85× 提速**（79.9s → 41~43s），且启动零写盘、零 mtime 抖动
（刷新因此也不再反复重解析这批卡）。

## 十、正则/状态栏脚本增删交互修复（2026-09-13 晚）

**用户反馈**：添加正则/状态栏脚本后**反馈缓慢、必须切换选项卡才能看到效果**；**删除没有任何提示**。

### 10.1 根因

`App.vue` 的 `cardData` 是 `shallowRef`，深层数组变更（`extensions.regex_scripts` 的 push/splice）
不会触发视图更新，必须手动 `triggerRef`。同文件的 `syncRegexScriptField`、批量克隆/删除**都有**
这个调用，唯独这两处漏了：

```js
const addRegexScript = () => { … arr.push({ … }); };                 // ← 无 triggerRef
const deleteRegexScript = (index) => { … regexScripts.value.splice(index, 1); };  // ← 无 triggerRef、无确认、无日志
```

于是：新增/删除后列表不变（切 Tab 时子树 `v-if` 重挂载才重新求值 → 「切 Tab 才看到效果」）；
删除既不弹确认也不留日志 → 「没有任何提示」。

### 10.2 修复

- 两处补 `refreshCardData()`（= `triggerRef(cardData)` + 失效该卡 Token 缓存）+ 操作日志；
- 删除改为 `confirmDialog`（原生「确认操作」对话框）：文案点明脚本名、是否为状态栏/美化模板
  （`<status>` 触发）、以及「需点保存卡片才写回文件」；确认后按对象身份重新定位并删除，避免弹窗期间索引漂移。

### 10.4 补记（2026-09-13 深夜）：上一节的修复只覆盖了「卡上已有脚本数组」的分支

复测时用一张**原本没有** `extensions.regex_scripts` 的卡（「斗罗大陆」）点击「+ 立即新增一条正则脚本」，
面板纹丝不动（徽标 0 条、DOM 0 行），必须切 Tab 才显示 —— 用户最初反馈的现象仍能复现。根因：

- `regexScripts = computed(() => safeData.value.extensions?.regex_scripts || ...)`；
- **Vue 3.4+ 的 computed 在新值 `Object.is` 等于旧值时不再向下传播**：`triggerRef(cardData)` → `safeData` 重算 → 返回**同一个对象** → 依赖它的 `regexScripts` 不会被标脏，返回缓存的旧值；
- 卡上**已有**该字段时：`ensureRegexScriptsArray()` 原地 `push`，computed 缓存的**就是同一个数组对象**，`.length` 天然变化 → 表现正常（§10.3 的 21→22 正是这个分支）；
- 卡上**没有**该字段时：先新建数组再赋值（整体替换）→ 缓存里的旧空数组永不失效 → 一直显示 0 条。

**修复**：新增 `cardContentVersion`，`refreshCardData()` 时自增；`regexScripts` 取值前先读一次该版本号，
于是「数组被整体替换」也能被正确标脏重算。

## 十一、库加载二轮提速 + PNG 内嵌提取缓存移除（2026-09-13 深夜）

### 11.1 测量方法

每次测量都**先杀掉 Electron 再重启**（同一大库 `I:\03\角色色卡`：11,186 卡 / 9.76GB / 11,667 文件），
读取渲染端启动日志里的一行分项：

```
[profile] 解析分项: fetch=…ms worker=…ms assemble=…ms 总文件=11667
[startup] 蒙版淡出(总耗时): …ms       ← 用户可感知的「首屏就绪」时间
```

三项含义：`fetch` = 主进程批读 + PNG 内嵌提取（或命中缓存）→ 渲染端拿到原始数据；
`worker` = Worker 里 `JSON.parse` 纯文本卡；`assemble` = 主线程组装卡片对象 / 血统鉴定 / 分类打标。

### 11.2 P0：PNG 卡不再重复搬运文本

`parseChunkInWorker` 只把「需要 `JSON.parse` 的纯文本卡」送 Worker。PNG 卡的 `embeddedData`
本来就是主进程解析好的对象，此前还会被再送进 Worker 走两趟 structured clone（万卡库 ≈1.2GB 级搬运）。

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| worker | 6.9s | **1.5~2.0s** |
| assemble | 31s | **9.9~11.0s** |

### 11.3 P1：后台（窗口隐藏）不再让索引/预热永久停摆

| 位置 | 旧实现 | 隐藏窗口时的行为 | 新实现 |
|---|---|---|---|
| `searchIndex.buildAsync` 分片让步 | `requestIdleCallback(timeout:50)` + `setTimeout(60)` 竞速 | idle 永不回调；`setTimeout` 被节流到 ≥1s（后台 5 分钟后更慢）→ 224 片要跑几十分钟 | `yieldToMain()`：前台 idle / 后台 `MessageChannel` |
| `tokenCache.warmupAsync` | **纯** `requestIdleCallback` | **永不回调** → 永不完成 | 同上 |
| App 启动闸门 `waitIdleThenRun` | 单独 `await requestIdleCallback(cb, {timeout})` | 连 timeout 都不兑现 → 实测 **3 分钟仍未开始建索引**（搜索恒空） | `waitForIdle()`（保证返回，含通道兜底） |

实测（窗口全程隐藏）：11,186 卡索引（349,552 词）与 Token 预热（11,186 次 / 1.45s）均正常完成。
`yieldViaChannel` 另有两点防御：`MessageChannel` 仅在真实 DOM 环境创建，且 Node 下 `unref()`（否则 `node --test` 会因活跃句柄跑完不退出）。

### 11.4 P2：内嵌提取缓存是**负优化** —— 已移除（含一次性回收）

同机交替 A/B（每次重启，同一大库，同一链路）：

| 方案 | fetch | worker | assemble | 合计 | 缓存占盘 |
|---|---|---|---|---|---|
| **无缓存** | 2.7~3.1s | 1.5~1.9s | 9.9~10.5s | **16.0~17.0s** | 0 |
| v1 `.json` 分片（24 片） | 9.3s | 2.0s | 11.0s | 36.9~43.3s | 1.17GB |
| v2 `.json.gz` 分片（23 片） | 29.1s | 1.6s | 52.8s | **85.3s** | 385MB |
| v8 二进制分片（过渡试验） | 62.5s | — | — | **137s** | 385MB |

**机理**：从 PNG 头部提取内嵌 JSON 本身只要 ~3s（`readPngEmbeddedFromFile` 自适应窗口 + 128 路并发 +
按需流式，边到边组装、GC 可回收）；而缓存会把 11.6k 张卡、约 1.2GB 的**对象**一次性常驻主进程 →
堆压力/GC 抖动 + 额外 IPC 克隆，反而慢 2~5 倍。缓存体积压缩（gzip）只减少磁盘与读取量，
并不能消除「对象常驻」这个根因，故 v2 仍比 v1 更慢（v1 那次部分未命中、提取与命中交错，掩盖了部分代价）。

v8 二进制更慢的机理独立且值得记一笔：`v8.deserialize` 产出的对象处于 **dictionary-mode**，
跨 IPC structured clone 与后续属性访问都明显变慢 —— 对「要给渲染进程用」的数据，`JSON.parse` 反而是快路径。

**处置**：
- 删除整块缓存实现（**-173 行**：`embedCache*` / `EMBED_CACHE_*` / `gzipAsync`/`gunzipAsync` / `approxEmbedSize` / 分片读写 / `zlib` 依赖）；
- 新增 `cleanupLegacyEmbedCache()`：启动时一次性删除历史 `embed_cache_*`（本机 **44 个文件 / 758MB**，含旧 `.json`、`.json.gz`、`.bin` 与残留 `.part`），用 `.embed_cache_removed` 标记保证只扫一次目录。

### 11.5 P2b：载入期「非角色卡文件」日志降噪

`console.warn` 逐条打印会污染日志并拖慢 console 转发（实测单次加载 500+ 条）。
改为：同「原因 + 文件名」只打 1 条、总量封顶 40 条、收尾一行汇总 + 一条「已折叠 N 条」提示：

```
[载入] 跳过 385 个非角色卡/不可解析文件（同类日志已折叠 345 条）
```

### 11.6 回归验证（本轮）

| 项目 | 结果 |
|---|---|
| `npm test` | **178 / 178** 通过（5.2s，进程正常退出） |
| `npm run build:web` | `built in 2.07s` ✅ |
| 大库加载 | **16.0s**（11,186 张全部到位；跳过文件汇总正确） |
| `scripts/library-dup-search-refresh.mjs` | 全程 `dup(lib)=0 / dup(list)=0`；库稳定 11,186；搜索→刷新、连点刷新 ×6 无崩溃（堆峰值 3.3GB） |
| 正则脚本增删（§10.4） | 新增首条 / 删除二次确认 / 确认后立即刷新 全部 ✅ |

### 11.7 经验沉淀（避免重犯）

1. **不要为「本来就便宜」的数据加磁盘缓存**：先量「重算成本」再量「缓存加载成本」，
   本库里后者（读 385MB + gunzip + `JSON.parse` 1.2GB + 对象常驻）远大于前者（~3s 提取）。
2. **大对象跨进程只走一次**：能传字符串/文本就让对端自己 `JSON.parse`，别在主进程把 1.2GB 对象常驻；
   更要避免 `v8.serialize` 交付给 IPC（dictionary-mode 反效果）。
3. **前台/后台的调度语义不同**：`requestIdleCallback` 在隐藏窗口**不可依赖**；
   需要「一定推进」的后台任务用 `MessageChannel`（并保留定时器兜底，Node 下记得 `unref`）。
4. **Vue 3.4+ computed 的「值不变则不传播」**：`shallowRef` + 整体替换数组/对象时，
   依赖它的 computed 可能永不重算 —— 需要版本号（`cardContentVersion`）显式打破缓存，
   不要依赖「原地 push 恰好正常」的巧合。
