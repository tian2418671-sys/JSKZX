# 插件预览渲染 · 初期评估方案

> 项目：JSK管理（SillyTavern 角色卡管理器）
> 主题：插件库「效果」页的预览渲染功能
> 版本：初审稿　日期：2026-11-08
> 提交：上游评审

---

## 摘要

插件库的「效果」页，目标是不启动 SillyTavern，直接在应用里看到插件跑起来的样子。
这条功能做了接近两个月，已经迭代四代架构，但目前**仍不可用**——用户实测「点击后下面就是空白」。

本方案给出四个判断：

1. **架构方向是对的，但实现有致命结构缺陷。** `buildHostDom()` 的函数头在某次编辑中丢失，
   导致一半宿主 DOM 骨架（15 个 wand 容器、`#message_template`、`#extensionsMenuButton`）
   从未输出到页面。这是当前「所有插件都没效果」的第一大根因。
2. **之前两轮优化方向错了。** 事件脉冲和导航条解决的是「插件不动」和「内容在别处」，
   但真实插件库里 6 个样本没有一个属于这两类问题，所以收益接近 0。
3. **真正的瓶颈不是「跑不起来」，是「跑起来了但看不见」。** 且 6 个样本里有 3 个
   本来就没有界面（纯逻辑脚本 / 主题配置），需要靠分类呈现而不是统一沙箱。
4. **离「能用」不远，约 2 天。** 但需要换思路：从「堆沙箱能力」转为「按类型分流呈现」。

## 一、这条功能是怎么走过来的

### 1.1 起点：为什么需要预览

插件库（`js/components/PluginWorkspace.vue`）能扫描、导入、编辑外部插件文件：
酒馆助手脚本 JSON、扩展工程目录、正则脚本、快速回复、UI 主题。

用户打开一个插件，只能看到源码。想知道「它长什么样」，必须走：
装进真酒馆 → 重启 → 打开聊天 → 找到入口 → 点开。

对「只想判断这插件值不值得用」的人来说，这个链路太重。所以有了「效果」页。

### 1.2 第一代：手搓迷你 jQuery（已废弃）

最初思路是「缺什么补什么」：

```text
buildMemoryStorage()      内存版 localStorage（sandbox 下原生会抛 SecurityError）
buildMiniJquery()         手写迷你 $（链式、append、on、css、text…）
buildEventSourceStub()    事件总线桩
buildGlobalStubs()        window.TavernHelper / SillyTavern / toastr …
```

**失败原因**：插件用的 jQuery 方法千奇百怪（`$.extend`、`$.Deferred`、`$.ajax`、
`data()`、动画、复杂伪类选择器）。补一个漏三个，而**漏掉时是静默失败**
——不抛错、不产 DOM，表现和「插件本来就没内容」完全一样。

这就是第一代留下的最大教训：**静默失败比明确报错危险得多，因为它无法被排查。**

### 1.3 第二代：换真库（当前架构的地基）

关键决策：**不再手写，直接内联真库源码**。`hostStub.js` L15-L26：

```js
import jquerySource from 'jquery/dist/jquery.min.js?raw';
import lodashSource from 'lodash/lodash.min.js?raw';
import handlebarsSource from 'handlebars/dist/handlebars.min.js?raw';
import showdownSource from 'showdown/dist/showdown.min.js?raw';
import dompurifySource from 'dompurify/dist/purify.min.js?raw';
```

注入顺序（`buildPluginPreviewHtml` 内，L1756-L1763）：

```html
<script>${buildMiniJquery()}</script>   <!-- 现在实际 return jquerySource，即真 jQuery -->
<script>${lodashSource}</script>
<script>${handlebarsSource}</script>
<script>${showdownSource}</script>
<script>${dompurifySource}</script>
<script>window.__jskTemplates = ${templatesJson};</script>
<script>${buildEventSourceStub()}</script>
<script>${buildGlobalStubs(plugin)}</script>
```

这一代是正确的，也是当前唯一扎实的部分。

> 遗留命名问题：`buildMiniJquery()` 已名不副实——它现在只有一行 `return jquerySource;`。
> 行数统计显示 112 行，是因为缺陷 1（见第二章）那段游离代码被算进了它的范围。

### 1.4 第三代：宿主 DOM 骨架

插件不是自己创建整页，而是往酒馆已有节点里塞东西。`buildHostDom()` 负责生成：

```text
#chat / #chat-history           消息区
#extensionsMenu                 魔法棒菜单（含 15 个 *_wand_container）
#extensions_settings            扩展设置面板（含 16 个 *_container）
#extensions_settings2           更多扩展面板（含 15 个 *_container）
#leftSendForm                   底部发送区按钮位
.options-content                选项区（含 <hr>，插件往里插链接）
#message_template               消息克隆模板
#zoomed_avatar_template         立绘弹窗模板
```

缺失这些节点时，插件 jQuery 的空集合 `.append()` **静默失败**——第一代的教训在这里重演。

### 1.5 第四代：事件脉冲 + 导航条 + 透视卡（2026-10-25）

上游评审后加了三样：

| 机制 | 代码位置 | 想解决什么 | 实际效果 |
| --- | --- | --- | --- |
| 初始化事件脉冲 | L1766 起的 `<script>` | 插件等 `APP_READY`/`CHAT_CHANGED` 才动手 | 未命中 |
| `__jskRenderChat()` | L223-L277 | `#chat` 无真实消息气泡，插件查 `.mes` 得 0 | 部分有效 |
| 挂载点导航条 | L1800-L1860 | UI 塞在看不见的区域 | 产生了假信号 |
| 静态透视卡 | `hostStubProbe.js` | 纯逻辑插件空白时解释原因 | 有效但触发不了 |

> 用户实测评价：「比之前强了不少，但收益基本为 0。」

原因在第二章的缺陷 8 —— 这两个机制在真实样本上几乎没有命中率。

## 二、现在面临的真实问题

以下 8 个缺陷全部经过代码核对，不是推测。

### 缺陷 1 · `buildHostDom` 函数头丢失，一半骨架从未输出 ⚠️ 最严重

证据（`hostStub.js` L1450-L1546）：

```js
L1450: `;                    ← buildTavernThemeCss 的 return 结束
L1451: }                     ← buildTavernThemeCss 结束
L1452:
L1453: <div id="options" class="options-content" ...>   ← ⚠️ 没有函数头
L1454:   <hr>
       ...
L1532: </div>`;              ← 一个孤立的模板字符串
L1533: }
L1534:
L1535: /** 生成酒馆宿主 DOM 骨架…… */
L1544: function buildHostDom() {
L1545:     return `
L1546: <div id="chat" ...>    ← 真正输出的只有这份
```

`buildHostDom` 的函数头（注释 + `function buildHostDom() { return \``）在某次编辑中被删除。
后果：L1453-L1532 变成**游离表达式语句**，值被丢弃，永不进入 HTML。

**实测验证**（对 L1545-L1598 统计）：

```output
_wand_container 数量        0      ← 应有 15 个
#message_template           false  ← 插件克隆消息的必需节点
#extensionsMenuButton       false  ← folder4.0.json 第一句就依赖
#zoomed_avatar_template     true   ← 侥幸保留
#leftSendForm               true   ← 侥幸保留
```

而被丢弃的 L1453-L1532 恰好包含：

```output
_wand_container      15 个
#message_template    true
#extensionsMenuButton true
extension_container  47 个
```

**这就是「所有插件都没效果」的第一大根因。**

### 缺陷 2 · 源码里有两份完整骨架，30 个 ID 重叠

```output
游离段（L1453-L1532）     ID 数 53
实际输出段（L1545-L1598） ID 数 32
两段共有 ID               30 个
```

重叠的 30 个包括：`options`、`send_form`、`extensions_settings`、
`extensions_settings2`、`assets_container`、`typing_indicator_container`、
`expressions_container`、`sd_container`、`tts_container`、`rvc_container`、
`stt_container`、`audio_container`、`silence_container`、`objective_container`、
`blip_container`、`live2d_container`、`vrm_container`、`timelines_container`、
`webllm_container`、`rss_container`、`websearch_container`、`emulatorjs_container`、
`qr_container`、`translation_container`、`caption_container`、`idle_container`、
`summarize_container`、`hypebot_container`、`regex_container`、`zoomed_avatar_template`。

**当前因为缺陷 1，游离段不输出，所以运行时暂时只有一份。**

**但这是定时炸弹**：任何人「修好缺陷 1」而没删副本，立刻变成 30 个重复 ID。
jQuery 的 `$('#extensions_settings')` 只取第一个，插件往另一个里塞，
两边不是同一节点 → 显示/折叠逻辑全错，**且不报任何错**。

> 因此阶段 0 必须**同时**做两件事：补函数头 **+** 删副本。只做一件都是灾难。

### 缺陷 3 · `showMessage` 4 秒后自动删除

`hostStub.js` L829 附近：

```js
setTimeout(function(){ try{ el.remove(); }catch(e){} }, 4000);
```

`statusSystem.js` 的**唯一输出途径**就是 `SlashRunner.showMessage(status, "状态面板")`。
4 秒后内容消失，且是 `position:fixed` 浮层，不占文档流，滚动也找不回。

### 缺陷 4 · iframe 处于不透明源

`PluginWorkspace.vue` L121：

```html
<iframe v-else-if="previewState.url" :src="previewState.url" sandbox="allow-scripts" ...>
```

没有 `allow-same-origin` → 不透明源。后果：

- `localStorage` / `sessionStorage` 抛 SecurityError（已有内存兜底）
- `document.cookie` 不可用
- `IndexedDB` 不可用
- `fetch('./data.json')` 失败
- `new Worker()` 失败

### 缺陷 5 · 插件 UI 分散在酒馆各处，宿主竖向堆在一页

真实酒馆：设置抽屉在右侧、魔法棒菜单在输入框上方、消息界面板在楼层内。
宿主：全部竖向排列 + 一个导航条。用户看到「一堆空框」。

导航条的检测逻辑又过严（要求「有尺寸 + 有文字」），折叠内容检测不到 → 导航不出现。

### 缺陷 6 · 主题类插件（JSON 配色）完全没有处理

`晦明v2.6.json` 的真实结构：

```json
{
  "name": "晦明v2.6",
  "blur_tint_color": "rgba(248, 247, 245, 1)",
  "main_text_color": "rgba(57, 56, 60, 1)",
  "chat_tint_color": "rgba(238, 237, 237, 1)",
  "user_mes_blur_tint_color": "rgba(238, 237, 237, 1)",
  "bot_mes_blur_tint_color": "rgba(238, 237, 237, 1)",
  "shadow_color": "rgba(53, 43, 34, 0.16)"
}
```

**纯样式配置，没有一行逻辑。** 当前流程走「读 `scripts[].content` → 空 → 报错」，
所以它永远显示「插件没有可运行的脚本内容」。

### 缺陷 7 · 没有文件系统上下文

插件里 `fetch('./assets/x.json')`、`import('./mod.js')`、`new Worker('./w.js')` 全部失效。
`js/utils/pluginResPath.js` 只改写 HTML/CSS 里的相对路径，够不到 JS 运行时的请求。

### 缺陷 8 · 真实样本里一半「本来就没 UI」

| 插件 | 文件大小 | 真实类型 |
| --- | --- | --- |
| `晦明v2.6.json` | 48.7 KB | UI 主题（配色） |
| `statusSystem.js` | 2.5 KB | 命令脚本（有 UI，但 4 秒消失） |
| `更好的聊天记录管理 .json` | 30.9 KB | DOM 脚本（面板在 `.options-content`） |
| `folder4.0.json` | 59.7 KB | DOM 脚本（依赖 `#extensionsMenuButton`） |
| `酒馆助手脚本-发送前最后正则.json` | 3.0 KB | **纯逻辑，无 UI** |
| `酒馆助手脚本-玉藻前一键写卡器 (1).json` | 0.5 KB | **纯逻辑，无 UI** |

6 个里 3 个本来就不该有界面。但当前没有机制告诉用户这件事，
用户看到空白只会认为「软件坏了」。

### 2.1 一个具体例子：为什么「更好的聊天记录管理」点了没反应

它的第一句代码：

```js
const t = $(".options-content").find("hr").last();
if (!$("#option_chat_history_manager").length) {
  const o = $("<a>", { id: "option_chat_history_manager", ... })
    .append($("<i>", { class: "fa-lg fa-solid fa-history" }))
    .append($("<span>").text("聊天记录管理"));
```

它做的是：在 `.options-content` 的最后一个 `<hr>` 后面插一个「聊天记录管理」链接，
点开才显示面板。

宿主里确实有 `.options-content` 和 `<hr>`，所以链接能被创建。但是：

1. 这个链接被塞在页面最上方一个只有 40px 高的区域里，视觉上几乎看不见；
2. 点开后 `t.empty(); t.append(...)` 填的容器在宿主里结构不对。

**结论：不是「插件没跑」，而是「跑了，但结果落在看不见的地方」。**

## 三、要实现的效果与当前进度

### 3.1 按类型分流，而不是统一沙箱

这是本方案的核心转向。

| 类型 | 判定依据 | 期望效果 | 技术手段 |
| --- | --- | --- | --- |
| **主题** | 顶层 ≥3 个配色字段 | 色板 + 2 条模拟气泡，套用配色 | 映射 CSS 变量，**不跑脚本** |
| **纯逻辑脚本** | 无 `.html`/`.css`，源码无 DOM 操作 | 能力卡（监听事件 / 调用 API） | `hostStubProbe.js` 已有 |
| **DOM 脚本** | 有 DOM 操作或模板 | 沙箱渲染 + 自动滚到产出区域 | 修缺陷 1/2/3/5 |
| **扩展工程** | `kind === 'extension'` | bundle + Handlebars 模板渲染 | 已有基础，需补同源 |

### 3.2 当前进度（真实评估）

## 四、技术方案

### 阶段 0 · 修结构缺陷（必须先做，0.5 天）

#### 0.1 修复 `buildHostDom` 函数头 + 删除副本

在 L1452 后补回函数头，同时**删掉 L1545-L1598 的第二份副本**，
只保留一份完整骨架（以 L1453-L1532 那份为准，它更完整）。

验证：

```powershell
node --check js/plugins/hostStub.js
# 输出 HTML 里 *_wand_container 应为 15 个
# #message_template / #extensionsMenuButton 应存在
# 重复 ID 应为 0
```

#### 0.2 加重复 ID 门禁

新增 `scripts/check-duplicate-ids.mjs`：解析 `hostStub.js` 里所有 `id="xxx"`，
统计重复，重复即失败。加入 `npm run guard:*` 系列。

#### 0.3 `showMessage` 改常驻

```js
// 之前：setTimeout(el.remove, 4000)
// 之后：常驻 + 右上角关闭按钮；最多堆叠 3 条，超出清最旧
```

### 阶段 1 · 分类预览器（1 天）

#### 1.1 新增 `js/plugins/pluginClassify.js`（纯函数 + 单测）

```js
export const PLUGIN_KIND = {
  THEME: 'theme',           // 配色 JSON
  LOGIC: 'logic',           // 纯逻辑脚本
  DOM_SCRIPT: 'domScript',  // 有 DOM 操作
  EXTENSION: 'extension',   // 扩展工程
};

export function classifyPlugin(plugin) { /* ... */ }
```

判定顺序：

1. `kind === 'extension'` → `EXTENSION`
2. 顶层 ≥3 个配色字段 → `THEME`
3. 有 `.html` 模板或 `.css` → `DOM_SCRIPT`
4. 源码命中 DOM 操作正则 → `DOM_SCRIPT`
5. 否则 → `LOGIC`

#### 1.2 主题预览器 `js/plugins/themePreview.js`

把酒馆主题 JSON 映射到 CSS 变量：

```output
JSON 字段                        CSS 变量
────────────────────────────────────────────────────────
main_text_color                  --SmartThemeBodyColor
italics_text_color               --SmartThemeEmColor
blur_tint_color                  --SmartThemeBlurTintColor
chat_tint_color                  --SmartThemeChatTintColor
user_mes_blur_tint_color         --SmartThemeUserMesBlurTintColor
bot_mes_blur_tint_color          --SmartThemeBotMesBlurTintColor
shadow_color                     --SmartThemeShadowColor
blur_strength                    --SmartThemeBlurStrength
```

输出一个独立 HTML 预览页（不跑脚本），含标题、色板色块、2 条模拟消息气泡、按钮样例。

### 阶段 2 · 修可达性（0.5 天）

#### 2.1 自动聚焦产出区域

渲染完成后（多轮 500 / 1500 / 3000ms）：

1. 统计每个挂载点里「插件产出」的可见节点数（排除预置 `.mes`）
2. **有产出的区域自动 `scrollIntoView`**（取产出最多的那个）
3. 区域顶部加标签：「⚙️ 扩展设置区（插件界面在这里）」

#### 2.2 导航条改用 DOM diff 判定

前两版都错：

- 第一版 `childElementCount > 0` → 假信号（永远非空）
- 第二版「有尺寸 + 有文字」→ 折叠内容检测不到

第三版：**对每个挂载点做「插件执行前 / 后 DOM 快照 diff」**
（`outerHTML.length` + 子节点数），只有**发生变化**才算产出。
既不误报，也能抓到折叠内容（折叠是 CSS 隐藏，DOM 仍变化）。

### 阶段 3 · 同源沙箱（1 天）

**现状**：

```html
<iframe :src="previewState.url" sandbox="allow-scripts">
```

`previewState.url` 是 `app://index.html/__jsk_preview__/<id>.html`（主进程内存 store）。

**目标**：改为

```html
<iframe :src="url" sandbox="allow-scripts allow-same-origin">
```

同源后解锁：`localStorage`、`fetch('./x')`、`Worker`、`IndexedDB`、`import()`。

**风险**：插件代码可访问应用同源资源。
**权衡**：本地工具 + 用户主动预览自己装的插件，可接受。
**缓解**：预览页单独用 `persist:plugin-preview` 分区，不共享主应用 session。

### 阶段 4 · 运行时请求代理（0.5 天）

同源后 `fetch('./data.json')` 的相对路径基准是
`app://index.html/__jsk_preview__/<id>.html`，解析成
`app://index.html/__jsk_preview__/data.json` → 不存在。

解决：协议处理器加分支——

```output
app://index.html/__jsk_preview__/<id>/<相对路径>
                ↓
   按 previewStore.get(id).rootDir 读盘
```

与现有 `PLUGIN_RES_PATH_PREFIX`（`/__jsk_plugin_res__/<previewId>/<rel>`）合并成一套。

### 阶段 5 · 带入测卡工作区（1 天）

对纯逻辑脚本 / 深度耦合插件，给出口：

```text
[🧪 在测卡工作区中测试]
```

点击 → 切到测卡模式 → 把该插件临时挂到当前会话（内存态，切换即卸载）。

这是真正的「接真酒馆」，但**不依赖外部酒馆**——测卡工作区本身就有
角色卡、聊天记录、LLM API、沙箱。

## 五、未来计划与技术选型

### 5.1 三个基本判断

#### ① 「预览」不该追求 100% 真实

真实酒馆的渲染涉及：宏替换 → 正则 → Markdown → DOMPurify → 楼层面板注入。
全对齐等于重写酒馆。目标是「**能看出这插件干什么**」，不是「像素级一致」。

#### ② 类型分流比能力堆叠重要

6 个真实样本里 3 个本来没 UI。把「类型判断 + 对应呈现」做好，
比给沙箱再加 50 个 API 桩有用得多。

#### ③ 静态分析可以承担更多

`hostStubProbe.js` 现在只用来解释「为什么空白」。未来可扩展成**插件说明书**：

- 解析出它注册了哪些命令 / 按钮 / 钩子
- 画出「会往哪个区域注入什么」
- 对酒馆助手脚本，提取 slash 命令并**逐个按钮化**，点了就在沙箱里执行

这条路不依赖运行时，**永远不会因为沙箱缺能力而失效**。

## 八、补充：方案里刻意没展开、但会影响成败的点

前七章是主线。以下是复核代码时发现、独立于主线的补充事项。

### 8.1 测试盲区是缺陷 1 能潜伏这么久的真正原因

现状：项目 90 个测试文件，插件相关 6 个：

```output
cardPlugins.test.mjs
cardPluginsPanel.test.mjs
pluginResPath.test.mjs
pluginScanner.test.mjs
hostStub.test.mjs         ← 只测 hostStubPure.js 的纯函数
hostStubProbe.test.mjs
```

`hostStub.test.mjs` 目前 import 的是 `hostStubPure.js`：

```js
import { rewriteEsmModule, stripEsmSyntax, parseSlashCommand,
         escapeHtml, encodeStyleTags, decodeStyleTags } from '../js/plugins/hostStubPure.js';
```

也就是说：**`buildPluginPreviewHtml()` 的输出从来没有被任何测试断言过。**

所以那段游离代码（缺陷 1）可以安然存活——因为它不抛错、不影响纯函数，
只是静默地少输出一半 DOM。

**这是必须补的**，否则同类问题会再次发生。建议新增
`test/hostStubOutput.test.mjs`，断言生成的 HTML 里：

```output
断言项                                        期望
──────────────────────────────────────────────────────
存在 id="chat"                                ✓
存在 id="chat-history"                        ✓
存在 id="extensionsMenuButton"                ✓
存在 id="message_template"                    ✓
存在 id="zoomed_avatar_template"              ✓
*.wand_container 出现次数                      15
id="xxx" 无重复                                ✓
包含 eventSource 桩                            ✓
包含 __jskRenderChat                           ✓
```

**这一项应并入阶段 0**（成本约 2 小时，收益是永久防回归）。

### 8.2 `buildMemoryStorage` 是缝在模板字符串里的函数源码

`hostStub.js` L851-L854：

```js
// 内存 localStorage（data: URL 沙箱下原生 localStorage 不可用）
try { localStorage.getItem('__jsk_probe__'); } catch(e) {
  const _s = (${buildMemoryStorage.toString()})();
  Object.defineProperty(window, 'localStorage', { get: function(){ return _s; } });
}
```

这里用 `Function.prototype.toString()` 把一个函数**转成源码字符串**再塞进模板。
它能工作，但有两个隐患：

1. **一旦 `buildMemoryStorage` 内部引用了外部变量**（哪怕只是常量），
   转成字符串后那个引用就会变成未定义 —— 属于「改一行就炸、且炸得莫名其妙」的写法。
2. 压缩/混淆后 `toString()` 结果不稳定。

**建议**：阶段 1 重构时，把这类「函数转字符串」的写法统一改为
「在模板里直接内联实现」，或统一走 `plugin-host.js` 这类独立打包产物。
这一项不紧急，但**每次改 `hostStub.js` 都有踩中的风险**，记在这里防止遗忘。

### 8.3 方案里的「6 个样本」不足以代表用户真实场景

那 6 个文件来自 `E:\AI\酒馆工具\酒馆助手插件`。它们的构成是：

- 2 个纯逻辑
- 1 个主题
- 2 个 DOM 脚本
- 1 个命令脚本

**缺的关键类型**：

- **扩展工程**（有 `manifest.json` + bundle js/css + html 模板）——这是酒馆生态里最主流的一类，方案里只有 1 行描述，没有样本验证
- **依赖 LLM 的插件**（会调 `generateQuietPrompt`）——沙箱里必然不出内容，需要明确「这是预期行为」
- **依赖世界书 / 角色卡的插件**

**建议**：验收清单之外，再准备 1~2 个扩展工程样本。
如果用户手上没有，可以从 `SillyTavern/public/scripts/extensions/` 里取一个官方扩展做基准。

否则可能出现「6 个样本全过了，但用户实际用的插件仍然不行」。

### 8.4 一个容易被忽略的体验问题：预览没有「重新加载」

插件源码在左侧编辑区改完后，右侧预览不会自动刷新。
用户改一行 → 切到效果页 → 看到的还是旧结果（因为 `previewState.url` 没变）。

**建议**：阶段 2 顺带加一个「🔄 重新预览」按钮，
或监听 `pluginDirty` 变化时在预览区顶部显示「源码已修改，点击刷新预览」。

这属于小成本、高感知的改动，但它解决的是「改了没反应」这类最容易让人怀疑功能坏掉的问题。

### 8.5 关于「带入测卡工作区」的一个前置确认

阶段 5 的做法是把插件临时挂到测卡会话。
但需要先确认一件事：**测卡工作区的插件挂载机制，和插件预览的宿主是不是同一套？**

从代码结构看，测卡用的 `js/composables/chat/useChatSandbox.js` 与
`js/plugins/hostStub.js` 是**两套独立实现**（前者注入到消息 iframe，后者生成完整预览页）。

如果是两套，阶段 5 就不是「加一个按钮」，而是「把插件从 A 环境搬到 B 环境」，
需要考虑：

- 插件在 A 里的注册状态（命令/按钮）能否迁移
- 搬过去后原预览页要不要销毁
- 两边的事件系统是否互通

**建议在阶段 5 动工前先做一次可行性验证**（约 2 小时），
确认「同一份插件源码在两边都能跑」，再决定是否投入 1 天。

### 8.6 建议给「预览失败」定义一个明确的出口

用户最难受的不是「预览不出来」，而是「不知道是插件的问题还是软件的问题」。

建议在预览区固定放一条说明（不是只在空白时出现）：

```text
这是一个模拟运行环境，用于判断插件的大致效果。
不连接真实酒馆、不请求模型、不写任何数据。
以下情况属于正常：
  · 纯逻辑插件（自动总结、变量初始化）本身没有界面
  · 依赖聊天内容的插件只能看到大致样式
  · 需要联网 / 需要模型的插件不会真正执行
```

这条说明的成本几乎为零，但能消除大部分「是不是坏了」的误判。
