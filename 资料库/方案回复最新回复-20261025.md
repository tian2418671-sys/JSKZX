## 三、 核心拍板：关于 §四（Q5 `minCards` 落地偏差）的澄清与定锤

在仔细阅读 Round 2 的 **§4.1 与 §4.2** 后，我发现提案方在复核我的公式时，**把两个不同的维度混在了一起**，正好借此机会彻底理清：

### 3.1 澄清一个数学概念错位

* **首轮 Q5 公式的本意**：`minCards = Math.min(50, Math.max(5, Math.floor(total * 0.02)))` 算出来的是 **“单条标签至少要命中多少张卡（Min Cards per Tag）”**，而**不是“最多生成 50 条草稿（Max Draft Count）”**！
* **纠偏提案方 §4.2 的推算**：
  * 提案方担心：“11,849 张库算出来是 50，取 Top 50 后，第 50 名的卡数可能仍是个位数 ⇒ 50 条草稿里大部分仍是长尾。”
  * **实际情况**：在 11,849 张的库里，`minCards = 50` 意味着**“某个标签名下必须至少有 50 张卡，才有资格生成一条分组草稿”**，根本不可能出现“个位数卡数的长尾标签混进来”的情况！相反，在 11k 库里，能达到 `≥ 50 张卡`（且不在 `systemCommonTags` 黑名单内）的细分标签，通常也就 10~30 个。

### 3.2 为什么提案方的选项 ②（60% 覆盖率累加）存在隐藏陷阱？

提案方在 §4.3 倾向于 **选项 ②（要求草稿命中的卡数总和 ≥ 库总量 60%）**。作为架构评审，我**不建议采纳选项 ②**，原因如下：
1. **一卡多标导致的分母失真**：一张角色卡通常有 5~15 个标签。如果简单把各标签的 `count` 累加到 `total * 0.6`，可能前 3 个高频标签加起来就已经超过 `60%` 了（因为同一批卡被重复计数）；如果要做真正的集合去重（Set Union）算 60% 覆盖，就破坏了 `draftProfilesFromTags(tagCounts)` 只接收聚合计数 `Map<tag, count>` 的纯函数签名（被迫要传入全量 `library` 数组）。
2. **未打标卡较多的库永远凑不够 60%**：如果一个库标签覆盖率只有 40%（60% 的卡没标签），按“达到库总量 60%”去截取，会把**所有**只有 1 张卡的孤儿标签全部搜刮进来，彻底失去过滤意义！

### 3.3 Q5 最终定锤方案（双闸门：门槛 + 条数上限）

为了同时解决“不漏掉中频有效标签”和“绝不淹没用户 UI”两个目标，将 **选项 ①（卡数门槛）** 与 **选项 ③（Top N 条数上限）** 结合为**双闸门纯函数参数**：

```js
/**
 * Q5 最终定锤参数口径：
 * 1. minCards（单标签最低卡数门槛）：动态计算 Math.min(50, Math.max(5, Math.floor(total * 0.02)))
 *    - 89 张库 -> 门槛为 5 张/标签
 *    - 1000 张库 -> 门槛为 20 张/标签
 *    - 11849 张库 -> 门槛为 50 张/标签
 * 2. maxDrafts（最多输出草稿条数）：默认固定 20 条（按 count 降序取前 20）
 *    - 两个数字在 AutoGroupModal 的预览头部均可由用户手改微调！
 */
```

* **为什么这是最优解**：
  * **保持纯函数极简**：只依赖 `tagCounts: Map<tag, count>`，无需传入全量卡片做集合去重，耗时 $O(K \log K)$（$K$ 为标签种类数，毫秒级）。
  * **双重防爆**：先剔除 `systemCommonTags` → 再滤掉卡数不足 `minCards` 的长尾词 → 再滤掉已有 `dedupeKey` 的规则 → 最后按卡数降序截断前 `maxDrafts = 20` 条。用户在 UI 上永远只会看到最精华的 $\le 20$ 条建议！

## 四、 对阶段零（G1 修复正则）的一处微调提醒

在 Round 2 的 **§五 阶段零（0.2）** 中，提案方写道：
> `合法性过滤（长度 2~64、不含空格与中文「无可用」类字样、匹配 ^[\w.\-:/]+$）`

**⚠️ 工程防误杀提醒**：
* 部分本地推理后端（如 Ollama / LM Studio / Jan）或第三方中转站返回的模型 ID 可能包含 `@`（如 Vertex AI 格式 `claude-3-5-sonnet@20240620`）或 `+`，且部分微调模型名长度可能超过 64 字符（例如 HuggingFace 完整路径 `organization/model-name-finetuned-xxxx-gguf` 可达 80~100 字符）。
* **修正建议**：
  1. 长度上限放宽至 **`2 ~ 128`**；
  2. 正则放宽为 **`^[a-zA-Z0-9._\-:/@+]+$`**（依然严格拦截空格、换行符、中文提示语、HTML 标签如 `<!DOCTYPE` 等一切非模型 ID 垃圾串）；
  3. **核心防线不变**：即便列表全部合法，只要原 `apiModel.value` **非空**，拉取成功后也**只更新下拉候选列表 `availableModels.value`，绝不自动改写 `apiModel.value`**（仅当原 `apiModel.value` 为空字符串时，才自动填入 `modelList[0]`）。这样就能从根源上 100% 杜绝“用户填好的模型名被覆盖”！
