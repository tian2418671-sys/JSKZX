## 二、 为什么不用重做方案 B/D？代码库里已有现成解药！

评估稿第 2 节指出的四大死因（`$` 残缺、缺 `TavernHelper`、缺聊天 DOM 数据、缺生命周期事件），其实**不需要搬运真酒馆**，用极小代价就能解决 85% 以上：

### 破局点 1：直接引入真 `jquery.min.js`（87KB），废除手写迷你 `$`
* **现状痛点**：`js/plugins/hostStub.js` 里花了几百行手写了一个迷你 `$`，缺 `$.extend`、`$.Deferred`、复杂伪类选择器，插件一调就静默死。
* **新方案**：在项目静态目录放一份标准的 `jquery-3.7.1.min.js`（约 87KB，零外部网络依赖），在预览页最顶部通过 `<script src="..."></script>` 同步加载**真 jQuery**。
* **收益**：成本仅 1 个静态文件，彻底消灭所有因 `$` 方法不全导致的静默崩溃。

### 破局点 2：跨模块复用项目已有的 `useChatSandbox.js` / `iframeGlobals.js`
* **现状痛点**：评估稿提到「`TavernHelper` 功能集很大，逐个桩实现不现实」。
* **代码事实**：我们项目的**【测卡工作区】已经写好了完整的酒馆助手沙盒桩**（见 `js/composables/chat/useChatSandbox.js` 与 `js/chatHost/iframeGlobals.js`），里面已经有现成的 `window.TavernHelper`、`SillyTavern.getContext()`、变量读写（`getvar`/`setvar`/`insertOrAssignVariables`）、宏替换（`substituteParams`）和事件机制！
* **新方案**：把 `useChatSandbox.js` 里的 `TavernHelper` 与 `SillyTavern` Mock 抽成公共模块注入 `hostStub.js`，不要在 `hostStub.js` 里维护第二套残缺的全局变量。

### 破局点 3：预置「3 条仿真对话气泡」+「自动生命周期脉冲」
* **现状痛点**：评估稿 2.5 指出「很多插件等 `CHAT_CHANGED` / `MESSAGE_RECEIVED` 才动作，或者针对 `#chat` 里的消息做渲染，空环境里自然不动」。
* **新方案**：
  1. **内置标准酒馆消息 DOM**：在 `buildHostDom()` 的 `#chat` 容器里，默认预置 **2~3 条符合酒馆真实 DOM 结构的消息气泡**（含 `.mes[is_user="true"]`、`.mes[is_user="false"]`、`.mes_block .ch_name`、`.mes_text`），甚至在最后一条 AI 消息里预埋一段常见的 `<status>状态栏示例</status>` 文本。
  2. **自动触发事件脉冲链**：当插件脚本加载完毕（`DOMContentLoaded` + 100ms）后，宿主自动按顺序广播一次标准生命周期事件：
     ```js
     eventSource.emit(event_types.APP_READY);
     eventSource.emit(event_types.SETTINGS_LOADED);
     eventSource.emit(event_types.CHAT_CHANGED, 'preview_chat_01');
     eventSource.emit(event_types.CHARACTER_MESSAGE_RENDERED, 1);
     eventSource.emit(event_types.MESSAGE_RECEIVED, 1);
     ```
  3. **顶部增加「交互模拟器」工具条**：在预览画面顶部提供 3 个手动按钮：
     * `[💬 模拟收到 AI 消息]`（往 `#chat` 追加一条带状态的假回复并触发 `MESSAGE_RECEIVED`）
     * `[⚙️ 查看扩展设置区]`（自动滚动/高亮 `#extensions_settings` 与 `#extensions_settings2`，很多扩展把 UI 塞在这里，用户没往下滚所以以为是空白！）
     * `[🪄 查看魔法棒菜单]`（展开 `#extensionsMenu`）

### 破局点 4：静态 AST/正则预检 —— 诚实告知「无 UI 插件」与「定位挂载点」
* **现状痛点**：用户打开一个后台功能型插件（如纯自动总结、纯变量初始化脚本），本来就没有可见 UI，用户看到空白以为是软件坏了。
* **新方案（采纳评估稿方案 C + 第七节建议）**：
  在加载插件前，用轻量正则扫描源码：
  1. **挂载点自动聚焦**：如果检测到插件只往 `#extensions_settings` 塞了面板，没有动 `#chat`，预览页直接默认展开并高亮「扩展设置抽屉」，而不是让用户对着空白的聊天区发呆！
  2. **纯逻辑脚本诚实诊断 Card**：如果插件既没有 `.html` 模板、没有 `.css`、源码里也不含任何 DOM 挂载操作，直接跳过沙盒渲染，展示一张清爽的**「插件能力说明书（静态透视卡）」**：
     * 📌 **插件类型**：后台逻辑脚本（本身不生成可见界面）
     * 🎧 **监听事件**：`MESSAGE_RECEIVED`, `GENERATION_ENDED`
     * 🔧 **调用 API**：`generateQuietPrompt`, `TavernHelper.getVariables`
     * 🚀 **操作引导**：`[ 一键在【测卡工作区】中挂载体验 ]`

## 三、 联动大招：打通「插件库」与「测卡工作区」

评估稿问「怎么在有聊天数据的地方看插件效果」—— **我们的【测卡工作区】（`useChat.js` + `useChatPlugins.js`）本身就是一个自带角色卡、自带聊天记录、自带 LLM API、自带沙盒的微型酒馆！**

* 对于重度依赖聊天上下文和 LLM 生成的插件（如酒馆助手脚本、动态状态栏），在「插件库」右侧预览栏顶部直接放一个醒目按钮：
  👉 **「🧪 带入【测卡工作区】实战测试」**
* 点击后自动切换到测卡模式，并将该插件临时挂载到当前测试会话中。这样**零成本实现了评估稿中的“方案 B”，且完全不需要用户本机安装外部 SillyTavern**！

## 四、 实施路线图（分两步走，不返工）

### 第一步（止血与立竿见影，约 0.5~1 天）
1. **换真 jQuery**：本地引入 `jquery.min.js` 注入 `hostStub.js`，删掉手写迷你 `$`。
2. **填仿真对话与自动脉冲**：在 `#chat` 预置 2 条标准 `.mes` 消息气泡，脚本载入后自动 emit `APP_READY` → `CHAT_CHANGED` → `MESSAGE_RECEIVED`。
3. **自动聚焦非聊天挂载点**：检测若 `#extensions_settings` / `#extensionsMenu` 子节点增加，自动置顶展示这些区域（解决“UI 渲染在折叠菜单里导致用户看不见”的假空白）。
4. **诚实诊断面板升级**：对纯后台逻辑脚本展示「插件静态透视卡（监听了什么事件 / 调了什么 API）」+「带入测卡工作区测试」按钮。

### 第二步（深度复用，约 0.5 天，视第一步效果按需推进）
1. 将 `js/chatHost/iframeGlobals.js` 中的 `TavernHelper` 桩复用到 `hostStub.js`。
2. 在预览区工具条加上 `[💬 发送模拟消息]` 按钮，允许用户点击触发一次动态消息渲染。

> **总结给下游的一句话**：
> 不要去嵌真酒馆（方案 B），也不要去搬酒馆前端整包（方案 D）。**换上真 `jquery.min.js` + 预置 2 条 `.mes` 假消息 + 自动派发一次 `CHAT_CHANGED / MESSAGE_RECEIVED` 事件 + 自动展开有内容写入的 `#extensions_settings` 挂载区**，就能用 10% 的工作量解决目前 80% 的“空白无效果”问题；剩下的纯后台逻辑脚本，直接用「静态能力透视卡 + 一键跳测卡工作区」优雅兜底！
