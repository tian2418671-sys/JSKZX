> 1. **阶段 0（修骨架 \+ 删副本 \+ 补输出测试）是否立刻做？**  
   * **拍板：立即执行（P0 Blocker）。** 不修好 hostStub.js L1453-L1598 的游离 DOM 与重复 ID，后续任何调试都是盲人摸象。  
> 2. **阶段 3（sandbox="allow-scripts allow-same-origin"）的安全边界是否接受？**  
   * **拍板：不接受直接开启 allow-same-origin，改用「专用无特权 Scheme（jsk-preview://）或 Web 端 Service Worker / Blob 拦截」方案。**  
   * **致命隐患纠正**：在 HTML 规范与 Electron/WebView 中，当 \<iframe src="app://..."\> **同时**具有 allow-scripts 和 allow-same-origin 时，iframe 内的恶意或写歪的第三方插件脚本可以直接访问 window.parent / window.top，不僅能调用 window.parent.electronAPI（读写本地磁盘文件！），甚至能直接執行 window.frameElement.removeAttribute('sandbox') 彻底逃逸沙箱！且 \<iframe\> 标签不支持像 \<webview\> 那样单独指定 partition 属性（iframe 强制继承父窗口的 app:// Session）。  
   * **彻底解法**：注册一个独立的标准自定义协议 **jsk-preview://\<previewId\>/index.html**（与主应用的 app:// **跨源隔离**，但对插件自身而言是**完整的标准同源环境**）。这样既保留 sandbox="allow-scripts allow-same-origin" 从而 100% 解锁 localStorage、IndexedDB、Worker、fetch('./assets/x.json') 和 import('./mod.js')，又因为 jsk-preview:// 与父窗口 app:// 跨源（Cross-Origin），浏览器内核天然阻断插件访问 window.parent.electronAPI！  
> 3. **是否明确放弃「像素级真实」？**  
   * 拍板：明确放弃。 预览的核心目标是「3 秒内看懂插件是什么类型、注入了什么入口、展开后长什么样」。  
> 4. **阶段 5（带入测卡工作区）是否必要？**  
   * 拍板：暂缓（降为 P3）。 如 8.5 节所述，useChatSandbox.js 与 hostStub.js 是两套独立体系。通过本次方案把「命令脚本按钮化」和「DOM 挂载抽屉化」做好后，95% 场景无需跳出插件库。  
> 5. **验收标准确认**  
   * 拍板：采用 6 个现有真实样本 \+ 补充 1 个标准 manifest.json 扩展工程样本（共 7 个样本）作为自动化 \+ 人工双重验收基线。

#### **方案模块 2：四路分流引擎（解决缺陷 6、8：半数插件本无 UI）**

不再把所有文件一股脑丢进 iframe 跑脚本，而是在 PluginWorkspace.vue 点击「效果」时，先经由 classifyPlugin(plugin) 分流为 4 种专用视图：

Plaintext

                       │  
                       ├── \[2. LOGIC 纯逻辑脚本\] ─► 静态 AST/正则探针「插件说明书」+ 触发器/Slash命令一键试跑台  
classifyPlugin(plugin) ┤

                       │

**1\. 分类器 js/plugins/pluginClassify.js 实现要点：**

JavaScript  
export const PLUGIN\_KIND \= {  
  THEME: 'theme',  
  LOGIC: 'logic',  
  DOM\_SCRIPT: 'domScript',  
  EXTENSION: 'extension',  
};

const THEME\_COLOR\_KEYS \= \[  
  'main\_text\_color', 'italics\_text\_color', 'underline\_text\_color', 'quote\_text\_color',  
  'blur\_tint\_color', 'chat\_tint\_color', 'user\_mes\_blur\_tint\_color', 'bot\_mes\_blur\_tint\_color',  
  'shadow\_color', 'border\_color'  
\];

const DOM\_OP\_RE \= /\\\$\\s\*\\(\|jQuery\\s\*\\(\|document\\.(createElement\|querySelector\|getElementById)\|\\.append\\s\*\\(\|\\.prepend\\s\*\\(\|\\.html\\s\*\\(\|insertAdjacentHTML\|renderExtensionTemplateAsync\|SlashRunner\\.showMessage\|toastr\\./;

export function classifyPlugin(plugin) {  
  if (\!plugin) return PLUGIN\_KIND.LOGIC;  
  if (plugin.kind \=== 'extension' \|\| plugin.manifest) return PLUGIN\_KIND.EXTENSION;

  // 1\. 判定 UI 主题 JSON（顶层命中 \>= 3 个酒馆配色字段）  
  const rawObj \= plugin.rawJson \|\| plugin.contentObj;  
  if (rawObj && typeof rawObj \=== 'object') {  
    const hitColors \= THEME\_COLOR\_KEYS.filter(k \=\> k in rawObj);  
    if (hitColors.length \>= 3) return PLUGIN\_KIND.THEME;  
  }

  // 2\. 判定含 HTML/CSS 资产的插件  
  if ((plugin.html && plugin.html.trim()) \|\| (plugin.css && plugin.css.trim())) {  
    return PLUGIN\_KIND.DOM\_SCRIPT;  
  }

  // 3\. 判定脚本源码是否包含 DOM 注入或弹窗输出  
  const code \= extractAllScriptCode(plugin);  
  if (DOM\_OP\_RE.test(code)) {  
    return PLUGIN\_KIND.DOM\_SCRIPT;  
  }

  // 4\. 其余归为纯逻辑脚本（如发送前正则、变量初始化、写卡器）  
  return PLUGIN\_KIND.LOGIC;  
}

#### **方案模块 3：「跑了但看不见」的终极解法——挂载区自动嗅探与抽屉展开（解决缺陷 5 & 2.1 案例）**

为什么 更好的聊天记录管理.json 和 folder4.0.json 跑起来了却看不见？

> 1. 宿主把 60 多个空容器堆在一起，真正被插入了 \<a id="option\_chat\_history\_manager"\> 的 .options-content 混在一堆空框里；  
> 2. 很多插件往 .options-content 或 \#extensionsMenu 插完入口按钮后，**必须用户点击一次该入口**，或者展开 \<div class="inline-drawer-content" style="display:none"\>，真正的面板才会渲染出来！

**解决方案：在 hostStub.js 尾部注入「智能挂载嗅探器（Mount Inspector）」**

> 1. **只显示有产出的挂载区，隐藏所有空挂载区！**  
   * 在插件脚本运行前，对所有 \[data-jsk-zone\] 容器记录初始快照（initialChildCount \+ initialHtmlLen）。  
   * 使用 MutationObserver 监听变化。一旦某个挂载区被插件插入了新节点：  
     * 给该挂载区加上醒目的高亮边框和顶部状态栏：✨ 插件在此区域注入了界面：选项菜单 (.options-content)；  
     * **自动隐藏**没有任何变化的空挂载区（如空的 \#extensions\_settings2），让画面瞬間干净！  
> 2. **自动展开隐藏抽屉 \+ 自动提示可点击入口**：  
   * 若插件注入的是 .inline-drawer（酒馆标准折叠抽屉），预览环境自动将其 .inline-drawer-content 设为展开状态，无需用户盲猜去点小箭头。  
   * 若插件在 .options-content 或 \#extensionsMenu 中仅插入了一个入口按钮（如 \<a id="option\_chat\_history\_manager"\>），嗅探器自动在该按钮旁打上脉冲高亮角标 👈 插件新增入口，点击打开面板，并自动 scrollIntoView({ behavior: 'smooth', block: 'center' })。

#### **方案模块 4：独立跨源协议 jsk-preview:// 解决同源与文件上下文（解决缺陷 4、7）**

为了同时满足「插件内部拥有完整同源能力（localStorage / Worker / fetch('./data.json')）」和「严禁插件触碰主应用 app:// 的 electronAPI」：

> 1. **主进程注册 jsk-preview:// 协议**（与 app:// 不同 scheme，因此浏览器强制判定为 Cross-Origin）：  
   * 请求 jsk-preview://\<previewId\>/\_\_entry\_\_.html → 返回内存中生成的 buildPluginPreviewHtml() 内容。  
   * 请求 jsk-preview://\<previewId\>/\<relPath\>（如插件内部调用 fetch('./assets/config.json') 或 import('./utils.js')） → 协议处理器根据 previewStore.get(previewId).rootDir 解析出本地磁盘真实路径，经过 isPathAllowed(realPath, rootDir) 校验防目录穿越后，直接流式返回本地文件并附带正确的 MIME Type（.js 返回 application/javascript，.json 返回 application/json）！  
> 2. **Iframe 标签配置**：  
>    HTML  
>    \<iframe  
>      v-else-if\="previewState.url"  
>      :key\="previewState.refreshKey"  
>      :src\="previewState.url"  
>      sandbox\="allow-scripts allow-same-origin allow-modals"  
>    \>\</iframe\>

>    因为 src 是 jsk-preview://\<previewId\>/\_\_entry\_\_.html，开启 allow-same-origin 后，它只拥有 jsk-preview:// 域的权限，与父窗口 app://index.html 完全隔离，window.parent.electronAPI 访问会被内核级同源策略直接拦截抛错，安全与兼容性两全其美！
