## 一、 方案整体质量评价（为什么这是一份极佳的提案）

在进入具体方向拆解前，必须肯定本方案评估稿的三个核心工程亮点：

## 二、 核心方向逐项深度评审

### 2.1 方向 A（库画像） vs 替代路径（质检扩展）：**建议降级并入，不建独立弹窗**

* **提案原意**：保留 4 项独有能力（① 标签×分组交叉矩阵、② 标签池健康度 `systemCommonTags`、③ 近 12 周活跃度时间线、④ Token 分位数 P50/P90/P99），新建 `LibraryPortraitModal.vue` 与 `useLibraryPortrait.js`。
* **评审挑战（Critical）**：
  1. **心智割裂风险**：对用户而言，“看哪些卡有问题（质检）”和“看库结构哪里失衡（画像）”本质上都是**同一次卡库体检的两种视图（明细视图 vs 宏观分布视图）**。如果分成两个弹窗、两个入口（工具菜单里既有“一键质检”又有“库画像”），且 D-A1 还要让画像去复用质检的缓存结果，用户在未跑质检时直接点开画像会出现“数据为空或被迫触发质检”的尴尬链路。
  2. **活跃度时间线（区块 ③）的数据陷阱**：文件系统的 `mtime` 在用户进行批量重命名、批量移动分组或备份恢复时会被成批刷新，导致“近 12 周修改柱状图”出现失真的尖峰，参考价值有限。
* **评审裁决**：
  * **触发提案 §一之前 (3) 的合并条款，但不完全砍掉独有能力**。
  * **做法**：**不新建 `LibraryPortraitModal.vue` 独立弹窗**，而是在现有的 `QualityCheckModal.vue` 顶部增加 Tab 切换：**`[📋 巡检清单 (现有)]` | `[📊 结构画像 (新增)]`**。
  * **保留区块**：在 `[📊 结构画像]` 页签中，只落地含金量最高的 **① 标签×分组交叉矩阵**、**② 标签池健康度（对比 `systemCommonTags`）**、**④ Token 分位数（P50/P90/P99）**。砍掉易失真的 ③ 活跃度时间线。这样既满足了“≥3 项独有能力”，又实现了 **100% 共享质检数据生命周期、零新弹窗接线成本（省去 `App.vue` 5 处改动）**。

### 2.2 方向 B（标签回灌闭环）：**B1/B3 全力支持，B2 永久搁置**

* **评审意见**：**设计极其优雅，投入产出比（ROI）全篇最高。**
  * **B1（标签 → 自动分组档案草稿）**：直接复用 `computeTagStats` 的 `tagCounts` 喂给 `autoGroup.js`，且严格遵守 `F5`（只进 `AutoGroupModal` 预览草稿，必须走 `moveCardToGroup` 执行以保护会话/变量树派生键），逻辑严丝合缝。
  * **补充约束**：生成草稿时，除过滤 `minCards >= 5` 外，**必须排除黑名单高频通用词**（如 `Furry`、`NSFW`、`Male`、`Female` 等顶层宽泛标签，或允许用户在预览时一键全选/反选），防止一键生成十几个过于宽泛的分组。
  * **B2（打标稳定度 Jaccard）**：同意提案判断。当前 LLM 温度与 Prompt 策略下，同卡重复打标本身就不具备确定性基线，落盘历史标签纯属徒增 `app_config` 或本地磁盘负担，**直接否决，无需后置评估**。

### 2.3 方向 C（重型卡存档管家）：**核心差异化护城河，C1~C4 批准，C3 需加一道防线**

* **评审意见**：重型卡（独立前端卡）是项目的核心壁垒，利用现有的 `manifest`（`F7`）和 `storageInfo`（`F8`）做可视化是绝佳的体验闭环。
* **针对 C3（换地址沿用旧档）的安全加固**：
  * 提案中提到“对比 `manifest.url` vs 当前条目 `url`，提示后由用户选”。
  * **架构隐患**：重型卡的存档（IndexedDB / LocalStorage）落盘在 Electron 的 `partition` 目录下，且与 Origin（协议+域名+端口）强绑定。如果新旧 URL 的 **Origin 发生变化**（例如从本地不同端口或不同托管域名迁入），单纯用文件复制恢复 `backup` 目录，Chromium 的 LevelDB 会因为 Origin 不匹配而无法读取旧数据！
  * **修正要求**：在 C3 的实现规格中必须写明——仅当**同 Origin 下路径变化**，或者恢复机制明确是通过脚本注入/同固定 Partition 映射时才可沿用；若跨 Origin 换址，UI 需明确提示“跨域名换址可能无法直接读取浏览器内部存储”。
* **针对 C5（存档差异）**：同意后置。只比对 `manifest.files[]` 的 `rel + size` 在 LevelDB 场景下意义有限（因为 LevelDB 会频繁触发 Compaction 合并 `.ldb` 文件，文件名和大小全变，普通用户看不懂 `.ldb` 文件差异），次版再议。

### 2.4 方向 D（卡片画像 / 库地图）：**正式驳回（Reject），避免陷入可视化泥潭**

* **评审意见**：虽然提案人给出了复用 `useGraph` 性能治理参数、禁用力导图的克制方案，但从产品价值看：
  1. 将 `X = Token 量级`、`Y = 标签数` 画在 11,849 个点的二维散点图上，**绝大多数点会高度重叠在左下角（低 Token、1~5 个标签）**，形成一团无法交互的色块（Overplotting）。
  2. 散点图连线展示“重复簇”远不如现有的 `DedupeModal` 分组列表直观高效。
  3. **结论**：不要为了“视觉冲击”去承担 11k 节点的渲染维护成本。单卡维度的信息聚合（D-2）未来若真有需要，直接在现有的卡片详情侧栏里加一个“健康度角标”即可，**彻底砍掉 D-1 库地图与 D-3 孤岛清单**。

### 2.5 中等价值（E1~E4）与体验补漏（G1~G4）评审

* **G1（模型名静默覆盖 `#hot-bug-1`）**：**最高优先级（P0）**。完全同意提案判断，属于破坏用户配置的数据级 Bug，立即建档修复。
* **E4（搜索语法帮助浮层）**：**批准（P1）**。20 行代码解决 `tag:` / `author:` / `wb:` / `-排除` 的可发现性问题，性价比极高。
* **G3（打标日志只看失败） & G4（世界书过滤原因说明）**：**批准（P2）**。属于极低成本消除用户困惑的“防报 Bug”特性，建议随本版一并合入。
* **E3-A（导出 HTML 分享卡片页）**：**暂缓或作为独立支线**。导出单文件 HTML 涉及封面图 Base64 内联体积控制、CSS 样式内联与排版美观度打磨，极其消耗前端调试时间，建议不要阻塞 B1/C1~C4 主线。
* **E1（自然语言搜索） & E2（变更提醒）**：同意提案结论，**本版不做**。

## 五、 批准后的施工路线图（修正版）

请按以下裁定后的顺序编写实现规格并推进施工（全程**零主进程改动、零新增 IPC**）：

1. **阶段零（P0 止血，独立 PR/Commit）**：
   * 登记 `docs/bugs/` → 修复 **G1**（`useChat.js` 拉取模型列表增加合法性校验与非空保护，禁止静默覆盖已保存的 `apiModel` 并落盘）+ 补充单测。
2. **阶段一（纯函数先行 + 单测过关）**：
   * **A-Pure**：在 `js/utils/` 下编写结构画像纯函数（仅计算：`标签×分组矩阵`、`systemCommonTags 差集诊断`、`Token P50/P90/P99 分位数`），并在 11k 模拟库下验证 `CHUNK=200` 分片耗时。
   * **B1-Pure**：在 `js/utils/autoGroup.js` 追加 `draftProfilesFromTags()` 纯函数（含动态 `minCards` 默认值与 `dedupeKey` 幂等去重）+ 完整边界单测。
3. **阶段二（UI 闭环与轻量化补漏）**：
   * **A-UI + B3**：改造 `QualityCheckModal.vue`，新增 `[📊 结构画像]` 页签，接入上述 3 项独有视图，并在未打标/低覆盖处提供一键跳往「AI 打标」或「自动分组」的快捷入口（B3）。
   * **B1-UI**：改造 `AutoGroupModal.vue`，接入「🏷 从高频标签生成规则草稿」预览交互。
   * **E4 + G3 + G4**：搜索框语法浮层（20 行）、打标日志窗「只看失败」过滤开关、世界书剔除原因气泡说明。
4. **阶段三（重型卡存档管家 C1~C4）**：
   * 扩展 `HeavyCardWorkspace.vue` 存档面板：落地时间线（按天折叠）、空间占用榜、今日游玩推荐、同源换址恢复提示（含跨 Origin 风险拦截）。
5. **阶段四（门禁验收）**：
   * 依次执行：`guard:scope` → `npm test` → `npm run build:web` → Electron 真实启动冒烟 → 89 张真库与 11,849 张压测库双库回归（断言前后 `app_config.json` 与卡片文件 `mtime` 零污染）。
